# 转载关系断言生命周期

## 目标与领域规则

转载关系采用不可变断言历史。修订和撤销通过新断言的 supersedes_relation_id 关联旧断言，不覆盖历史。

- 状态：proposed、confirmed、retracted。
- asserted_at 表示业务断言时间，observed_at 表示系统观察时间。
- 替代断言必须指向同一转载主体、同一关系类型的既有断言；一条历史断言最多一个直接后继。
- proposed 后继不提前改变当前关系；替代链后续出现 confirmed/retracted 时，沿链的所有祖先断言均退出当前关系图，不能因中间 proposed 状态而复活旧边。
- 当前 confirmed 关系形成 DAG，允许一个转载主体关联多个不同原始主体，拒绝重复边和环。
- 版本证据成对绑定双方内容版本；任一侧内容变化后旧证据仍保留并评估为 stale。

## 事务与并发契约

生产实现必须将 Observation、Version、全局 Relation history 的读取和 AppendNewsItemRelation 放在同一事务中。版本归属通过 NewsItemVersion.ObservationID 回溯 Observation.NewsID/SourceID 校验。EvidenceObservation 如提供则必须指向转载方 Observation；若不提供，必须成对提供双方版本证据，且版本各自回溯到对应主体的 Observation。原始方版本必须来自 ToNewsID/ToSourceID 对应的 Observation。提交带版本证据的新断言时，双方版本必须分别是各自主体的最新版本；旧断言可保留 stale。任何校验或写入失败必须回滚整个追加。

**仅把读取历史、校验和追加放进同一个普通事务并不足以保证无环。** 在 MariaDB 默认 REPEATABLE READ 等快照隔离语义下，两个并发事务可能分别读取同一份旧历史：事务甲验证 A→B，事务乙验证 B→A，双方各自通过 DAG 校验后提交，最终形成环。因此，事务端口还必须提供关系图级别的并发串行化保证：

1. 在执行事务回调、读取任何关系历史之前，先取得跨进程、跨实例共享的关系图写锁。
2. 锁必须基于稳定存在的协调资源，例如专用锁行；不能依赖对空结果集执行 `SELECT ... FOR UPDATE`。
3. 锁持有期间完成证据读取、全局历史读取、DAG/替代链校验、追加和事务提交；提交完成后才释放锁。
4. 另一种可接受方案是数据库真正的 SERIALIZABLE 隔离，并正确处理序列化失败；失败时必须重跑完整事务回调，不能只重试 append。
5. 进程内 mutex 不满足多实例部署要求。首期采用全局关系图写锁，避免按连通分量加锁时跨分量并发合并造成竞态。
6. relation ID 唯一和 supersedes_relation_id 唯一约束是最终防线，但不能替代图级串行化。
7. 并发冲突应返回可识别、可重试的冲突错误；重试受幂等键、deadline 和预算限制。

N6 必须包含真实数据库并发集成测试：两个事务并发尝试 A→B 与 B→A，最多一个成功且最终历史无环；两个事务并发为同一旧断言创建不同后继，最多一个成功。还需验证锁释放、事务回滚、跨实例竞争和完整历史读取。

当前内存 Repository 仅用于验证 Application 业务逻辑和回滚语义，不证明生产数据库具备上述并发保证；本阶段不实现数据库、DDL 或锁表。
