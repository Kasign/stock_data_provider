# 新闻数据模型与质量契约

> 版本：设计草案 v0.1  
> 状态：新闻业务逻辑模型草案；物理存储与通用诊断契约延期至公共服务阶段

## 1. 设计原则

- 原始来源证据与标准化业务字段分离。
- 新闻记录、正文内容、内容版本、来源和关联事实职责清晰。
- 所有重要字段保留来源、采集时间和可信度。
- 区分 NULL、未知、未采集、明确为空和采集失败。
- 首期使用 canonical symbol + market/exchange 作为证券关联业务键；当前未发现统一 security_id，不虚构主数据外键。
- 不将搜索摘要等同于原文正文。
- 不将模型推断写入来源事实字段。

## 2. 时间语义

| 字段 | 含义 | 约束 |
|---|---|---|
| `published_at` | 来源声明的原始发布时间 | 必须记录来源及可信度；无法确认则为空 |
| `available_at` | 信息实际可被市场参与者获取的时间 | 无可靠证据不得推算或伪造 |
| `fetched_at` | 系统从来源获取记录的时间 | 系统生成，统一 UTC 存储 |
| `normalized_at` | 系统完成标准化的时间 | 系统生成 |
| `system_observed_at` | 系统首次观察到该记录的时间 | 首次写入后不可被后续采集覆盖 |
| `source_version` | 来源侧版本或内容版本标识 | 无来源版本时使用内部版本策略，不伪造来源版本 |

禁止将搜索引擎更新时间冒充原始发布时间，禁止将当前采集时间冒充历史可用时间。时区、原始时区、解析方式和时间可信度需要可追溯。

历史研究和回测必须遵循 point-in-time 原则：只使用当时已经可获得且系统有证据证明可用的数据。

## 3. 逻辑实体与表边界（N1 Review 修订稿）

当前讨论模型为 **11 个新闻业务实体 + 2 个可选执行记录实体 + 1 个候选 Schema 迁移账本**。仅用于领域概念讨论，不代表当前阶段必须逐表落库；物理表结构、迁移账本和诊断执行记录均延期至公共服务阶段。

| 表 | 唯一职责 | 关键边界 |
|---|---|---|
| `news_sources` | 发布来源身份 | 媒体、监管机构、交易所、公司等，不代表搜索 Provider |
| `news_source_endpoints` | 来源采集入口 | 一个来源可有多个 RSS/Atom/API/网站入口 |
| `news_source_policy_versions` | 发布来源授权策略历史 | 控制该来源/入口可采集、可保留的内容范围 |
| `news_provider_policy_versions` | 搜索 Provider 输出使用权历史 | 与发布来源原文版权策略分离 |
| `news_items` | 稳定新闻主体 | 只保存身份、来源和生命周期/观察聚合字段，不复制当前标题等元数据 |
| `news_item_identifiers` | 新闻身份凭据及历史别名 | 来源原始 ID、规范 URL 等；Hash 命中后必须比对原文 |
| `news_observations` | 每次发现/采集的候选观测 | 保存当时 Provider 实际返回的有限证据，不等于新闻主体 |
| `news_item_versions` | 新闻元数据版本 | 标题、摘要、规范 URL、发布时间等的唯一权威版本来源 |
| `news_item_contents` | 版本内容载荷 | 正文/附件文本等可独立授权、清理的内容 |
| `news_relations` | 新闻与证券/行业的关联断言 | 追加式断言历史，不直接等同当前有效关系 |
| `news_relation_evidence` | 关联断言证据 | 证据绑定具体 relation，不复制整篇正文 |
| `news_ingestion_runs` | 可选的新闻业务执行记录 | 是否需要独立业务运行实体，待公共服务执行记录契约明确后再决定；不承担通用诊断 |
| `news_ingestion_run_steps` | 可选的新闻业务阶段记录 | 当前作为未来诊断/执行追踪候选，不属于已冻结业务实体 |

另有候选 `news_schema_migrations`，当前不建设；未来优先遵循公共服务的统一 Schema/Migration 机制。

### 3.1 权威字段归属与去冗余规则

- `news_items` 不保存 title、summary、canonical_url、language_code、published_at、available_at；这些元数据只由 `news_item_versions` 保存。
- `news_items` 保留 source_id、status、first_observed_at、last_observed_at、created_at、updated_at。first/last observed 是由 observations 聚合维护的查询辅助字段，不替代观测明细。
- `news_item_versions` 是标题、摘要、规范 URL、语言、发布时间、available_at、source_version 等新闻元数据的权威版本来源。
- `news_item_contents` 只保存正文和附件提取文本等独立载荷；不得再以 content_role=title/summary 重复保存版本表中的标题/摘要。
- `news_observations` 保留 Provider/来源当次实际返回的 candidate_title、candidate_url、candidate_snippet 等快照，即使这些字段后来与标准化版本不同，也不能回写成主体事实。
- `news_item_identifiers` 保存已确认的身份凭据；observations 保存发现证据，两者不可互相替代。
- `provider_code` 在 observation 与 Provider 策略引用中表达搜索输出来源。它必须从 Provider Adapter 一直保留到候选 DTO，不能用 publisher/source 字段替代；执行记录是否携带 provider_code 等公共服务执行契约确定后再决定。
- `source_id` 等跨表冗余字段必须由复合外键或 Repository 事务校验保证一致，不能只依赖调用方约定。
- 不增加 Provider 注册表、原始大响应表、去重日志表或 current-version 映射表；首期不需要这些独立实体。

### 3.2 时间字段权威归属

| 时间 | 权威归属 | 语义 |
|---|---|---|
| `published_at` / 原始时间文本 / 时区 / 解析状态 | version | 来源声明的发布时间 |
| `available_at` / 证据 | version | 有证据证明的信息可获取时间；未知保持 NULL |
| `observed_at` | observation | 系统观察到候选结果的时间 |
| `fetched_at` | observation 或来源采集结果 | 实际请求/采集时间，不代表发布时间 |
| `normalized_at` | version | 标准化完成时间 |
| `first_observed_at` / `last_observed_at` | item | 从观测聚合的首次/最近观察时间 |
| `created_at` / `updated_at` | 各表 | 数据库记录生命周期时间 |

搜索、正文抓取和标准化可能发生在不同时间，必须分别记录执行阶段；不能用单个 fetched_at 代替所有阶段时间。

## 4. 去重和版本识别

不能只按标题去重。候选信号包括：

1. 来源原始 ID（同一来源内优先）。
2. 规范 URL。
3. 来源标识与规范 URL 的组合。
4. 正文/原始内容指纹。
5. 标题、发布时间、来源等辅助相似度。

必须区分：
- 同一条新闻的重复抓取。
- 不同来源转载同一内容。
- 同一新闻后续修订。
- 标题相似但内容不同的独立新闻。

去重决策需要保留匹配依据，避免误合并造成证据丢失。

## 5. 来源和内容质量

质量至少覆盖：

- 来源身份是否明确。
- 来源权威等级。
- 发布时间可信度。
- 内容完整度（仅标题、摘要、正文、附件等）。
- 正文可访问性。
- 规范 URL 有效性。
- 重复判断及匹配依据。
- 证券/行业关联质量。
- 采集延迟和数据新鲜度。
- 内容版本变化和历史可追溯性。

质量状态不能只用布尔 success 表示；需要区分成功、部分成功、降级、跳过、失败和未知，并与项目现有质量状态契约保持一致。

### 5.1 新闻业务质量与通用诊断的边界（通用诊断延期）

当前新闻模块只负责业务质量判断，不负责通用诊断状态：

- 新闻数据质量：valid、degraded、invalid、unknown；具体字段质量必须保留原因和证据。
- Freshness：fresh、stale、unknown、not_applicable；按来源时间与系统观察时间计算，不得用 fetched_at 冒充源端时间。
- 授权状态：approved、restricted、pending、revoked，独立于技术可用性。

执行检查状态（passed/failed/skipped）、Provider/来源可用性（available/degraded/unavailable）属于通用诊断维度，统一延期至公共服务，不由新闻模块自行定义或持久化。

一次搜索 HTTP 请求成功，不代表候选有用；搜索成功不代表正文获取成功；正文获取成功不代表解析成功；解析成功不代表身份匹配、关系准确或允许持久化。这些判断由新闻业务质量规则表达原因和证据，不构建 Probe 或诊断报告。

新闻业务质量规则由 Domain/Application 负责计算并返回业务原因与证据；通用执行诊断、Run/Step 历史、Probe 和诊断查询统一延期至公共服务阶段。当前不实现诊断存储、新闻诊断历史或公网诊断路由。

## 6. 来源分级

至少区分：
- 官方披露：监管机构、交易所、法定信息披露平台、上市公司公告。
- 新闻媒体和行业来源。
- 搜索引擎或聚合 Provider：例如 Bocha、Tavily、Brave、SearXNG。

不同类别采用不同的权威性、时间可信度和完整度评价规则。搜索结果只能作为发现入口，不天然等同于权威原始来源。

## 7. 数据库约束

- 未来持久化阶段只新增新闻专属表；当前不实施 DB/Redis 接入。
- 不修改或重建行情、财务、估值、证券主数据表。
- 迁移必须可重复执行，包含启动检查和明确的回滚/恢复策略。
- 评估唯一索引、查询索引、历史版本增长和数据保留成本。
- 正文存储策略须遵守来源授权和保留限制。
- 物理表结构须经 N1 评审后冻结。

### 7.1 关键约束与并发规则（待转物理 DDL）

- `news_item_identifiers` 的 source_id 必须与对应 news_items.source_id 一致；优先使用复合唯一键和复合外键表达。
- 身份 Hash 命中后必须比较 identifier_value 原文；发现同一来源的 source-native-id 与 normalized-url 分别指向不同 news_id 时，标记 conflict，不自动合并。
- 新闻主体创建、身份凭据写入、版本新增和 item 聚合字段更新应在同一事务中完成；并发唯一键冲突后重新读取并核对身份，不做盲目覆盖。
- `news_relations` 追加式修正/撤销；建议对 supersedes_relation_id 建唯一约束，并在锁定 news_items 行的事务内检查断言链。
- 运行记录和阶段记录的唯一键、幂等键及重试语义不在当前领域模型阶段冻结；等待公共服务执行记录/诊断契约后再决定是否需要新闻专属实体。
- 事实表不使用级联删除；来源停用、新闻撤回、授权撤销和内容到期是不同操作。
- Schema 迁移必须有版本、checksum、命名锁和部分 DDL 失败后的结构核验/恢复流程。

## 8. 验收要点

固定样本覆盖时间缺失、时区、重复抓取、跨来源转载、内容修订、正文缺失、错误证券关联、来源不可用和历史可追溯场景。不得以新闻数量或接口 HTTP 200 作为唯一验收标准。

## 8.1 通用诊断契约（延期至公共服务阶段）

诊断至少覆盖以下阶段：配置/凭证检查、Provider 连通性、搜索契约、来源入口访问、正文获取、解析、标准化、身份去重、版本写入、证券/行业关联、持久化与新鲜度。并非每次业务请求都执行所有主动检查；按触发场景选择检查，避免无意义请求和 Provider 配额消耗。

每项检查必须包含：对象类型及标识、能力/阶段、状态、检查时间、耗时、错误分类/错误码、脱敏摘要、输入/输出计数、质量指标、是否可重试和证据引用。未配置或因授权策略跳过的能力应为 skipped，不得记为 failed 或 available。

诊断需要覆盖“请求成功但零有效结果”“结果被质量规则过滤”“来源不可访问”“解析失败”“身份冲突”“版本未变化”“授权禁止保存”“部分写入/部分关联”等情况。诊断本身不自动修复数据，也不绕过质量门禁或授权策略。

## 9. N1 对现有模型的核对补充（2026-11-05）

现有 go-core/internal/domain.NewsItem 只有标题、摘要、URL、来源、发布时间、检索时间、相关性和维度字段；不包含正文、available_at、来源原始 ID、首次观察时间、原始响应证据、内容版本、采集状态或证券关联证据。它是分析消费 DTO，不应直接作为新闻持久化实体。

现有公告模型 domain.StockAnnouncement 提供 article_id、symbol、title、announcement_date、可选 published_at、source、source_version、fetched_at 和质量字段，可作为公告来源适配输入；它仍不是统一新闻实体或版本仓库。

market-data 现有持久化表使用 canonical symbol（如 600519.SH），但已核实的迁移表清单未显示统一 security master 外键。首期新闻关联使用 canonical symbol + market/exchange，并保留原始代码与规范化证据；未来若建立统一 security master，再单独设计映射。

现有 Searcher 会过滤无效/缺失发布时间的候选，并把发布时间缩减为 YYYY-MM-DD。新新闻模型应保留原始时间文本、解析值、时区和可信度；未知时间不能因为现有搜索适配器的过滤策略而在领域契约中被定义为不允许存在。

## 10. N1 证券与行业关联键补充（2026-11-05）

当前已确认 Go 侧 canonical symbol 规范化和证券目录快照，但未发现统一持久化 security master 或统一 security_id 外键；交易状态历史按 symbol 维度存储。旧 Python 的 stock_daily 存在 canonical_id 分析目标键，但未发现独立证券主表。行业数据目前以名称/文本映射和 Provider 返回值为主，未发现统一 industry_id 与分类版本主数据。

新闻首阶段不能假设 security_id/industry_id 已存在。首期使用 canonical symbol + market/exchange 作为关联键，同时保存原始代码、规范化结果、来源和证据；行业关系保存分类体系、来源代码/名称、有效时间和采集时间，未来主数据建立后再映射。


## 11. 公共服务延期后的模型使用边界（2026-11-05）

本文件此前的逻辑实体、表关系和并发约束作为领域建模参考保留，但不构成当前阶段的物理数据库实施任务。用户已确认 DB、Redis 和通用诊断能力由公共服务统一建设，新闻模块当前不得自行实现这些基础设施。

当前仍需在业务层确定：
- 新闻主体、来源、身份凭据、搜索观测、元数据版本、正文载荷和证券/行业关系的职责。
- 身份识别、去重、转载区分、版本变化和关联修正规则。
- 时间、授权、内容完整度和关联可信度等业务质量规则。
- Application 用例需要的最小 Repository 端口，但接口按业务操作定义，不机械对应每张候选表。

当前暂缓：
- 13 个候选实体的字段级 MariaDB DDL、索引、外键和建表顺序。
- `news_schema_migrations`、DDL 锁、checksum 和数据库恢复机制。
- `news_ingestion_runs` / `news_ingestion_run_steps` 的诊断持久化设计。
- SQL 事务、并发唯一键重读、数据库分页和 Redis 缓存实现。

业务测试可使用固定样本、fake Repository 和内存测试替身验证规则；不得据此声称持久化、跨进程幂等或历史查询已经实现。待公共服务契约稳定后，再复核逻辑模型并形成物理存储设计。


## 12. Provider 来源身份与观察记录解耦（2026-11-05）

新闻候选至少有两种不同来源身份：

- `provider_code`：本次搜索结果由哪个搜索/聚合 Provider 返回，例如 bocha、tavily、brave、searxng。
- `provider_item_id`：搜索 Provider 返回结果的标识，仅用于 Provider provenance/观测，不得作为发布来源的身份凭据。
- `source_item_id`：发布来源自身声明的原始文章 ID（RSS GUID / Atom entry ID 等），只在对应 source 范围内参与身份识别。
- `publisher_source`：候选新闻实际由哪个媒体、监管机构、交易所或公司发布。

两者不可复用同一字段。ProviderItemID 与 SourceItemID 也不可混用：ProviderItemID 不参与 source-native-id 身份凭据；只有来源明确声明的 SourceItemID 才能参与。Feed entry author 是作者元数据，不等于 publisher_source；发布者身份必须来自已登记 Source 配置。Provider 输出授权由 provider_code 对应的策略决定；正文抓取、内容保存和来源可信度由 publisher_source 对应的来源策略决定。Provider policy 必须分别表达允许用途、请求内临时处理、跨请求缓存、持久化、对外展示/再分发和保留期限；某一用途获准不能推导其他用途也获准。

`news_observations` 是新闻业务证据，不应强制依赖通用诊断 Run/Step。Observation 应能独立记录候选、provider_code、publisher_source（可未知）、观察时间、查询上下文摘要和结果指纹；未来可以可选关联公共服务的 execution_ref，但不能要求 run_step_id 非空才能形成业务观察。

当前不冻结 Observation 的数据库唯一索引。业务幂等应按可验证的候选来源身份、查询上下文和结果指纹设计，避免依赖已延期的诊断 run_step 唯一键。历史 Python 导入观察也必须能够在没有原始运行步骤记录的情况下保留其证据来源。



## 13. Source 与 Endpoint 授权策略作用范围

来源策略采用分层继承，不在每个入口重复复制发布者许可：

- Source 级策略是默认规则，覆盖该发布者的所有 endpoints。
- Endpoint 级策略按需建立，只记录相对 Source 默认规则的差异。
- Endpoint 策略默认只允许收紧权限；若有单独书面许可允许更宽范围，必须有独立授权证据、适用内容/用途/期限和生效时间。
- endpoint 没有独立策略时继承 source 策略；source 策略未核验则 endpoint 不能自动 approved。
- Provider 输出策略、Source 策略、Endpoint 策略、用途和保留期限必须共同通过，才允许相应字段进入持久化流程。

该规则当前只冻结领域策略语义，不代表已经实现策略存储或策略评估服务；后续由新闻业务 Domain/Application 实现，通用诊断仍由公共服务提供。


## 14. N1-A 领域语义冻结补充（2026-11-05）

本节用于消除时间字段、身份解析、版本识别和关系断言中的歧义；它冻结业务语义，不冻结物理 DDL。

### 14.1 时间字段的唯一语义

| 字段 | 唯一含义 | 生成/更新规则 |
|---|---|---|
| `published_at` | 发布者明确声明的发布时间 | 同时保留原始时间文本、原始时区、解析状态和解析器版本；无法可靠解析则为 NULL |
| `available_at` | 有证据证明内容首次对市场参与者可获得的时间 | 必须附可追溯证据；不得从 published_at、搜索引擎更新时间或 fetched_at 推算 |
| `observed_at` | 某一次搜索结果或来源采集记录被系统观察到的时间 | 每次 observation 独立生成，不覆盖历史 observation |
| `fetched_at` | 系统完成一次来源内容响应体获取的时间 | 仅在真实完成抓取时产生；搜索候选响应时间不能冒充正文抓取时间 |
| `normalized_at` | 某一新闻元数据版本完成标准化的时间 | 每个版本独立记录；重复处理但结果未变不创建新版本 |
| `first_observed_at` | 系统首次观察到该新闻主体的时间 | 由最早 observation 聚合得到，创建后不可回拨或覆盖 |
| `last_observed_at` | 系统最近一次观察到该新闻主体的时间 | 由 observation 聚合更新 |
| `created_at` / `updated_at` | 数据库记录生命周期时间 | 仅表达记录写入/更新，不表达新闻发生、发布或可获得时间 |

`system_observed_at` 不再作为独立业务时间字段：其“系统首次知道该新闻”的含义由 `news_items.first_observed_at` 唯一承载；单次发现时间统一使用 `news_observations.observed_at`。禁止在 version、observation 和 item 上重复保存同一语义的系统观察时间。

### 14.2 新闻主体与身份解析

1. 搜索候选首先形成 observation；只有发布来源身份可确认，且至少存在来源原始 ID 或规范 URL 一项身份凭据时，才允许创建 news_item。
2. `news_items.source_id` 必须指向真实、已登记的发布来源；发布者未知或无法映射时只保留 observation，不创建通用 unknown source。
3. 身份唯一范围为同一 source 内。不同 source 的转载默认是不同 news_item，不进行跨来源自动合并。
4. 同一 source 内优先使用 source-native-id 识别主体；规范 URL 作为身份凭据/别名。标题、摘要和内容指纹只参与候选匹配与版本判断，不单独构成主体唯一身份。
5. Hash 仅用于索引和快速定位；命中后必须比较原始 identifier_value。Hash 相同但原文不同按冲突处理。
6. 同一 source 的 source-native-id 与 normalized-url 若分别指向不同 news_item，必须返回 identity_conflict 并隔离，不自动合并。
7. URL 发生变化时保留旧 identifier 并标记 historical，新增当前 URL identifier；不得覆盖旧 URL 以丢失身份历史。
8. identifier 状态使用 active、historical、invalid。一个 source/type/hash 只能对应一个主体；primary 由业务选择规则推导，不额外维护 is_primary。

### 14.3 外部来源版本与内部内容版本

- 作者（author）是独立来源元数据，与发布者身份分离；作者变化属于来源元数据变化，应参与内容版本指纹。
- `source_version` 是发布者提供的外部修订标识；缺失时保持 NULL，不能用内部版本号伪造。
- `version_no` 是同一 news_item 内部单调递增的版本序号，从 1 开始；只由系统分配。
- `version_fingerprint` 根据标准化后的权威元数据和获准保存的内容载荷确定。不得包含 fetched_at、observed_at、normalized_at、抓取耗时等纯采集时间字段。
- 与当前最新版本 fingerprint 相同的重复抓取不创建新版本；若内容经历 A → B → A，恢复到历史内容 A 时应追加新版本，以保留真实修订时间线。仅抓取时间、观察时间或 Provider 变化不创建新版本。
- 标题、摘要、规范 URL、语言、发布时间或获准保存的正文发生实质变化时创建新版本。source_version 变化作为来源修订证据保存；若权威内容 fingerprint 未变化，不单独制造内容版本。
- 当前版本按最大 version_no 获取，不维护可变 current_version_id。旧版本不可原地覆盖。
- 正文载荷必须绑定具体 version，并独立接受 Provider 输出策略、Source/Endpoint 授权和保留期限检查。
- 正文载荷状态仅表达载荷保存状态：available（载荷可读取）、restricted（因授权/法律限制不可读取）、expired（保留期限已到，等待清理）、purged（载荷已清除，仅保留政策允许的审计元信息）。未采集正文不创建空内容记录。

### 14.4 Observation 与业务处理状态

Observation 是不可丢失的发现证据，不等同于新闻主体，也不等同于通用诊断 Run/Step。每条 observation 至少保留 provider_code（若由搜索 Provider 产生）、publisher/source（可未知）、observed_at、查询上下文摘要、候选原始字段、字段缺失状态和结果指纹。

- observation 初始可为 unmatched；身份解析成功后关联 news_id 并标记 matched。
- 发现身份冲突标记 conflict；按明确规则判定为无效/不纳入时标记 rejected。
- observation 原始候选字段和首次观察时间不可被后续标准化结果覆盖；匹配状态和 news_id 是解析结果，可在保留审计证据的前提下更新。
- 未能形成 news_item 的 observation 仍然是有效业务证据，不要求关联诊断 run_step。

### 14.5 新闻主体、授权与内容状态分离

`news_items.status` 只表达主体生命周期：active、withdrawn。来源撤稿/明确撤回可使主体变为 withdrawn；普通内容修订只增加 version，不改变主体生命周期。

以下状态不得塞入 news_items.status：
- 来源/Provider 授权：approved、restricted、pending、revoked。
- 正文载荷存储：available、expired、purged、not_collected 等内容载荷状态。
- 新闻质量：valid、degraded、invalid、unknown。
- 技术执行结果：success、empty、failed、skipped。

授权撤销或正文到期只影响对应载荷的访问/保存状态，不自动等同于来源撤稿；内容删除后可按政策保留必要的非内容审计元信息。

### 14.6 证券/行业关系断言

- 证券关系使用 canonical symbol + market/exchange 作为当前阶段业务键，并保存原始代码、规范化规则版本、来源和证据；不虚构 security_id。
- 行业关系保留分类体系、来源行业代码/名称快照、有效时间和系统观察时间；不虚构 industry_id。
- 关系采用追加式断言。修正或撤销通过新断言引用 supersedes_relation_id，不原地修改旧断言。
- 关系断言状态使用 proposed、confirmed、rejected、retracted。来源明确披露且证据可定位时可进入 confirmed；标题/正文匹配、规则或模型推断默认 proposed；人工核验可确认或驳回。
- 当前关系必须沿 supersedes 链计算：被后继断言替代的旧断言不是当前关系；链末端 rejected/retracted 不构成有效当前关系。不能只查询 confirmed 状态。
- 每条新闻最多只能有一个当前 confirmed 的 `primary_subject` 关系；该约束跨证券与行业主体共同计算，多个并存属于历史冲突。`mentions` 关系不受此数量限制。
- proposed 后继不改变当前关系；若 proposed 断言被 retracted，只撤销该 proposed 断言本身，不得越过它撤销更早的 confirmed 祖先关系。confirmed 后继则可穿过 proposed 中间态生效。
- `retracted` 是终态断言，不允许再被后继断言 supersede；如需重新建立关系，应创建不引用该撤销断言的新断言，并由当前关系唯一性规则校验。
- 同一旧断言最多有一个直接 superseding 断言；并发写入时由 Repository 事务约束，未来物理实现时落实唯一约束和链校验。
- 关系断言 ID、NewsID、SupersedesRelationID，以及证据中的 RelationID、SourceVersionID、ObservationID 必须使用规范标识，不允许首尾空白；Domain 入口不得依赖 Application 代为清洗。
- 证券关系的 Market/Symbol、行业关系的 ClassificationSystem/ClassificationVersion/IndustryCode/IndustryName，以及证据的 FieldPath/RuleVersion/ModelVersion，同样不得包含首尾空白；名称字段不做大小写或内部空白改写。



## 15. N4 首批身份凭据规则（2026-11-05）

- 身份凭据只在已确认的 source 范围内匹配；不同 source 即使原始 ID 或 URL 相同，也不自动合并，转载保留为不同新闻主体。
- 首批凭据类型为 source-native-id 与 normalized-url。来源原始 ID 仅做首尾空白清理；URL 必须先通过来源 HTTP(S)/Host/Port allowlist，再使用 URL 规则生成规范值。
- Hash 使用 SHA-256 作为索引键；匹配必须同时核对 source_id、identifier_type、hash 和 identifier_value 原文。Hash 相同但原文不同返回 hash_collision。
- 同一候选的多个凭据命中不同 news_id 时返回 multiple_items 冲突，禁止自动合并。
- active 与 historical 凭据都参与身份匹配；invalid 凭据不参与。历史 URL 因此仍可识别原主体。
- 本批仅提供纯 Domain 凭据构造和已有凭据解析；不负责创建 news_item、写入观察记录、变更 URL 历史状态或跨进程并发幂等。上述行为需后续 Application/Repository 契约与持久化阶段完成。


## N3 Feed 附件质量映射

- Feed 附件元数据进入独立的 Domain ContentAttachmentMetadata 层，保存原始声明、规范字段、长度和校验问题；不把附件当作正文，也不触发下载。
- 仅存在附件而没有正文/来源摘要时，内容质量为 degraded（attachment_only_no_body），不能将附件元数据视为正文可用。
- 附件声明异常以 content 维度的 attachment_* 原因码表达；附件元数据问题不会直接使整个 Feed 文档解析失败。
- 附件元数据参与内容版本指纹；原始声明变化可以被版本历史观察到。


## N3 Feed 解析结果映射契约

- Feed `guid` / Atom `entry.id` 映射到来源原始身份 `SourceItemID`；搜索 Provider 的 `ProviderItemID` 仅用于 Provider provenance，不参与来源内身份凭据。
- Feed `author` 独立映射到作者字段，不得填充发布者身份；`PublisherName` / `PublisherDomain` 必须由已登记 Source 配置显式提供。
- Feed 附件映射为独立 `ContentAttachmentMetadata`，保留原始声明、规范值和校验问题；附件不构成正文，附件单独存在时内容质量为 degraded。
- 作者和附件元数据参与内容版本指纹；Provider 搜索摘要、Provider 条目 ID、Source 条目 ID 和采集时间不参与内容版本指纹。
- Parser 不负责身份解析、来源授权或业务质量结论；上述结果分别由 Application/Domain 流程负责。


- Feed 离线解析使用 Go XML 解码，不展开外部实体；外部 DTD/实体不能成为文件读取或网络访问通道。外部正文引用（Atom content src）只保留声明元数据，不在 Parser 或 ResearchUpdate 阶段请求该 URL。

## 15. N3 Feed 元数据与版本指纹 v2（2026-11-05）

- 当前内容指纹算法标识为 `news-version-v2`。v2 在既有来源元数据、摘要和正文基础上，明确纳入 Feed 正文原始 Content-Type 声明、Atom 外部正文引用及附件原始/规范元数据。
- Provider 搜索摘要、Provider/Source 条目身份 ID、观察时间和采集上下文仍不参与内容版本指纹。
- Atom `content src` 仅作为来源声明元数据参与指纹；它不是正文载荷，不触发 URL 请求。
- 正文载荷在标准化时将 CRLF 统一为 LF；存储内容与版本指纹使用相同换行语义，避免同一内容因平台换行差异被错误去重。
- 当前尚无生产 Repository 或已持久化版本指纹，因此本次算法标识升级不涉及历史数据库迁移。
- Candidate 同时保留 RawURL 与 CanonicalURL。IngestCandidate 仅在 Source URL Policy 允许时写入 CanonicalURL；原始 URL 不被覆盖，身份凭据和内容版本指纹共用同一规范化规则。ResearchUpdate 不持有 URL Policy，调用方必须传递 Observation 中已规范化的 Candidate；缺少 CanonicalURL 时仅按原始 URL 参与指纹，不自行推导或改写。


- 版本更新的 URL 信任边界：`ApplyResearchUpdate` 必须从事务内读取并验证的 Observation 取回 `RawURL` / `CanonicalURL`，覆盖请求方候选中的 URL 字段后再计算指纹。ResearchUpdate 请求可以提供内容元数据，但不能重新指定身份 URL 或伪造策略规范化结果。


### N3 在线采集授权版本溯源

在线 Source Adapter 的采集结果必须同时保留：

- SourcePolicyVersionID：本次评估使用的发布来源授权策略不可变版本引用，必填。
- EndpointPolicyVersionID：只有存在独立 EndpointPolicy 时必填；继承 Source 策略时为空。
- PolicyEvaluatedAt：执行授权交集评估的 UTC 时间。
- EvidenceRef 仍是授权证据引用，不得替代策略版本 ID。

Observation 领域模型已增加上述版本引用和评估时间字段；CollectSourceResult 可转换为 ObservationPolicyTrace，并由 IngestCandidate.ExecuteWithPolicyTrace 写入 Observation。策略版本 ID 纳入 Observation 幂等载荷比较，防止同一幂等键跨策略版本重放。策略版本内容仍由统一 Source Catalog/策略注册能力管理，新闻模块本批不实现策略注册表或数据库。
