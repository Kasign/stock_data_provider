### 5.1 NEWS-POST-01：Feed 生产触发权与执行边界（已完成当前范围决策）

- Researchflow Domain/Application 拥有 Run/Stage/Attempt 和 Stage Scheduler/Worker/WorkerPool；Scheduler 负责一个 Run 内的 Stage 依赖、就绪、重试和派发，不是通用 Cron Scheduler。
- Server 的 `researchflowRuntimeComponent` 负责组合根装配、扫描循环启停、Worker Pool 生命周期和进程关闭协调；它不拥有 Researchflow 的业务调度算法，也不替业务调用方决定何时创建 Run。
- 当前 News Search Stage 由 Researchflow Run 驱动，执行的是搜索候选；它不等于 Feed/Source 的持续采集。News 的 CollectSource 是单次受控调用，IngestCollectedSource 使用调用方提供的 IdempotencyPrefix，不创建持久化 CollectionRun 实体。
- 当前没有独立于 Researchflow 的 Feed 持续生产调用方或已确认的定时采集业务场景。因此当前范围不建设 News 自有 Cron、Scheduler、后台队列、独立 Worker 或 CollectionRunID；这不是永久禁止未来增加，而是没有调用场景时不预建。
- 责任规则：调用方模块拥有业务触发策略（何时执行、执行目的、周期/事件条件）；被调用模块提供有界 Application 用例和领域语义；执行机制由实际用例所属模块提供；Server 只负责将后台组件装配进进程并管理 Start/Stop/Shutdown 和共享资源。
- 若未来由 Researchflow 发起 Feed 采集，Researchflow 创建 Run/Stage/Attempt 并决定触发；News 提供 Feed 采集 Stage 所需的领域能力，复用 Researchflow 执行上下文。若由其他业务模块发起，则由该调用方持有触发策略和执行身份。
- 不把 RequestID 当作任务身份；不把 Researchflow Run/Stage/Attempt 复制为 News 领域身份；NewsItem/Observation/Version 身份及现有业务幂等键继续由 News 管理。
- 当前决策结果：NEWS-POST-01 关闭；未来出现明确调用方和生产触发需求时，作为新调用场景重新评审，不预设 CollectionRunID 或通用任务系统。

### 5.2 NEWS-POST-02：生产组合与真实网络

#### 当前代码核对事实

- Provider 路径：News Config 已装载 Bocha/Tavily/Brave/SearXNG 配置；`NewPlatformProviderSet` 为每个 Provider 创建独立 Platform HTTP 策略适配器；Server 的 `newNewsSearchStageComposition` 已装配该 ProviderSet，当前 Search Stage 生产路径已存在。
- Source 路径：Application 已定义 `SourceCatalog`/`SourceTransport`；当前唯一 Catalog Adapter 是启动期不可变 `StaticSourceCatalog`。`NewPlatformEndpointTransport` 能按每个 Source/Endpoint 创建独立 Platform DestinationPolicy 传输器。
- `CollectSource` 只执行受控 RSS/Atom 获取和解析，结果保持 transient，不写 DB；`IngestCollectedSource` 是独立的授权复核与 Observation 元数据写入用例，要求调用方提供 `IdempotencyPrefix`。
- News Config 当前只包含搜索 Provider 和 Evidence Cursor Key Ring，没有 Source/Endpoint 注册配置。News Migration 持久化授权策略版本/当前指针，但没有 Source/Endpoint 目录表。
- Server 当前装配了 Search Provider/Stage 和 News→Research Evidence Query；没有装配 SourceCatalog、Source Endpoint Transport、CollectSource 或 IngestCollectedSource。因此“Provider 搜索生产链路已接入”不能推导为“Feed/Source 生产采集已接入”。

#### 仍需核实/补齐

- Source/Endpoint 注册数据：当前 `StaticSourceCatalog` 已可承载可信启动快照，但 News Config 没有 Source 注册配置，且没有确认的管理/更新调用场景。当前先不新增目录表、管理 API 或动态配置系统；待调用方明确来源清单维护方式后再定。
- 调用方：调用方负责选择 Source/Endpoint、Purpose、内容/存储级别、Retention、批次和幂等前缀；News 提供 Collect 与 Ingest 用例，不自行创建调度器。
- 采集前策略预检：已新增窄 Port `CurrentSourceCollectionPolicyResolver` 和 `MySQLRepository.ResolveCurrentSourceCollectionPolicies`。Storage 在只读事务快照内读取当前指针及不可变 payload，核验策略身份、版本、领域结构和 PayloadHash；Catalog 中 Endpoint Policy 版本为空时，必须确认数据库中也不存在 Endpoint 当前指针。Application 使用解析出的当前策略执行 `EvaluateSourceCollectionPolicy`；解析器缺失、读取失败、版本不一致或策略拒绝均在 `SourceTransport.Do` 前 fail-closed。生产组合应显式使用 `NewCollectSourceWithPolicyResolver`；兼容构造器仅在 Catalog 同时实现 Resolver 时可用，否则拒绝采集。
- 预检与撤销语义：不跨外部 HTTP 请求持有数据库事务/行锁，避免把网络延迟变成策略发布阻塞和连接池占用。成功预检是一次采集执行的授权决策点；决策点之后发生的策略撤销不追溯取消已经开始的请求，但 Ingest 仍在 Observation 写事务中锁定当前策略版本并复核，版本变化则拒绝持久化。若业务要求“撤销提交后连已预检但尚未发出的请求也必须阻止”，则需要单独的短期授权租约/请求闸门设计，不能声称普通预检实现了这一强语义。
- `collect_source_test.go` 已覆盖当前策略解析成功后使用数据库策略而非目录旧策略、解析失败时网络调用次数为零、缺少 Resolver 时 fail-closed。`mysql_repository_integration_test.go` 增加 MariaDB 集成测试，覆盖 Source 当前版本切换、旧版本拒绝、当前 revoked 策略读取，以及 Catalog 未记录 Endpoint Policy 但数据库新增 Endpoint 当前指针时拒绝。
- `source_ingest_test.go` 还覆盖部分批次提交后使用同一 `IdempotencyPrefix` 重试可收敛。调用方必须对同一逻辑采集执行的重试复用 Prefix；新的逻辑执行应使用新的 Prefix，不能每次 Attempt 都生成新 Prefix，否则会破坏重试去重语义。
- 在 SourceCatalog 和 Endpoint Transport 真实装配后，逐 Endpoint 核验授权策略版本、DestinationPolicy、超时/响应限制、解析和持久化门禁。

- Provider 与每个 Source Endpoint 必须独立创建精确 DestinationPolicy 的 BoundDoer；Provider 与 Source 不得共用宽泛 Doer。
- Platform Client、Secret 和共享资源由 Server 持有；News 不创建第二套 HTTP Client/连接池。
- Provider Output Policy、Source Policy、Endpoint Policy 按现有授权模型求交集；未授权、unknown、pending、revoked 均 fail closed。
- 先做受控环境验证，再对已确认许可的真实 Provider/Source 做 DNS、出口、重定向、响应体限制、Deadline、解析、身份、Observation 和持久化端到端验收。
- 缺凭证、无授权、未配置或无可比较样本标记 skipped/not_comparable，不得标成通过；不得为验收故意修改真实凭证制造故障。
- 不增加 News 对外 HTTP API；不修改 `cmd/**`、`internal/server/**` 或公共 Platform 代码。

### 5.3 NEWS-POST-03：Diagnostics 注册

- 当前 Server 已注册 ParserChecks、ProviderConfigChecks；News 另有 SourceEndpointCheck、ProviderOutputPolicyCheck/ResolverCheck、StorageChecks、ObservationRetentionCheck 和单条 BusinessQualityCheck 工厂。
- 只有对应 Repository、SourceCatalog、Policy Resolver 等真实依赖已装配，才注册依赖型 Check；不注入 nil/fake 以制造绿色状态。
- Provider/Source 未配置或没有许可时使用 skipped/not_comparable；依赖不可用或 Check 执行异常按失败；有数据但业务质量/新鲜度不满足阈值时按降级或领域 invalid 记录，不能把平台 Runner failed 与业务数据 invalid 混为一谈。
- BusinessQualityCheck 是单条 Evidence 的质量评估，不默认注册为全局 Readiness Check。
- 每个 Check 必须记录调用场景、数据来源、reason_code、safe_message、attributes 白名单和四态判定：通过、降级、失败、不可比较。

### 5.4 NEWS-POST-04：Cleaner 周期执行接入

- ObservationRetentionCleaner、EvidenceSnapshotRetentionCleaner 等是 News 提供的一次性、有界 Application 用例，只负责清理语义、批次边界和持久化结果，不负责决定何时运行。
- 是否周期执行及执行频率由实际调用方决定：若是业务流程的一部分，由该业务模块持有触发策略；若是部署级维护任务，则由明确的运维/应用组合入口配置触发。不得仅因 News 拥有 Cleaner 就默认由 News 自建定时器。
- Server 负责将已确定的后台组件装配进进程，并管理进程级 Start/Stop/Shutdown、共享资源和优雅关闭；不代替调用方决定业务周期，也不新增通用 Task Queue。
- 不在 API 请求路径同步执行大批清理。未确定调用方和频率前，Cleaner 保持可被显式调用，不声称周期 Worker 已接入。
- 验收必须使用真实 MariaDB 验证到期边界、批次上限、重复执行、并发执行、失败重试、Context 取消和关闭行为；只有真实周期运行记录才可证明周期执行闭环。

### 5.5 NEWS-POST-05/06：available_at 与 Research B 组

- available_at 必须来自经授权来源明确声明的首次公开可获取时间，保留字段路径、原始值、证据 URL、策略版本、内容版本、采集时间和解析器版本。
- 普通 published_at/published_date、RSS pubDate、Atom published/updated、HTTP Date/Last-Modified、Provider 索引时间、fetched_at、observed_at 均不能替代。
- 证据缺失、冲突、授权不明或语义不清时保持 NULL/不可比较并从严格 PIT 结果排除。
- 在 POST-05 获得合格来源证据前，POST-06 不启动，不产生生产 Research Evidence 成功写入。

## 6. 验收状态统一定义

- **通过（PASS）**：精确 SHA 的代码/契约测试通过；需要真实数据或网络时，必须有对应真实 Provider/Source、授权、持久化和运行证据。
- **降级（DEGRADED）**：检查能够执行，但覆盖、新鲜度或业务质量不满足完整门槛；必须保留稳定 reason_code 和证据。
- **失败（FAIL）**：配置/依赖/数据完整性/安全边界违反要求，或 Check 自身执行异常；说明失败责任层，不把 Provider 业务失败误映射为 Platform Check 失败。
- **不可比较（NOT_COMPARABLE）**：缺凭证、未授权、未配置、没有真实样本或缺少可比基准；不得折算为通过或失败。
- 测试替身只证明测试路径；真实数据验收必须说明来源、样本范围、采集时间、授权状态、持久化结果和精确 SHA。
- 新增字段必须在任务记录中给出来源、语义、时间口径、可空条件和授权要求；新增接口必须给出真实调用方和调用场景。
