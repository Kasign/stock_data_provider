# 新闻模块总体设计

> 版本：设计草案 v0.1  
> 状态：待 N1 代码盘点和评审冻结

## 1. 建设目标

为 A 股低频研究提供可追溯、可验证、可按历史时间使用的新闻基础数据。核心产物是新闻事实、原始证据、来源信息、时间信息、内容版本、证券关联和质量状态，不是模型观点或交易信号。

## 2. 职责边界

### 新闻基础设施（本专项）

- 新闻来源和 Provider 管理。
- 搜索结果接入、正文采集与内容抽取。
- 原始记录保存、标准化、去重和版本识别。
- 新闻与证券、行业的基础关联及关联证据。
- 数据持久化、查询 API、质量诊断和采集可观测性。

### 事件研究（不属于本专项）

- 多篇新闻聚合为事件。
- 事件分类、生命周期和状态变化。
- 影响方向、影响时效、不确定性及价格验证。
- 事件解释、研究结论和后续跟踪。

对应总体规划任务：新闻基础设施主要映射 DATA-016、MIG-005；事件研究对应 RESEARCH-004、MIG-006。两者不得混为一个新闻采集模块。

### 研究编排（不属于本专项）

消费新闻和事件数据，与行情、财务、估值等信息组合分析。新闻模块不生成买卖信号，不负责完整研究决策。

## 3. 架构原则

1. 模块化单体，不新建独立微服务。
2. 复用现有 Go 服务、数据库、Redis、配置、日志、诊断和部署。
3. 优先复用现有新闻搜索适配器，不重复实现相同 Provider。
4. Domain 不依赖 HTTP、SQL 或 Provider。
5. Application 编排用例，不直接执行 SQL。
6. Adapter 负责外部来源协议和响应转换。
7. Repository 负责持久化。
8. Handler 负责 HTTP DTO、参数校验和响应。
9. 不直接依赖 LLM，不将模型生成内容当作来源事实。
10. 不修改行情、财务、估值模块既有行为。

## 4. 目标职责分层

以下是职责参考，不要求机械创建目录；N1 应先遵循仓库现有结构：

- Domain：新闻、来源、内容版本、关联事实和质量状态。
- Application：搜索、采集、标准化、去重、查询和诊断用例。
- Adapter：搜索 Provider、官方信息源、正文采集和解析。
- Repository：新闻专属数据持久化。
- Handler：新闻 API。

已有 `newssearch`、`news_cutoff` 等代码必须先盘点后决定复用、扩展或迁移，不能另起平行实现。

## 5. 数据流

1. Application 根据查询或采集任务选择已启用来源。
2. Provider Adapter 获取候选新闻并保留来源原始标识。
3. 内容采集器在合法、可访问的前提下获取正文或公告原文。
4. 标准化器生成规范字段，同时保留原始字段和证据。
5. 去重与版本识别确定新记录、重复记录或内容更新。
6. 证券/行业关联生成关联事实及证据。
7. Repository 持久化记录、内容、版本和关联。
8. 查询 API 返回数据及来源、时间、完整度和质量元信息。
9. 诊断体系记录 Provider 可用性、延迟、错误和质量结果。

## 6. 与其他分支隔离

- 本专项只在 `feat/research-news-ingestion` 开发。
- 目标集成分支为 `feat/full-go-data-providers-api-switch`。
- 不修改 WebUI 分支、整体规划分支和 main。
- 开发期间只新增新闻专属代码、测试和 `doc/news/**`。
- 数据库首阶段只新增新闻专属表，不修改现有行情、财务、估值和证券表。
- 不改变既有公共 API 行为。
- 不删除 Python Bridge 或旧新闻调用链。
- 不创建 PR、不合并，除非另行获得明确授权。

## 7. 安全与合规

- 不开放任意 URL 抓取接口，避免 SSRF。
- 对来源设置访问频率、超时、大小限制和并发限制。
- 明确来源授权、robots 约束、版权和内容保留策略。
- 原始 HTML/正文的存储范围必须在 N1 明确，不能默认长期保存所有第三方全文。
- 日志不得输出 API Key、Token 或敏感请求头。

## 8. N1 待确认事项

- 当前 Go 新闻搜索能力、调用方和依赖关系。
- Python 新闻链路完整范围。
- 现有 DB、Repository、Handler、Probe 和质量契约约定。
- 正文采集的合法来源、授权及存储边界。
- 证券/行业 ID 与关联能力。
- API 路由和错误响应的现有规范。

上述事项核实前，不冻结代码目录、表结构和 API 实现细节。

## 9. N1 第一轮代码证据盘点（2026-11-05）

> 基于 feat/research-news-ingestion 当前代码的静态盘点。未执行 Provider 请求、未连接生产数据库。代码存在不等于目标环境已运行或真实数据已验收。

### 9.1 运行架构：仓库存在两条 Go 运行路径

**统一部署路径**（根目录 docker-compose.yml）：
- stock-analysis-server 由根模块 cmd/analysis-api 启动，监听 8092。
- stock-analysis-data 由 services/market-data 启动，监听 8091。
- stock-analysis-web 由 web 启动，监听 8093。
- 该 Compose 未启动 go-core 或 python-bridge。

**可选迁移路径**（docker/docker-compose.go-migration.yml 的 go-migration profile）：
- 启动 python-bridge、stock-analysis-data 和 go-core。
- go-core/cmd/analysisd 通过 pythonbridge.Client 调用 Python Bridge，并通过 marketdatahttp.Client 调用 market-data。
- 该路径是独立的旧迁移 profile，Compose 注释要求不要与根目录统一部署栈混用。

因此，原先建议的 go-core/internal/news 只能作为旧迁移路径中的分析新闻能力扩展点，不能直接作为当前统一部署的新闻基础设施落点。新闻持久化与查询 API 的目标进程尚需确认。从统一部署结构看，优先评估根 Go 模块增加独立 internal/news/ 业务包，由 cmd/analysis-api 组装，复用 internal/platform/httpapi 和 internal/adapters/storage/mysqlredis；这仍是建议，N1 结束前不冻结。不要把新闻持久化放进 services/market-data，该服务负责行情及公告等数据源能力。

### 9.2 现有 Go 新闻搜索能力

go-core/internal/adapters/newssearch/search.go 已有实质实现：
- 原生搜索 Provider：Bocha、Tavily、Brave News、显式配置的 SearXNG。
- 可选 StockAnnouncementSource，由启动组装注入 marketdatahttp 客户端。
- Python Bridge SearchAdapter 作为兼容 fallback。
- 多维查询计划、并发请求、超时、结果过滤、相关性排序、来源域名加权、营销词过滤。
- 进程内缓存默认 10 分钟，上限 512 个 key；请求超时默认 10 秒；查询计划最多 5 个。
- 去重依赖规范 URL 和标准化标题，不是跨来源内容指纹或新闻实体级去重。
- 当前过滤无法解析发布时间、过旧或未来发布时间的结果；这会丢失“发布时间未知但仍可作为待核实候选”的信息。
- 股票公告候选只请求第 1 页、最多 100 条；公告源失败或超过 2 秒会降为无公告候选，不单独返回结构化采集诊断。
- 当前 domain.NewsItem 只有 title、summary、url、source、published_at、retrieved_at、relevance、dimension；没有正文、available_at、source item ID、原始响应证据、内容版本、采集任务状态或证券关联证据。
- 原生 Searcher 将 published_at 格式化为日期，不保留精确时分秒。
- 以上适合继续作为搜索适配器复用，但不等于新闻采集入库、来源管理、内容版本和查询 API 已实现。

### 9.3 分析流程边界

- go-core/internal/application/stock_flow.go 和 market_flow.go 通过 ports.NewsSearcher 调用个股/市场新闻搜索。
- go-core/internal/application/news_cutoff.go 负责分析参考时点过滤：显式 as_of 严格排除缺失/非法发布时间；实时分析可保留但标记为未核实；未来发布时间始终排除。
- news_cutoff.go 是分析流程的证据有效性规则，应留在 application，不迁入新闻基础设施模块。
- go-core/internal/domain.NewsItem 和 ports.NewsSearcher 是现有分析消费契约。新新闻持久化领域不应直接扩展共享模型承载采集细节；应由新闻模块自己的模型承接，再由分析适配器转换为旧 NewsItem。

### 9.4 Python 新闻调用链

当前 Python Bridge：
- python_bridge/capability_app.py 暴露 POST /internal/v1/search/stock-news 和 POST /internal/v1/search/market-news，使用 X-Python-Bridge-Token。
- python_bridge/capabilities/search.py 的个股入口调用 src.search_service.get_search_service().search_comprehensive_intel(...)，再扁平化各维度结果；市场入口调用 MarketAnalyzer.search_market_news()。
- go-core/internal/adapters/pythonbridge.SearchAdapter 对应调用上述两个 Bridge 路由。
- go-core/cmd/analysisd/main.go 组装 legacySearch、原生 newssearch.NewFromEnv(...)、StockFlow 和 MarketReviewFlow。原生搜索可用时优先；无原生结果时才回退 Python Bridge。
- python_bridge/go_core_client.py 是 Python 调用 Go Core 的统一入口，GO_CORE_ENABLED 默认 false；它暴露分析工作流调用，不是新闻采集 API。
- 固定旧 Python 源码提交 Kasign/daily_stock_analysis@7a21cd76952c7fe44a7fc5a6113a5b2b8a16bb32 另有 Agent 搜索工具：src/agent/tools/search_tools.py 的 search_stock_news 和 search_comprehensive_intel 调用共享 SearchService，并通过 _persist_news_response 调用 save_news_intel；src/market_analyzer.py 会合并已持久化的市场情报与搜索新闻。
- 旧 Python 新闻链路不仅是 Bridge 两个函数，还包含 Agent 工具和本地情报持久化/读取。还需追踪 API、Bot、Scheduler 等入口是否直接触发这些能力，不能只迁移 Bridge 端点就宣称旧链路已退役。
- 根目录统一 Compose 不包含 Python Bridge/go-core；只有可选 go-migration profile 包含它们。Python 兼容迁移的实际生产使用范围需结合部署环境确认。

### 9.5 数据库、Repository 与迁移现状

静态盘点确认至少有两套 MariaDB 接入：
1. 根 Go 模块 internal/adapters/storage/mysqlredis：通过 database/sql 创建并持有 *sql.DB 与 Redis 客户端；cmd/analysis-api 复用该 Store 启动任务队列、Runner 和 HTTP API。Store 暴露 DB，Migrate 通过内嵌 SQL CREATE TABLE IF NOT EXISTS 建立 analysis_runs、analysis_stage_events、analysis_snapshots、analysis_tasks；CheckSchema 检查这 4 张表。
2. services/market-data/internal/repository：独立 OpenMySQL、独立 Store 和 Repository，Migrate 通过 Go 代码内嵌 SQL 创建 market_data 专属表，包含 Probe 历史、行情、日 K 版本、财务版本、公司行为等。

go-core/go.mod 没有 SQL/Redis 驱动依赖；go-core 下未发现迁移目录或新闻 Repository。因此不能把新闻 Repository/MySQL 实现直接放在 go-core 并假设它可以复用统一部署服务的数据库连接。

当前可见迁移方式是服务内嵌 SQL 与启动 schema 检查，不是统一的独立 migration runner；未发现可直接复用的全仓库迁移版本账本。实施前需确定新闻表由哪个服务 Store 管理、如何处理已有库升级，以及是否需要显式 schema version，不能另建 DB 连接池或迁移系统。

### 9.6 证券主数据与公告复用边界

- 现有 Go 新闻消费和公告接口使用证券代码/标准 symbol（如 600519.SH）作为关联标识。
- services/market-data 已有公告 Provider、公告模型和 HTTP 能力，go-core/newssearch 通过 StockAnnouncementSource 调用；不应复制公告 Provider。
- 当前 market-data SQL 表清单未发现可作为统一证券主数据外键的 security master 表；不能假定存在稳定内部 security_id。需继续核实根服务证券标准化、股票代码映射与退市/更名处理，再决定新闻关系表暂时使用 canonical symbol 还是引用统一 security ID。
- 行业标准 ID 与行业分类版本也尚未确认。

### 9.7 HTTP、认证、分页和错误契约

- 统一部署主 API 在 internal/platform/httpapi.Server 注册分析 runs/tasks 路由，统一包裹 request ID、请求日志和 panic recoverer；当前没有新闻路由。
- 根 API 错误响应使用 code、message（及可选 request_id）；任务事件接口使用 after_sequence + limit，不能据此推断所有列表都应采用 offset 分页。
- market-data 是独立服务，使用自己的 API Key、错误 envelope、Probe 路由和分页/参数规则。不要将它的认证直接复制给主分析 API。
- go-core HTTP Server 使用 X-Go-Core-Token，目前只暴露分析工作流路由。
- 候选 /api/v1/news* 路由需要落到目标服务确认后再冻结；需明确新闻读写权限、搜索是否触发外部调用、限流、分页和部分 Provider 失败语义。

### 9.8 诊断能力复用判断

market-data 已有统一 Provider Probe，支持 connectivity、contract、quality、freshness、cross_provider、storage 检查，并结合 Provider、Normalize、Validator、Reporter、Freshness Evaluator、Probe History。该体系是新闻诊断设计的重要参考，但当前检查项和证据模型面向行情能力，不能原样视为新闻采集诊断已经存在。

新闻模块应复用通用 HTTP 超时、日志脱敏、状态语义和可观测性约定；新闻自身仍需覆盖 search、fetch、parse、normalize、deduplicate、persist、relation 等阶段。搜索成功不能代表正文抓取、标准化或入库成功。未配置 Provider 应为 skipped；部分能力可用应 degraded；不能用统一 success 布尔值抹平各阶段结果。

2. news_cutoff.go 继续留在 go-core/internal/application，不迁移。
3. 现有 go-core/internal/adapters/newssearch 和 Python Bridge 保留为兼容/搜索适配路径，不搬迁、不删除。

5. 路由、中间件和统一错误格式复用最终选定服务现有 HTTP 层；不要在新闻模块内再造 Server。
6. 先复用 market-data 公告能力；不在新闻模块复制公告 Provider。

8. 采集任务、原始证据保留策略、内容版本、幂等、来源授权/保留、配额和清理仍是设计必须项。

### 9.11 旧 Python 新闻持久化与 API 的进一步核对

固定旧上游提交 Kasign/daily_stock_analysis@7a21cd76952c7fe44a7fc5a6113a5b2b8a16bb32 中，新闻持久化并非单一表：
- news_intel：保存 Agent/SearchService 搜索结果，包含 query_id、股票代码/名称、维度、查询词、Provider、标题、snippet、URL、来源、published_date、fetched_at 和请求来源元数据；旧模型对 URL 使用全局唯一约束。
- intelligence_sources：可配置来源目录，含 source_type、URL、enabled、scope_type/scope_value、market、描述、最近状态/错误/采集时间。
- intelligence_items：来源采集后的资讯条目，含 source_id/source_name/source_type、标题、摘要、URL、来源、published_at、fetched_at、scope、market 和 raw_payload；唯一约束按 source_id + URL + scope + market 组合，另有范围时间索引。
- IntelligenceRepository 提供来源 CRUD/状态更新、条目 upsert、分页查询和按 fetched_at 保留期清理。upsert 会更新已有条目的摘要、来源、发布时间、抓取时间和 raw_payload，不保留内容修订历史；这正是新版本模型需要补强的地方。
- IntelligenceService 提供来源模板、创建/列表、dry-run 测试、单来源抓取、启用来源批量抓取、自动刷新、错误脱敏和 retention。采集来源包括 RSS/Atom 与 NewsNow；抓取前有 URL/DNS 校验和重定向限制，不能将任意 URL 抓取能力简化成开放代理。
- 旧 API 已有 intelligence 路由：来源创建/列表/模板/默认来源、来源测试、单来源 fetch、enabled sources fetch、已入库 items 分页查询。列表 page_size 上限 100。
- MarketAnalyzer 在市场复盘时触发 refresh_auto_sources 并读取已持久化 market intelligence；Agent 搜索工具另写 news_intel。两套旧数据语义不同，迁移时不可粗暴合并为一个没有来源类型区分的表。
- Bot 的 /research 命令会启动 ResearchAgent/工具注册；API 有独立 intelligence endpoints。已确认这两类入口存在，但尚未穷尽 Agent Tool Registry 的所有注册方、旧分析入口和 Scheduler 的直接触发关系。

因此，Go 新闻模块的迁移对象至少需要区分“搜索发现结果”和“配置来源采集条目”，并决定是否把旧 news_intel 仅作为历史研究证据迁移，而不是把它与持续采集的 intelligence_items 混成同一来源实体。新设计需补充旧表到新模型的映射、保留期、去重冲突处理、来源配置迁移与回滚计划。
