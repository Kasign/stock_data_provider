# 新闻模块总体设计

> 版本：设计草案 v0.3  
> 状态：新闻领域架构内部收敛完成；已对齐公共平台规划，待用户评审确认

## 1. 建设目标

为 A 股低频研究提供可追溯、可验证、可按历史时间使用的新闻基础数据。核心产物是新闻事实、原始证据、来源信息、时间信息、内容版本、证券关联和质量状态，不是模型观点或交易信号。

## 2. 职责边界

### 新闻基础设施（本专项）

- 新闻来源和 Provider 管理。
- 搜索结果接入、正文采集与内容抽取。
- 原始记录保存、标准化、去重和版本识别。
- 新闻与证券、行业的基础关联及关联证据。
- 新闻业务模型、查询用例、来源授权、采集与标准化、去重版本、证券/行业关联。
- 持久化和通用诊断依赖公共服务，当前阶段不自行实现。

### 事件研究（不属于本专项）

- 多篇新闻聚合为事件。
- 事件分类、生命周期和状态变化。
- 影响方向、影响时效、不确定性及价格验证。
- 事件解释、研究结论和后续跟踪。

对应总体规划任务：新闻基础设施主要映射 DATA-016、MIG-005；事件研究对应 RESEARCH-004、MIG-006。两者不得混为一个新闻采集模块。

### 研究编排（不属于本专项）

消费新闻和事件数据，与行情、财务、估值等信息组合分析。新闻模块不生成买卖信号，不负责完整研究决策。

## 3. 架构原则

1. 模块化单体，不新建独立微服务。
2. 新闻业务模块落在根 Go 模块，随 `stock-analysis-server:8092` 统一部署，由 `cmd/analysis-api` 组装。
3. DB、Redis 和通用诊断统一由公共服务提供；新闻模块当前不创建独立连接、客户端、缓存、诊断框架或诊断存储。
4. 迁移必要的 Provider 协议处理并按新契约重构到根模块；不复用旧 Searcher 聚合、缓存、fallback 或旧 DTO。
5. Domain 不依赖 HTTP、SQL 或 Provider。
6. Application 编排用例，不直接执行 SQL。
7. Adapter 负责外部来源协议和响应转换。
8. Repository 负责未来持久化端口实现。
9. 当前不建设新闻专属 Handler 或 HTTP 路由。
10. 不直接依赖 LLM，不将模型生成内容当作来源事实。
11. 不修改行情、财务、估值模块既有行为。

## 4. 目标职责分层

以下是目标职责分层；按业务用例逐步落地，不机械创建空目录：

- Domain：新闻、来源、内容版本、关联事实和质量状态。
- Application：搜索、采集、标准化、去重、查询和来源管理用例；不承载通用诊断框架。
- Adapter：搜索 Provider、官方信息源、正文采集和解析。
- Repository：定义新闻业务所需的持久化端口；具体 DB/Redis Adapter 等公共服务就绪后再实现。
- HTTP Adapter：当前阶段不新增新闻专属 Handler 或 HTTP 路由；由同进程 Application 接口供现有业务流程调用。若未来既有 Server API 需要对外提供新闻相关能力，由该 API 层负责适配，不在新闻模块新增独立入口。

已有 `newssearch`、`news_cutoff` 等代码必须先盘点后决定复用、扩展或迁移，不能另起平行实现。

## 5. 数据流

1. Application 根据查询或采集任务选择已启用来源。
2. Provider Adapter 获取候选新闻并保留来源原始标识。
3. 内容采集器在合法、可访问的前提下获取正文或公告原文。
4. 标准化器生成规范字段，同时保留原始字段和证据。
5. 去重与版本识别确定新记录、重复记录或内容更新。
6. 证券/行业关联生成关联事实及证据。
7. 业务层通过定义清晰的 Repository 端口表达未来持久化需求；当前先实现领域规则和可测试的 Application，不实现 DB/Redis Adapter。
8. 查询用例返回新闻业务数据及来源、时间、完整度和质量元信息；当前由内部 Application 接口提供。
9. 通用诊断和执行历史由公共服务统一承接，新闻模块只提供必要的业务结果与质量事实，不实现诊断系统。

## 6. 与其他分支隔离

- 本专项只在 `feat/research-news-ingestion` 开发。
- 目标集成分支为 `feat/full-go-data-providers-api-switch`。
- 不修改 WebUI 分支、整体规划分支和 main。
- 开发期间只新增新闻专属代码、测试和 `doc/news/**`。
- 当前阶段不新增新闻数据库表、不实现 SQL/Redis Adapter；公共服务接入阶段再确定统一迁移和存储方案。
- 不改变既有公共 API 行为。
- 不删除独立旧 Python 服务或与本专项无关的 go-core 代码；但新模块不依赖旧链路，也不为其开发兼容代码。
- 不创建 PR、不合并，除非另行获得明确授权。

## 7. 安全与合规

- 不开放任意 URL 抓取接口，避免 SSRF。
- 对来源设置访问频率、超时、大小限制和并发限制。
- 明确来源授权、robots 约束、版权和内容保留策略。
- 原始 HTML/正文的存储范围必须在 N1 明确，不能默认长期保存所有第三方全文。
- 日志不得输出 API Key、Token 或敏感请求头。

## 8. N1-A 收口口径

首轮代码、运行边界、Provider/来源条款、领域模型、时间语义、身份/版本/关系、证券关联、Application 契约及公共平台接入边界已完成静态核查和内部收敛。当前不再将以下事项作为 N1-A 阻断项：

- 旧 Python Agent/Bot/Scheduler 等全部调用方穷尽：新模块不兼容旧链路，历史数据导入属于可选 H1；不需要为了兼容目标继续穷举调用方。
- 统一 security_id/industry_id：当前代码未发现统一主数据 ID，首期以 canonical symbol + 市场/交易所为业务键，行业保留分类体系、代码/名称快照和时间证据；不虚构 FK。
- 来源授权：已完成首轮公开条款核查，但不是对所有来源的授权批准。未明确许可的 Provider/Source 继续 pending/restricted，不真实抓取、不持久化受限输出。
- 新闻 HTTP 路由/OpenAPI：当前不建设新闻独立 API，不注册新闻路由；内部 Application 契约是本阶段接口交付物。
- DB/Redis/通用诊断：按用户决策延期，等待公共服务，不在新闻模块临时实现。

N1-A 最终冻结仍需用户评审确认。确认前不进入 N2；确认后按 9.16.4 的修订路线实施。

## 9. N1 第一轮代码证据盘点（2026-11-05）

> 基于 feat/research-news-ingestion 当前代码的静态盘点。未执行 Provider 请求、未连接生产数据库。代码存在不等于目标环境已运行或真实数据已验收。

### 9.1 运行架构：仓库存在两条 Go 运行路径

**统一部署路径**（根目录 docker-compose.yml）：
- stock-analysis-server 由根模块 cmd/analysis-api 启动，监听 8092。
- stock-analysis-data 由 services/market-data 启动，监听 8091。
- stock-analysis-web 由 web 启动，监听 8093。
- 该 Compose 未启动 go-core 或 python-bridge。

**可选迁移路径**（docker/docker-compose.go-migration.yml 的 go-migration profile）：
- 启动 python-bridge、stock-analysis-data 和 go-core。
- go-core/cmd/analysisd 通过 pythonbridge.Client 调用 Python Bridge，并通过 marketdatahttp.Client 调用 market-data。
- 该路径是独立的旧迁移 profile，Compose 注释要求不要与根目录统一部署栈混用。

因此，原先建议的 go-core/internal/news 只能作为旧迁移路径中的分析新闻能力扩展点，不能作为当前统一部署的新闻基础设施落点。用户已确认新闻基础设施由根 Go 模块承载，随 `stock-analysis-server:8092` 部署；建议以根模块独立 `internal/news/` 业务包组织，由 `cmd/analysis-api` 组装，复用 `internal/platform/httpapi` 和 `internal/adapters/storage/mysqlredis`。具体目录仍须按实现前的最新代码结构复核。不要把新闻持久化放进 `services/market-data`，该服务负责行情及公告等数据源能力。

### 9.2 现有 Go 新闻搜索能力

go-core/internal/adapters/newssearch/search.go 已有实质实现：
- 原生搜索 Provider：Bocha、Tavily、Brave News、显式配置的 SearXNG。
- 可选 StockAnnouncementSource，由启动组装注入 marketdatahttp 客户端。
- Python Bridge SearchAdapter 作为兼容 fallback。
- 多维查询计划、并发请求、超时、结果过滤、相关性排序、来源域名加权、营销词过滤。
- 进程内缓存默认 10 分钟，上限 512 个 key；请求超时默认 10 秒；查询计划最多 5 个。
- 去重依赖规范 URL 和标准化标题，不是跨来源内容指纹或新闻实体级去重。
- 当前过滤无法解析发布时间、过旧或未来发布时间的结果；这会丢失“发布时间未知但仍可作为待核实候选”的信息。
- 股票公告候选只请求第 1 页、最多 100 条；公告源失败或超过 2 秒会降为无公告候选，不单独返回结构化采集诊断。
- 当前 domain.NewsItem 只有 title、summary、url、source、published_at、retrieved_at、relevance、dimension；没有正文、available_at、source item ID、原始响应证据、内容版本、采集任务状态或证券关联证据。
- 原生 Searcher 将 published_at 格式化为日期，不保留精确时分秒。
- 以上适合继续作为搜索适配器复用，但不等于新闻采集入库、来源管理、内容版本和查询 API 已实现。

### 9.3 分析流程边界

- go-core/internal/application/stock_flow.go 和 market_flow.go 通过 ports.NewsSearcher 调用个股/市场新闻搜索。
- go-core/internal/application/news_cutoff.go 负责分析参考时点过滤：显式 as_of 严格排除缺失/非法发布时间；实时分析可保留但标记为未核实；未来发布时间始终排除。
- news_cutoff.go 是分析流程的证据有效性规则，应留在 application，不迁入新闻基础设施模块。
- go-core/internal/domain.NewsItem 和 ports.NewsSearcher 是现有分析消费契约。新新闻持久化领域不应直接扩展共享模型承载采集细节；应由新闻模块自己的模型承接，再由分析适配器转换为旧 NewsItem。

### 9.4 Python 新闻调用链

当前 Python Bridge：
- python_bridge/capability_app.py 暴露 POST /internal/v1/search/stock-news 和 POST /internal/v1/search/market-news，使用 X-Python-Bridge-Token。
- python_bridge/capabilities/search.py 的个股入口调用 src.search_service.get_search_service().search_comprehensive_intel(...)，再扁平化各维度结果；市场入口调用 MarketAnalyzer.search_market_news()。
- go-core/internal/adapters/pythonbridge.SearchAdapter 对应调用上述两个 Bridge 路由。
- go-core/cmd/analysisd/main.go 组装 legacySearch、原生 newssearch.NewFromEnv(...)、StockFlow 和 MarketReviewFlow。原生搜索可用时优先；无原生结果时才回退 Python Bridge。
- python_bridge/go_core_client.py 是 Python 调用 Go Core 的统一入口，GO_CORE_ENABLED 默认 false；它暴露分析工作流调用，不是新闻采集 API。
- 固定旧 Python 源码提交 Kasign/daily_stock_analysis@7a21cd76952c7fe44a7fc5a6113a5b2b8a16bb32 另有 Agent 搜索工具：src/agent/tools/search_tools.py 的 search_stock_news 和 search_comprehensive_intel 调用共享 SearchService，并通过 _persist_news_response 调用 save_news_intel；src/market_analyzer.py 会合并已持久化的市场情报与搜索新闻。
- 旧 Python 新闻链路不仅是 Bridge 两个函数，还包含 Agent 工具和本地情报持久化/读取。还需追踪 API、Bot、Scheduler 等入口是否直接触发这些能力，不能只迁移 Bridge 端点就宣称旧链路已退役。
- 根目录统一 Compose 不包含 Python Bridge/go-core；只有可选 go-migration profile 包含它们。Python 兼容迁移的实际生产使用范围需结合部署环境确认。

### 9.5 数据库、Repository 与迁移现状

静态盘点确认至少有两套 MariaDB 接入：
1. 根 Go 模块 internal/adapters/storage/mysqlredis：通过 database/sql 创建并持有 *sql.DB 与 Redis 客户端；cmd/analysis-api 复用该 Store 启动任务队列、Runner 和 HTTP API。Store 暴露 DB，Migrate 通过内嵌 SQL CREATE TABLE IF NOT EXISTS 建立 analysis_runs、analysis_stage_events、analysis_snapshots、analysis_tasks；CheckSchema 检查这 4 张表。
2. services/market-data/internal/repository：独立 OpenMySQL、独立 Store 和 Repository，Migrate 通过 Go 代码内嵌 SQL 创建 market_data 专属表，包含 Probe 历史、行情、日 K 版本、财务版本、公司行为等。

go-core/go.mod 没有 SQL/Redis 驱动依赖；go-core 下未发现迁移目录或新闻 Repository。因此不能把新闻 Repository/MySQL 实现直接放在 go-core 并假设它可以复用统一部署服务的数据库连接。

当前可见迁移方式是服务内嵌 SQL 与启动 schema 检查，不是统一的独立 migration runner；未发现可直接复用的全仓库迁移版本账本。实施前需确定新闻表由哪个服务 Store 管理、如何处理已有库升级，以及是否需要显式 schema version，不能另建 DB 连接池或迁移系统。

### 9.6 证券主数据与公告复用边界

- 现有 Go 新闻消费和公告接口使用证券代码/标准 symbol（如 600519.SH）作为关联标识。
- services/market-data 已有公告 Provider、公告模型和 HTTP 能力，go-core/newssearch 通过 StockAnnouncementSource 调用；不应复制公告 Provider。
- 当前 market-data SQL 表清单未发现可作为统一证券主数据外键的 security master 表；不能假定存在稳定内部 security_id。需继续核实根服务证券标准化、股票代码映射与退市/更名处理，再决定新闻关系表暂时使用 canonical symbol 还是引用统一 security ID。
- 行业标准 ID 与行业分类版本也尚未确认。

### 9.7 HTTP、认证、分页和错误契约

- 统一部署主 API 在 internal/platform/httpapi.Server 注册分析 runs/tasks 路由，统一包裹 request ID、请求日志和 panic recoverer；当前没有新闻路由。
- 根 API 错误响应使用 code、message（及可选 request_id）；任务事件接口使用 after_sequence + limit，不能据此推断所有列表都应采用 offset 分页。
- market-data 是独立服务，使用自己的 API Key、错误 envelope、Probe 路由和分页/参数规则。不要将它的认证直接复制给主分析 API。
- go-core HTTP Server 使用 X-Go-Core-Token，目前只暴露分析工作流路由。
- 当前没有新闻独立对外 HTTP API 的计划，`/api/v1/news*` 不属于本阶段实现范围，不注册新闻专属路由。新闻查询、搜索、来源管理和诊断优先作为 Application 用例供内部调用。
- 如未来现有 Server 的某个对外 API 确实需要新闻数据，由该既有 API 定义对外 DTO、权限、限流和分页；不得因此默认新增新闻独立路由。

### 9.8.1 新闻诊断的必要性与实现边界

诊断是新闻基础设施的必要能力，不是后续可选的运维装饰。新闻链路包含 Provider 搜索、来源访问、正文抓取、解析、标准化、身份去重、版本持久化和证券/行业关联；任一阶段失败都可能表现为“没有新闻”，如果没有阶段证据，就无法区分无结果、过滤、限流、解析失败、授权禁止和存储故障。

诊断按两种方式运行：
- 被动诊断随每次正常业务执行产生，是默认方式；阶段状态、耗时、计数和错误写入 run/step。
- 主动 Probe 由内部受控调用触发，只检查明确选择的能力；不默认全文抓取、不默认写入正式新闻、不绕过授权，也不在常规 CI 消耗真实 Provider 配额。

诊断不增加独立业务表：执行证据复用 `news_ingestion_runs` 和 `news_ingestion_run_steps`；候选和匹配证据复用 `news_observations`、`news_item_identifiers`；数据质量从版本、内容和关系证据计算。诊断历史通过内部 Application 查询，不新增新闻公网诊断路由。

诊断状态、Provider 可用性、数据质量、Freshness 和授权状态必须分开表达，不能用一个 success 布尔值覆盖。例如连通性通过但有效候选为零，连通性仍 passed，搜索质量可 degraded；授权不允许保存时，持久化为 skipped/restricted，而不是技术失败。

### 9.8 诊断能力复用判断

market-data 已有统一 Provider Probe，支持 connectivity、contract、quality、freshness、cross_provider、storage 检查，并结合 Provider、Normalize、Validator、Reporter、Freshness Evaluator、Probe History。该体系是新闻诊断设计的重要参考，但当前检查项和证据模型面向行情能力，不能原样视为新闻采集诊断已经存在。

新闻模块应复用通用 HTTP 超时、日志脱敏、状态语义和可观测性约定；新闻自身仍需覆盖 search、fetch、parse、normalize、deduplicate、persist、relation 等阶段。搜索成功不能代表正文抓取、标准化或入库成功。未配置 Provider 应为 skipped；部分能力可用应 degraded；不能用统一 success 布尔值抹平各阶段结果。

### 9.9 第一轮盘点后的架构修正

1. 新闻基础设施确定落在根 Go 模块独立业务包，随统一部署 `cmd/analysis-api` / `stock-analysis-server:8092` 运行；不得落入 go-core 或 services/market-data。
2. news_cutoff.go 继续留在 go-core/internal/application，不迁移。
3. 现有 go-core/internal/adapters/newssearch 和 Python Bridge 保留为兼容/搜索适配路径，不搬迁、不删除。
4. 新新闻模型、Repository 接口和采集状态放在新闻模块内部，不扩展共享 domain.NewsItem 承担持久化领域。
5. 当前不注册新闻专属 HTTP Handler 或 `/api/v1/news*` 路由；Application 通过同进程接口供现有分析流程及内部调用方使用。若既有 Server API 将来需要输出新闻数据，由既有 API 负责 DTO 和安全边界。
6. 先复用 market-data 公告能力；不在新闻模块复制公告 Provider。
7. 数据库连接复用根服务已有 *sql.DB，新闻表由对应 Store 的既有迁移入口管理；不新增数据库、Redis 或独立连接池。
8. 采集任务、原始证据保留策略、内容版本、幂等、来源授权/保留、配额和清理仍是设计必须项。

### 9.11 旧 Python 新闻持久化与 API 的进一步核对

- intelligence_items：来源采集后的资讯条目，含 source_id/source_name/source_type、标题、摘要、URL、来源、published_at、fetched_at、scope、market 和 raw_payload；唯一约束按 source_id + URL + scope + market 组合，另有范围时间索引。

- 旧 API 已有 intelligence 路由：来源创建/列表/模板/默认来源、来源测试、单来源 fetch、enabled sources fetch、已入库 items 分页查询。列表 page_size 上限 100。
- MarketAnalyzer 在市场复盘时触发 refresh_auto_sources 并读取已持久化 market intelligence；Agent 搜索工具另写 news_intel。两套旧数据语义不同，迁移时不可粗暴合并为一个没有来源类型区分的表。
- Bot 的 /research 命令会启动 ResearchAgent/工具注册；API 有独立 intelligence endpoints。已确认这两类入口存在，但尚未穷尽 Agent Tool Registry 的所有注册方、旧分析入口和 Scheduler 的直接触发关系。

## 9.14 来源合规边界与 API 安全风险

旧 Python `IntelligenceService` 已实现：
- 仅允许 HTTP(S)，禁止 URL credentials 和 localhost/私网/保留地址；
- DNS 解析与实际连接阶段再次校验，避免 DNS rebinding；
- RSS/Atom 最多受控重定向，NewsNow 不跟随重定向；
- 禁用环境代理、限制响应体大小和超时；
- 对抓取错误做脱敏；默认自动采集开关关闭。

但未发现以下逐来源策略字段或执行逻辑：授权依据/许可类型、服务条款 URL、robots.txt 策略、允许抓取范围、正文/摘要许可、内容留存期限、删除请求处理、来源配额/并发策略和来源政策复核时间。代码文档称“合规”不能代替对每个来源条款的核验。NewsNow 公共示例实例也明确不保证稳定性/可靠性，生产建议自建或使用可控实例。

旧模板含 SEC、HKEX 等 RSS 与 NewsNow 聚合源，但模板存在不等于已完成逐来源法律/合同许可核验。当前不能据此批准全文抓取或长期保存全文；首阶段应优先保存必要元数据、短摘要和来源链接，并为正文存储设计授权状态与可删除机制。

**当前 HTTP 暴露边界**：根 Go `internal/platform/httpapi.Server.Handler()` 当前仅挂 request-id、日志和 recoverer，静态盘点未发现认证中间件。但新闻模块当前不新增 HTTP Handler、新闻专属路由或公网管理接口，因此不把 Server 认证中间件实现列为新闻模块独立交付项。若既有 Server API 后续增加新闻数据访问，必须先由该 API 任务核实认证/授权；来源管理和主动采集仍保持内部运维能力，不得顺带开放为公网接口。

## 9.17 来源授权核查结论（2026-11-05）

第一轮公开条款核查已整理到《新闻来源授权矩阵》。关键结论：Provider 输出权利和原始发布来源内容权利必须独立判断；Brave Search API 不允许持久化 Search Results；博查现行协议对服务数据收集有禁止条款，搜索输出存储权利待书面确认；Tavily 官方帮助中心允许保存其输出，但不替代原始发布者授权；HKEX RSS 的存在不代表允许服务端自动抓取，HKEX Terms 明确限制程序化访问、系统性建库和文本/数据挖掘。SEC/EDGAR 有较明确的政府创作内容和公共申报内容复用说明，同时要求声明 User-Agent 并遵守 10 req/s 上限。SSE、SZSE、CNINFO 的许可边界不同，不能一概按公开信息处理。

当前接入默认策略以《新闻来源授权矩阵》第 6 节为准；未明确允许的来源按 pending/restricted 处理，不自动抓取、不持久化搜索结果或全文。以上为公开文本的工程风险判断，不构成法律意见；实际账号补充协议和书面许可优先。


## 9.18 历史方案：根模块与 go-core 新闻搜索共享 Provider（已废弃，仅作决策背景）

最新代码核查确认：

- 根服务模块路径为 `example.com/stock-analysis-flow`，由根目录 `go.mod` 管理。
- `go-core` 是独立嵌套模块 `github.com/Kasign/stock_data_provider/go-core`，拥有自己的 `go.mod`。
- 现有搜索实现位于 `go-core/internal/adapters/newssearch`，并依赖 `go-core/internal/domain` 与 `go-core/internal/ports`。
- 根模块不能直接导入 go-core 的 `internal` 包；嵌套模块边界也意味着不能把现有目录当作根模块内部包直接引用。
- 当前 `Searcher` 把多个 Provider 的候选合并、过滤和排序后映射为 `domain.NewsItem`。最终 `NewsItem.Source` 表示发布来源，不是搜索 Provider；最终 DTO 不保留 provider_code。Searcher 的 10 分钟进程缓存也缓存了合并后的候选。
- Provider 结果中间结构虽能知道某个查询计划由哪个 Provider 执行，但 provider 身份没有传递到最终候选和输出，不能支持逐 Provider 的持久化策略。

### 9.18.1 当时的设计约束（历史背景）

当时为了同时服务根模块与 go-core，提出不能直接 import `go-core/internal/adapters/newssearch`，并试图避免复制 Provider HTTP 实现。该双调用方前提已被用户撤销，当前实施依据以 9.21 为准。

以下内容是当时为了兼容根模块与 go-core 双调用方提出的共享适配方案，现已由 9.21 明确废弃，不得作为实施依据：

1. 把 Provider 协议适配和中立候选模型抽取到一个不依赖根业务模块、也不依赖 go-core domain 的共享 Go library module（建议位置 `shared/newsprovider/`）。
2. 共享包只定义 Provider 接口、配置、请求、候选和 Provider 级失败结果；不引用 `domain.NewsItem`、`ports.NewsSearcher`、SQL、Redis 或诊断服务。
3. 候选必须保留 `provider_code`、`provider_item_id`（如有）、`publisher/source`、原始 URL、原始发布时间文本、snippet 和请求观察时间。Provider 来源与发布来源不能共用一个字段。
4. 根模块 `internal/news` 负责 Provider 策略过滤、来源授权判断、领域标准化、去重和业务 Application。
5. go-core 保留现有 `NewsSearcher` 对外契约，由原有 Adapter 将共享候选映射为旧 `domain.NewsItem`，避免本专项直接破坏旧分析流程。
6. 共享包不能依赖任一调用方的 fallback、业务 DTO、公告 Repository 或内部诊断模型；公告数据通过独立中立接口适配。
7. Provider 的结果留存策略必须在候选进入缓存、日志、持久化或迁移前执行。Brave 结果不得进入长期缓存/数据库；博查在书面确认前不持久化；Tavily 仍需叠加原始发布来源授权。
8. 如果共享 module 的依赖和发布方式无法在两个 Go module 中稳定管理，先评估将现有搜索能力迁移到独立公共包的最小变更方案，不允许退化成复制 Provider 实现。

### 9.18.2 缓存和结果策略

- 共享 Provider 层默认不缓存结果；是否允许短暂缓存由 Provider 策略显式授权。
- 不能对合并后的混合结果使用统一 10 分钟缓存，因为其中可能包含禁止长期存储或仅允许临时使用的 Provider 输出。
- 临时处理所需的内存驻留时间应尽量缩短；超出请求生命周期的缓存必须有明确条款依据。
- Provider 失败与候选质量问题分开表达；当前阶段只返回业务调用结果，不实现通用诊断历史。
- 任何持久化前必须同时满足 Provider 输出策略和发布来源内容策略。

## 9.19 根模块新闻包结构与内部 Application 契约（2026-11-05）

### 9.19.1 根模块现有架构证据

- 根服务采用 `internal/analysis/app` 定义 Application ports、`internal/analysis/domain` 定义分析领域、`internal/analysis/modules` 定义插件/模块契约、`internal/service/wiring.go` 负责具体组装，`cmd/analysis-api/main.go` 是进程启动入口。
- `internal/analysis/app.Dependencies.Data` 是行情/财务等市场数据采集入口，输出 `MarketSnapshot`；新闻不应伪装成行情数据源或直接塞进 `MarketSnapshot`。
- `internal/adapters/marketdata` 和 `internal/adapters/pythonapi` 是独立 typed HTTP clients；当前 Python API client 没有新闻搜索方法。
- 根服务已有 `internal/adapters/storage/mysqlredis`，但 DB/Redis 当前由公共服务统一承接，新闻模块不直接依赖它。
- 当前根分析 Runner 的依赖中没有 News Application。新闻模块先独立提供同进程 Application，不为接入新闻而修改现有 Runner 或行情采集契约。

### 9.19.2 建议目录边界

```text
internal/news/
  domain/                 # 新闻、来源、候选、版本、关联和业务质量规则
  app/                    # Search/Collect/Normalize/Relate 等用例与 ports
  adapters/
    provider/             # 根模块原生 Provider Adapter
    source/               # 已批准的 RSS/Atom/官方来源适配
    parser/               # HTML/Feed/编码/时间解析
```

不要求一次性创建所有目录；按业务用例逐步增加。当前不创建 `repository/mysql`、`repository/redis`、`diagnostics`、`http` 或独立服务包。

### 9.19.3 当前内部 Application 用例

建议先冻结两个明确的业务入口：

1. `SearchCandidates(ctx, request)`：执行候选搜索，返回带 Provider provenance 的候选和 Provider 级部分失败信息；默认不写入持久化，也不隐式抓取全文。
2. `CollectSource(ctx, request)`：仅对已启用且授权策略允许的 source/endpoint 执行抓取、解析和标准化，返回新闻业务对象及质量原因；当前不写入 DB/Redis。

可拆分纯业务能力：
- `NormalizeCandidate`：标准化标题、URL、时间文本和来源字段。
- `IdentifyCandidate`：根据来源原始 ID/规范 URL 生成身份候选，不自动跨来源合并。
- `AssessBusinessQuality`：评估时间可信度、内容完整度、来源身份和关联证据。
- `ResolveSecurityRelations`：基于 canonical symbol 生成关联候选及证据，不依赖尚不存在的 security_id。

当前不实现持久化查询 `GetNews`、来源配置 CRUD HTTP API、诊断查询或主动 Probe。未来存储就绪后再增加查询和 Repository 驱动用例。

### 9.19.4 Application 输入输出约束

`SearchCandidates` 输入至少包括 query、证券 canonical symbol（可选）、查询维度、时间窗口、结果上限和调用上下文。输出至少包括：
- Candidate：provider_code、provider_item_id（可选）、publisher_source（可未知）、title、snippet、原始 URL、原始发布时间文本、观察时间、query dimension。
- ProviderOutcome：provider_code、业务执行结果、候选数量、错误类别/错误码；不包含诊断历史。
- SearchResult：候选列表、部分成功标识和业务原因。不能只返回旧 NewsItem，否则 Provider provenance 和未知时间证据会丢失。

`CollectSource` 输入使用已登记 source/endpoint 标识，不接受任意用户 URL。输出保留原始字段、标准化字段、时间解析状态、内容完整度和授权判断。授权 pending/restricted 时不抓取或不保存受限制内容。

错误类别属于业务调用契约，例如 invalid_request、provider_unavailable、provider_partial_failure、policy_restricted、source_unavailable、parse_failed、identity_conflict、quality_rejected、unsupported_capability。不要把这些错误类别伪装成通用诊断状态或持久化诊断报告。

### 9.19.5 与上层分析的协作

新闻 Application 与现有分析 Runner 保持独立。未来 Context & Evidence 或研究编排模块通过构造函数注入 News Application，按需消费新闻事实、来源证据、时间和关联；不通过内部 HTTP，不修改行情 DataCollector 的语义，也不让新闻模块反向依赖 Quant Engine/研究编排。

（历史方案，已废弃）旧 Python API、Bot、Agent 和 go-core 调用链曾计划逐调用方切换；当前不要求新新闻模块兼容这些调用方，也不实施灰度、双写或双运行。旧服务是否退役由其独立项目决定。




### 9.19.6 Application 结果状态与边界冻结补充

#### SearchCandidates

输入包含非空 query、可选 canonical symbol、query dimension、时间窗口、结果上限和调用上下文。Provider 选择与凭据来自内部配置，不接受调用方传入任意 URL 或绕过授权策略。

每个 Provider/query dimension 任务独立返回 ProviderOutcome：
- `success`：请求成功且返回至少一个候选。
- `empty`：请求成功但没有候选；不是失败。
- `failed`：请求实际执行但发生超时、协议错误、限流或 Provider 错误。
- `skipped`：未配置、被禁用、当前能力不支持或策略明确禁止执行；必须携带原因，不得计为 available。

聚合 SearchResult 状态：
- `success`：所有实际执行任务成功，且至少有候选。
- `empty`：所有实际执行任务均成功但总候选数为零。
- `partial`：至少一个任务成功/empty，且另有任务 failed/skipped。
- `failed`：存在实际执行任务但全部失败，且没有可用候选。
- `skipped`：没有任何任务实际执行，全部被跳过。

ProviderOutcome 的技术执行状态与候选业务质量分开。候选被质量规则拒绝，不得反向把 Provider 请求标记为 failed。SearchCandidates 默认只返回候选和执行结果，不隐式抓取全文、不持久化、不跨请求缓存；Provider 输出策略必须分别判定请求内处理、内部返回、跨请求缓存、持久化和对外展示/再分发；某一用途获准不代表其他用途获准。首期不跨请求缓存；日志和诊断摘要不得包含受限原文、snippet 或完整响应。

#### CollectSource

输入必须是已登记的 source_id + endpoint_id、采集目的和受控采集参数；不接受任意 URL。调用前计算 Provider/Source/Endpoint/用途/保留期限的授权交集。

返回按 endpoint 和处理阶段组织的业务结果，明确 fetch、parse、normalize、identify 的成功、部分成功、失败或跳过原因。授权 pending/restricted/revoked 时不得执行受限制的抓取或内容保存；未配置能力为 skipped，不是 failed。没有身份凭据的内容只形成 observation，不创建 news_item。

#### 纯业务用例

- `NormalizeCandidate`：纯转换，不访问网络、不写存储；输出标准化字段、原始字段映射、时间解析状态和字段缺失原因。
- `IdentifyCandidate`：输出 identified、unidentifiable 或 conflict，并附命中的身份凭据及证据；不得自动跨 source 合并。
- `AssessBusinessQuality`：输出 valid、degraded、invalid 或 unknown，并附字段级原因；不返回通用 Probe/诊断状态。
- `ResolveSecurityRelations`：输出 proposed/confirmed/rejected 等关系断言及 evidence；匹配/模型推断默认 proposed，不把推断升级为来源明确事实。

所有用例均通过 Go error 表达调用级不可继续错误，通过结构化业务结果表达部分成功、跳过和质量降级；不能把可恢复的单 Provider 失败吞成整体 error，也不能用 HTTP 风格状态码替代领域状态。当前这些用例只定义内存结果，不要求新闻 DB/Redis 或通用诊断服务。

## 9.20 来源策略按 Source/Endpoint 分层（2026-11-05）

来源策略采用“发布者级默认策略 + 可选入口级补充策略”，不为每个 endpoint 无条件复制一份相同策略：

- Source policy：表达发布者层面的默认许可、用途、内容类型、保存方式、保留期限、署名和删除要求，默认适用于该 source 下所有 endpoint。
- Endpoint policy：只有当某个 RSS/API/网站入口的条款、授权范围或访问约束与 source 默认策略不同时才单独登记。
- Endpoint policy 默认只能进一步收紧 Source policy。若有针对某 endpoint 的单独书面许可需要扩大权限，必须引用明确协议/许可证据、适用范围和有效期，不能仅靠配置字段覆盖。
- 没有 endpoint policy 时继承 source policy；source policy 未核实则整体为 pending，不能因为 endpoint 可访问或存在 RSS 就自动批准。
- Provider output policy 独立于 source/endpoint policy。

一次持久化决策必须同时满足 Provider 输出使用权、Source 发布者策略、Endpoint 访问/内容策略、当前用途和保留期限。任何一层 pending/restricted/revoked 都不能被其他层的 approved 覆盖。策略版本变化只影响之后的访问和保存决策；历史内容是否需要删除/限制，按新许可的追溯效力和明确要求处理，不自动假设授权变更可追溯或不可追溯。


## 9.21 最终 Provider 架构决策：根模块原生实现（2026-11-05）

### 9.21.1 决策依据

用户已明确整体服务尚未投入使用，不要求兼容旧 Go/Python 新闻服务。此前提出的 `shared/newsprovider` 独立 Go Module，是为了同时服务根模块和嵌套 go-core 模块而设计的折中方案；在不需要兼容旧调用方的前提下，它会额外引入模块版本、replace 路径、Docker 构建上下文和双调用方适配成本，不是当前系统的最优解。

### 9.21.2 目标结构

新闻 Provider 能力直接归属根 Go Module：

```text
internal/news/
  domain/
  app/
  adapters/
    provider/       # Bocha/Tavily/Brave/SearXNG 等搜索 Provider
    announcement/   # 官方公告/披露来源，独立于搜索 Provider
    source/         # RSS/Atom/已批准发布来源抓取
    parser/
    security/       # URL、DNS、重定向和响应安全策略
```

不创建 `shared/newsprovider`、新的 Go Module 或跨模块本地 replace。Domain 不依赖 HTTP/SDK；Application 依赖 Provider/Fetcher 端口；Adapter 实现端口并保留完整来源证据。依赖方向由根模块内部包边界控制。

### 9.21.3 现有代码迁移策略

- `go-core/internal/adapters/newssearch` 作为协议和历史行为参考，不作为新模块的依赖。
- 迁移必要的 Provider 请求/响应解析逻辑时，按新接口重新组织并补齐测试；不得复制旧 Searcher 的聚合、缓存、过滤排序和 fallback 结构。
- 不保留旧 `domain.NewsItem`、`ports.NewsSearcher` 转换层，不保留 Python Bridge fallback，也不维护双写或双运行路径。
- 先确认仓库内所有 Go 调用引用，再删除已废弃的旧新闻搜索接入；不删除与新闻无关的 go-core 代码。
- 旧 Python API、Agent、Bot 和旧 DTO 不作为新模块兼容目标。历史数据迁移仅在未来公共存储就绪且确认有保留价值时单独评估。

### 9.21.4 Provider 候选与执行结果契约

每条候选从 Adapter 返回时必须保留：
- `provider_code`、可选 `provider_item_id`。
- `publisher_name` / `publisher_domain`，与 Provider 身份严格分离。
- 原始标题、摘要、URL、原始发布时间文本及其字段缺失状态。
- `observed_at`、query dimension 和必要查询上下文。
- 不对未知发布时间、发布者或 Provider item ID 做推断填充。

Provider 执行结果按实际请求任务表达，而非仅按总搜索请求表达：Provider、query dimension、状态（success/empty/failed/skipped）、候选数、业务错误类别、耗时和观察时间。Provider 失败与候选质量拒绝分别表达；部分成功不得吞掉失败信息。

官方公告源使用独立端口，保留交易所/披露平台身份及公告原始 ID，不伪装成搜索 Provider。

### 9.21.5 缓存与留存

- 首期不建设跨请求 Provider 结果缓存，也不缓存混合结果。
- 请求内必要的短暂内存处理不构成跨请求缓存；不得写入日志或执行历史中留存受限内容。
- Provider 输出策略与原始发布来源策略分别判断；任一层 pending/restricted/revoked 都不能进入受限抓取或持久化流程。
- Brave 输出不长期缓存/持久化；博查在书面许可确认前不持久化；Tavily 仍必须叠加发布者内容许可。

### 9.21.6 部署与测试

- Provider Adapter 随根 `cmd/analysis-api` 统一构建、部署；不改变 go-core Docker 构建上下文。
- 根模块单独执行 gofmt、go test 和构建验证；Provider 契约测试使用固定响应样本和 fake HTTP server，不依赖真实 Key/配额。
- 新架构不为旧 go-core 或 Python 调用方设置兼容验收门槛。

本节优先于此前 9.18 中“抽取共享 Go library 并由根模块与 go-core 双向适配”的建议，以及 9.19 中关于旧 Python/Go 调用链兼容保留的阶段性建议。

## 9.23 与公共平台建设方案对齐（2026-11-05）

本节优先于 9.16 中对“公共服务提供 SQL Repository”的宽泛表述，并与公共平台契约对齐。

1. Platform 提供 DB/Redis 连接生命周期、通用事务/健康能力和 Migration Runner；Platform 不实现 News Repository，不拥有新闻业务表。
2. News 负责定义并实现自己的 Repository 接口、SQL、领域表、索引、数据保留和 Migration 内容。平台负责 Migration ID 校验、排序、并发互斥和统一执行记录；News Migration 使用 news/<version> 命名空间，根服务集成分支负责注册入口装配。
3. 当前 News 不创建数据库连接池、Redis Client、通用事务框架或私有 Migration 账本。待 PLAT-009 有正式契约和可用实现后，再实现新闻 SQL Repository 和 Migration。
4. MariaDB 是新闻事实数据持久化的首选。Redis 不是新闻首期必选项：当前不跨请求缓存 Provider 输出，也没有已确认的分布式任务/租约需求；只有出现明确跨进程协调、分布式限流或缓存需求时才评估接入。
5. 新闻同步 Application 不强制使用平台 Task。只有定时采集、长耗时或需要进程崩溃恢复的任务才接 PLAT-010；Task 只存执行生命周期元数据，Observation/Version/Relation 仍归 News。
6. News 通过 PLAT-007 注册领域 Check；质量、Freshness、授权状态由 News 定义，平台只执行和聚合。
7. 当前没有新闻独立 HTTP 路由，因此不接入 Service Key Middleware。未来既有 Server API 暴露新闻能力时，由该 API 统一认证和授权。
8. 平台 HTTP Client 是通用传输策略；Provider 配额/授权和 Source URL 的 SSRF 策略仍由 News 负责。真实抓取前必须确认平台 Client 支持安全重定向、DNS/IP 校验和每依赖并发策略；若平台契约未覆盖，应先在 PLAT-002/008 评审解决，不允许 News 私自复制通用 Client。

### 9.23.1 对原阶段路线的修订

- N2/N3/N4 的纯 Domain、固定协议样本、离线解析、身份和关系规则可独立开发，不依赖公共平台运行时代码。
- 真实 Provider/Source 网络调用依赖 PLAT-002 冻结及 PLAT-005/006/008 对应组件可用；未确认授权的来源继续 skipped/restricted。
- SQL Repository 和新闻 Migration 依赖 PLAT-009 的连接/Migration 能力，但实现归 News；Redis 仅按需。
- Diagnostics Adapter 依赖 PLAT-007；异步采集依赖 PLAT-010（仅当确有异步需求）。
- 跨模块验收依赖 PLAT-011；必要故障演练依赖 PLAT-012，不等待故障演练全部完成才开始纯业务开发。
