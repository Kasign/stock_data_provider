> 本文是 WebUI 后续开发的唯一总体规划与进度入口。新任务、优先级、执行状态、验收结果和下一步安排统一更新在本文。其他专项文档只保留功能契约、技术细节和验收标准，不再另行维护总体任务顺序。

## 1. 产品目标与边界

围绕国内 A 股市场观察、股票发现、个股研究、分析任务和持续跟踪，形成可持续使用的研究工作台。

- WebUI 负责页面交互、请求编排、状态展示和浏览器本地工作区。
- 行情事实、数据来源、质量状态、Provider 能力和分析结果以服务端真实响应为准；前端不补造数据、不将缺失值补零。
- 浏览器本地数据（自选股、筛选方案、研究笔记、报告归档、偏好等）必须明确标注本地范围，不伪装为服务端持久化或跨设备同步。
- 不提供券商交易下单能力。
- 使用原生 HTML、CSS、JavaScript ES Modules，不引入 React。
- 只修改当前 WebUI 分支；不创建新分支。代码按功能批次修改和提交，使用中文提交说明。
- 数据侧能力未完成真实验证时，WebUI 只记录依赖和缺口，不复制数据质量规则，不通过模拟响应宣称真实联调完成。

### P0-D：研究笔记与报告归档跨标签页一致性

状态：**已完成；WebUI Checks 与 Chromium Browser Smoke 均通过。**

#### 实施前现状核验（历史基线）

- 研究笔记使用 `stock-provider-webui.research-notes.v1`，localStorage 中保存 JSON 数组，最多 200 条；单条标题最多 100 字、正文最多 10,000 字、标签最多 12 个。记录字段包括 `id/title/content/symbol/taskId/runId/tags/createdAt/updatedAt`。
- Run 报告使用 `stock-provider-webui.research-reports.v1`，保存完整结果 JSON，最多 30 份；单份最多 700 KB、总量最多 4 MB。记录包含 `runId/taskId/analysisBase/symbols/status/corePass/asOf/createdAt/result`。
- 两个模块均执行结构校验、唯一 ID 校验、写入后回读比对；发现损坏数据时拒绝覆盖。报告归档按 `analysisBase + runId` 做重复归档幂等判断。
- 两个模块均由 `app.js` 初始化，但当前 `handleLocalStorageChange()` 未监听上述两个存储键。报告模块已返回 `render()`；笔记模块只返回 `createFromReport()`，未向应用层暴露重绘入口。
- 笔记编辑在打开时将内容放入表单，提交时重新读取当前数组，但没有校验编辑期间原记录是否变化：远端编辑可能被本地旧草稿覆盖；远端删除后，本地提交可能以相同 ID 将记录重新创建。
- 笔记/报告的新增、删除均为 localStorage 的读—改—写流程。回读校验只能确认本次写入当时可读，不能提供跨标签页事务或 compare-and-swap；两个标签页同时写入仍有最后写入覆盖另一方的风险。
- 工作区 JSON 备份明确不包含研究笔记和完整报告归档；导入会保留两者。报告支持 Markdown 下载，笔记目前没有同等的独立导出入口。迁移存储前必须单独考虑备份与恢复。

#### 方案比较

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| localStorage + storage event | 改动最小；保留现有 v1 数据、校验和备份边界；浏览器原生跨标签页通知 | 只解决通知与界面刷新，不提供并发写事务；需要编辑冲突保护 | **推荐作为第一阶段** |
| BroadcastChannel + 版本号/更新时间 | 消息可携带变更类型、记录 ID 和版本；可减少重复读取并便于提示冲突 | 消息可能丢失/重复；仍需 storage 作为持久化事实来源和 storage event 兜底；版本字段需要兼容迁移；不能解决写入竞争 | 暂不引入，除非后续需要更丰富的实时协作状态 |
| IndexedDB / 统一仓储 | readwrite transaction 可将读—改—写放在事务内；适合大报告和更强并发一致性 | 需要迁移两套 v1 数组、设计事务/版本、导入导出、配额错误、回滚和旧数据兼容；现有工作区备份不包含这两类数据，迁移丢失风险高 | 暂不采用；只有需要可靠并发写或突破 localStorage 容量时再立项 |

#### 推荐实施方案（已获用户确认，按以下范围实施）

**阶段 1：跨标签页刷新，不改数据 schema**

1. 从笔记/报告模块导出各自存储键常量；笔记模块与报告模块均暴露只读 `render()` 方法。
2. 在应用层 `handleLocalStorageChange()` 中监听两个键；收到变更后重读存储并重绘对应列表。收到 `clear()`（`event.key === null`）时同时重绘两者。
3. 不把外部标签页的数据直接拼接进当前内存数组；每次以 localStorage 最新可校验数据为准。写入失败或损坏时继续显示保护提示，不以空数组覆盖。
4. 编辑表单草稿与列表刷新分离：外部更新只刷新列表，不擅自重置用户正在编辑的表单。

**阶段 2：编辑冲突保护**

1. 打开笔记编辑时保存完整原记录快照；提交前重新读取并比较。
2. 原记录已被删除：拒绝以旧 ID 自动重建，保留草稿；用户可将草稿另存为新笔记，新记录使用新 ID。
3. 原记录已被其他标签页修改：拒绝静默覆盖，保留草稿，并提供重新载入最新版本/另存为新笔记两个显式动作。
4. 编辑期间收到跨标签页变化只刷新列表，不重置草稿；提交时再次比较快照，不依赖 storage 事件作为唯一冲突检测。
5. 删除笔记/报告前重新读取最新数据并确认目标仍存在；删除后重绘当前页，其他标签页通过 storage event 同步。
6. 报告归档仍以 `analysisBase + runId` 识别重复项；本阶段不声称解决两个标签页在同一瞬间同时归档的原子竞争。

**并发一致性边界**

localStorage + storage event 方案能解决“另一个标签页完成写入后，本页仍显示旧列表”的问题，并能拦截常见的编辑覆盖/删除复活；但无法保证两个标签页在极短时间内并发读—改—写绝不丢数据。若验收要求达到事务级并发一致性，应另行选择 IndexedDB 迁移，而不是把 BroadcastChannel 当作锁或事务机制。

#### 实施验收范围

- 双标签页新增、编辑、删除笔记后列表即时同步。
- 一侧编辑时另一侧更新同一笔记：旧草稿不能静默覆盖；另一侧删除时不能复活旧记录。
- 双标签页新增、删除报告后归档列表即时同步；重复 Run 归档保持幂等。
- 当前标签页自己的操作仍即时更新，不依赖 storage event（浏览器不会向写入方标签页发送该事件）。
- 损坏数据、不可读存储、写入失败时保留原始内容并显示错误；不把异常状态误判为空列表。
- 验证工作区 JSON 导入/导出仍不包含笔记/报告，且导入不会清除它们。
- Chromium 双标签页自动化覆盖，并对 320/768/1280/1600 视口做基础显示检查。

**实施约束：用户已确认采用“阶段 1 + 阶段 2”的 localStorage 最小同步方案，并接受上述并发边界。本批不迁移 schema，不引入 BroadcastChannel 或 IndexedDB。**

### 数据中心诊断展示边界与数值防御（2026-11-04）

## JavaScript 模块边界审查与渐进拆分计划（2026-11-04）

### 审查结论

当前前端已经存在按领域拆分的 ES Modules：市场总览、行情列表、个股研究、数据中心、研究笔记/报告、自选股数据/分组/排序、选股状态/条件/导出、告警状态、通知偏好等。无需推倒重来。

主要耦合集中在 `web/src/app.js`（约 6429 行）：入口同时承担全局状态、页面状态、跨模块协调、业务渲染、事件绑定、刷新与失效编排。部分页面能力虽有独立模块，但全局事件仍由入口直接绑定。其次 `data-center.js` 约 1100 行，内部包含 Provider 能力、被动诊断、Probe 结果、字段证据、覆盖率、历史和请求生命周期；可先抽离纯格式化/展示辅助，不应把状态生命周期拆散。 `api.js` 约 449 行，当前是 API 请求目录，行数本身不足以构成拆分理由。

### 拆分原则

1. 先建立依赖图和状态读写清单，再迁移代码；不做纯按行数拆分。
2. 业务模块负责自己的 DOM 渲染、事件和请求生命周期；跨模块协调由少量 coordinator 承担。
3. 通过显式依赖注入传递状态访问器、API 函数和跨模块回调；禁止新增长期隐式全局变量及循环 import。
4. 纯函数优先抽离到 shared；共享状态必须明确所有者，避免多个模块直接写同一状态字段。
5. 每次只迁移一个业务边界，迁移前后保持 DOM ID、API 契约、localStorage key、交互和可访问性行为不变。
6. 每批拆分必须有单元/浏览器回归，禁止以大规模重命名或全量格式化混入功能变更。

### 建议实施顺序

- JSR-0（已完成审查）：盘点模块、入口职责和主要候选边界。
- JSR-1：抽离 DOM/安全文本/下载等无业务状态的共享工具；只有确认无循环依赖后实施。
- JSR-2：拆分任务运行流与任务历史。优先迁移事件绑定和页面渲染，任务状态暂由入口通过明确接口提供；这是 app.js 中较清晰的独立业务域。
- JSR-3：拆分自选股页面控制器，将列表、导入、批量操作、报价刷新与入口解耦；复用现有 watchlist 数据模块。
- JSR-4：拆分设置页面控制器和连接配置协调，确保跨标签页、API base 变更、请求失效语义不变。
- JSR-5：拆分通知/问股/选股/告警页面控制器；这些页面当前后端能力尚未全部就绪，只迁移已有 UI 状态与展示，不增加模拟业务数据。
- JSR-6：拆分数据中心纯展示 formatter / renderer，保留统一请求代次和失效机制。
- JSR-7：评估 API client 按 market / analysis / diagnostics 分组的必要性；仅在依赖图显示职责冲突时拆分。
- JSR-8：全站依赖图复核、入口瘦身、循环依赖扫描及多视口浏览器回归。

### 暂不采用的方案

不引入 React/Vue、不更换构建体系、不增加状态管理框架、不一次性改造所有页面，也不在本轮重命名全部文件。当前原生 ES Modules + Node 测试的方式可以继续使用。

### 2026-11-05 JSR-6J：页面隐藏与 BFCache 恢复策略（已验收）

审查结论：
- SPA 内部切换页面不停止 Task 轮询。任务跟踪与当前 view 解耦，用户切到行情/自选/设置仍应持续跟踪。
- 浏览器标签页进入 hidden 状态时，若当前任务存在待执行轮询定时器或正在执行的轮询请求，则暂停该轮询：先保留任务 ID、Run ID、事件游标和已接收事件，再递增轮询代际、清除定时器并 abort 在途 Task/事件请求。
- 页面重新 visible 时，仅恢复此前因页面生命周期暂停的任务轮询，立即读取服务端状态和事件；不会对已结束/永久失败且本来已停止的任务无条件重启。
- `pollTaskSafely` 增加 hidden 兜底：即使定时器在浏览器完成 visibilitychange 处理前触发，也不会在隐藏页面继续发请求。
- BFCache `pagehide/pageshow` 仅在 `event.persisted` 时参与暂停/恢复；与 visibilitychange 可能重叠，生命周期 adapter 对重复 pause/resume 去重。
- 页面销毁（非 BFCache pagehide）不额外写入持久化状态；浏览器恢复页面时由正常启动或 BFCache 恢复路径处理。
- 市场总览、市场活动、行情查询、个股研究、数据中心均无周期性后台轮询。它们已发起的一次性请求即使在标签页隐藏后完成，仍可提交有效状态/DOM 结果；不做隐藏即丢弃，避免页面恢复后丢失结果或引入额外重查。任务轮询在途请求则因高频和可续读游标而主动取消。
- 不暂停服务端任务本身；只暂停浏览器端读取频率。SPA 导航、任务创建/切换、连接变更和手动刷新仍沿用现有代际与取消机制。

实施：
