# Notification 通知领域与投递设计

## 1. 目标

建设独立、可复用、可追踪和可恢复的通知业务模块。首期服务于研究完成、风险变化和用户明确配置的通知，不建设通用消息平台。

## 2. 领域模型

- NotificationEvent：事件 ID/type/version、发生时间、来源模块、主体引用、幂等键和受 Schema 约束的 payload。
- Subscription：订阅主体、事件类型、受限过滤条件、recipient_scope、渠道/模板引用、状态和不可变版本。
- Template：模板 ID/version、事件 Schema 绑定、变量 allowlist、渲染和大小限制。
- Channel：渠道类型、配置/Secret 版本引用、限流和超时策略。
- Delivery：一次确定的投递计划、recipient_ref、状态、幂等键和时间。
- DeliveryAttempt：单次外部调用的追加式记录、租约/fencing、结果分类、耗时和下次重试时间。

## 3. 生命周期与可靠性

Delivery 状态：queued → sending → sent / retry_wait / failed / skipped / blocked / unknown。unknown 表示外部渠道可能已接受但本地未获确认，必须先对账或使用渠道幂等能力，不能盲目重发。每次真实调用追加 Attempt；重试有限并带退避/jitter；永久错误不重试。Outbox/Inbox 保障本地事件接收，不保证外部 exactly-once。

订阅/渠道/模板版本在 DeliveryPlan 创建时固定；发送前仍重新检查当前退订和授权状态。Worker 通过租约和 fencing 防止过期 Worker 覆盖新结果。详细迁移矩阵见 [03-ApplicationPort与投递状态契约](03-ApplicationPort与投递状态契约.md)。

## 4. 边界

Notification 负责模板、渠道 Adapter、Dispatcher、投递 Repository、重试和状态。Platform 提供认证、Secret、日志、Trace、HTTP Client、任务和存储基础设施。Quant/Research/Researchflow 产生版本化业务事件；告警条件由上游业务模块计算。Notification 不 import Researchflow。

## 5. 安全和诊断

Secret 通过 Platform Secret 接口获取；recipient_scope 只能从受控 Subscription/Channel 配置解析为 recipient_ref。禁止模型输出或任意上游文本直接指定真实接收人。模板变量、渠道目标和内容大小需校验；日志只保留安全摘要和必要引用。诊断区分未配置、权限失败、限流、网络失败、模板失败、发送拒绝和结果未知；Metrics 标签必须有界。测试发送必须显式指定目标并经过 allowlist。
