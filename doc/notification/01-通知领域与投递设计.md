# Notification 通知领域与投递设计

## 1. 目标

建设独立、可复用、可追踪和可恢复的通知业务模块。首期服务于研究完成、风险变化和用户明确配置的告警，不建设通用消息平台。

## 2. 领域模型

- NotificationEvent：event_id/type/version、occurred_at、source_module、subject_ref 和受控 payload。
- Subscription：订阅主体、事件类型、过滤条件、渠道引用、启停状态和版本。
- Template：模板 ID/version、格式、变量 Schema 和渲染策略。
- Channel：渠道类型、配置/Secret 引用、限流和超时策略。
- Delivery：一次投递、幂等键、目标、状态和时间。
- DeliveryAttempt：发送尝试、错误分类、耗时和下次重试时间。

## 3. 生命周期与可靠性

queued → sending → sent / retry_wait / failed / skipped。相同幂等键只产生一次有效投递；重试有限并带退避/jitter；永久错误不重试；超过预算后 failed。业务事件先持久化再投递，必要时使用 Outbox。通知失败不回滚研究结果。

## 4. 边界

Notification 负责模板、渠道 Adapter、Dispatcher、投递 Repository、重试和状态。Platform 提供认证、Secret、日志、Trace、HTTP Client、任务和存储基础设施。Quant/Research/Researchflow 产生业务事件或通知命令；告警条件由上游业务模块计算。Notification 不 import Researchflow。

## 5. 安全和诊断

Secret 通过 Platform Secret 接口获取；渠道目标、模板变量和内容大小需校验。测试发送必须明确目标。诊断区分未配置、权限失败、限流、网络失败、模板失败和投递失败。记录状态、尝试次数、耗时和错误码；Metrics 标签必须有界。
