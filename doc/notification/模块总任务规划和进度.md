## 1. 模块目标与边界

Notification 负责接收内部业务事件、订阅与受众快照、Fanout、DeliveryPlan、模板渲染、渠道适配、Delivery/Attempt 生命周期、重试、租约恢复、Unknown 对账和一致性诊断。

- Research/Researchflow 等生产方通过 Outbox 发布冻结事件；Server 负责 Relay 和进程组合装配。
- Notification 拥有自己的 Inbox、Subscription、FanoutWorkItem、Delivery、Attempt、Template、ChannelConfig 和领域 Migration。
- Platform 提供 Secret、HTTP Client、Storage 等技术原语；Server 负责 Worker 生命周期、路由和依赖注入。
- 不把 Inbox 接收当作外部渠道发送成功；外部渠道不承诺 exactly-once，ambiguous 结果必须进入 unknown 并对账。

## 4. 关键业务与安全规则

1. recipient_ref 只能是不透明稳定引用；敏感地址由受控 Recipient/Channel Adapter 解析。
2. recipient_scope 不等于真实发送目标。
3. Channel、Template 均按 DeliveryPlan 固定版本精确解析，不回退 latest。
4. 非空 Filter 无对应版本化 Matcher 时 fail closed；字段语义由事件 Owner 冻结，Notification 不自创 DSL。
5. 仅在渠道能力已验证支持时发送幂等键、采信 Retry-After 或执行 Delivery Lookup。
6. ambiguous outcome 不自动重试；必须先有外部查询证据并通过 Unknown 对账流程。
7. not_sent 必须有证据；不能以普通错误推断请求未发出。
8. 发送前重新校验 Subscription、Channel 版本和 Recipient 授权。
9. Attempt 追加历史不可覆盖；租约恢复需校验 Worker、版本和 fencing token。
10. 真实渠道未配置时保持 not_comparable/blocked，不用 Fake 宣称生产通过。

## 5. 依赖与责任

| 依赖方 | Notification 需要的能力 | 责任方 |

| 业务事件 Owner | event_type、schema_version、Payload Schema、非空 Filter 语义、模板文案 | 对应业务模块 |

| Server | Root Migration、Outbox Relay、Recipient Directory、Fanout/Delivery Worker、配置与生命周期 | Server |
| 真实渠道 | 协议、凭据、回执、幂等和 Lookup 语义 | 渠道 Provider/项目决策 |

## 6. 生产闭环顺序

1. 先确定首个真实渠道及发送目标权威身份目录。
2. 冻结 SecretRef、请求/响应、回执、幂等、Retry-After、Lookup 和 ambiguous 处理语义。
3. 由 Server 注入真实 Recipient Directory、ChannelAdapter 和 Fanout/Delivery Worker 生命周期。
4. 提供真实业务模板与事件 Filter 规则。
5. 使用真实 MariaDB/Redis、受控渠道环境验证发送、失败、重试、Unknown 对账、进程恢复和优雅关闭。
6. 分别验收 Outbox→Inbox、Inbox→Fanout、Delivery→Channel 三段链路，不合并成一个模糊的“通知成功”。
