## NTF-002 Review 结论

- Registry 只按 `template_id + version` 取模板，不存在 latest 回退；模板版本通过 JCS SHA-256 Digest 保持不可变。
- 模板变量必须声明 allowlist，绑定路径按 JSON Pointer 解析且最终值限制为标量；不支持任意模板控制流。
- HTML Body 使用 `html/template`，动态内容由标准库按上下文转义；Subject 使用文本模板，并拒绝 Unicode 控制字符，避免 CR/LF 等头部注入。
- 模板源、输出和事件载荷深度均有显式上限；Subject 与 Body 共享输出字节预算。
- 批量加载先读取、校验 Digest、校验定义并编译全部版本，再持锁检查冲突并统一写入，避免部分装载。
- MySQL Repository 对重复键读取现有记录并比较完整定义；Get 时重新校验定义和 Digest，检测持久化列与摘要不一致。
- 当前未发现需要修改代码的确定性缺陷。真实业务模板、变量来源和渠道格式仍未由业务 Owner 冻结，因此 NTF-002 不得标记整体 DONE。

## NTF-003 Review 结论

- Notification 当前实现的是渠道 SPI、配置版本仓储和运行时 Registry，不包含具体企业微信 Provider。
- Platform 的 `config.Secret` 和 `httpclient.Client.Bind` 足以作为具体 Adapter 的凭据与 HTTP 出口基础；SecretRef 只作为配置引用持久化，实际 Secret 由 Server 装配时注入。
- RecipientDirectory 由 Server 提供具体实现；Notification 只消费授权后的 opaque target，不接触明文地址。
- 企业微信作为首个真实渠道候选已确定，但必须先区分群机器人 Webhook 与自建应用 API，两者凭据、目标地址、回执/查询能力不同。真实投递当前为 NOT_COMPARABLE。

## 判定规则

- PASS：实现、调用场景、自动化测试和必要集成证据相互一致。
- DEGRADE：非关键依赖不可用，核心安全/一致性边界仍成立，并记录 reason_code/evidence_ref。
- FAIL：存在可复现的数据一致性、安全、状态迁移或调用边界缺陷。
- NOT_COMPARABLE：缺少真实渠道、身份目录或生产环境证据，无法验证外部行为。
