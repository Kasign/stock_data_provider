## Review 结论

- Attempt 在渠道 Send 前通过 StartWithLease 持久化；Attempt ID、AttemptNo、WorkerID、FencingToken 和 LeaseExpiry 形成完整调用证据。
- 发送 deadline 取 PerAttemptTimeout、Delivery Deadline、MaxElapsed 和当前 LeaseExpiry 的最早值，不能跨越租约继续发送。
- Attempt 完成先持久化，再读取 Delivery 最新投影并 CAS 更新状态；若 Attempt 或 Delivery 提交结果不确定，不重放渠道发送。
- 普通 Retry 只接受显式 retryable rejection，错误码来源是精确 ChannelConfig 的 allowlist；使用指数退避 full jitter，并受 MaxAttempts、MaxElapsed、Delivery Deadline 和可信 Retry-After 约束。
- not_sent 必须附 evidence_ref；unknown 不允许盲目重发，只有精确渠道版本的权威 Lookup 证据确认未接受，才可进入 RetryPolicy；Lookup indeterminate 保持 unknown。
- LeaseRecovery 区分未开始 Attempt、未完成 Attempt、accepted、rejected、ambiguous、not_sent；恢复写入使用数据库租约到期事实、Delivery Version 和 fencing token CAS。
- Delivery Unknown 的 Lookup 使用一致性快照、精确 ChannelConfig 版本、精确 Delivery/Attempt 身份、证据时间和独立 CAS；不改写原始 Attempt 历史。

## 本轮发现并修复的问题

### 问题：过期租约中的未完成 Attempt 无法通过 Provider Lookup 对账

原因：

- Worker 在渠道请求期间崩溃，Attempt 已 StartWithLease 持久化但尚未 Complete。
- LeaseRecovery 将该 Delivery 收敛为 unknown，这是正确的保守行为。
- 但原 Lookup Request Builder 和 verified evidence 只接受 `FinishedAt != nil` 且 Outcome=ambiguous 的 Attempt；未完成 Attempt 被拒绝，导致具备权威 Lookup 能力的 Provider 也无法对账这类崩溃。

影响：

- 该 Delivery 会停留在 unknown，不能通过已声明的 Provider Lookup 确认是否接受。
- 如果直接重试可能造成重复投递，因此不能用“自动重发”绕过。

最小修复：

- 允许最后一条 Attempt 为未完成态（FinishedAt/Outcome 同时为空）或完成态 ambiguous。
- Lookup 仍绑定 DeliveryID、AttemptID、ChannelRef、ConfigVersion 和稳定 IdempotencyKey。
- RetryPolicy 仅在 `ScheduleRetryAfterUnknownLookup` 的 evidenceConfirmed 路径接受未完成 Attempt；必须有 Provider 权威 not_accepted 证据且 observed_at 不早于 Attempt StartedAt。
- ordinary `ScheduleRetry` 仍拒绝未完成 Attempt；indeterminate 仍保持 unknown；不改写 Attempt 历史。
