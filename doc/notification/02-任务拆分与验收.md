## 3. 执行顺序与阶段门禁

### 阶段 0：文档与契约校准（当前阶段）

- [x] 核对分支 HEAD、最近提交和 Notification 相关代码路径。
- [x] 确认旧 Python/Web 通知代码不等于新领域模块。
- [ ] 修正 README 的分支/实现状态。
- [ ] 统一 Retry-After 与本地退避的计算语义。
- [ ] 明确 NTF-001 实现范围及模块级/L3 证据边界。

完成条件：文档不再声称模块分支未创建或能力已实现；契约不存在已知互相矛盾的重试表述。

### 阶段 1：NTF-001 核心领域实现（阶段 0 完成后启动）

1. 建立 `internal/notification/domain` 与必要的应用层包；不预先创建无调用场景的空目录/接口。
2. 实现受控 Event Envelope、source_module/event_type/schema_version 精确注册。
3. 使用 Draft 2020-12 Validator 加载仓库 Schema；Validator 不支持的关键字必须明确拒绝或报告不可比较，不能静默忽略。
4. 自动校验 4 份 Schema 和 6 个 Golden；校验 date-time format assertion。
5. 实现 RFC 8785 JCS + SHA-256 Fingerprint；禁止用普通 `encoding/json` 输出直接冒充 JCS。
6. 实现 Inbox 双唯一语义：`(source_module,event_id)` 与 `(source_module,idempotency_key)`；同键同 fingerprint 返回原结果，不同 fingerprint 返回冲突。
7. 实现 Subscription 不可变版本、受限 filters 和 recipient_scope 校验。
8. 实现 DeliveryPlan 固定版本快照、plan fingerprint 和唯一性。
9. 先用 Fake/内存 Repository 验证领域行为；不提前接 MariaDB、根 DI 或 HTTP。

阶段门禁：Schema/Golden、Registry digest 不可变、Fingerprint、幂等冲突、并发 fan-out、Subscription 版本、recipient_scope 和 DeliveryPlan 快照测试全部通过。任何未支持的 Schema 语义不能降级放行。

### 阶段 2：NTF-002 Template/Renderer

仅在真实模板调用场景明确后实现模板 API。变量来源必须绑定事件 Schema 和 allowlist；默认 HTML 转义；模板版本不可变。完成 Fake 渲染测试后再进入 Channel。

### 阶段 3：NTF-003 Channel Adapter

先定义最小 Channel Port 和 Fake Adapter。Secret 通过 Platform Secret 能力引用，不复制明文。逐渠道登记 supports_idempotency、supports_delivery_lookup、supports_retry_after、max_payload_bytes；未验证能力按 false/unknown 处理。没有真实凭据时只验收 Fake，不宣称真实渠道通过。

### 阶段 4：NTF-004/005 Dispatcher 与 Retry

先实现模块内有界执行、CAS、lease/fencing、Attempt 追加历史和可控 Clock。仅明确 rejected 且在渠道 retryable 白名单内才自动重试；Retry-After 与本地退避取较晚时间，且必须早于总 deadline。ambiguous/timeout-after-write 进入 unknown，不盲目重发。

### 阶段 5：NTF-006 Repository

定义 Notification 自己的 Repository Port 和持久化模型；先 Fake，再 MariaDB。真实唯一约束、事务隔离、锁竞争、进程恢复和 Migration 属 L3，需单独证据。不得擅自修改根 Migration 注册。

### 阶段 6：NTF-007 Diagnostics/API

仅当上游、运维或 WebUI 存在明确调用场景，且已有可查询真实数据时，才定义 API。诊断字段必须有数据来源、语义、脱敏规则和判定阈值；不能为 UI 占位增加 API。

## 4. 依赖分层

- NTF-001/002 可在模块分支独立完成领域模型、Schema/Fixture、模板渲染和 Fake 测试。
- NTF-003 的 Port、Fake Adapter 和错误分类可先做；真实发送需要真实凭据和受控目标。
- NTF-004/005 先做模块内有界 Dispatcher；Platform Task Queue 不是领域依赖。
- NTF-006 Repository Port/模型可先行；真实 DB 与根 Migration 属 L3。
- 根 DI、HTTP、Worker、Migration 注册由项目统一决策方统筹；本分支不越界修改。
- Researchflow、Quant、Research 的生产方接入独立验收，不阻断 Notification 独立 Domain/Fake 测试；未完成生产方 Contract Test 的事件不得宣称 L2。

## 5. 幂等、状态与恢复验收

- Event Inbox 幂等与 Delivery 幂等是两道防线，分别测试。
- 相同幂等键相同 fingerprint 返回原结果；同 key 不同 fingerprint 冲突且不覆盖旧数据。
- DeliveryAttempt 追加保存；每次真实渠道调用一个 Attempt，完成记录不可覆盖。
- 网络超时且无法确认渠道是否接收时进入 unknown；无渠道幂等/查询证据不得自动重发。
- Outbox 只保证本地事务与待投递事件原子性，不保证外部渠道 exactly-once。
- recipient_scope 与 recipient_ref 分离；真实目标只能由已授权 Subscription/Channel 配置解析。
- 退订抑制尚未发送的 queued/retry_wait；sending 的外部副作用不能承诺撤回。
- 状态更新采用 CAS/版本号和租约 fencing，过期 Worker 不能覆盖当前状态。

## 6. 验收结果分类

| 结果 | 判定标准 |
|---|---|
| 通过 | 对应测试/真实探针执行成功，有可复现报告、输入和提交 SHA |
| 降级 | 非核心依赖或能力缺失，但已定义的降级行为生效且不破坏安全边界 |
| 失败 | 必要条件不满足、断言失败、状态/数据不可信 |
| 不可比较 | 缺少真实凭据、真实数据、能力声明或对照证据，无法得出结论 |

不可比较不等于通过；Fake 测试不能证明真实渠道、MariaDB 或 Worker 的 L3 能力。

## 8. 验收门禁

- 真实渠道受控测试发送；无凭据标记不可比较/blocked，不标记真实发送通过。
- 幂等、重试、unknown 和恢复测试证明不会因不确定结果盲目重复发送。
- 发送失败不影响上游业务事务。
- Secret/目标/通知内容按安全策略脱敏。
- 测试发送不得触达未明确指定的真实订阅者。
- 模块级 Fake/内存测试与 L3 真实渠道、Storage、Worker 集成验收分开记录。
