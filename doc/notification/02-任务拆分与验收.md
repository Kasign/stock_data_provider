## 5. 幂等、状态与恢复验收

- Event Inbox 幂等与 Delivery 幂等是两道防线，分别测试。
- 相同幂等键相同 fingerprint 返回原结果；同 key 不同 fingerprint 冲突且不覆盖旧数据。
- DeliveryAttempt 追加保存；每次真实渠道调用一个 Attempt，完成记录不可覆盖。
- 网络超时且无法确认渠道是否接收时进入 unknown；无渠道幂等/查询证据不得自动重发。
- Outbox 只保证本地事务与待投递事件原子性，不保证外部渠道 exactly-once。
- recipient_scope 与 recipient_ref 分离；真实目标只能由已授权 Subscription/Channel 配置解析。
- 退订抑制尚未发送的 queued/retry_wait；sending 的外部副作用不能承诺撤回。
- 状态更新采用 CAS/版本号和租约 fencing，过期 Worker 不能覆盖当前状态。

## 6. 验收结果分类

| 结果 | 判定标准 |
|---|---|
| 通过 | 对应测试/真实探针执行成功，有可复现报告、输入和提交 SHA |
| 降级 | 非核心依赖或能力缺失，但已定义的降级行为生效且不破坏安全边界 |
| 失败 | 必要条件不满足、断言失败、状态/数据不可信 |
| 不可比较 | 缺少真实凭据、真实数据、能力声明或对照证据，无法得出结论 |

不可比较不等于通过；Fake 测试不能证明真实渠道、MariaDB 或 Worker 的 L3 能力。

### Delivery 一致性统一只读诊断

- 新增 `AssessDeliveryConsistency`，聚合 Delivery 快照、Attempt 历史与 StateEvent 历史的独立校验结果，不访问数据库、不自动修复，也不引入 Server 依赖。
- 两类历史分别通过 `AttemptsComparable` / `StateEventsComparable` 显式声明是否已完整读取；读取失败、未读取或完整性无法证明时标记 `not_comparable`，不得把空切片冒充完整历史。

- 该纯函数不保证三个输入来自同一数据库时点。调用方若分开读取，必须将读取失败/快照不可比标记为不可比较；本能力不声称提供原子快照读取。

### 租约恢复与 Unknown 对账交错竞争 Review（2026-11-10）

本轮检查 `RecoverExpiredLease`、`ReconcileUnknown`、Attempt Start/Complete 的事务锁与 CAS 边界，结论如下：

1. **两条状态推进路径由状态与版本隔离。** 租约恢复只接受当前 `sending`、预期 Delivery version 和当前 fencing token，并在数据库事务内再次检查租约已过期；Unknown 对账只接受当前 `unknown` 与预期 version。两者均锁定 Delivery 行并在同一事务中更新快照、追加 StateEvent。
2. **租约恢复先提交时，旧的 sending 恢复请求不能覆盖 Unknown 对账。** 恢复将状态改为 `unknown` 并递增 version；旧恢复请求随后因 status/version 不匹配而冲突。Unknown 对账只能基于新版本执行。
3. **Unknown 对账先提交时，旧的租约恢复请求不能覆盖终态或 retry_wait。** 对账将状态从 `unknown` 收敛并递增 version；旧恢复请求随后因 status/version 不匹配而冲突。
4. **Attempt Start 与恢复竞争有额外保护。** Start 事务要求 Delivery 仍为 `sending`、fencing token/Worker 匹配且数据库租约未过期，并更新 `attempt_count`；恢复写事务会比较当前与评估快照中的 `attempt_count`。若 Start 先提交，使用旧快照的恢复写入会冲突。
5. **Attempt Complete 与恢复竞争采取保守收敛。** Complete 与恢复都先锁 Delivery 行。若恢复依据先前读取的运行中 Attempt 将状态标记为 `unknown`，即使 Complete 随后才提交或先于恢复写入完成，未知状态仍要求 Provider 查询核验，不会盲目重发；若评估读取到已完成的 accepted/rejected 事实，则按该不可变 Attempt 结果收敛。

**结论：** 当前 MySQL 写入路径具备 status + version + fencing token + 行锁的 fail-closed 保护，没有发现两条路径能基于旧版本互相覆盖的缺口。本轮不增加重复的并发测试或改动状态机。该结论来自代码事务边界审查，尚无真实 MariaDB 并发执行证据；现有 MariaDB 集成测试仍需在配置 `NOTIFICATION_MARIADB_TEST_DSN` 的环境运行。


### MySQL Repository 事务锁顺序与死锁边界 Review（2026-11-10）

**锁顺序审查**

- Attempt `StartWithLease`：先锁 `notification_deliveries` 对应 Delivery 行，再检查 Attempt 历史并插入 Attempt，最后更新 Delivery 的 AttemptCount。
- Attempt `CompleteWithLease`：先锁 Delivery 行，再锁目标 Attempt 行，随后更新 Attempt。
- Delivery `UpdateWithLease`、`RecoverExpiredLease`、`ReconcileUnknown`：均先锁 Delivery 行，再更新 Delivery 并追加 StateEvent。
- Claim：先锁待领取 Delivery 行，再更新租约/版本并追加 StateEvent。
- 一致性快照使用只读 Repeatable Read 事务，不获取写锁；不会形成与上述写事务相反的行锁顺序。

**结论与限制**

1. 当前核心写路径的主锁顺序一致，未发现 Attempt → Delivery 与 Delivery → Attempt 的反向锁序环。
2. StateEvent 追加发生在持有 Delivery 行锁之后；未发现独立先锁 StateEvent 再锁 Delivery 的业务写路径。
3. Repository 没有自动重试死锁或锁等待超时。语句阶段遇到数据库错误会终止当前事务；调用方不应无条件重放整个业务操作。
4. 所有写事务的 Commit 错误目前保守映射为 `ErrPersistenceOutcomeUnknown`。即使底层错误看起来像数据库事务中止，也不能在未完成驱动错误码分类和真实 MariaDB 验证前自行降级为普通失败或重试授权。
5. 后续若增加自动重试，必须只针对数据库明确确认已回滚的死锁/锁等待中止，重新读取最新 Delivery/Attempt 状态并重新执行 CAS；不得重放渠道发送，也不得重试提交结果不确定的事务。

本轮为源码事务顺序审查，未运行 MariaDB 并发/死锁注入测试；因此结论不等于已证明不存在所有执行计划、索引和隔离级别组合下的死锁。

### Delivery 租约恢复前序 Attempt 结果一致性修复（2026-11-10）

- 并发事务审查确认：ClaimDue 在单事务中锁定 Delivery、推进 sending/version/fencing token 并追加 StateEvent；Attempt Start 在另一事务中先锁定同一 Delivery，再校验数据库时钟、Worker、token、version 和租约，原子追加 Attempt 与更新 attempt_count。Claim 成功但 Start 尚未提交时，过期恢复可见“当前 token 无 Attempt”，该场景可以安全重试。
- Completion 先在 Attempt Repository 事务中固化渠道结果，再由 Delivery Repository 执行带租约/token/version 的状态 CAS。两步之间崩溃时，Attempt 历史保留渠道结果；租约恢复按 accepted/rejected/ambiguous/not_sent 收敛，不重复调用渠道。恢复状态与 StateEvent 在同一事务提交。
- 所有相关写路径均先锁 Delivery，再访问 Attempt 或追加 StateEvent；未发现当前代码存在反向锁序。Inbox 唯一键冲突会先回滚接收事务，再按两个身份键查询；Inbox 与 Fanout 写入共享事务。真实 MariaDB 死锁/锁竞争证据仍缺。
- **发现并修复一处 fail-closed 缺口**：当当前 fencing token 尚无 Attempt 时，恢复逻辑原先直接判定“渠道调用尚未开始”。如果历史中上一条 Attempt 实际为 accepted、ambiguous 或不可重试 rejected，这与新租约进入 sending 的状态不一致；直接安全重试会放大重复外部副作用风险。现在要求前序历史必须以 retryable rejected 或 not_sent 结束，否则返回 `ErrLeaseRecoveryHistory`。
- 新增测试覆盖 retryable rejected/not_sent 允许无当前 Attempt 的租约安全重试，以及 accepted/ambiguous/永久拒绝三类历史必须 fail-closed。
