# Notification 事件接收与投递状态契约对齐补充

- 适用任务：NTF-001～007；首批生产事件映射见 05 文档
- 契约范围：NTF-CTR-001～003、INT-CTR-001、GOV-CTR-001～006、PLAT-CTR-001～005
- 状态：语义决议 accepted；Schema/Golden/模块 CI/并发与真实渠道证据按契约目录维持 pending_evidence
- 权威关系：03 文档定义 Application Port、Inbox/Subscription/Delivery 状态及 NTF-003 Channel Adapter 契约（第 8.4 节）；05 文档定义首批业务事件映射；项目级契约目录定义编号和状态

## 1. 责任边界与可靠交付

Notification 是事件接收与投递模块，不拥有 Quant RiskDecision、ResearchEvent 或 Researchflow Run 的业务事实，也不读取这些模块的 Repository。

- 生产方在自己的本地事务中提交业务状态和 Outbox；Notification 接收版本化 Envelope、校验 Schema、持久化 Inbox 并异步 fan-out。
- 不要求跨模块数据库事务；生产方 Outbox + Notification Inbox 提供可靠交付边界。
- PublishEvent 成功表示事件已被接收/幂等吸收，不表示订阅匹配成功、渠道已调用或用户已阅读。
- 不根据 event_type 猜 source_module，不从 Payload/LLM 输出推导 recipient，不接受任意地址、URL 或用户输入作为发送目标。
- Notification 只依赖 Platform 技术原语；不反向依赖业务模块领域类型。

## 2. Event Envelope 与 Schema Registry

注册键为 (event_type, schema_version)，注册后 Schema 内容和 digest 不可原地修改。首批 schema_version=1.0.0，Payload Schema 由 event_type + schema_version 唯一确定。

Envelope 至少包含 schema_version、event_id、event_type、source_module、occurred_at、published_at、correlation_id、idempotency_key、subject_ref、payload_fingerprint、payload。Ref 为不透明非空字符串；时间为 RFC3339Nano UTC；必需数组无元素时用空数组。

- event_id 是 NotificationEvent 身份，由生产方生成；不得复用来源领域对象 ID。
- source_module 是注册生产模块枚举；首批 quant/research/researchflow。
- idempotency_key 在 (source_module, idempotency_key) 范围内唯一，代表稳定发布意图。
- occurred_at 是来源事实时间，不是 Notification 接收时间；首批映射 Run.finished_at、RiskDecision.evaluated_at、ResearchEvent.changed_at。
- correlation_id 从可信父上下文继承；无父链路时由生产方生成，不信任客户端自报值。
- payload_fingerprint 按 RFC 8785 JCS + SHA-256 计算，输入字段固定为 event_type、schema_version、source_module、subject_ref、occurred_at、payload；event_id、idempotency_key、correlation_id、published_at 属传输/关联元数据，不进入指纹输入。

未知 event_type/schema_version、未知 source_module、非法时间、字段缺失、超大 Payload、fingerprint 不匹配必须 fail closed；不得回退旧 Schema，不写 Inbox/Delivery，不触发 fan-out。

## 3. Inbox 幂等与 fan-out

Inbox 建立两类独立唯一约束：
1. (source_module, event_id)：同事件身份去重。
2. (source_module, idempotency_key)：同发布意图幂等。

相同唯一键且 fingerprint 相同，返回原接收结果，不重复 fan-out；相同键但 fingerprint 不同，返回稳定 idempotency_conflict，不覆盖原事件。不同 source_module 使用相同 idempotency_key 不得误冲突。

首次接收在本地事务持久化事件与 fan-out 工作项。Subscription 匹配和 Delivery 创建异步执行；并发 fan-out 通过唯一约束/幂等只生成一个 DeliveryPlan。没有匹配订阅时不创建 Delivery，但保留受控 fan-out 统计。

## 4. Subscription / Recipient / DeliveryPlan 快照

Subscription 每次影响匹配、目标、Channel、Template 或过滤器的更新都产生新的不可变 version。单条 Subscription 只绑定一个 event_type；filters 使用该事件类型注册的过滤 Schema，不允许任意查询语言。

recipient_scope 首批仅允许 subscription_owner（由 owner_ref 在受控身份目录解析）和 preconfigured_target（由已授权 Channel 配置解析 recipient_ref）。recipient_ref 是稳定不透明目标引用，不是邮箱、手机号、URL 或明文地址。模型输出和业务 Payload 不能直接指定真实目标。

DeliveryPlan 创建时冻结 source_module/event_id、subscription_id/version、channel_ref/channel_config_version、template_id/template_version、recipient_ref、payload_fingerprint/plan_fingerprint、delivery_id 与 delivery_idempotency_key。授权策略版本集合必须保留 GOV-CTR-006 的完整 tuple：policy_type、policy_ref、policy_version；指纹计算前按 tuple 字典序规范排序，不得只保存或比较 policy_version 字符串。对应 AuthorizationRef 仅作为审计引用，不是 bearer token，且不参与 plan_fingerprint。配置变化不得原地修改历史计划。Secret 只保存 SecretRef；发送前检查当前 Subscription、recipient_ref、Channel 和 Secret 状态。

## 5. Delivery 与 Attempt 状态语义

状态必须区分：
- queued：已持久化等待执行；
- sending：Worker 持有有效 lease/fencing token，执行发送前检查或调用；
- retry_wait：渠道明确未接受且错误可重试；
- sent：渠道明确确认接受，不等于用户已阅读；
- skipped：规则决定不发送，如退订/过滤/目标撤销；
- blocked：发送前置条件不可用，尚无可确认外部副作用；
- failed：永久失败或预算耗尽且结果明确；
- unknown：请求可能已到达渠道但缺少可靠结果，必须对账或依赖渠道幂等能力。

blocked、skipped、failed、unknown 不得合并为通用 error。unknown 不允许直接 RetryDelivery；必须先通过渠道查询、回执或可证明的幂等协议对账。

DeliveryAttempt 是追加式历史；每次真实渠道调用创建一个 Attempt。attempt_count 只统计真实渠道调用，不统计 Schema/权限/配置预检查。Attempt 结果不可覆盖；租约接管时递增 fencing_token，旧 Worker 迟到写入必须拒绝。

发送前因退订而跳过必须记录 reason_code；系统依赖不可用不能伪装 skipped。请求可能已发出后超时/崩溃必须 unknown，不能直接 queued。

## 6. 重试、deadline 和人工操作

自动重试只允许渠道明确拒绝且 retryable 白名单命中的结果。Retry-After 与本地退避比较取较晚时间，但 next_attempt_at 不得超过 Delivery deadline。退避算法固定 exponential_full_jitter_v1；max_attempts、max_elapsed_ms、per_attempt_timeout_ms、base_delay_ms、max_delay_ms 和 deadline 必须显式配置，时间单位为 integer milliseconds。

同一 Delivery 的渠道幂等键在各 Attempt 间稳定；只有 Channel Capability 明确 supported 时才发送。超时后结果不确定且渠道不支持查询/幂等时保持 unknown，进入人工/运维对账，不自动重发。

人工重试必须具备可信操作者身份、原因、request_id、幂等键和审计记录；只允许明确 failed 且策略允许的对象。unknown 必须先对账；sent/skipped 不可普通重试。blocked 配置修复后的重新入队必须经过受控、幂等、可审计的重新评估操作，不得将通用 RetryDelivery 当作绕过授权/配置检查的入口。

## 7. 安全与错误

Platform Fault 只在模块内部使用；对外响应投影为受控错误 DTO，不暴露 cause、SQL、Provider 原始错误或 Secret。retryable 只是技术候选，不代表可以忽略状态、预算、deadline、Channel Capability 和幂等要求。

日志仅记录 event_id/delivery_id、受控引用、状态、reason_code、耗时和诊断引用。Secret、目标明文地址、完整 Payload、模板敏感变量不得进入默认日志或错误摘要。

## 8. Contract Test 最低矩阵

Schema Registry、Inbox 双唯一键、重放/冲突、并发 fan-out、Subscription 版本快照、recipient_scope、发送前撤销复核、全部状态迁移、CAS/fencing、Retry-After/deadline、unknown 对账、人工命令幂等、Outbox 回滚/重复投递恢复、Secret/地址/Payload 脱敏均须自动化覆盖。

ChannelConfig/Adapter/RecipientResolver 字段级约束和 Platform Secret/BoundDoer 接入边界见 03 文档第 8.4 节。当前仅有内存 Registry/Fake Adapter 与 opaque RecipientTarget 单测，尚无真实身份目录或渠道 Adapter。Fake Repository/Fake Channel/Fake Clock 只证明模块级行为；真实 MariaDB 事务/唯一约束、Worker 崩溃恢复和各渠道幂等/对账能力独立作为 L3 证据。不得把 Fixture 或 Fake Channel 结果写成真实渠道 supported。


## 9. Envelope 时间与指纹字段补充

- `published_at`：生产方将 NotificationEvent 写入 Outbox 的时间，使用 RFC3339Nano UTC；与 `occurred_at`（业务事实发生时间）分离。Outbox 重试必须复用原值，不得在每次发送时刷新。
- `payload_fingerprint`：生产方计算并随 Envelope 传输的小写 64 位 SHA-256。接收方必须按 03 文档规定的字段集合独立重算并比对；缺失、格式错误或不匹配均 fail closed。
- Fingerprint 输入仅覆盖 `event_type`、`schema_version`、`source_module`、`subject_ref`、`occurred_at` 和 `payload`；不覆盖 `event_id`、`idempotency_key`、`correlation_id`、`published_at`、接收时间或传输 Header。
- 六个 Golden 中的 `published_at` 为合成 Outbox 时间，仅用于验证字段格式和重放稳定性；Golden 中的 fingerprint 必须与其对应输入按 RFC 8785 计算结果一致。
