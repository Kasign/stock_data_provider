## 1. 建设目标

建立独立、可组合、可追溯的字段质量校验体系，使 Provider Adapter、数据标准化、主动诊断和数据入库使用一致的字段契约。

必须满足：

1. 标准化负责格式、代码、日期和单位转换；Validation 只判断，不修改输入。
2. 公共字段规则与 Provider 字段支持策略分离。
3. 诊断结果定位到字段、记录、证券和交易日期，并保留规则编码、严重级别、期望值及安全的实际值。
4. 缺失、NULL、0、空字符串保持不同语义；禁止为了通过校验而补零。
5. 停牌、新股、除权除息、非交易日、不同复权口径不得被简单规则误报。
6. Provider Probe 与入库质量门禁复用同一 Validator，不维护两套规则。
7. 新增字段/能力优先通过组合规则和能力策略完成，不要求修改校验核心流程。

## 2. 架构边界

建议依赖方向：

`Provider Adapter → Normalize → Validation → Probe / Data Service`

- **Provider Adapter**：请求上游、解析原始响应、字段映射；原始 JSON 类型错误应在解析边界捕获，避免反序列化后丢失字段路径和实际类型。
- **Normalize**：证券代码、日期、单位、精度、复权口径等标准化。转换行为必须明确且可追踪。
- **Validation**：执行字段契约和业务规则，输出结构化问题；无网络、数据库和全局可变状态，不修改输入。
- **Provider Probe**：组织 connectivity、contract、quality、freshness、cross_provider、storage 检查并汇总状态；不自行实现字段规则。
- **Data Service**：在入库或数据发布边界执行同一 Validator，根据明确的质量门禁策略决定拒绝、降级或允许。
- **Repository**：保存诊断结果，不重复校验。

建议目录：

```text

├── normalize/
│   ├── quote.go
│   ├── daily_bar.go
│   └── unit.go
├── validation/
```

## 3. 统一诊断模型

### 3.1 字段问题

建议模型字段：

| 字段 | 语义 |
|---|---|
| field | 标准字段名 |
| code | 稳定规则编码 |
| severity | error / warning / info |
| message | 面向开发和运维的短说明 |
| expected | 规则期望 |
| actual | 脱敏、限长后的实际值 |
| row_index | 响应记录位置 |
| symbol | 规范证券代码 |
| trade_date | 交易日期 |
| provider / capability | 来源和能力 |

第一批稳定规则编码：

- `required`：必填缺失
- `type_mismatch`：原始类型不匹配
- `invalid_number`：非数值、NaN 或 Inf
- `out_of_range`：数值超出范围
- `invalid_enum`：枚举非法
- `invalid_date`：日期非法
- `ohlc_relationship`：OHLC 关系错误
- `duplicate_record`：重复记录
- `unit_mismatch`：单位不符合契约
- `conditional_required`：满足条件时字段必填

问题数量必须有上限：同时记录实际问题总数、保留条数和截断标志。实际值不得包含 Token、Cookie、认证头、完整 URL 或原始响应全文。

### 3.2 Provider 字段策略

按 Provider + Capability + Field 配置：

- `required`：必须返回，缺失为 error。
- `optional`：允许缺失，缺失不报错。
- `unsupported`：Provider 明确不支持，不参与该字段合法性判定。
- `conditional`：满足业务条件时必需。

Provider 未声明支持策略时，使用能力契约明确给出的默认值；不能把未知策略自动视为 unsupported。Provider 声明支持但返回 NULL/非法值时，仍须按字段契约报告。

### 3.3 结果与状态

Validator 输出 error / warning / info 计数、问题总数、问题明细和截断标志。Probe 再将结果映射为各检查维度状态：

- 有 error：该检查 failed。
- 无 error、有 warning：该检查 degraded。
- 无问题：passed。
- 未配置凭证或不支持能力：按原因 skipped / not_configured / not_supported。
- 无足够可比数据：cross_provider 为 not_comparable 或 skipped，不伪装成 matched。

字段契约错误属于 contract；记录完整性、业务关系和质量疑点属于 quality。两者可复用规则执行结果，但统计归属要明确，避免重复计数。

## 4. 当前代码基线与已发现的迁移风险

### 4.1 `normalize.ValidateQuote` 当前规则

当前实现位于 `services/market-data/internal/normalize/normalize.go`，实际行为如下：

1. Quote 指针不能为 nil。
2. symbol、source 必须存在；symbol 必须已经是规范六位代码和交易所后缀。
3. quality_status 只允许 valid、degraded、stale、unknown；invalid 和未知值拒绝。
4. adjustment_basis 只允许 none、forward_adjusted、backward_adjusted、unknown。
5. current_price、open、high、low、prev_close 必须存在、有限且大于零。
6. low 不得高于 high；open/current_price 必须处于 low/high 区间。
7. change、change_percent、volume_ratio、turnover_rate 存在时必须有限；volume_ratio、turnover_rate 还不得为负。
8. change 与 current_price - prev_close 的差异不得超过 0.02 CNY。
9. change_percent 与计算值差异不得超过 0.15 个百分点。
10. volume 必须存在且非负。
11. amount 存在时必须有限且非负；amount_unit 必须为 CNY。
12. amount 缺失时，quality_status 不能是 valid；同时当前函数会把 amount_unit 改为 unknown，并追加两条 quality reason。
13. amount 与 volume 不能出现一正一零；两者均为正时，amount/volume 隐含均价必须位于 low×0.5 到 high×2 范围。
14. volume_unit 必须为 shares。

**重要迁移风险：当前 ValidateQuote 不是纯校验函数。** amount 缺失时会修改 Quote 的 AmountUnit 和 QualityReasons。迁移前必须梳理调用方是否依赖该副作用。新 Validator 不得复制这一副作用；应把缺失金额导致的质量降级放入明确的 Normalize/质量标记步骤，旧入口在兼容期保留原行为或通过有测试保护的包装层维持兼容。

另外，价格必填、volume 必填等规则可能对停牌、新股或特定快照状态过严。不能在没有场景上下文时直接把旧规则照搬成永久公共契约。

### 4.2 `normalize.ValidateAndSortBars` 当前规则

该函数同时承担参数校验、记录过滤、标准化、排序和质量标记，并非单纯 Validator：

1. start/end 必须为严格 YYYY-MM-DD；非法时返回对应 warning。
2. 非法 trade_date 的记录被丢弃。
3. start 之前的记录静默过滤；end 之后记录被丢弃并产生 warning。
4. 同一 trade_date 只保留第一条通过前序校验的记录，后续重复记录丢弃。
5. OHLC 必须有限、为正，且 high/low/open/close 关系合理。
6. volume 必须存在且非负；volume_unit 必须为 shares。
7. amount 存在时必须有限、非负；amount 与 volume 不能一正一零。
8. 仅在 adjustment_basis=none 时执行 amount/volume 隐含均价与 OHLC 的量级交叉检查；复权 K 线不执行该检查。
9. change_percent 存在时必须有限。
10. adjustment_basis 只允许 none、forward_adjusted、backward_adjusted。
11. period 必须为 1d。
12. source 缺失时改为 unknown，并把 quality_status 设为 unknown，追加 source_missing。
13. 函数将每条记录的 symbol 覆盖为请求 symbol。
14. amount 缺失时将 amount_unit 设为 unknown、质量状态至少降级为 degraded，并追加质量原因；amount 存在时 amount_unit 必须为 CNY。
15. quality_status 缺失时标为 unknown；只接受 valid、degraded、stale、unknown，invalid 或未知状态的记录丢弃。
16. 最终按 trade_date 升序排序；超过 limit 时保留最新 limit 条并产生 bars_truncated_to_limit。
17. warning 去重；OHLC 详细值最多记录前五条。

**重要迁移风险：** 该函数把校验和数据变更混在一起，且对被过滤记录只返回字符串 warning，无法稳定定位字段和行号。新实现应拆成：
- 请求范围与日期参数校验；
- 单条 DailyBar 的字段/业务规则校验；
- 记录过滤与去重策略；
- 规范化、排序和 limit 处理；
- 结构化问题汇总。

旧函数在兼容期保持签名和行为。不得把排序、截断、symbol 覆盖等操作放入纯 Validator。

### 4.3 当前明确的测试和诊断风险

- Quote 当前多个字段使用 map 遍历校验，多个字段同时非法时，首个错误的顺序可能不稳定；结构化 Validator 必须保证问题顺序确定。
- DailyBar 当前重复日期、范围过滤、记录丢弃等情况只能得到 warning 字符串，结构化迁移需保留 row_index、symbol、trade_date。
- 原始 JSON 类型错误需要在 Adapter 解码边界保留；转换成 Go 零值后不能再推断源端实际类型。
- 现有 amount 缺失语义必须继续为 NULL/unknown/degraded，不得补零。
- amount/volume 交叉检查必须尊重复权口径，不能将复权价格与未复权成交额直接比较。
- 诊断 checks 目前已有 connectivity、contract、quality、freshness、cross_provider、storage；本次字段校验工作是在现有 checks 上增量接入，不重建 Probe 框架。
- cross_provider 必须继续拒绝 degraded/unknown 样本；当前真实黄金样本尚未证明 valid matched，不得改变门禁以制造通过结果。

## 6. 测试验收标准

每个能力至少覆盖：

- 正常值、缺失值、NULL、0、空字符串；
- 类型错误、非法枚举、非有限数值、范围边界；
- 重复记录、非法日期、超出请求范围；
- 单位不一致和复权口径差异；
- 停牌、新股、除权除息、非交易日；
- Provider required / optional / unsupported / conditional；
- 问题数量截断、实际值脱敏；
- 同一输入重复执行结果一致；
- Validator 不修改输入；
- Probe 与入库的质量结论一致。

真实 Provider 探测不代替固定夹具测试；固定夹具通过也不代表真实 Provider 在线可用。

## 9. 第一批任务进展（2026-11-02）

本轮已完成第一批的主要静态盘点，并将逐字段明细、调用点和测试覆盖写入 `doc/字段校验规则矩阵.md`。

### 已确认的调用链

- Quote Adapter：NetEase、Sina、Tencent、Yahoo 在返回前调用 `normalize.ValidateQuote`。
- Quote Probe：`service/provider_probe.go` 在 Provider 返回后再次调用 `normalize.ValidateQuote`。
- DailyBar Adapter：Baostock、Hithink、NetEase、Pytdx、Sina、Tencent、Yahoo 通过 `normalizeProviderDailyBars` 调用 `normalize.ValidateAndSortBars`。
- DailyBar Probe：`service/provider_probe.go` 在 Adapter 已经整理过的结果上再次调用 `normalize.ValidateAndSortBars`。

因此当前 Probe 存在二次校验。尤其 DailyBar 的无效记录在 Adapter 公共 helper 中已经被过滤，Probe 无法恢复字段、实际值和原始行号；当前只剩 rejectedRows 计数及统一 quality reason。

### 已确认的解析边界

- NetEase 数值字段使用 `json.RawMessage`，但解析错误仍转换为普通 error。
- Sina Quote 使用文本字段索引；Sina DailyBar 使用 `json.RawMessage`，逐行解析失败只累计 rejectedRows。
- Tencent DailyBar 使用 `[][]json.RawMessage`，只接受前六列为 string/number；其他类型只增加 rejectedRows，字段索引和实际类型未保留。
- Yahoo Quote 使用静态结构体，部分必填数值是非指针 float64；缺失/null 可能落为零值，类型不符通常导致整体 Decode 失败。Yahoo DailyBar 指针数组能区分 null，但类型错误仍是整体解码失败。

### 已确认的特殊场景上下文能力

现有服务已提供 TradingCalendar、SecurityTradingStatus、PriceLimitEventEvidence、历史涨跌幅规则解析和 MarketSession。新 Validator 不应在内部请求这些数据，应由调用方预先获取最小、不可变的上下文快照传入。MarketSession 只描述市场时段，不替代个股停牌状态或临时交易所公告。

## 32. 跨 Provider 复权基准元数据传递与比较门禁审查（2026-11-04）

### 32.1 当前缺口

- `DailyBar` 已定义 `AdjustmentMethod` 和 `AdjustmentRefDate`。
- Probe 构造 `CrossProviderDailySnapshot` 时只传递 `AdjustmentBasis`；每根 bar 的 method/ref date 被丢弃。
- 比较器只校验 `AdjustmentBasis` 相同，不校验参考日期/参考语义。
- 服务层先按相同 adjustment enum 配对，再调用比较器；因此比较器需要具备独立防御门禁，不能依赖调用方预筛选。

### 32.2 修复契约

1. 快照保留复权元数据，并要求同一快照内的复权元数据一致；混合元数据快照不可比较。
2. none 口径不要求参考日期。
3. qfq/hfq 口径只有双方参考基准可证明兼容时才可比较。参考日期缺失或基准语义未知时返回 not_comparable，不以相同 enum 作为充分条件。
4. 比较结果应保留左右 Provider 的 method/ref date 证据和不可比较原因。
5. 不能把 adjusted 的 not_comparable 统计为 Provider 数据错误，也不能统计为 matched。

### 32.3 必测反例

- 同为 backward，但 method/reference semantics 不同。
- 同为 backward，一侧有 reference date、另一侧缺失。
- 两侧 reference date 不同。
- 同一 Provider 的返回行中 method/ref date 不一致。
- 两侧均为 none 时仍能进入既有比较路径。
- service 层配对与比较器单独调用得到一致的可比较性结论。

当前为代码审查结论和待实现契约；本节没有声称代码已修复。阶段 B 继续。


## 2026-11-04 阶段 B：复权基准比较门禁实施记录

本轮针对跨 Provider 日 K 对账的复权口径误放行风险，实施保守门禁：

- `none`（不复权）继续沿用既有比较路径，不要求复权元数据。
- `forward_adjusted` / `backward_adjusted` 必须逐根 K 线提供非空 `AdjustmentMethod` 与 `AdjustmentRefDate`。
- 同一 Provider 快照内所有 K 线的 method/refdate 必须一致；缺失或行间不一致时，结果为 `not_comparable`。
- 两侧复权 method 与 reference date 必须完全一致，才允许进入 OHLC/成交量/成交额数值比较。仅 `AdjustmentBasis` 相同不再构成可比证据。
- Probe 结果保留左右 Provider 的 method/refdate，便于解释被跳过的比较。
- 服务层仍按同证券、同复权枚举配对；比较器统一执行基准门禁，避免服务层与比较器各自采用不同标准。

当前规则有意偏保守：不同 Provider 的方法标识不同，即使其算法可能在经济含义上等价，也会被标记为不可比较。后续如需放宽，必须先建立有来源证据和回归样例的跨 Provider 基准映射；不得直接按 method 名称猜测语义，也不得用共同日期归一化替代绝对基准证明。

本规则仅防止错误 matched，不代表已经证明各 Provider 的复权值彼此正确。真实 Provider 样本仍需分别记录来源算法、参考日期、因子来源及数据质量。CI 通过仅代表代码测试通过，不替代真实数据验收。
