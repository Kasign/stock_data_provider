# DATA-CTR-005 / DATA-CTR-007 解阻方案

- 维护范围：Data 对外日线数据事实、精度与 Snapshot；Research 负责 Evidence 映射；Server 负责可信身份注入和组合装配。
- 工作分支：`repair_all` 聚合协调；不代表 `feat/data` 已同步。
- 当前状态：`IN_PROGRESS_DESIGN_REVIEW`；本文是实现方案建议，不将 deferred 契约擅自标为 frozen。
- 基线：`repair_all` SHA `740e7e37e876d77b1d24ade93f426d21346a8201`。
- 依据：DEC-PLAT-002-020、DEC-PLAT-002-038、DEC-PLAT-002-047；PLAT-002 登记簿中 DATA-CTR-005/007 均为 deferred。

## 1. 真实问题和现状证据

DATA-CTR-007 不能直接在当前 `DailyBarsSnapshot` 上增加一个 `snapshot_ref` 字段解决。当前实现存在四个独立缺口：

1. **数值精度在 Provider 入口已丢失。**
   - `internal/marketdata/model.DailyBar` 的 OHLC、Amount、ChangePercent、MA 字段为 `float64`。
   - `internal/marketdata/app.DailyBar` 同样以 `float64` 暴露，`DailyBarsSnapshot` 只有 Symbol、AdjustmentBasis、QualityStatus、Warnings、SystemObservedAtCutoff、Bars。
   - Tushare、BaoStock 的日线数值解析使用 `strconv.ParseFloat`；Hithink 日线 JSON 结构直接解码为 `*float64`。
   - 因此不能把现有 float64 格式化成字符串并宣称恢复了 Provider 原始十进制精度。

2. **数据库有固定精度，但不等于来源精度契约。**
   - `market_data_daily_bars` 与 revision 表的 OHLC 使用 DECIMAL(20,8)，Amount 使用 DECIMAL(24,2)，ChangePercent 使用 DECIMAL(16,8)。
   - 这些是当前存储列定义，不证明所有 Provider 的原始精度、调整后价格精度或字段舍入语义均已得到供应商证据。
   - v2 必须明确源值保真、存储精度、派生计算精度三者的区别，不能把数据库 scale 当作源端精度。

3. **现有 Snapshot 不是不可变内容资源。**
   - 当前 Application Reader 每次调用 DataService，映射实时返回的 DailyBar 列表；没有独立的不可变 Snapshot Payload、内容寻址存储或精确 Snapshot 读取。
   - 当前 DTO 没有实际 interval、不可变交易日历版本、SnapshotRef、Payload fingerprint 或 AuthorizationRef。
   - 当前 DailyBars PIT 是按历史修订重建查询结果，不等于该次结果已物化为可长期复用的不可变输入。

4. **现有 source_version 不是 Provider 数据版本。**
   - Tushare 日线写入常量 `tushare-pro-daily-v2-adjustment-factor`，BaoStock 写入 `baostock-public-tcp-v1`，Hithink 使用适配器版本常量；它们描述的是 Provider/Adapter 接口或映射版本，不是某证券某交易日的上游数据修订版本。
   - `validation.IsIdentifiableSourceVersion` 只拒绝空字符串和 `unknown`，不验证该值是否为 Provider 数据版本。
   - DailyBars Service 要求一次 Provider 响应中的所有 Bars 使用同一个 SourceVersion，且不会混合不同 Provider 的行；这可作为查询批次来源身份，但不能把 Adapter 版本升级为数据版本。
   - v2 必须区分 `adapter_version` / `normalization_version` 与可选的 `provider_data_version`。上游没有提供可验证数据版本时必须显式缺失，不得将 adapter 常量或 fetched_at 填入。

5. **交易日历不可变版本资源（历史缺口，已在本分支补齐）。**
   - 初始审计时仅发现 Redis 12 小时缓存；后续已增加 Migration V5 与 MariaDB 不可变日历 Snapshot Repository，使用 SHA-256 内容寻址、不可覆盖写入、精确读取和内容校验，详见本文 1.1 之后的实现验收记录。
   - `DataService.TradingCalendar` 在 Provider 获取和 Redis Cache 命中路径均持久化日历内容版本；`TradingCalendarAsOf` 只从 Repository 读取截止时点前已观察的版本，不访问当前 Cache 或实时 Provider。
   - 当前 `TradingCalendarSnapshot.SourceVersion` 仍是 Provider/Adapter 版本，与独立的 `CalendarRef` 内容身份分开；多 Provider 内容冲突、非交易日推断等质量事实继续保留。
   - 尚未完成的是：DailyBars coverage 评估实际使用的同一 `CalendarRef` 尚未传播到 DailyBars v2 Snapshot Header。不得在评估后通过第二次日历查询补造引用。

6. **DATA-CTR-008 Manifest 不能单独代表 Payload。**
   - 已冻结的 Manifest Schema 1.0.0 目前只包含 caller/purpose、证券、日期范围、复权、system_as_of 和 sources 等元数据。
   - Schema 没有行情 Payload 字段，也没有 Payload Schema/内容指纹字段。
   - DEC-PLAT-002-020 要求 Snapshot 身份绑定不可变行情内容；Research Evidence 的 source/version/locator 还必须分别指向 Snapshot、可验证 Provider 数据版本和具体记录定位。

结论：DATA-CTR-005 的 v2 精度保真 DTO、interval/交易日历元数据是 DATA-CTR-007 的前置；DATA-CTR-007 再提供不可变 Payload、Manifest 绑定和授权读取。QNT-CTR-003 Factor 依赖这两个能力，不能先做生产 Factor Stage。

## 2. 推荐的目标边界

### 2.1 DATA-CTR-005：DailyBars v2

保持现有 v1 HTTP/Application DTO，不做静默改型。新增版本化的 v2 DTO，统一以规范化十进制字符串表达精确数值：

- OHLC、Amount、ChangePercent、移动均线等数值字段使用 Decimal String；Volume 使用整数 shares。
- 字符串必须是规范化十进制格式，不允许指数形式、NaN、Infinity、前导加号或无意义前导零；负零归一化规则明确。
- 不设全项目统一 scale。每个字段定义单位、允许 scale/范围、来源保真规则和缺失语义；没有来源精度证据时标记 unknown/degraded，不补位、不舍入伪造精度。
- Provider Adapter 在首次解析时保留原始十进制词法值：字符串响应直接按十进制解析；JSON number 使用保留原始 number token 的解码方式。不得先转 float64 再转字符串。
- 现有 float64 v1 由同一内部权威值投影生成；v1 投影允许按既有行为输出，但不能反向成为 v2 的数据来源。
- DTO 显式包含 interval（首批只允许已验证的 `1d`）、交易日历不可变版本引用、adjustment_basis、adjustment_method/reference_date、source/source_version、provider_time（仅来源明确支持时）、fetched_at、system_observed_at、quality_status 和 reasons。
- 交易日历版本必须来自 Data 自己已持久化、可精确读取的日历版本；缺失时明确 unknown，不能用当前日历版本覆盖历史事实。
- Quant 对具体指标的样本连续性、停牌、缺失和精度误差策略仍由 Quant Registry 决定；Data 只提供事实。

### 2.2 DATA-CTR-007：不可变 Snapshot Payload

采用 Data-owned 的单一 Snapshot 资源，不建设通用文件/对象存储平台：

1. 以一次明确查询为边界，物化一个证券、一个 interval、一个日期范围、一个 adjustment basis/reference 和一个 system_as_of 的完整结果。
2. Payload 包含 Payload Schema 版本、查询边界、v2 Bars、交易日历版本、每条记录的来源/版本/观察时间/质量和完整性信息；按交易日升序、字段规范化后生成 canonical JSON。
3. Payload fingerprint = SHA-256(JCS(canonical payload))。同一 Payload fingerprint 必须对应字节语义完全相同的内容；相同身份不同内容不得覆盖。
4. Manifest 继续复用 DATA-CTR-008 已冻结的职责和字段，不把行情正文塞进 Manifest。Manifest fingerprint 独立计算。
5. SnapshotRef 必须绑定 Manifest 与 Payload 两者，而不能仅由 Manifest 元数据计算。建议定义为对 `manifest_fingerprint + payload_fingerprint` 的规范化组合计算 SHA-256；具体公式写入 DATA-CTR-007 新版契约和 Golden。现有 DATA-CTR-008 Golden 中两个 fingerprint 暂时相等只是旧样例，不能被误当成 Payload 已被绑定的实现证据。
6. Snapshot 读取按不透明 SnapshotRef 精确定位，重新校验 Manifest/Payload 指纹和请求主体；内容寻址不替代授权。
7. 每次受保护读取由 Data 复核当前策略。AuthorizationRef.resource_ref 精确绑定 SnapshotRef；Manifest.caller_ref 与 AuthorizationRef.subject_ref 完全一致，主体必须来自 Server 可信 Principal Context，不能来自请求体或 API Key。
8. Snapshot 只保存本次研究需要的行情和追溯元数据，不复制 Provider 全库；保留策略必须覆盖引用它的 Run deadline、重试、恢复和审计需要，具体 TTL 由部署/业务保留策略提供，不在代码里硬编码猜测值。

### 2.3 Research Evidence 映射

- `source_owner=data`。
- `source_ref` 指向不可变 SnapshotRef。
- `source_locator` 指向 Payload 内精确证券、交易日和记录/字段范围。
- `source_version` 只填可由对应记录证明的 Provider 数据版本；没有 Provider 版本时显式缺失。一个 Evidence locator 跨越多个 Provider 版本时，不得任选一个版本冒充整体版本；应按来源版本拆分 Evidence 或在契约中定义可验证的组合版本引用。
- `authorization_ref` 由 Data 签发，Research 每次消费仍需通过 Data Owner 当前授权复核。
- Research 不解析 Data SQL、不复制 Data Model、不自行拼接 SnapshotRef；Researchflow 通过公开 Application Port 组合输入。

## 3. 不应采用的方案

- 不将当前 float64 用 `FormatFloat` 转字符串后称为 Decimal v2。
- 不直接把 `Bundle.snapshot_id`、查询 Request ID、数据库主键或 revision hash 当 SnapshotRef。
- 不仅对 Manifest 元数据做 Hash，却声称 Snapshot Payload 已被内容寻址。
- 不把 `FetchedAt`、`SystemObservedAt` 或当前 Provider 时间写成 `AvailableAt`。
- 不把数据库 DECIMAL(20,8)/DECIMAL(24,2) 的列 scale 当成所有 Provider 源端精度证明。
- 不由 Quant 实现 Data Snapshot/交易日历，不由 Research 自己读取 Data Repository。
- 不在 DATA-CTR-005/007 仍 deferred 时开放 QNT-CTR-003 Factor 生产输入。

## 7. DATA-CTR-008 Manifest 1.0.0 与 DEC-PLAT-002-020 的语义冲突

本轮进一步核对了已冻结的 DATA-CTR-008 Manifest Schema 1.0.0 和 Golden：

- 1.0.0 的 `sources[].source_version` 是必填非空字符串；现有 Golden 将 `2026-11-06T04:59:58Z`（采集时间）写入该字段。
- DEC-PLAT-002-020 明确要求 Evidence 的 version 表达可获得的 Provider 数据版本；没有 Provider 数据版本时必须显式缺失。Adapter/接口版本和 fetched_at 都不能替代 Provider 数据版本。
- 1.0.0 没有独立的 `adapter_version` / `normalization_version`，也没有 `payload_schema_version`、`payload_fingerprint`、`interval` 和 `trading_calendar_ref`。因此当前 Golden 不足以证明 Manifest 与行情 Payload 绑定，也无法完整表达 Quant 所需的日历版本。
- DATA-CTR-008 1.0.0 已冻结，本方案不修改其 Schema/Golden。建议新增版本化 1.1.0：`source_version` 保持必填但允许显式 null；新增必填 `adapter_version`、`normalization_version`、`payload_schema_version`、`payload_fingerprint`、`interval`；新增显式 nullable `trading_calendar_ref`；Manifest fingerprint 必须覆盖 payload_fingerprint，SnapshotRef 由该 Manifest fingerprint 派生。这样保留 1.0.0 历史兼容，同时满足 DEC-020 的来源版本语义和不可变内容寻址。
- 1.1.0 仍需通过项目级契约评审后才能冻结；在此之前不让 Research/Quant 消费旧 Golden 中的时间戳 source_version。


## 8. D2 交易日历不可变资源实现（repair_all）

- 已在 Data Repository 增加 Migration V5 表 `market_data_trading_calendar_snapshots`，保存规范化日历内容、内容指纹、source/adapter_version、质量、首次 fetched_at 和 system observed_at。
- `CalendarRef` 为 `data_calendar:sha256:<fingerprint>`；指纹覆盖日期区间、逐日交易事实、来源、Adapter 版本和质量证据，不覆盖重复抓取时间。相同内容重复抓取复用同一 Ref 和首次观察时间；内容/来源版本/质量变化生成新 Ref。
- `SaveTradingCalendarSnapshot` 使用不可覆盖的插入语义；`GetTradingCalendarSnapshot` 精确读取并重新计算校验指纹。物理 Schema 检查已并入 `ValidateCompatibilitySchema`，用于发现 Migration checksum 之外的手工漂移。

### 1.3 跨 Provider 共性事实

- 默认启用的 7 个 DailyBars Provider 在当前 `FetchDailyBars` 构造中均写入本地 `FetchedAt` 和静态 `SourceVersion`；本轮没有发现任何一个默认 Provider 为 DailyBar 填充 `ProviderTime`。因此 fetched_at 只能表达本系统请求/接收时间，不能冒充源端发布时间。
- 所有 Provider 的 `SourceVersion` 当前用于标识 Adapter/API/协议版本，不是某证券某交易日的上游数据修订版本。Evidence 的 provider_data_version 必须独立表达；没有来源版本时为 null。
- `model.DailyBar.RawVolume` / `RawAmount` 当前仍是 `*float64`，名字中的 Raw 不代表原始十进制词法值；现有数据库 revision metadata 不能恢复已经丢失的 token。
- Data DailyBars Service 每次选择一个 Provider 的完整结果，不在一个返回批次内混合多个 Provider；Snapshot sources 应保留这个单一来源边界。未来如允许合并，必须改变 Snapshot 的来源版本映射契约，不得静默混合。
- 当前配置默认 `adjustment_basis=forward_adjusted`。Snapshot 身份必须绑定 adjustment_basis、具体 adjustment_method 和 reference_date；不能只记录“前复权”标签。

**D1 全量范围结论：** 10 个 Provider 均已在至少部分请求路径生成 `DailyBarExactValues` sidecar；默认启用的 7 个来源覆盖 Eastmoney、BaoStock、Tencent、Sina、Netease、TickFlow、Pytdx。可配置的 Hithink 也从 JSON RawMessage 生成 sidecar；Tushare 仅在 none 复权路径生成，QFQ/HFQ 调整后目前没有精确值 sidecar；Yahoo 仅 none 路径生成，QFQ/HFQ 经 float64 因子计算后没有精确值 sidecar。现有 v1 `RawVolume/RawAmount` 仍是 float64 兼容字段。所有默认来源均缺 ProviderTime/逐行数据修订版本，因此 v2 必须显式缺失并依赖 Data 的 system_observed_at、adapter/normalization version、内容指纹和质量信息，不得伪造。


Pytdx 数值表示依据：`github.com/injoyai/tdx v0.0.86` 的 [protocol 文档](https://pkg.go.dev/github.com/injoyai/tdx/protocol) 定义 `Price` 为 int64、单位厘，并提供 `Int64()` / `String()`。因此不需要 fork 依赖；Data Adapter 应直接保留该定点值/十进制字符串，避免调用 Float64() 后再格式化。Amount 的单位语义仍需独立确认，不能仅因复用 Price 类型就推断成交额单位。


### 1.4 精确值 sidecar 的真实调用链核验（2026-11-19）

### 1.5 精确值 sidecar 的边界与未关闭证据（2026-11-19）

## 2.4 D2 DailyBars v2 字段级设计草案（未冻结）

本节只作为 Data 内部设计审查输入，不修改项目级契约登记簿，不代表 DATA-CTR-005 已重新进入冻结审查。

### 2.4.1 DTO 边界

建议将 v2 分为 Snapshot Header 与 Bar Record，避免把区间级事实重复写入每一条 Bar：

- Snapshot Header：schema_version、symbol、interval、adjustment_basis、adjustment_method、adjustment_reference_date、可选 provider_snapshot_time、trading_calendar_ref、system_observed_at_cutoff、quality_status、quality_reasons、warnings、bars。provider_snapshot_time 仅表达 Provider 响应级数据就绪/快照时间，不得复制成每根 Bar 的 provider_time。
- Bar Record：trade_date、is_partial、OHLC、volume_shares、amount_cny、change_percent、source provenance、precision evidence、quality_status/reasons。
- interval 首批只允许 1d；不能从 period 字符串之外推断其他周期。
- trading_calendar_ref 必须是 Data 实际用于该次交易日缺失/连续性判断的不可变 CalendarRef；若没有可验证引用则显式 null/unknown，不能在 Snapshot 生成后再查询当前日历替代。
- Snapshot Header 不包含 SnapshotRef/AuthorizationRef 的临时占位字段；它们属于 DATA-CTR-007 的资源身份和授权边界。

### 2.4.2 字段映射与精度语义

| v2 字段 | 当前权威来源 | v2 表达草案 | 当前缺口/约束 |
|---|---|---|---|
| symbol / trade_date | Data Model | canonical symbol / YYYY-MM-DD | 交易日按 Asia/Shanghai 市场日历解释 |
| interval | 当前 Bar Period 与查询用例 | enum/string，首批固定 1d | 当前 Application Snapshot 未显式暴露 interval |

| quality_status / reasons | Data Validator / Normalizer | closed enum + stable reason codes | 保留来源缺失、单位推断、停牌/缺数、复权不确定等事实 |

### 2.4.3 精度证据与原始值保留

- v2 数值字段使用 canonical Decimal String 表达数学数值；这不等于供应商合同精度。每个字段还需要独立的 precision evidence，至少区分 provider_contract、observed_token、protocol_fixed_scale、unknown。
- observed token 的小数位数只证明本次响应 token 的表示，不证明供应商承诺的最大精度或舍入规则。协议固定 scale（如 TDX Price 的厘）可按协议证据记录。
- 若需保留原始 lexical scale，必须保留原 token 或明确的 source_fraction_digits；不能从 canonical value 反向推断尾随零。
- raw_source_values 只用于追溯：raw_volume + raw_volume_unit、raw_amount + raw_amount_unit + raw_amount_field；消费者使用规范化后的 volume_shares / amount_cny。单位未知时保留原值但规范化字段置 null/degraded。
- ChangePercent 必须显式记录 origin（provider / derived / unavailable）。derived 只能使用可验证的 Decimal 输入和冻结公式；不得从 float64 格式化成字符串。
- MA5/MA20/MA120/MA250 不属于 Data v2 原始行情事实，继续由 Quant Registry/算法拥有。

### 2.4.4 复权与交易日历约束

- OHLC Decimal 必须是请求复权口径下最终输出值；同时绑定 adjustment_basis、adjustment_method，以及与该方法匹配的 reference semantics。日期锚定方法必须提供 reference_date；明确的 Provider 累积因子方法可以没有显式 reference_date，但必须有可验证的固定锚点/累计口径说明，不能把空值默认为已知。
- RawVolume/RawAmount 仍表示单位归一化前的来源值；不得因为 OHLC 已复权就把原始成交量/额误标为复权值。
- Eastmoney/BaoStock/Tencent/Sina/Netease/TickFlow/Pytdx 的默认路径已有 ExactValues；Tushare/Yahoo 的 QFQ/HFQ 目前缺精确调整结果，必须先补精确计算或明确 v2 不支持对应路径，不能投影 float64。
- Data 已有独立不可变 CalendarRef Repository，但 DailyBars 质量评估当前没有将实际使用的 CalendarRef 传播到 Application Snapshot。D2 必须由同一次 DailyBars 评估返回该引用，不能通过二次独立查询取得近似版本。
- CalendarRef 缺失、日历质量 degraded 或交易日连续性无法确认时，Data 保留明确质量状态；Quant 对依赖完整连续交易日的 Factor 必须拒绝或映射 unknown/insufficient_data，不能自行推断日历。

### 2.4.5 设计审查与 Golden 验收范围

1. 默认 7 个 Provider 的 none/支持的 QFQ/HFQ Golden；Tushare/Yahoo 可配置路径的复权精度限制单独列出。

### 2.4.7 CalendarRef 同一性传播：D2 实施决策（未冻结）

代码复核确认，当前 `dailyBarCoverageSufficient` / `dailyBarCoverageSufficientAsOf` 只返回通过与否及 warnings，实际读取的 Calendar Snapshot 与 `CalendarRef` 被丢弃。Application Reader 因此无法证明 Snapshot Header 中的日历引用就是质量评估实际使用的版本。

D2 实施时按以下边界改造，禁止二次查询补引用：

1. 将 coverage helper 的内部返回值收敛为一个 `DailyBarCoverageEvidence`，至少包含 `calendar_ref`（nullable）、`calendar_quality_status`、`expected_trading_days`、`minimum_required_bars`、`coverage_basis`（exchange_calendar / weekday_estimate）、`coverage_sufficient` 和 warnings。

### 2.4.15 复权 reference date 与累积因子锚点边界（2026-11-23，待契约审查）

## 2026-11-23 RepairAll 最新代码审计基线（优先于本文早期 D1 盘点）

> 本节是当前代码事实的权威更新。本文第 1 节中“DailyBar OHLC 只剩 float64”“没有精确值 Sidecar”等初始审计描述属于历史基线，不能再直接用于判断当前代码；以本节和对应 Data 卡点文档为准。

### 已确认的现有能力

1. **单 Bar 版本历史已经能保存精确值。** `market_data_daily_bar_versions.metadata` 通过 `marshalDailyBarMetadata` 保存 `DailyBarExactValues` sidecar；`dailyBarRevisionHash` 基于完整 `dailyBarMetadata` 计算，覆盖 ExactValues、来源、复权、质量等内容，仅排除 fetched_at、normalized_at、system_observed_at。current/PIT 读取路径可以恢复 sidecar。不得再规划第二套逐 Bar 版本存储。
2. **单 Bar revision 不是整次查询 Snapshot。** `market_data_daily_bars` 是可更新当前视图；`ListBarsAsOf` 读取各来源/日期的历史修订，再由 Service 选择来源一致的序列。它没有一次查询结果级的内容寻址入口，也没有将该次 Bars、CoverageEvidence、同次 CalendarRef 和 Manifest 绑定成不可变资源。因此不得把 revision_hash、数据库主键或 Bundle.snapshot_id 当 SnapshotRef。
3. **交易日历 Snapshot 已完成。** Migration V5 的 `market_data_trading_calendar_snapshots` 已有内容寻址、幂等不可覆盖写入、精确读取、读取时重算摘要和篡改拒绝。DailyBars Snapshot 只需复用该 Repository 模式，增加整次查询结果级记录，不重复实现 Calendar。
4. **首个 SMA 的精确输入可以收窄。** 默认 Provider 优先级首位 Eastmoney；OHLC ExactValues 从原始 CSV 字段字符串构造，CloseEvidence 保留 observed token 和 source fraction digits。首个用例可限定 `adjustment_basis=none`，只将精确 Close 字符串作为指标输入，禁止从 float64 反向生成 Decimal。BaoStock/Tushare/Netease/TickFlow 也存在原始字符串或 JSON number token 路径；Pytdx 的 Price.Int64 + ProtocolScale 是协议定点表示，不得误称原始词法精度。
5. **来源版本必须分层。** Provider `SourceVersion` 当前是 Adapter/API/协议版本常量，不是逐 Bar 上游数据修订版本；默认 Eastmoney 日线没有逐 Bar ProviderTime/provider_data_version。DEC-PLAT-002-020 明确 Research Evidence 的 version 只表示可获得的 Provider 数据版本，不存在时显式缺失。Adapter 版本和 FetchedAt 均不得冒充。
6. **发现冻结契约的真实冲突。** DATA-CTR-008 1.0.0 Schema 将 `sources[].source_version` 列为 required 且要求非空字符串；其 Golden 示例填了时间戳。该字段无法表达当前 Provider 无数据版本的真实情况，与 DEC-PLAT-002-020 决议冲突。不得修改 1.0.0 Schema/Golden，也不得在生产中用 Adapter 常量、FetchedAt 或任意占位字符串绕过。
7. **Snapshot 身份边界。** PayloadFingerprint = SHA-256(JCS(canonical Payload))；ManifestFingerprint 独立计算；SnapshotRef 必须绑定两者，对二者的规范化组合计算 SHA-256。DATA-CTR-008 旧 Golden 中两个 fingerprint 相等只反映旧 Manifest-only 示例，不证明 Payload 已纳入身份。具体算法归 DATA-CTR-007 新版契约与 Golden 定义。

### 当前实现决策与准入门槛

- 不新增逐 Bar 版本表；只新增整次 DailyBars 查询的不可变 Snapshot 记录。
- Payload 首期仅包含 SMA 所需的精确 Close/OHLC、交易日/interval/复权口径、同次 CalendarRef/CoverageEvidence、来源身份、可证明的 Adapter/标准化版本、可选 Provider 数据版本、采集/系统观察时间和质量事实。

- 下一个执行项：形成 DATA-CTR-008 来源版本字段的版本演进决议和 DATA-CTR-007 SnapshotRef/Manifest/Payload 的明确版本方案；确认生产方、Research/Quant 消费者、Schema/Golden 与 GOV-CTR-006 resource_ref 影响后，再进入代码实现。


## 2026-11-23 DEC-PLAT-002-055：来源版本冲突的正式裁决
