## 1. 总体目标

完成国内 A 股数据服务的 Go 原生化和可验证交付，使数据能力不仅“代码存在”，还具备可解释的数据质量、明确的时间与单位语义、可追溯的 Provider 来源、稳定的持久化行为和可重复的真实环境验收证据。

最终交付必须满足：

1. 国内 A 股主要数据域的服务能力和 Provider 能力边界明确。
2. 数据标准化不伪造缺失值、不混淆单位、复权口径和时间语义。
3. 统一诊断体系能够发现并结构化呈现数据问题，且不重复建设已有框架。
4. 财务、估值、公司行动、历史成分等时点数据满足可证明的 PIT 约束；不能证明时明确降级或标记未知。
5. API、数据库、Provider 原始响应和标准化结果之间可追溯、可对账。
6. 通过代码测试、真实 Provider 请求和部署验收分别提供证据，不互相替代。

## 5. 统一状态定义

所有阶段和子任务只使用以下状态：

- `未开始`：尚未核对或实施。
- `进行中`：已有明确执行批次，尚未达到完成标准。
- `代码完成`：实现和对应自动化测试已提交；不代表真实 Provider 或部署通过。
- `CI通过`：指定 SHA 的相关工作流全部完成且通过；必须记录 SHA 和 Run。
- `真实验收通过`：真实 Provider/数据库/部署环境按验收标准执行并留有证据。
- `降级可接受`：存在已知缺失或限制，但符合明确契约并有原因记录。
- `阻塞`：缺少权限、凭据、环境或外部能力，写明解除条件。
- `不支持`：Provider/数据源明确不具备该能力，不等同于失败。
- `未执行`：没有实际执行证据，不得推断为通过。

## 15. 2026-11-04 DailyBar 交易上下文复用核查

本节为当前代码静态核查，不代表新增实现或真实 Provider 验收。

### 15.1 已有能力

- `TradingCalendar`：`DataService.TradingCalendar` 会校验完整自然日覆盖、日期连续性、交易日数量、来源/版本和 fetched_at；多个日历 Provider 结果冲突时降级，不会把缺失日期自动补成交易日。

- `DataService.SecurityTradingStatus`：按证券和交易日查询 Provider，并验证证券身份、有效名称区间、交易日/停牌状态、上市日期等字段；可保存历史修订，另有严格的 `SecurityTradingStatusAsOf` 只读历史接口。

### 15.2 当前缺口与结论

- DailyBar Probe 目前调用 `FetchDailyBars(symbol, "", "", 5, adjustment)`，对返回数据执行通用字段/日期/复权/质量校验；它不请求固定日期窗口，也没有逐日核对日历应有交易日。
- SecurityTradingStatus Probe 使用当前上海日期的样本日，与 DailyBar 返回的最近 5 条记录并非同一日期集合。因此即使三个独立能力都成功，也不能证明“无 K 线”是非交易日、停牌、新股上市前，还是 Provider 漏数。
- Tushare 状态实现本身是严格降级的：缺少有效历史名称、ST 权威名单、停牌证据或上市交易日计数时返回 unknown/degraded；不能把这些 unknown 当成正常交易状态。
- 当前可复用的数据模型和服务已存在，但“逐日关联判断”尚未实现。不能在通用 Validator 中仅凭空 K 线推断停牌或 Provider 漏数。

### 15.3 下一批建议（编码前需确认）

建议采用最小闭环，而不是新增平行 API 或重写 Provider：
1. 将 DailyBar Probe 的样本窗口改为可确定的最近 N 个自然日/交易日范围，保留每个 Provider 原始返回日期集合。
2. 对该窗口读取完整交易日历，并按证券读取对应交易日的历史交易状态；对没有交易日状态的日期，明确区分非交易日与状态 unknown。
3. 仅对“已确认交易日、证券已上市、非停牌/已复牌且日 K 缺失”的日期计入可比较缺口；停牌、上市前、非交易日、状态 unknown 分别记录为排除项或不可比较项。
4. Provider 漏数的判定必须要求日历和证券状态上下文均可信；上下文缺失时返回 unknown/not_comparable，不得判 failed 或补造数据。
5. 增加确定性单测覆盖正常交易、停牌、上市前、新股首日、非交易日、日历缺失、状态未知、Provider 漏数及多个 Provider 覆盖差异。

## 19. 跨 Provider 复权基准信息丢失风险（2026-11-04）

### 19.1 代码核验发现

对当前 HEAD `88eac9e70bb77dd02d05ed868daf9d6ca41dffa5` 的跨 Provider 日 K 比较链路进行只读审查，发现：

1. Provider 返回的 `model.DailyBar` 已包含 `AdjustmentBasis`、`AdjustmentMethod`、`AdjustmentRefDate`。
2. `DataService.ProbeProviderCapabilitiesWithOptions` 构造 `CrossProviderDailySnapshot` 时，只复制 `AdjustmentBasis`，没有复制每根 K 线的 `AdjustmentMethod` 和 `AdjustmentRefDate`。
3. `CrossProviderDailySnapshot` 本身也没有复权方法/参考日字段。
4. `CompareCrossProviderDailyBars` 只比较 `AdjustmentBasis` 是否相同；同为 `backward` 的两个样本即使一个按请求起点重基准、另一个为累计后复权，也会继续进入 OHLC 比较。
5. `buildCrossProviderProbeCheckResults` 还会在进入比较器前按相同 `AdjustmentBasis` 配对，不能识别参考基准不一致。

现有比较器测试的 matched 样例均为 none 口径；没有覆盖相同 adjustment enum、不同 reference semantics 的反例。因此目前的自动化测试没有证明 HFQ/QFQ 比较安全。

### 19.2 风险判定

这是比较链路的真实设计缺口，不是 Provider 返回数据错误，也不是已经证实发生过的错误 matched 记录。当前已归档的 HFQ 样本均未形成严格 matched；在修复前，不应将 Probe 中任何 adjusted matched 结论当作有效验收证据。

### 19.3 修复方案（待实现）

- 扩展比较快照，保留来源 K 线的 `AdjustmentMethod` 与 `AdjustmentRefDate`，并检查同一快照内部这些元数据是否一致。
- 比较器对 none 口径维持现有路径；对 qfq/hfq 增加复权基准门禁。只有双方能够证明参考基准兼容时才进入 OHLC 数值比较；未知基准返回 `not_comparable`，不得按 enum 相同放行。
- 服务层配对逻辑必须使用同一套可比较性判定，不得在调用比较器前因 adjustment enum 相同而丢弃基准差异。
- Probe 结果应保留双方复权方法/参考日和不可比较原因，便于诊断和历史审计。
- 增加回归测试：相同 enum、不同参考日；一侧未知参考日；请求起点重基准对累计 HFQ；快照内部方法/参考日不一致；none 口径兼容性不回退。
- 在元数据链路修复并完成 CI 前，adjusted cross-provider matched 结果不得作为验收依据。

### 19.4 对账策略边界

可研究将各 Provider 价格序列按共同锚点归一化后比较相对走势，但这只能作为单独的相对收益/形态比较指标，不能代替绝对价格基准验证；只有在确认不同源之间仅存在固定乘数差异、而非加法调整或算法差异后才可启用。不得通过简单缩放把当前 600036.SH 的样本差异强行变成 matched。

当前阶段 B 增加一项 P0：修复复权基准元数据在 Probe 比较链路中的丢失和误放行风险。该项完成前，真实 HFQ 数值对账保持暂停；不修改 Provider 转换算法。


## 2026-11-04 阶段 B：复权基准比较门禁实施记录

本轮针对跨 Provider 日 K 对账的复权口径误放行风险，实施保守门禁：

- `none`（不复权）继续沿用既有比较路径，不要求复权元数据。
- `forward_adjusted` / `backward_adjusted` 必须逐根 K 线提供非空 `AdjustmentMethod` 与 `AdjustmentRefDate`。
- 同一 Provider 快照内所有 K 线的 method/refdate 必须一致；缺失或行间不一致时，结果为 `not_comparable`。
- 两侧复权 method 与 reference date 必须完全一致，才允许进入 OHLC/成交量/成交额数值比较。仅 `AdjustmentBasis` 相同不再构成可比证据。
- Probe 结果保留左右 Provider 的 method/refdate，便于解释被跳过的比较。
- 服务层仍按同证券、同复权枚举配对；比较器统一执行基准门禁，避免服务层与比较器各自采用不同标准。

当前规则有意偏保守：不同 Provider 的方法标识不同，即使其算法可能在经济含义上等价，也会被标记为不可比较。后续如需放宽，必须先建立有来源证据和回归样例的跨 Provider 基准映射；不得直接按 method 名称猜测语义，也不得用共同日期归一化替代绝对基准证明。

本规则仅防止错误 matched，不代表已经证明各 Provider 的复权值彼此正确。真实 Provider 样本仍需分别记录来源算法、参考日期、因子来源及数据质量。CI 通过仅代表代码测试通过，不替代真实数据验收。
