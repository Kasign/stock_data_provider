## 1. 状态定义

| 标记 | 含义 |
|---|---|
| 已实现 | 当前 `ValidateQuote` 或 `ValidateAndSortBars` 明确执行 |
| 部分实现 | 有基础检查，但缺少字段级问题、上下文或完整语义 |
| 未覆盖（本函数） | 这两个函数未校验；不代表其他模块一定没有校验 |
| 待确认 | 必须结合 Provider 契约、调用点或业务场景确定 |

严重级别建议：error 表示违反明确字段契约；warning 表示数据可用但质量降级；info 表示 Provider 不支持或仅提示。严重级别不能仅根据当前函数“丢弃记录”这一实现动作机械推断。

## 2. Quote 字段规则

| 字段 | 当前规则 | 当前状态 | 目标规则 / 迁移关注点 |
|---|---|---|---|
| symbol | 必填；必须是规范六位 A 股代码及交易所后缀 | 已实现 | required + 证券主数据校验；保留 BJ 等市场规则 |
| source | 必填 | 已实现 | required；Provider 标识应来自适配器注册信息 |
| quality_status | valid/degraded/stale/unknown；invalid/未知值拒绝 | 已实现 | invalid_enum；缺失和来源质量状态分开诊断 |
| adjustment_basis | none/forward/backward/unknown | 已实现 | invalid_enum；Quote 是否允许 unknown 需按接口契约确认 |
| current_price | 必填、有限且 > 0 | 已实现 | required + invalid_number + out_of_range；停牌/无成交快照条件待确认 |
| open | 必填、有限且 > 0 | 已实现 | 同上；盘中/停牌状态下的可用性需确认 |
| high | 必填、有限且 > 0 | 已实现 | 同上；OHLC 关系单独规则 |
| low | 必填、有限且 > 0 | 已实现 | 同上 |
| prev_close | 必填、有限且 > 0 | 已实现 | 新股首日、特殊无昨收场景需条件化 |
| change | 可缺失；存在时有限；与 current_price-prev_close 误差不超过 0.02 CNY | 已实现 | invalid_number + derived_consistency；容差按源端精度配置 |
| change_percent | 可缺失；存在时有限；与计算值误差不超过 0.15 个百分点 | 已实现 | invalid_number + derived_consistency；明确百分点单位和精度 |
| volume | 必须存在且非负 | 已实现 | required / conditional 需结合停牌和快照状态；单位统一 shares |
| amount | 可缺失；存在时有限且非负 | 已实现 | optional 或 conditional；缺失必须保留 NULL |
| amount_unit | amount 存在时必须 CNY；amount 缺失时当前函数改成 unknown | 已实现 | unit_mismatch；纯 Validator 不修改字段 |
| volume_unit | 必须为 shares | 已实现 | unit_mismatch；Provider 原始单位在 Adapter/Normalize 转换 |
| volume_ratio | 可缺失；存在时有限且非负 | 已实现 | out_of_range；定义负值和特殊状态边界 |
| turnover_rate | 可缺失；存在时有限且非负 | 已实现 | out_of_range；明确百分比单位 |
| OHLC 关系 | low<=high；open/current_price 位于 low/high 区间 | 已实现 | ohlc_relationship；是否需要按停牌/盘中状态调整待确认 |
| amount/volume | 不允许一正一零；两者为正时隐含均价需在 low×0.5 到 high×2 | 已实现 | unit_mismatch / cross_field_consistency；容差与场景需要有明确证据 |

| amount_unit | amount 存在时必须 CNY；缺失时当前函数改为 unknown | 已实现 | unit_mismatch；纯 Validator 不修改字段 |

## 4. 必须补充的 A 股上下文

| 场景 | 规则影响 | 当前状态 |
|---|---|---|
| 停牌 | 允许无成交或成交量为零；价格和时间字段应结合停牌状态解释 | 待确认 |
| 新股上市首日 | 可能没有常规 prev_close；涨跌幅限制也可能不同 | 待确认 |
| 除权除息 | 前收盘价、涨跌幅和复权序列可能有特殊口径 | 待确认 |
| 非交易日 | 快照可能是上一交易日；不能仅凭日期较旧判 invalid | 待确认 |
| 盘中行情 | quote 字段可能更新时间不完全同步，需设置派生字段容差 | 待确认 |
| 复权日 K | 成交额/成交量通常保持未复权基础，不能与复权 OHLC 直接做均价量级比较 | 部分实现 |
| 北交所 | 代码格式、Provider 支持和单位可能与沪深不同 | 需按 Provider 能力策略区分 |

上述场景需要明确的交易日历、证券上市状态、停复牌或特殊交易事件上下文。缺少上下文时，不得猜测为正常交易，也不应把不确定情况直接判为硬错误。

| 文件 | 调用位置 | 当前作用 |

### 8.3 原始响应解析方式

| Provider | Quote 原始解析 | DailyBar 原始解析 | 字段问题丢失点 |
|---|---|---|---|
| NetEase | JSONP 解包后反序列化到结构体；数值字段使用 `json.RawMessage`，逐字段调用 `parseNeteaseNumber` | CSV/历史响应解析后构造 DailyBar，再进入公共 helper | 解析错误多被转换为通用文案；实际 RawMessage 未进入统一问题模型 |
| Sina | 文本 CSV/逗号分隔字段，按固定索引解析，必填解析器有字段名 | JSON 数值字段使用 `json.RawMessage`，逐行解析；解析失败只累计 rejectedRows | Quote 错误未保留实际值；DailyBar 只保留被拒数量 |
| Tencent | CSV 字段按索引读取，错误常只带字段索引 | JSON `[][]json.RawMessage`，前六列允许 string 或 number；对象等其他类型只增加 rejectedRows | 不支持的类型未保留字段索引、原始类型和行号 |
| Yahoo | JSON 反序列化到静态结构体；部分必填价格为非指针 float64 | OHLCV 数组使用指针，NULL 可识别；非预期 JSON 类型通常导致整体 Decode 失败 | Quote 非指针数值的缺失/null 可能表现为零值；整体 Decode 错误未转成字段级问题 |

`decodeSingleJSON` 使用 `UseNumber` 并拒绝尾随 JSON 内容，这是有价值的通用边界，但它本身不会自动生成字段路径级问题。

### 8.4 对新架构的直接影响

1. 字段问题必须在 Adapter 原始解析阶段和公共 Validator 阶段分别捕获；前者负责类型/解析错误，后者负责标准化模型的字段契约和业务关系。
2. DailyBar 的结构化问题必须在记录被过滤之前生成，否则 Probe 无法找回无效行。
3. 不能只在 Probe 再跑一次 Validator。Probe 应消费 Provider 采集过程中产生的校验报告；兼容期对尚未提供报告的旧 Provider 才使用受控 fallback。
4. 建议使用请求级、上下文隔离的 Validation Reporter 传递本次 Provider 调用的结果，避免全局状态和跨 Provider 串扰。Reporter 不持久化、不发网络请求；Probe 负责汇总。
5. `normalizeProviderDailyBars` 需要接收 context 或显式 report sink，并把每条记录的 row_index、symbol、trade_date 和问题保留下来；公共接口不应继续只返回字符串 warning。
6. Quote Adapter 的兼容期旧校验入口应包装新 Validator，但不应让 Probe 和 Adapter 各自维护规则副本。

### 10.2 已有 A 股场景上下文能力

当前代码已有可复用的来源证据服务，不需要在 Validator 内部访问 Provider 或数据库：

- `TradingCalendar`：交易日状态。
- `SecurityTradingStatus`：按证券和日期提供历史交易状态，包含交易日已知状态、停牌状态、上市日期/上市交易日序号、风险警示状态、退市状态及来源质量。
- `ResolvePriceLimitRuleFromTradingStatus`：组合历史证券状态与特殊涨跌幅事件证据。
- `PriceLimitEventEvidence`：按证券/日期提供特殊无涨跌幅限制事件及来源、覆盖区间和观察时间。
- `MarketSession`：按交易日历和时刻计算竞价/连续交易/午休等时段；其注释明确不覆盖证券级停牌和临时交易所公告。

这些能力应在调用方预先取得后，以不可变、最小化的上下文快照传入 Validator。Validator 不应自己发起这些查询，否则会引入网络、数据库依赖和难以复现的隐式行为。

建议上下文只包含规则真正需要的字段，例如：
- trade_date、market_session；
- trading_day_known、is_trading_day；
- suspension_status；
- listing_status_known、listing_trading_day_number；
- risk_warning_status、delisting_status；
- price_limit_exception_status；
- adjustment_basis。

上下文证据缺失、过期或质量未知时，conditional 规则不能假装已确认；应输出 warning/info 或 skipped 证据，具体由字段策略决定。

## 11. 深入代码核对：迁移前必须处理的行为差异

### 11.1 Quote 的确定性与副作用

1. `ValidateQuote` 使用 map 遍历多字段数值检查。Go map 遍历顺序不稳定，因此多个字段同时非法时，旧函数返回的第一条错误不保证稳定。新 Validator 必须用固定规则顺序输出完整问题列表。
2. `ValidateQuote` 在 amount 缺失时会写入 `AmountUnit=unknown`，并追加两条 QualityReasons。新 Validator 不得复制该副作用；旧入口兼容测试需要明确断言旧行为，避免悄悄改变现有调用方。
3. `ValidateQuote` 将 volume 设为必需且要求 VolumeUnit=shares。NetEase Adapter 在 volume 解析失败时会把质量标记为 degraded、记录 `volume_missing_or_invalid`，但同时把 Volume 留空、VolumeUnit 设为 unknown，随后仍调用 ValidateQuote，因此最终会返回错误而不是 degraded Quote。需要明确这属于“缺量数据不允许返回”的硬门禁，还是应该允许降级 Quote；不能只保留质量原因却误认为已经支持缺量降级。
4. Quote 的价格、涨跌额、涨跌幅等在 Provider Adapter 中已有部分源端交叉校验，随后 Normalize 又校验一次。迁移时要区分源端原始字段一致性与标准化字段一致性，避免把同一问题重复报告。

### 11.2 DailyBar 的身份与过滤边界

1. `ValidateAndSortBars` 在所有字段校验通过后才将 trade_date 写入 seen，因此同日第一条无效记录不会阻止后续同日有效记录；当前语义是“保留首条有效记录”，不是“无条件保留源端首条”。
2. 函数将每条记录的 Symbol 覆盖成请求 symbol，未检查原始 Symbol 是否为空或与请求证券不一致。若 Provider 映射错误证券，现有逻辑可能把错误记录标记成请求证券。新流程必须在覆盖/规范化前验证身份；不能直接把 symbol 覆盖当作标准化。
3. start 范围之前的记录当前静默过滤；end 之后记录会产生 warning；公共 Provider helper 会将越界数据统一降级。这些属于响应范围契约，不应与单条 OHLC 字段错误混为一类。
4. DailyBar 的字段值在 Go 模型中大多已是 float64/int64。进入 Validator 时，原始 JSON 的对象/数组/null/字符串类型错误可能已经被反序列化器拒绝或被解析函数转换为普通 error。字段名、原始类型和行号必须在 Adapter 解析阶段捕获。

### 11.3 原始类型诊断的最小边界

建议 Adapter 侧统一产出以下信息，不将完整原始响应传给诊断 API：

- `field`：Provider 原始字段名或映射后的标准字段名；
- `expected_type`：number / integer / string / date / array 等；
- `actual_type`：null / string / number / object / array / missing；
- `actual_preview`：限长、脱敏的值摘要；
- `row_index`：数组/CSV 记录序号；
- `provider_field`：可选的源端字段标识；
- `code`：type_mismatch / required / invalid_number / invalid_date。

解析阶段的问题和标准模型校验问题应使用同一 FieldIssue 表达，但需要保留 `stage=parse|normalize|validate`，方便区分错误发生在哪个边界。

### 11.4 推荐的请求级报告传递方式

不要在 Provider 实例或包级变量上保存报告。建议每次调用由 Service 创建请求级报告容器，通过 context 传递只读接口或显式参数传给 Adapter：

- 报告容器在单次请求中独占，不能跨请求复用。
- Adapter 只追加问题，不直接决定 Probe 的最终状态。
- Provider 返回值、报告和错误一起返回 Service；不要依赖 context 的隐式副作用作为唯一数据通道。
- Probe 对报告做汇总和截断，输出结构化字段问题。
- 入库流程调用相同 Validator，质量门禁独立决定 reject/degrade/accept。
- Reporter 需限制最大问题数，并统计 total_count / returned_count / truncated。

优先考虑显式返回：
`(data, ValidationReport, error)`。
若为了兼容既有 Provider 接口而使用 context reporter，必须保证 context scope、生命周期、并发安全和取消语义明确，且最终仍由 Service 显式取回报告。

## 12. 当前结论与下一批验收前置条件

- Quote/DailyBar Validator 应输出完整问题集合，不采用“遇到第一条错误立即返回”的旧模式。
- Parse 阶段需保留原始 JSON 类型，Normalize 阶段只做明确转换，Validate 阶段只做无副作用判断。
- DailyBar 身份校验必须先于 symbol 覆盖；Provider 返回的错证券数据不能被修正为目标证券。
- 缺量 Quote 的产品语义必须明确：硬失败还是 degraded 可返回。当前 NetEase 代码的质量标记与最终返回行为不一致。
- 对 amount 缺失、volume 缺失、停牌和非交易日分别定义 required/conditional 策略，不能用一条全局 required 规则覆盖所有场景。
- 新旧兼容层需有行为测试，覆盖副作用、过滤顺序、重复日期和 limit 截断。

第一批静态盘点已足以开始设计核心模型，但当前会话仍未取得完整 Git Tree SHA / 可检出工作区，因此尚不能安全创建基于现有分支的多文件原子提交，也无法在本地运行 Go 测试。不要将以下工作标为已完成：Validation 代码实现、Provider 接入、Probe 接入、构建和测试。

### 19.1 Probe 请求/响应契约核验

当前 HEAD 的以下字段已在 HTTP 请求模型、Service ProbeOptions、Go 响应模型和 OpenAPI 中对应：

- 请求 `daily_bar_adjustments`：只允许 `none`、`forward_adjusted`、`backward_adjusted`；数组唯一，最多 3 项；只允许与 `daily_bars` capability 同时使用。

- 每个已注册 DailyBarProvider 对每个请求口径生成独立 Probe job；结果 `ProviderProbeItem.adjustment_basis` 标明实际探测口径。
- 批次 `requested_daily_bar_adjustments` 保留用户请求口径；单项状态支持 `returned`、`returned_degraded`、`returned_unknown`、`failed`、`skipped`、`not_configured`、`not_supported`。
- 明确不支持的复权口径映射为 `not_supported` / `daily_bar_adjustment_not_supported`，不计入 failed；普通网络、超时、鉴权、权限、数据契约和因子缺失错误仍按实际错误处理。
- 跨 Provider 检查只对同一 adjustment_basis 的快照建立比较；不同口径不进入数值比较。

配置状态说明：

- 默认关闭的 HiThink、Tushare、Yahoo 不会进入已注册的 `barProviders` 列表，因此不会为它们逐一生成 Probe item。

- HiThink/Tushare 被显式启用时，配置加载会校验 API Key/Token；缺少凭据会阻止服务启动，不会作为正常 Provider 请求失败伪装成数据故障。
