## 2. 当前任务：DATA-002

**目标：** 核实现有 DailyBar 链路的质量判定和复权参考基准，确保 none/forward/backward 的数据语义可追溯，交易日期、停牌、缺失、上市/退市边界不被混淆。

### 2.1 任务范围

1. Provider 日 K 原始字段和复权请求参数：
   - 请求口径、源端 method、原始字段、单位和标准化字段；
   - none/forward/backward 的 AdjustmentMethod、AdjustmentRefDate、因子来源和版本；
   - 缺失参考日期时的质量状态与比较门禁。
2. DailyBar Service 质量链：
   - 交易日历上下文、证券状态、停牌与非交易日；
   - 上市首日、退市边界、窗口截断、分页完整性；
   - 缺失、重复、真实零值、成交量/成交额单位和字段质量。
3. 跨 Provider 比较：
   - 同证券、同交易日、同复权口径、同 method/ref date 的前置条件；
   - not_comparable、degraded、failed、passed 的判定边界。
4. 真实证据：
   - 复用已有 Runtime Acceptance Log 和历史 Artifact；
   - 仅在代码差异影响结果且有凭据/配额许可时，才提出最小化真实复验；不自动触发批量探测。

### 2.3 DATA-002-A 首轮代码核对结果

本轮已核对 `DataService.DailyBars`、`DailyBarsAsOf`、Provider DailyBar 实现、Normalize、Validation、复权重建和跨 Provider 比较代码。当前确认：

1. 已有能力，不重复开发：
   - `DailyBars` 已实现 Provider 回退、熔断/重试、缓存契约校验、来源/版本一致性、部分 K 线降级保留、MariaDB stale 兜底、限量和窗口校验。
   - `normalize.ValidateAndSortBars` 已处理证券身份、日期范围、OHLC、成交量/成交额单位、金额/成交量一致性、重复日期、质量状态和 limit 截断。
   - `validation.ValidateDailyBar` 已有结构化字段诊断。
   - `DailyBarsAsOf` 已使用持久化原始日 K 与 PIT 复权因子重建历史视图。
   - `adjustment_rebuild.go` 已隔离同证券、同 Provider、同 SourceVersion 因子，处理 AvailableAt/SystemObservedAt、因子修订哈希和前复权参考锚点。
2. 发现的接入缺口：
   - `daily_bar_trading_context.go` 已实现交易日历 + SecurityTradingStatus 对缺失日期的判断、并发缓存和每轮 Probe 最多 10 次状态查询预算；`provider_probe.go` 已在 daily_bars Probe 中调用该 helper，并将上下文降级原因合入 Probe 结果。
   - 普通 `DataService.DailyBars` 读取路径只用 `TradingCalendar` 计算覆盖率，没有逐日查询证券状态；`DailyBarsAsOf` 也不调用该 helper。当前不能把 helper 误判为死代码。下一步需确认普通读取接口是否有明确消费者要求解释停牌/上市前缺口；如果没有，保留 Probe 诊断边界，不把昂贵的逐日状态查询无条件接入每次行情读取。PIT 路径则必须单独使用 as_of 可见的状态证据，不能复用当前状态查询结果。
3. 现有覆盖率规则：
   - 显式 start/end 请求优先用 TradingCalendar 的 TradingDays，门槛为 `minimumDailyBarCoverage` 的 65%。
   - 日历不可用时退回工作日估算并附 degraded warning；无 start 的 lookback 请求使用请求条数阈值，不使用日历。
   - 需要核对 65%/80% 门槛是否与阶段五验收规则一致，以及停牌/上市前日期是否应从分母扣除；暂不调整阈值。
4. Provider 复权元数据现状：
   - Eastmoney、Hithink、BaoStock、Tencent、TickFlow 使用各自原生 qfq/hfq method，但当前实现未填 `AdjustmentRefDate`。
   - Pytdx、Yahoo 会填充参考日期；Tushare 前复权会填充参考日期，后复权不填。
   - Sina、NetEase 只提供未复权日 K。
   - Service 对 forward 缺少参考日期会降级；跨 Provider adjusted 比较要求 method/refDate 完整一致，因此缺少参考日期的序列保持 not_comparable。不能通过推测请求 endDate 补齐参考日期。
5. 当前未发现需要新增 DailyBar 字段的证据。现有 `AdjustmentMethod`、`AdjustmentRefDate`、Factor Source/Version/Hash、`SystemObservedAt` 已覆盖主要追溯维度；是否有字段缺口需在逐 Provider 语义核验后再判断。

   - `CompareCrossProviderDailyBars` 已由 Provider Probe 使用。调整口径必须一致；adjusted 还必须有完全一致的 `AdjustmentMethod` 和 `AdjustmentRefDate`，日期集合必须完全一致，输入质量必须 valid；金额缺失/精度未知会得到 partial/not_comparable，不会伪装 matched。
   - 现有测试覆盖 80% lookback、65% 交易日覆盖门槛、日历不可用降级、复权参考日期和跨 Provider 元数据不一致。门槛有固定测试，但仍需确认与业务验收目标一致，不先改数值。
7. 当前没有发现可以安全统一不同 Provider 复权算法名称的依据。Provider-specific method 不同导致 adjusted 跨源对账保持 not_comparable，是现有保守门禁；不得把 method 字符串改成泛化的 qfq/hfq 来强行比较。

### 2.4 DATA-002-C 交易日期与缺失日 K 归因首轮核对

1. 已有交易上下文实现不是普通行情读取热路径：
   - `assessDailyBarTradingContext` 只由 Provider Probe 调用；在 Probe 内按 `symbol + trade_date` 共享状态查询，最多 10 个唯一证券状态查询，超预算显式 degraded。
   - 普通 `DailyBars` 与 `DailyBarsAsOf` 不逐日查 SecurityTradingStatus。这是有意控制 N+1 请求和存储成本，不是漏接一个可直接无预算调用的 helper。
   - PIT 路径不能复用当前 SecurityTradingStatus 快照；如果未来需要 PIT 缺失归因，必须使用 `as_of` 可见的历史状态证据。
2. 已有缺失日归因规则：
   - 日历缺失/降级、来源冲突时不确认漏数；仅质量有效的日历可支撑确定性缺失结论。历史日历仅缺发布时间的受控例外保留显式 warning。
   - 对日历交易日缺 K，先要求状态快照整体 valid、日期/交易日身份匹配、上市状态已知且上市日期合法。
   - 上市日期之前归为 `daily_bar_excluded_before_listing`；全天停牌归为 `daily_bar_excluded_suspended`；盘中停牌不解释全天日 K 缺失，若日历有效则记录 `daily_bar_missing_during_intraday_suspension`；无停牌事件/已复牌时记录 `daily_bar_missing_on_confirmed_trading_day`。
   - 状态缺失、状态质量非 valid、上市/停牌未知或查询失败均降级，不把未知日期计为已确认 Provider 漏数。
   - 真实样本仍有限：Pytdx 已有官方临停/全天停牌窗口证据；BaoStock 有指定停牌/复牌及 ST 字段样本；Tushare SecurityTradingStatus 因 40203 权限限制未完成。不能外推到完整证券状态覆盖。
3. 覆盖率门槛并非“真实数据通过率”：
   - 显式日期区间：优先用 TradingCalendar.TradingDays，最低返回门槛为预期交易日数的 65%；日历不可用时退回工作日估算并附 degraded warning。
   - lookback 请求：按请求条数至少 80%（最低 20 条）的门槛；少于 20 条的请求只要求有返回。
   - 65% 是 Service 判断 Provider 返回是否足以进入后续流程的保守下限，不代表其余 35% 都是合理停牌/上市前缺口，也不代表覆盖率达到 65% 就能标记质量 valid。缺失日期解释仍需独立交易上下文证据。
   - 阶段五验收计划没有找到将 65% 定义为业务验收通过线的依据；质量方案明确要求真实边界矩阵及证据，不支持把当前门槛提升为验收结论。因此暂不改阈值。
4. 当前结论：现有 Probe 上下文判定边界保守且有预算；不应把它接入普通 DailyBars 热路径。DATA-002-C 剩余工作是将现有真实事件样本、证券状态来源覆盖、交易日历样本和缺失日期分类逐项映射到固定验收矩阵，并保持未证实样本为 unknown/unverified。
