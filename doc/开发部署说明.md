# 开发、部署与本地运行说明

更新日期：2026-11-19

## 1. 仓库运行边界

- `web/`：原生 HTML/CSS/JavaScript ES Modules WebUI。
- `internal/server/`：唯一外部 HTTP 入口与组合根。
- `internal/marketdata/`：Root Server 同进程 Data 模块，复用 Root 的 MariaDB、Redis 和受控出站能力。
- News、Research、Researchflow、Quant、LLM、Notification 等模块由 Root Server 按各自契约装配。
- 生产 Compose 仅运行 `stock-analysis-server` 和 `stock-analysis-web`；不部署独立 Data HTTP 服务。

## 2. WebUI 本地开发

进入 `web/` 后查看 `package.json` 的 scripts。WebUI 只访问同源 Root API：

- Data、Owner Session、Root readiness：`/api/**`。
- Root liveness：`/healthz`。
- 不配置独立行情/分析 Base URL；浏览器设置中的旧路径会被规范化为 Root 同源入口。
- 浏览器不保存或发送 Data API Key / `X-API-Key`，也不持有 Owner Bearer 或第三方 Provider 凭据。

本地开发若未启用 Owner Session，受保护业务接口将按 Server 认证策略拒绝请求；不得通过关闭认证或注入静态 Owner Bearer 绕过。

## 3. 生产部署

以根目录 `docker-compose.yml`、`.env.example` 和当前代码为准。生产 Compose 只有两个应用服务：`stock-analysis-server` 与 `stock-analysis-web`；Data 在 Root Server 进程内运行，不存在独立 Data 容器。

### 3.1 部署前准备

1. 备份目标 MariaDB 中本项目使用的完整数据库（结构和数据），并确认可以恢复到隔离数据库。至少保留一份本次升级前备份。
2. 确认 MariaDB、Redis 与应用容器接入同一个外部 Docker 网络 `1panel-network`；核对 `DB_HOST/DB_PORT/DB_NAME/DB_USER` 和 `REDIS_ADDR/REDIS_PASSWORD`。
3. 复制 `.env.example` 为 `.env`。已有环境禁止覆盖；应先备份，再按变量逐项合并。
4. 配置真实 `PLATFORM_ADMIN_TOKEN`、数据库/Redis 凭据和所需 Provider 凭据。Token 使用高熵随机值，不要提交到 Git。
5. 设置 `OWNER_SESSION_PUBLIC_ORIGIN` 为 WebUI 对外的精确 HTTPS Origin（无路径、无尾斜杠）。
6. 在目标部署主机完成 Argon2id 基准测试，再填写 `OWNER_SESSION_ARGON2_MEMORY_KIB`、`OWNER_SESSION_ARGON2_ITERATIONS`、`OWNER_SESSION_ARGON2_PARALLELISM`。Compose 会拒绝缺少这些值的启动配置。
7. 显式配置两个独立开关：`DB_AUTO_MIGRATE` 只控制旧 Analysis Store 的基础表迁移；`MIGRATION_ENABLED` 控制 Root Registry 中 Data/News/Research/Quant/Researchflow/Notification 等模块 Migration。两者不能互相替代。

### 3.2 首次部署（数据库尚未迁移、Owner 尚未初始化）

首次部署必须先完成 Root Migration 和 Owner Credential 初始化，再启动对外服务：

1. 在 `.env` 中首次部署时设置 `DB_AUTO_MIGRATE=true`、`MIGRATION_ENABLED=true`、`MIGRATION_TIMEOUT=2m`。`DB_AUTO_MIGRATE` 先创建/检查旧 Analysis Store 必需表；随后 `MIGRATION_ENABLED` 执行 Root Registry 中所有已注册模块的 Migration，包括 Data V1-V9，不是只迁移 Data。
2. 生成一次性 Owner 初始密码文件。文件必须是普通文件且权限严格为 0600：
   ```bash
   install -d -m 700 secrets
   umask 077
   openssl rand -hex 32 > secrets/owner-init
   chmod 600 secrets/owner-init
   ```
   将文件内容安全保存到密码管理器；不要把它放进 Git 或日志。
3. 运行一次性初始化命令。命令以文件所有者 UID/GID 运行，使容器内进程能够读取 0600 文件：
   ```bash
   SECRET_FILE="$PWD/secrets/owner-init"
   SECRET_OWNER="$(stat -c '%u:%g' "$SECRET_FILE")"
   docker compose --env-file .env run --rm --no-deps \
     --user "$SECRET_OWNER" \
     -e OWNER_SESSION_INITIAL_SECRET_FILE=/run/secrets/owner-init \
     -v "$SECRET_FILE:/run/secrets/owner-init:ro" \
     stock-analysis-server owner-init
   ```
   `owner-init` 会先执行/校验完整 Root Migration，再初始化 Owner Credential；它不是 HTTP 初始化接口。
4. 看到初始化成功后确认密码管理器中已保存初始密码，再删除一次性文件：`rm -f secrets/owner-init`。SSD、快照和写时复制文件系统不能保证 `shred` 物理擦除，因此重点是限制权限、避免备份/提交并尽快删除。
5. 将 `.env` 的 `DB_AUTO_MIGRATE` 和 `MIGRATION_ENABLED` 都改为 `false`。后续正常启动不再执行 DDL：旧 Analysis Store 只检查基础表，Root Registry 只读校验模块 Migration 版本/checksum。
6. 执行 `bash scripts/deploy-go.sh`。脚本会校验 Compose、构建 Server/WebUI 两个镜像、启动两个服务，并检查容器健康状态及带 Owner Bearer 认证的 Root `/readyz`。

### 3.3 已初始化环境升级

1. 先备份 MariaDB，并记录当前部署 Git SHA、容器镜像 ID、`.env` 备份和当前服务状态。
2. 在 `.env` 中临时设置 `MIGRATION_ENABLED=true`；只有本次版本确实包含旧 Analysis 基础表变更时才同时设置 `DB_AUTO_MIGRATE=true`。执行 `bash scripts/deploy-go.sh`，Root 在开始接受请求前执行已注册模块 Migration。
3. 只有 Migration、容器健康检查和认证后的 `/readyz` 全部通过，才将 `MIGRATION_ENABLED` 改回 `false`；若本次打开了 `DB_AUTO_MIGRATE`，也将其改回 `false`。
4. 使用 `docker compose --env-file .env up -d --no-build stock-analysis-server` 重建 Server 容器，使其以只读 Migration 校验模式启动；再次检查 `/readyz`。
5. 如果 Migration 报告 `recovery_required`、DDL 部分执行或 Schema 校验失败，立即停止后续部署，不要反复重跑 Migration。先检查 Migration 报告和 MariaDB 状态，按备份恢复或人工 DBA 恢复方案处理。

### 3.4 部署检查与回滚边界

- `scripts/deploy-go.sh` 是当前统一部署脚本，只管理 `stock-analysis-server` 和 `stock-analysis-web`；不再构建、启动或检查独立 Data 服务。
- Server 容器健康检查只证明进程存活；脚本另行调用 Owner Bearer 保护的 `/readyz`，检查 Root Migration 版本/checksum、Data 物理 Schema、MariaDB/Redis 等必需依赖。
- `MIGRATION_ENABLED=false` 是生产常态。若缺少 Migration、checksum 不一致或存在未登记版本，Server 应 fail-closed，不得临时关闭 Readiness 绕过。
- 代码回滚优先恢复上一版应用代码/镜像，保留已成功应用的向前兼容 Migration；不要自行删除 V7-V9 策略、决策、撤销和审计表，也不要编造 down migration。
- 只有确认数据库结构或数据已损坏且已制定恢复窗口时，才考虑从升级前备份恢复数据库。恢复会丢失备份之后的写入；必须停应用并明确业务数据损失边界。
- 不要对共享 Redis 执行 `FLUSHALL` 或清空整个 DB。Owner Session Redis Key 与其他模块缓存共用实例时，只允许按明确前缀和范围处理。
- 首次部署/升级完成后，再执行浏览器 Owner Session 登录、Owner 策略首次发布、受控 API 读取和真实 Provider 出站/数据质量验收。CI、容器健康检查和 Readiness 均不能替代真实 Provider 数据验收。

## 4. API 路由与认证

- Nginx 的唯一业务 upstream 是 `stock-analysis-server:8092`，`/api/` 原样转发，不做路径改写。
- WebUI 使用 HttpOnly Owner Session Cookie；CSRF Token 只保存在页面运行时内存，所有非安全 Session 请求发送 `X-CSRF-Token`。
- Server Data 路由显式允许 `owner_session` 和 `owner_bearer`；Owner Bearer 仅供受控运维调用，不下发浏览器。
- `POST /api/v1/data-sources/probe` 必须通过 Session Origin/Host 与 CSRF 原子校验。
- `GET /api/readyz` 是浏览器只读就绪视图；Root 原始 `/readyz` 与 `/diagnostics` 仍为 Owner Bearer 运维路由。
- Data 领域资源授权仍由 Data 自身按 DATA-CTR-008 执行；Owner Session 不等于领域授权通过。

## 5. 部署边界

- 不存在独立 Data 服务、Data API Key、`/market-api/` upstream 或 `/analysis-api/` upstream。
- 不保留旧服务、旧 Key 兼容层或双轨回滚部署资产。
- 旧 Data HTTP 认证契约 DATA-CTR-006 已退役；唯一认证权威是 SRV-CTR-002 1.1.0。
- Provider 凭据属于服务端配置，不得与已退役的浏览器 Data API Key 混淆。

## 6. 运行与验收

完整浏览器验收以 `doc/WebUI提测验收清单.md` 为准。自动化测试、HTTP 健康检查、Provider 能力声明和真实 Provider 数据验收是不同证据；不得用其中一项替代其他项。
