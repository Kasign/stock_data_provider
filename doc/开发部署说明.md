# 开发、部署与本地运行说明

更新日期：2026-11-24

## 1. 仓库运行边界

- `web/`：原生 HTML/CSS/JavaScript ES Modules WebUI。
- `internal/server/`：唯一外部 HTTP 入口与组合根。
- `internal/marketdata/`：Root Server 同进程 Data 模块，复用 Root 的 MariaDB、Redis 和受控出站能力。
- News、Research、Researchflow、Quant、LLM、Notification 等模块由 Root Server 按各自契约装配。
- 生产 Compose 仅运行 `stock-analysis-server` 和 `stock-analysis-web`；不部署独立 Data HTTP 服务。

## 2. WebUI 本地开发

进入 `web/` 后查看 `package.json` 的 scripts。WebUI 只访问同源 Root API：

- Data、Owner Session、Root readiness：`/api/**`。
- Root liveness：`/healthz`。
- 不配置独立行情/分析 Base URL；浏览器设置中的旧路径会被规范化为 Root 同源入口。
- 浏览器不保存或发送 Data API Key / `X-API-Key`，也不持有 Owner Bearer 或第三方 Provider 凭据。

本地开发若未启用 Owner Session，受保护业务接口将按 Server 认证策略拒绝请求；不得通过关闭认证或注入静态 Owner Bearer 绕过。

## 3. 生产部署

以根目录 `docker-compose.yml`、`.env.example` 和当前代码为准。生产 Compose 只有两个应用服务：`stock-analysis-server` 与 `stock-analysis-web`；Data 在 Root Server 进程内运行，不存在独立 Data 容器。

### 3.1 部署前准备

1. 备份目标 MariaDB 中本项目使用的完整数据库（结构和数据），并确认可以恢复到隔离数据库。至少保留一份本次升级前备份。
2. 确认 MariaDB、Redis 与应用容器接入同一个外部 Docker 网络 `1panel-network`；核对 `DB_HOST/DB_PORT/DB_NAME/DB_USER` 和 `REDIS_ADDR/REDIS_PASSWORD`。
3. 复制 `.env.example` 为 `.env`。不要覆盖目标环境已有 `.env`；应先备份，再按变量逐项合并。
4. 配置真实 `PLATFORM_ADMIN_TOKEN`、数据库/Redis 凭据和所需 Provider 凭据。Token 使用 `openssl rand -hex 32` 生成 64 位十六进制字符串，写入 `.env` 时不加引号且单独占一行，不要提交到 Git。部署脚本会用它检查受保护的 `/readyz`，因此使用 `scripts/deploy-go.sh` 时必填。
5. 设置 `OWNER_SESSION_PUBLIC_ORIGIN` 为浏览器访问 WebUI 的精确 Origin（无路径、无尾斜杠）。本地 HTTP 调试可设置 `http://127.0.0.1:8093` 或 `http://服务器IP:8093`，同时设置 `OWNER_SESSION_COOKIE_NAME=owner_session`、`OWNER_SESSION_COOKIE_SECURE=false`；正式 HTTPS 必须改回 `__Secure-owner_session` 和 `true`。
6. 配置 Owner Session 参数：调试环境按第 5 步使用 HTTP Origin 与非 Secure Cookie；正式环境使用 HTTPS Origin 与 Secure Cookie。Origin 只含协议、主机和可选端口，不带路径；管理员密码校验强度建议先使用：内存 `65536` KiB（64 MiB）、重复计算 `3` 轮、并行计算 `1` 个线程。这三个值控制密码校验的计算成本：设置得越高，批量猜测密码越困难，但登录验证会更慢、占用更多内存。调试阶段先使用建议值即可，暂时不需要自行调整。Compose 会拒绝缺少这些值的启动配置。
7. 配置 §MIGRATION_TIMEOUT=2m§。数据库迁移由 Root Server 启动统一自动执行，不再设置 §DB_AUTO_MIGRATE§ 或 §MIGRATION_ENABLED§。本次 Schema 基线重建要求使用新的空数据库，服务不会自动清理或转换旧数据库。

### 3.1.1 Owner Session 参数说明

| 配置项 | 中文含义 | 建议起始值 | 约束/说明 |
|---|---|---:|---|
| `OWNER_SESSION_PUBLIC_ORIGIN` | 浏览器访问 WebUI 的精确来源地址 | 调试时 `http://127.0.0.1:8093` | 必须与浏览器地址栏的协议、主机和端口完全一致；不带路径、参数或末尾斜杠 |
| `OWNER_SESSION_COOKIE_NAME` | 浏览器 Session Cookie 名称 | HTTP 调试 `owner_session`；HTTPS `__Secure-owner_session` | 使用 `__Secure-` 前缀时必须通过 HTTPS |
| `OWNER_SESSION_COOKIE_SECURE` | 是否只允许通过 HTTPS 发送 Cookie | HTTP 调试 `false`；HTTPS `true` | 仅 HTTP 调试可设 false；正式环境必须 true |
| Compose 固定项 | Owner Session 启用状态、Cookie Path、CSRF Header | `true`、`/api`、`X-CSRF-Token` | 由根 `docker-compose.yml` 固定，不要在 `.env` 重复配置 |
| `OWNER_SESSION_IDLE_TTL` | Session 空闲有效期 | `12h` | 默认 12 小时 |
| `OWNER_SESSION_ABSOLUTE_TTL` | Session 绝对有效期 | `168h`（7 天） | 即使持续操作也不能超过 |
| `OWNER_SESSION_REDIS_KEY_PREFIX` | Redis Session Key 前缀 | `stock-analysis:owner-session` | 通常保持默认 |
| `OWNER_SESSION_ARGON2_MEMORY_KIB` | 每次密码校验使用的内存 | `65536` KiB（64 MiB） | 数值越大越占内存；代码上限 262144 KiB |
| `OWNER_SESSION_ARGON2_ITERATIONS` | 每次密码校验重复计算的轮数 | `3` | 轮数越多，校验越慢；代码上限 10 |
| `OWNER_SESSION_ARGON2_PARALLELISM` | 每次密码校验可同时使用的计算线程数 | `1` | 代码上限 8；调试阶段保持 1 即可 |
| `OWNER_SESSION_LOGIN_ACCOUNT_MAX_FAILURES` | 单账号失败次数阈值 | `5` | 15 分钟窗口 |
| `OWNER_SESSION_LOGIN_IP_MAX_FAILURES` | 单来源 IP 失败次数阈值 | `10` | 15 分钟窗口 |
| `OWNER_SESSION_LOGIN_WINDOW` | 登录失败统计窗口 | `15m` | 默认 15 分钟 |
| `OWNER_SESSION_LOGIN_BASE_BACKOFF` | 达到限制后的初始等待时间 | `1s` | 逐步退避 |
| `OWNER_SESSION_LOGIN_MAX_BACKOFF` | 最长退避等待时间 | `15m` | 默认最多 15 分钟 |


Notification 还需要配置 `NOTIFICATION_EVENT_MAX_ENVELOPE_BYTES`、`NOTIFICATION_EVENT_MAX_PAYLOAD_BYTES` 和 `NOTIFICATION_EVENT_MAX_JSON_DEPTH`：单条通知事件消息允许的最大大小，单位为字节。调试建议 `1048576`（1 MiB），超过限制的消息会被拒绝，避免异常大消息占用过多内存。
Compose 固定 Owner Session 启用状态、Cookie Path 和 CSRF Header；Cookie 名称与 Secure 属性允许通过 `.env` 覆盖，以支持本地 HTTP 调试。HTTP 调试配置不得用于正式部署。历史旧 News 检索链路的 `BOCHA_API_KEYS`、`TAVILY_API_KEYS`、`GO_NEWS_*` 等配置已从当前部署模板移除；当前 News 配置统一使用 `NEWS_PROVIDER_*`。\n\nArgon2id 的 `65536 / 3 / 1` 是项目安全设计文档中的建议起始参数。它不是已在你的目标服务器测得的最优值。部署前应在目标服务器测量单次登录验证耗时及预期并发下的内存峰值；密码哈希是 CPU/内存密集型操作，不能只看单次耗时。若服务器资源不足，应先测量并评估，不要盲目增大参数。


### 3.2 首次部署与本次 Schema 基线切换

本次数据库方案不做旧 Schema、旧 Migration History 或旧业务数据兼容。新基线把每个模块当前最终结构定义为 V1，因此**不能在保留旧 Migration History 的数据库上原地升级**。

1. 在 MariaDB 管理端由部署者显式创建新的空数据库，并将 .env 的 `DB_NAME` 指向它。确认旧业务数据不需要保留后，再由部署者决定是否删除旧数据库。Server 启动和 `owner-init` 都不会执行 DROP DATABASE、TRUNCATE 或自动清空旧表。
2. 复制 .env.example 为 .env。不要覆盖目标环境已有 .env；逐项合并真实数据库、Redis、Provider 凭据和 `PLATFORM_ADMIN_TOKEN`。只保留 `MIGRATION_TIMEOUT=2m`，不再配置两个迁移开关。
3. 配置 Owner Session 参数和精确 `OWNER_SESSION_PUBLIC_ORIGIN`。正式 HTTPS 使用 Secure Cookie；HTTP 只用于受控调试。
4. 生成一次性 Owner 初始密码文件。文件必须是普通文件且权限严格为 0600：
   ```bash
   install -d -m 700 secrets
   umask 077
   openssl rand -hex 32 | tr -d '\n' > secrets/owner-init
   chmod 600 secrets/owner-init
   ```
   将文件内容安全保存到密码管理器；不要把它放进 Git 或日志。
5. 校验 Compose 配置并构建 Server 镜像（此时不要启动长期服务）：
   ```bash
   docker compose --env-file .env config --quiet
   docker compose --env-file .env build stock-analysis-server
   ```
6. 运行一次性初始化命令：
   ```bash
   SECRET_FILE="$PWD/secrets/owner-init"
   SECRET_OWNER="$(stat -c '%u:%g' "$SECRET_FILE")"
   docker compose --env-file .env run --rm --no-deps \
     --user "$SECRET_OWNER" \
     -e OWNER_SESSION_INITIAL_SECRET_FILE=/run/secrets/owner-init \
     -v "$SECRET_FILE:/run/secrets/owner-init:ro" \
     stock-analysis-server owner-init
   ```
   `owner-init` 会先连接 MariaDB，注册并执行全部模块 Migration，校验完整 Migration History 和 checksum，然后再初始化 Owner Credential。迁移完成前不会创建 Redis、Repository 或 HTTP 依赖。
7. 初始化成功后确认密码管理器已保存初始密码，再删除一次性文件：`rm -f secrets/owner-init`。SSD、快照和写时复制文件系统不能保证 `shred` 物理擦除，因此重点是限制权限、避免备份/提交并尽快删除。
8. 执行 `bash scripts/deploy-go.sh`。正常 Server 启动会调用同一个 Migration Registry：已由 `owner-init` 应用的 V1 会校验 checksum 并跳过；随后创建 Redis、Repository、Worker 和 HTTP 依赖，再检查 `/readyz`。

### 3.3 已初始化环境部署与后续升级

- 对本次新基线切换：必须使用新的空数据库，不能复用仍有旧版本记录的数据库。旧数据库中的 V1–V9 等历史记录与新单一 V1 不兼容；不提供自动转换或兼容模式。
- 对已经完成本次基线切换的后续版本：只需更新代码/镜像并执行 `bash scripts/deploy-go.sh`。Server 启动自动执行尚未应用的 Migration，不需要修改 .env 开关。
- `MIGRATION_TIMEOUT` 控制一次完整 Migration 执行和校验的超时，默认 2 分钟，最大 30 分钟。只有确实需要时才调整。
- 如果 Migration 失败、出现 running/failed 历史记录、checksum 不一致或物理 Schema 校验失败，Server 必须 fail-closed。Runner 不自动重跑失败版本；先检查 Migration 报告和 MariaDB 实际结构，再由维护者人工恢复。
- `owner-init` 与正常 Server 使用同一套 Database Bootstrap。不要单独手动运行某个模块的 `Migrate()`，也不要绕过 Root Registry。

### 3.4 部署检查与回滚边界

- `scripts/deploy-go.sh` 只管理 `stock-analysis-server` 和 `stock-analysis-web`；不再构建、启动或检查独立 Data 服务，也不要求迁移开关。
- Server 容器健康检查只证明进程存活；脚本另行调用 Owner Bearer 保护的 `/readyz`，检查 Root Migration 版本/checksum、Data 物理 Schema、MariaDB/Redis 等必需依赖。
- 每次启动都会先执行统一 Migration；缺少版本、checksum 不一致、存在未知 namespace/version 或未完成记录时必须 fail-closed，不得关闭 Readiness 绕过。
- 后续版本回滚优先恢复上一版应用代码/镜像，保留已经成功应用的向前 Migration；不得修改已发布 V1，也不要自行删除策略、决策、撤销和审计表或编造 down migration。
- 本次基线切换前的旧数据库不属于新 Migration History 的可回滚目标。若需要恢复旧系统，应恢复旧代码与旧数据库备份；新库与旧库切换造成的数据差异必须由部署者明确确认。
- 不要对共享 Redis 执行 `FLUSHALL` 或清空整个 DB。Owner Session Redis Key 与其他模块缓存共用实例时，只允许按明确前缀和范围处理。
- Data 不自动创建默认授权策略。首次部署后，Owner Policy GET 在首次发布前返回 404 是预期行为；必须通过 `POST /api/v1/owner/data/daily-bars-access-policy/versions` 使用 Owner Session Cookie 与 CSRF Token 发布第一版策略。授权策略未发布前，读取保持 fail-closed。
- 首次部署/升级完成后，再执行浏览器 Owner Session 登录、Owner 策略首次发布、受控 API 读取和真实 Provider 出站/数据质量验收。CI、容器健康检查和 Readiness 均不能替代真实 Provider 数据验收。

## 4. API 路由与认证

- Nginx 的唯一业务 upstream 是 `stock-analysis-server:8092`，`/api/` 原样转发，不做路径改写。
- WebUI 使用 HttpOnly Owner Session Cookie；CSRF Token 只保存在页面运行时内存，所有非安全 Session 请求发送 `X-CSRF-Token`。
- Server Data 路由显式允许 `owner_session` 和 `owner_bearer`；Owner Bearer 仅供受控运维调用，不下发浏览器。
- `POST /api/v1/data-sources/probe` 必须通过 Session Origin/Host 与 CSRF 原子校验。
- `GET /api/readyz` 是浏览器只读就绪视图；Root 原始 `/readyz` 与 `/diagnostics` 仍为 Owner Bearer 运维路由。
- Data 领域资源授权仍由 Data 自身按 DATA-CTR-008 执行；Owner Session 不等于领域授权通过。

## 5. 部署边界

- 不存在独立 Data 服务、Data API Key、`/market-api/` upstream 或 `/analysis-api/` upstream。
- 不保留旧服务、旧 Key 兼容层或双轨回滚部署资产。
- 旧 Data HTTP 认证契约 DATA-CTR-006 已退役；唯一认证权威是 SRV-CTR-002 1.1.0。
- Provider 凭据属于服务端配置，不得与已退役的浏览器 Data API Key 混淆。

## 6. 运行与验收

完整浏览器验收以 `doc/WebUI提测验收清单.md` 为准。自动化测试、HTTP 健康检查、Provider 能力声明和真实 Provider 数据验收是不同证据；不得用其中一项替代其他项。


### Notification 启动必填配置补齐（2026-11-24）

Notification 事件接收需要显式配置以下三个资源限制，缺少任意一项都会导致 Server 启动配置校验失败：

- `NOTIFICATION_EVENT_MAX_ENVELOPE_BYTES`：完整事件消息最大字节数，当前建议 1048576（1 MiB），代码上限 64 MiB。
- `NOTIFICATION_EVENT_MAX_PAYLOAD_BYTES`：事件中 payload 最大字节数，必须大于 0 且不超过完整事件大小；当前建议 1048576（1 MiB）。
- `NOTIFICATION_EVENT_MAX_JSON_DEPTH`：JSON 最大嵌套层数，当前建议 64，代码上限 128。

这三项已在 `.env.example` 的 Notification 模块分区中列出。已有服务器的 `.env` 需要手动合并新增项，不要直接覆盖原文件。
