## 1. 问题定义与证据

阶段 2.1 的 L3 测试 `TestQuantResearchMariaDBRedisL3` 已跑通真实 MariaDB/Redis + 生产组合根 + 真实 Worker OS 进程 + 四 Stage 派发（`AttemptNo>=1`），但四个 Stage 终态均为 `failed`，原因是隔离库无行情 PIT 种子数据，Data 的 `GetDailyBarsV2` 在 `ListBarsAsOf` 处 fail-closed。这是**正确行为**，不是缺陷。

本专项要验证的是：当隔离库存在合法行情种子时，同一条真实链路能否让四个 Stage 产出可授权读取的成功/合法降级结果。不得通过伪造快照、降低 fail-closed 门禁或替换 Data Application 语义来"制造"通过。

## 2. 当前事实（代码级核实）

### 2.1 PIT 查询读 DB，不是网络

`internal/marketdata/application/reader.go:182-293` `GetDailyBarsV2` 最终调用 `backend.DailyBarsAsOfWithCoverageEvidenceFromSources`；`internal/marketdata/service/data.go:4247-4328` 的 `dailyBarsAsOfWithCoverageEvidence` 直接经 `s.store.ListBarsAsOfFromSources` / `ListBarsAsOf` **从 MariaDB 读已记录的 bar revisions**，不做 Provider 网络调用。因此向隔离库写入合法 bar 修订即可驱动真实 Data Module，无需注入 HTTP doer。

### 2.2 种子必须满足的真实门禁

bar 成为 PIT 候选（`data.go:4310-4320`）需同时满足：
- `NormalizeSymbol` 通过且与查询 symbol 一致；
- `AdjustmentBasis == storageBasis`；
- `NormalizationVer == normalize.Version`；
- `SourceVersion` 为可识别的非空版本串；
- `FetchedAt` / `NormalizedAt` / `SystemObservedAt` 均非零且不晚于 asOf；
- 经 `coherentStoredSeries` 一致性校验与 `ValidateAndSortBars`。

覆盖率证据（`data.go:4351-3710`、`reader.go:236-291`）要求显式 start/end、`CoverageBasis=exchange_calendar`、非空 `CalendarRef`、`CalendarQualityStatus=valid`，否则整条快照降级为 `degraded`，Quant 输入适用性门禁会拒绝。因此种子还必须包含一张 valid 交易日历快照。

快照创建与授权读取（`daily_bars_close_series_snapshot.go`、`create_*.go`）要求：
- `DailyBarsCloseSeriesSnapshotCreator` 读到的 bars 含精确 Close 证据（`app.DailyBarExactValues.CloseEvidence`，`observed_token` + fraction digits）；
- `DataAuthorizationOwner` 能解析到已发布的 `authorization.DailyBarsV2PolicyRef` 策略版本（`PolicyApproved`、`AllowedPurposes` 含 `quantstage.QuantPurposeCode`、`RequiredScopes` 含 `security.ScopeDataRead`）；
- 授权决策带 `PurposeCode` / `AuthorizationRef`，Authorized Reader 复核当前策略与撤销状态。

### 2.3 三类种子的现有写入 API（均为生产代码）

| 种子 | API | 位置 |
|---|---|---|
| PIT bars | `Store.UpsertBars([]model.DailyBar)` | `internal/marketdata/repository/mysql.go:244` |
| 交易日历 | `Store.SaveTradingCalendarSnapshot(snapshot, observedAt)` | `internal/marketdata/repository/trading_calendar.go:42` |
| 授权策略 | `Store.PublishDataAuthorizationPolicyVersion(...)` | `internal/marketdata/repository/data_authorization_policy.go:25` |

现有 e2e 的构造口径（`quant_factor_end_to_end_test.go:174-255`：`quantFactorEndToEndCloses` 20 根真实量级收盘价 + 精确值证据 + `minimumRequiredBars=bars-2` + 已发布 DataAccessPolicy）可作为"合法种子"的事实参考，但那些测试用**内存 Store + 自建 PIT reader**，不满足"真实 Data Module 读 MariaDB"的 L3 语义，不能直接复用其 store。

### 2.4 四 Stage 的不同预期

| Stage | 最小样本 | 预期结果 | 说明 |
|---|---|---|---|
| `quant.sma20` | 20 根 | 合法 `insufficient_data` 降级 result | 与 factor 共用同一日历；factor limit=6 且 Quant `minimum_coverage=1`，因此本专项只提供 6 个交易日，sma20 只能降级 |
| `quant.factor` | 6 根 | 成功产出 result | 三因子 Close-only；momentum_5d 用 6 根真实计算 |
| `quant.trend` | 61 根（momentum_60d） | 成功产出 result | 种子 36 根；momentum_60d 降级但方向可判定，Stage `succeeded` |
| `quant.risk` | 事实快照 | **恒 `reject`**（语义正确） | 缺 `price_limit` / `tradable_volume` 两项外部事实；拒绝表达为 Stage `succeeded` + `decision_status=reject` + `result_status=rejected`，可追溯 |

因此 L3 通过的正确口径是：factor/trend 产出成功 result，sma20 产出合法 `insufficient_data` 降级 result（Stage `degraded` + `quant_sma20_insufficient_data`），三者均有 OutputRef；risk 产出 Stage `succeeded` + `decision_status=reject` + `result_status=rejected`，缺项为 `price_limit`/`tradable_volume`；Run 终态为成功。任何"四 Stage 全 succeeded"的断言都错误地把风险拒绝当成成功，禁止使用。

## 3. 方案选项

### 方案 A：向隔离库写真实种子 + 真实 Data Module（推荐）

在 L3 测试创建隔离库、应用迁移后，用生产 repository API 写入：61 根以上合法 bar revisions（含精确 Close 证据、PIT 时间戳、`NormalizationVer`）、一张覆盖同区间的 valid 交易日历快照、一条已发布 DataAccessPolicy（Owner scope、quant purpose、data:read）。随后照常创建 Run、启动真实 Worker，Data Module 从 MariaDB 读种子并经 Creator/Authorized Reader 产出授权快照。

- 优点：完全走真实 Data 代码路径与 MariaDB 持久化；无伪造快照、无降低门禁；与 L3 既有编排链路零冲突。
- 代价：需精确构造三类相互关联且满足 PIT/指纹/授权门禁的种子；首轮需多轮失败→归因→修正（属规则 12 的正常根因排查，不是降低标准）。
- 边界：bar 为**合成但合法**的交易日序列（如现有 e2e 的 20 根真实量级收盘价），不是某只真实证券的历史行情；这是测试 fixture 的正常语义，不是"伪造数据"——伪造指篡改门禁证据或跳过校验。

### 方案 B：给 Worker 进程注入受控 eastmoney HTTP doer

让真实 eastmoney provider 通过受控 HTTP 响应返回合成行情，日历/授权仍走种子。

- 缺点：`marketdataconfig.LoadForRoot()` 无 HTTP doer 注入点（`bootstrap.go:75`、`marketdata_module.go`）；要么为此开一个仅测试用的配置口子（引入无生产调用方的接口，违反 AGENTS.md 规则 10），要么改成进程内 Worker（丢失 L3 真实 OS 进程语义）。不推荐。

### 方案 C：只扩现有内存 e2e，不动 L3

用现有 `quant_factor_end_to_end_test.go` 的内存 Store 模式补 sma20/trend 的种子 e2e。

- 缺点：不验证真实 MariaDB + 真实 Worker 路径，退回到 L2 证据，不满足本专项目标。不推荐。

## 4. 推荐路线（方案 A）

1. **种子 helper**（新增测试辅助，仅测试代码）：构造 61+ 根 bar revisions + valid 交易日历 + 已发布 DataAccessPolicy，经生产 repository API 写入 L3 隔离库。精确 Close 证据、PIT 时间戳、`normalize.Version`、`data:read` policy 全部按 `data.go:4310-4320` 与 `quant_factor_end_to_end_test.go` 的真实口径构造。
2. **接入 L3**：在 `TestQuantResearchMariaDBRedisL3` 应用迁移后、创建 Run 前调用种子 helper；把终态断言从"四 Stage 均 terminal"收紧为"三 Stage succeeded + result 可授权读取、risk 可追溯 reject、Run 成功"。
3. **变异验证**：至少三处——① 去掉日历种子使日历降级 → 三 Stage 应拒绝产出；② 去掉授权策略 → 快照授权失败；③ 篡改 bar 的 `SystemObservedAt` 到 asOf 之后 → PIT 过滤掉。每处均需测试变红后恢复。
4. **CI 门禁**：复用现有 `integration-ci.yml` 的 L3 步骤（已要求 `--- PASS`），无需新增开关；本专项在同一 opt-in 开关下执行。
5. **文档回填**：`doc/quant/13` 第 12.4 节边界、退役执行清单 2.1 行、联调进度文档同步为"已验证"。

## 5. 需要拍板的设计决策

| # | 决策点 | 推荐 | 理由 |
|---|---|---|---|
| D1 | 种子 bar 口径 | 合成但满足全部 PIT/精确值门禁的 36 根交易日序列（9 月 30 天 + 10 月末 6 天，非真实证券历史） | 测试 fixture 的正常语义；满足门禁即可验证链路。因 sma20/factor 共用 10 月窗口日历且 factor limit=6、`minimum_coverage=1`，10 月只保留 6 个交易日；sma20 因此合法降级，不放宽门禁 |
| D2 | risk 终态处理 | 保留恒 `reject`，断言"可追溯拒绝"而非产出成功 result | 当时缺涨跌停制度表与可成交量模型两项外部事实（`tradable_volume` 后由 DEC-PLAT-002-066 用 Eastmoney 五档盘口解决，仅剩 `price_limit`）；不能为"四 Stage 全绿"而伪造事实或放宽门禁 |
| D3 | 种子 helper 落点 | 放在 L3 测试文件内（或同包 `_test.go`），不进入生产代码 | 种子是测试 fixture，不是生产工具；避免无生产调用方的接口 |
| D4 | 是否给 L3 加独立开关 | 不新增，沿用 `QUANT_RESEARCH_MARIADB_REDIS_L3_TEST` | 一个 L3 门禁，避免开关碎片化与 SKIP 误绿 |

## 7. 实施记录与真实缺陷归因（2026-11-26）

本轮按方案 A 实施，新增 `internal/server/bootstrap/quant_research_l3_seed_test.go`，并收紧 `TestQuantResearchMariaDBRedisL3` 的终态断言。过程中先失败再归因、逐层修正 fixture 与真实生产缺陷，未降低任何测试或契约门禁：

1. `SourceVersion=eastmoney-l3-seed-v1` 不满足 Close Series 首批白名单 `eastmoney-stock-api-v1` → 改为生产支持的接口版本常量；未扩展白名单。
2. PIT warning `daily_bars_reconstructed_from_recorded_revisions` 被当作质量降级，与 DATA-CTR-007 强制 PIT cutoff 的要求结构性矛盾，导致 PIT Snapshot 永远无法达到 `valid` → 在 `normalize.HasQualityDegradingBarWarnings` 中把该提示性 warning 与 `bars_truncated_to_limit` 同列，并同步修正 `normalize_test.go` / `reader_test.go` 断言。PIT、内容寻址、授权读取、精确 Close 证据等门禁均未放宽。
3. 种子 bar 缺 `Volume`/`Amount`/单位，`normalize.ValidateAndSortBars` 全部丢弃 → 按 `shares`/`CNY` 补齐规范化字段和精确证据；目标是把 fixture 做到合法，而不是跳过校验。
4. 交易日历按精确 start/end 查询，sma20/factor 的 `10-01..10-30` 与 trend 的 `09-01..10-30` 是两张快照 → 分别写入两张合法日历；10 月窗口只保留最后 6 个交易日，与 factor limit=6 和 Quant 100% 覆盖率门禁一致。
5. risk 交易状态事实缺 `SecurityName`/`NameEffectiveFrom`/`ListingTradingDayNumber`，生产 PIT 校验正确拒绝 → 补齐有效历史名称和上市交易日序号；不发布 price_limit/tradable_volume，risk 仍恒 reject。
6. 真实授权决策持久化首次暴露生产缺陷：Application 签发结构与 Repository 规范化校验结构的 JSON 字段顺序不一致，导致所有真实 MariaDB `AppendDataAuthorizationDecision` 在 `market-data authorization decision invalid` 失败 → 按 Golden 的规范化字节顺序调整 Application 结构体字段顺序，保留 Repository 的逐字节防漂移校验，不加旁路。

最终本地实测终态：`Run=succeeded`；`quant.factor=succeeded`、`quant.trend=succeeded`、`quant.sma20=degraded [quant_sma20_insufficient_data]`、`quant.risk=succeeded`，四 Stage 均有 `OutputRef`；risk payload 为 `status=reject`、`result_status=rejected`、`missing_facts=[price_limit,tradable_volume]`。

## 8. 明确边界（不做）

- 不引入涨跌停制度表 / 可成交量模型（属 1.4 独立立项，本专项只验证"有种子能产出"，不验证"门禁放行"）；
- 不为 HTTP doer 注入开生产配置口子；
- 不改任何契约状态（QNT-CTR-003 仍 `deferred`、004/005 仍 `frozen`）；
- 不把合成 bar 冒充真实证券历史行情，不伪造 PIT/授权证据；
- 不覆盖 HTTPS 浏览器 + CSRF 传输层（仍属 Server 卡点 379 的目标环境验收）。
