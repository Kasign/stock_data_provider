## 0. 结论摘要

阶段 2.2 **不是"从零实现"，而是"把已装配但从未发生的行为接通并验收"**。

- `Run ↔ Quant Result` 的强类型关联校验器**已存在且已生产装配**，四个 Quant Stage 的封闭规格表、Payload/Quality 双 Validator、`result_id` 精确比对、fail-closed 分流都有实现与测试；
- Quant 侧授权读取 Port（`GetResult` + MySQL 授权读取器 + `FOR UPDATE` 撤销竞态护栏）**也已存在且已装配**；
- 真正的缺口是：这条链**没有任何生产消费者**——组合根把对象图构造完就存进结构体，全仓无任何 Stage / Worker / HTTP 发起读取，L3 集成测试也零引用。即"对象图存在、行为从未发生"。

**推荐路线**：本组严格限定在**领域层 + 组合根 + 真实 Worker 可信边界**，以现有 L3 真实 MariaDB/Redis 闭环作为消费锚点，补端到端贯通与四类 fail-closed 变异验证；**不新增 HTTP 端点、不碰完整报告正文**。报告正文链路依赖的 LLM Gateway 与 News `available_at` 真实来源证据，按用户已确认的口径**如实保留为外部阻塞**，不用空壳结果资源冒充"报告能力已具备"。

> 关键提醒：不得因为"对象已装配 / 单测已覆盖"就把 2.2 判为完成。验收必须落在**真实生产对象图上的行为**（`AGENTS.md` 规则 11/14）。

## 3. 问题定义：2.2 真正要闭环什么

清单退出条件是「同 Run 关联可读；跨 Run、无关联、伪造 RunRef、撤销竞态均 fail-closed」。这些语义在**单元层与存储层**已有覆盖，但在**生产全链**上逐项留白：

| 验收语义 | 现有覆盖 | 精确空白 |
|---|---|---|
| 同 Run 关联可读 | `quant_result_association_test.go:90-150`、`quant_factor_end_to_end_test.go:395-434`、`authorized_reader_integration_test.go:12-84` | 全部用 stub 构造 verifier / stub reader，**没有**贯通 `bootstrap → newResearchflowComposition → GetResult.Execute → VerifyResultAssociation → WithCurrentResultAccessPolicy → GetRecord` 的真实链 |
| 跨 Run fail-closed | `quant_result_association_test.go:216-229`、`stage_output_reader_test.go:151,185` | 现有是**篡改单条 Stage 行 RunRef** 的完整性变异；缺「Run A 与 Run B 都真实持久化，用 Run B 的合法 `result_id` 配 Run A 的合法 `run_ref` 发起完整读取并断言拒绝」的端到端用例 |
| 无关联 / 伪造 RunRef | `quant_result_association_test.go:161-207,278-306`、`get_result_test.go:274-305` | 单元层充分；缺生产对象图上的同类断言 |
| 撤销竞态 fail-closed | `policy_owner_integration_test.go:192-267`（真实 MariaDB `FOR UPDATE` 串行化 Revoke） | 只在**存储策略 guard 层**；缺 `GetResult.Execute` / 组合根层「读取过程中 revoke → 不返回 Envelope」的端到端用例 |
| 规格表完整性 | `quant_result_association_test.go:308-336` | `:320` 只遍历断言 SMA20 + Factor，**未断言 Trend/Risk**（Risk 靠 `quant_risk_stage_test.go:397` 单点补，Trend 无同等级断言） |

**一句话**：2.2 的交付物是**让已经写好的门禁在真实生产链上真的发生，并且每一种拒绝都能被端到端证明**，外加把 Evidence 侧的同类空白补上、把 L3 门控遗漏修掉。
