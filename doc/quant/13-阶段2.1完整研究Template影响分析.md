## 1. 结论摘要

**2.1 现在做不成，但缺口不是"少写一个模板"。**四个 Quant Stage（sma20 / factor / trend / risk）已经各自可执行、可持久化、可授权读取，把它们放进同一个模板这件事，被三处结构性缺口和两处契约约束挡住：

| 缺口 | 性质 | 后果 |
|---|---|---|
| **B1 参数作用域** | 代码结构 | 一个模板只有**一份**参数文档，四个 Stage 的执行器都用 `DisallowUnknownFields` 严格解码各自的字段集，四份 Schema 的字段集**互斥**（`trade_date` vs `start_date/end_date`，`limit` 下限 20/6/61 不同）。合并模板后**四个 Stage 全部参数非法**。 |
| **B2 外部 `$ref` 被禁用** | 校验器约束 | 合并模板的参数 Schema 不能用 `$ref` 引用四份既有 Schema，只能把约束**内联**（`$defs`），产生重复维护。 |
| **B3 依赖校验器为 nil** | 生产装配缺口 | `DependencyOutputValidator` 只有接口无实现，生产 `NewScheduler(..., nil, ...)`。**任何带依赖的 Stage 在上游成功后会让调度器直接报错**，下游永不执行。 |
| **B4 模板指纹不可漂移** | 契约/运维约束 | 指纹由结构体 JCS 计算，`Publish` 遇同 ref+version 不同指纹即冲突并阻断启动。给模板结构加字段必须 `omitempty`。 |
| **B5 SRV-CTR-001 冻结请求 Schema 绑定 News 参数** | 契约 | 冻结的 `create-run-request-1.0.0.schema.json` 把 `parameters` 直接 `$ref` 到 `news-search-parameters-1.0.0`。Quant Run 在契约层面"无位置"，而运行时并不按它校验——契约与实现已经不一致。 |

**推荐路线**：新增 `quant.research@1.0.0` 模板 = 四个 Stage **并列、无依赖**、参数按 Stage 命名空间化；把 B1 修在**请求组装层**（Worker）而不是改四个执行器；B4 用 `omitempty` 规避；B5 单独立 DEC 出新版请求 Schema。

**关键判断**：v1 **不声明 Stage 间依赖**。理由不是"偷懒"，而是三条硬事实：① 四个 Stage 各自独立创建 Data 快照，没有任何一个读另一个的输出；② 生产依赖校验器为 nil，加依赖必然阻断；③ 装饰性依赖会制造"看起来有序、实际不传递数据"的假语义。真正的 Stage 间数据传递是 Signal 链路（QNT-CTR-006 仍 `deferred`）与报告聚合（2.3）的事，不属于 2.1。

## 3. 五个缺口的详细判断

### B1 参数作用域（阻塞项，必须本轮解决）

现状是"一份文档喂给所有 Stage"，而各 Stage 的字段集互斥。三条可能路线：

| 路线 | 做法 | 判断 |
|---|---|---|
| **A. 命名空间化（推荐）** | 模板参数改为 `{"stages": {"quant.sma20": {...}, "quant.risk": {...}}}`；Worker 组装 `StageExecutionRequest` 时按 `Stage.Code` 取子树 | **推荐**。四个执行器与其 20+ 测试**零改动**；严格解码的好处全部保留；非法参数在 CreateRun 阶段就被拒绝 |
| B. 并集 Schema + 宽容解码 | 顶层放开 `additionalProperties`，执行器去掉 `DisallowUnknownFields` | **否决**。严格解码是唯一挡住"字段拼错被静默忽略"的机制；`limit` 下限冲突无法用一个值表达；等于用全局放松换取局部便利 |
| C. 只做单 Stage 模板，Run 内多次提交 | 前端连续创建 4 个 Run | **否决**。这会把"一次研究"拆成四个无关联 Run，`Run↔Result` 关联（2.2）与报告（2.3）失去锚点，用户看到的是四条独立记录 |

A 路线的**落点很关键**：切片必须发生在 Worker 组装请求处（`worker.go` 附近），不能在四个执行器里各写一遍，也不能靠在模板里塞固定字段名。

**显式优于隐式**：建议给 `template.WorkflowTemplate` 增加 `ParameterScope`（`"template"` | `"per_stage"`，`omitempty`）。理由：
- 靠"有 `stages` 键就切片"是形状嗅探，未来任何人加一个叫 `stages` 的业务字段就会静默改变语义；
- 加了 `omitempty` 且既有模板该字段为空 ⇒ 序列化字节**完全不变** ⇒ 指纹不变 ⇒ 不会触发 B4 的启动失败；
- 新模板显式声明 `per_stage`，语义可读、可测。

配套校验（CreateRun 阶段 fail-closed）：`per_stage` 模板必须满足——
1. 参数根只有 `stages` 一个键，`stages` 内键集合 **恰好等于**解析后可执行 Stage 的 code 集合，不多不少；
2. 每个子树必须非空 object；
3. `template` 作用域模板**不得**出现 `stages` 键（防止两种形态混用）。

### B2 外部 `$ref` 禁用（约束，靠测试兜住）

合并 Schema `quant-research-parameters-1.0.0` 只能内联四份子约束。这带来**两份真相**：`doc/researchflow/schema/quant-*-parameters-1.0.0.schema.json` 与合并 Schema 的 `$defs`。处置：

- 合并 Schema 的 `$defs` 由四份既有 Schema 的**逐字节复制**得到（不重写、不"顺手优化"）；
- 新增一条契约测试：四份既有 Schema 的 `properties`/`required`/`additionalProperties` 与合并 Schema `$defs` 中对应子树**深度相等**，漂移即失败；
- 不引入代码生成器（本轮收益不足以摊平生成器本身的维护成本），但测试必须能在"只改了一边"时立刻红。

### B3 依赖校验器为 nil（若声明依赖则必然阻断）

`scheduler.go:102` 的 nil 检查发生在**上游已成功且已有 OutputRef** 之后，所以症状是：Run 正常启动、第一个 Stage 成功、随后调度报错，下游 Stage 永远停在 `pending`，Run 卡到 Deadline 才失败。这是最难排查的一类失败——表面上"跑了一半"。

因此 v1 的模板**不声明依赖**。若未来确实需要依赖（例如"风险门禁必须在趋势之后"），必须同时交付 `DependencyOutputValidator` 的生产实现，不能只加 `Dependencies` 字段。

### B4 模板指纹不可漂移（约束，决定实现细节）

`Publish` 在启动时执行，指纹不匹配 = 启动失败。所以：
- 新增字段必须 `json:"...,omitempty"`，且既有模板取零值；
- **不允许**改动既有模板的任何字段值（包括把 `Priority` 从 0 调成别的值）；
- 合并 Registry 必须是**新版本号**（建议 `1.6.0`），不能就地改 `1.5.0` 的 Entry 集合。

### B5 SRV-CTR-001 冻结请求 Schema 绑定 News 参数（契约，须单独立 DEC）

实际情况：运行时**不**按该 Schema 校验请求（`researchflow_http.go:135` 直接 decode 进 `CreateRunCommand`，参数校验交给模板的 `ParameterSchemaRef`），但冻结文档写着 `$ref` 到 News 参数、且契约正文说"首期 News Search 参数"。结果是**文档与实现不一致**，而 2.1 会让这个不一致变成"Quant Run 用的是契约里不存在的参数形态"。

三条路线：

| 路线 | 内容 | 判断 |
|---|---|---|
| **A. 新增 `create-run-request-1.1.0`** | `parameters` 改为 `{"type":"object"}`，正文写明"参数形态由 `template_ref` 指向的模板参数 Schema 决定，本 Schema 只约束顶层信封" | **推荐**。与实现一致；对 1.0.0 是新增版本而非篡改；News 现有请求在 1.1.0 下依然合法 |
| B. 保持 1.0.0，只在正文加注 | 不动 Schema，只补一句"News 专属" | 次选。Schema 仍撒谎（`$ref` 存在即意味着约束存在），下游工具按 Schema 生成的客户端会误判 |
| C. 本轮不处理 | 记录为已知不一致 | 不推荐。2.1 的交付物会正式引用这个契约 |

该项属于 `frozen` 契约变更，必须走 DEC 与版本登记，不能顺手改。

## 4. 待确认决策

| 编号 | 决策 | 推荐 | 理由 |
|---|---|---|---|
| **D1** | 参数如何分流 | **A：命名空间化 + 显式 `ParameterScope`** | 四个执行器零改动；严格性不降；非法参数在 CreateRun 即拒 |
| **D2** | v1 是否声明 Stage 间依赖 | **否，四个 Stage 并列** | 无数据依赖 + 校验器为 nil + 避免假语义 |
| **D3** | 模板组成 | `quant.sma20 + quant.factor + quant.trend + quant.risk` 四 Stage；**不含 Signal** | Signal 无生产 Stage、QNT-CTR-006 仍 `deferred`；参数不要求 Signal 引用是上一轮已确认的 D3 |
| **D4** | `quant.research` 的 `RequiresHardRiskGate` | **false（不声明）**，与四个单 Stage 模板一致 | 声明 hard_risk 需要 Gate Registry 注入且会改变 Run 终态语义（`actionable/blocked`），属 2.4 的风险语义统一，不在 2.1 |
| **D5** | 传播策略 | 四个 Stage 统一 `OnDegraded=Accept`、其余 `Fail` | 与既有单 Stage 模板一致；risk 的 `reject` 是 `succeeded`，不走 degraded 路径 |
| **D6** | SRV-CTR-001 处置 | **A：新增 1.1.0 + DEC**；本轮只登记决策与文档，代码不改 | 冻结契约不能顺手改；但必须在 2.1 交付前定 |

**D1 的一个子问题需要一并确认**：`per_stage` 模板的**参数 Schema 归属**。
- 选项 1（推荐）：合并模板引用**一份新的** `quant-research-parameters-1.0.0`（信封 + `$defs` 内联四份子约束），Worker 只按 code 切片，不再对子树做二次 Schema 校验（子树约束已在合并 Schema 里生效）。
- 选项 2：合并 Schema 只约束信封形状（`stages` 为 object），每个 Stage 执行前用该 Stage 的既有 Schema 再校验一次子树。更严格但要在 Worker 里引入参数 Schema 依赖（Worker 目前不持有校验器），并把"参数错误"从 CreateRun 推迟到执行期——**违背 fail-fast**，不推荐。
