## 1. Data 依赖

| 依赖项 | Quant 用途 | 当前状态 | 责任方/解锁条件 |
|---|---|---|---|
| DailyBars v2 Decimal | Indicator/Factor 价格序列精确输入 | DATA-CTR-005 deferred；当前 v1 为 HTTP JSON number / InProcess float64 | Data Owner 完成精度可保真的 v2 DTO、scale/舍入、单位/缺失语义、interval、交易日历版本和真实 DTO/Golden |
| Snapshot 与 Evidence Locator | 输入快照身份、内容寻址和可追溯引用 | DATA-CTR-007 deferred | Data Owner 完成 Manifest、Snapshot 引用和访问契约 |
| PIT/复权 | 防止未来数据泄漏，保证价格口径一致 | 需按冻结 Data 契约验收 | Data 提供 available_at、source_version、adjustment_basis/reference_date 等权威元数据 |
| 交易日历/停牌 | 确认序列连续性和有效样本数 | 当前生产输入未闭环 | Data 提供版本化交易日历、交易状态及停牌/缺失区分 |
| 证券/行业主数据 | Market/Industry/Stock 分析 | 未满足对应分析输入 | Data 提供历史有效期、版本和稳定引用 |

Data v1 代码核验（只读 `feat/data`，HEAD `4fb13f3b9c2904b6a3a976075539c5d86a1b92ab`）：`internal/marketdata/app/port.go` 的 DailyBar OHLC/Amount/ChangePercent 为 float64，QuoteSnapshot 价格/金额/比率为 *float64，Volume 为 *int64；`internal/marketdata/httpapi/openapi.yaml` 对价格/金额/百分比使用 JSON number，对 Volume 使用 integer/int64。该链路是现有兼容基线，不代表十进制精度保真。把 float64 格式化成 String 不构成 Decimal v2，也不能恢复源值精度。

Quant 不得复制 Data Provider、行情标准化、Snapshot 存储或交易日历权威事实。DATA-CTR-005/007 未解锁前，相关真实数据链路标记 blocked/not_comparable，不发布伪真实结果。

## 2. Server / Platform 依赖

| 能力 | 当前 Quant 代码 | 责任方与缺口 |
|---|---|---|
| 可信 Principal | PrincipalResolver Port | Server 注入真实认证上下文，不接受请求自报主体 |
| 授权复核 | GetResult 应用层校验 AuthorizationRef/PolicySnapshot | Server/Platform 提供当前策略快照、撤销检查及一致性边界 |
| Storage | Save/AuthorizedResultReader Port、MemoryRepository | Server/Platform 提供生产 Adapter、事务、Migration 和连接生命周期 |
| Access Audit | AccessAuditor Port、内存测试 | Server/Platform 提供持久化 Adapter、保留策略和故障注入 |
| Clock | Application 注入边界 | Server 提供可信 UTC Clock；不得由 Domain 调用 time.Now |
| Diagnostics/Fault | 复用 Platform 公共语义 | Quant 只定义领域 Check 和判定，不新增第二套通用诊断/故障框架 |

Quant 只维护领域端口、调用时机和必要契约测试；不在 `internal/quant/**` 内创建 SQL、Redis、通用 Storage、Authorization 或 Diagnostics 框架。

## 3. Researchflow 依赖

- Researchflow 是 Quant 计算 Application 的首要消费者。
- Quant 提供强类型 Application Facade、稳定请求/响应、ResultRef/Envelope 和授权读取用例。
- Researchflow 负责生成/传播 request_id、correlation_id、可信 CallerRef，调用公开 Application Port，校验并消费已注册 Payload。
- Research 不直接 import Quant；需要量化结果时由 Researchflow 编排并传递授权引用/结果上下文。
- 目前 Quant Application 只有 GetResult，没有 Indicator/Factor 计算 Facade；不得把纯函数串接为伪生产 Provider。
- 只有完整 Payload Schema/Golden/Validator 和 Registry 注册项均存在的 result_type 才允许跨模块发布。

## 4. 当前解锁顺序

1. Quant 内部：QNT-001 Registry Entry → QNT-002 Indicator Payload → QNT-014 计算 Facade。
2. Data：DATA-CTR-005/007 满足登记簿重新进入条件后，Quant 才执行 QNT-015 真实输入 Adapter；Factor 同时等待 QNT-CTR-003 状态变化。
3. Server/Platform：完成生产 Reader/Storage/Auditor/Principal/Clock 注入后，QNT-013 才能通过生产持久化与授权验收。
4. Researchflow：在 Quant Facade、Payload Registry、CallerRef 和授权读取均具备后，执行实际 Stage Provider 消费验收。
5. Trend/Market/Industry/Stock/Strategy/Backtest 按各自真实输入和算法决议推进，不因当前联调完成而提前开放。

## 5. 诊断判定边界

| 状态 | Quant 依赖判定 |
|---|---|
| pass | 依赖契约已冻结、真实输入可读、快照/授权/质量证据完整 |
| degraded | 依赖明确允许降级，且缺失字段不影响本用例的必要计算语义 |
| fail | 必需依赖不可用、授权拒绝、数据完整性/PIT/复权门禁失败 |
| not_comparable | 契约版本、复权基准、交易日历、时间窗口或样本集合不一致 |

skipped 不计为 pass；不可比较不能降级为“基本通过”。诊断状态不替代 Quant 的 quality_status/result_status。

## 6. QNT-013 生产结果持久化结构审查（2026-11-20）

审查基线：repair_all HEAD `08fd5ec165421e562a585e1412b190e76081cede`。本节是实现前的模块内设计审查，不等同于已冻结 SQL Schema 或已实现生产存储。

### 6.1 已有能力与边界

- Quant `result.Record` 由 `manifest.Manifest` 与原始 `json.RawMessage Payload` 组成；`Record.Validate/ValidatedSnapshot` 验证 Manifest 内容寻址身份与 Payload 指纹，并深拷贝输入。
- `manifest.Manifest` 已包含 result_id、manifest_fingerprint、result_fingerprint、result_type、scope、security_id、trade_date、period、quality_status、result_status、schema_version、payload_schema_version、algorithm_version、parameter_fingerprint、system_as_of、input_snapshot_refs。AuthorizationRef 不属于 Manifest，不应混入不可变结果身份。
- `Repository.Save` 的正式语义：相同 result_id 且内容一致幂等成功；相同 result_id 内容不一致返回 ErrResultConflict；唯一性判断与写入必须原子。
- Platform `internal/platform/storage` 已提供 SQL pool、namespace Migration Runner 和 checksum/history 校验；Server Migration Registry 接受模块拥有的 Migration 定义。Research `internal/research/storage` 提供模块自有 Repository + Migration + SQL 事务实现参考。
- 当前 Quant 没有 SQL Repository、Migration、读取 Adapter 或审计持久化 Adapter；不将 Research Repository 复制到 Quant，也不把 Quant 表结构放入 Server。

### 6.2 最小持久化模型（待代码实现与契约核对）

建议首版只建立一个不可变结果记录表，不预建索引目录、版本头表、Outbox 或派生查询表。建议逻辑字段如下，具体列类型/长度需由 Migration 实现和 MariaDB Integration 再验证：

| 字段 | 用途 | 约束建议 |
|---|---|---|
| result_id | 内容寻址主键 | ASCII 二进制比较；主键唯一；长度覆盖 `quant_result:sha256:` + 64 位小写 SHA-256 |
| manifest_fingerprint | Manifest 指纹冗余校验/冲突比较 | 固定 64 位小写十六进制 |
| result_fingerprint | Payload 指纹冗余校验/冲突比较 | 固定 64 位小写十六进制 |
| manifest_json | 完整不可变 Manifest 序列化 | 保留 input_snapshot_refs 显式空数组语义；读取时重新 Verify |
| payload_json | 原始 Payload JSON | 不做业务重塑；读取时重新 VerifyPayload |
| created_at | 首次成功持久化时间 | UTC DATETIME(6)，幂等重放不得覆盖 |

字段来源均为现有 `manifest.Manifest`、`result.Record` 和 Repository 契约；created_at 是存储审计时间，不得替代 system_as_of。现阶段没有已确认的列表/筛选查询用例，不增加 result_type/scope/system_as_of 二级索引。不得把 AuthorizationRef、subject_ref、policy_snapshot 或 access audit 放进结果 Manifest/结果表，它们属于独立授权和审计边界。

### 6.3 Save 原子语义建议

1. 事务外先执行 `ValidatedSnapshot`，避免把无效记录送入 SQL。
2. 使用 result_id 唯一键进行单条原子插入；冲突路径必须取得已有行的稳定锁并读取已有 manifest_fingerprint/result_fingerprint。
3. 两个指纹均一致则幂等成功，保留首次 created_at；不一致返回 ErrResultConflict，绝不覆盖 manifest_json/payload_json/created_at。
4. 不以先 SELECT 再 INSERT 的无锁流程实现唯一性检查；不得使用 REPLACE、无条件 UPSERT 覆盖不可变记录。
5. 并发 Integration 必须覆盖相同内容并发 Save、异内容相同 result_id 冲突、失败回滚、取消 Context、进程重启后可读和存储损坏拒绝。
6. DB 唯一键是最终并发仲裁；应用层指纹校验不能替代唯一约束。

### 6.4 授权读取与审计不能混入 Save Repository

- `GetResult.AuthorizedResultReader` 要求在一个可证明的线性化/一致性边界内读取当前 Quant Owner 策略快照、判定 subject/resource/purpose/content_level，并读取不可变结果；策略在检查与读取之间变化或无法证明同一策略版本时必须拒绝。
- 结果记录不包含可信主体，也不携带可直接复用的历史授权决策。AuthorizationRef 是本次读取返回的授权证明，不是存储层永久访问许可。
- `AccessAuditor` 必须单独持久化每次已识别主体的读取决策，且审计失败时 Application 不释放结果。审计事件不存储 Payload 或受限内容。
- 因此 Save Repository、AuthorizedResultReader、AccessAuditor 可共享 Quant 模块的 SQL 连接/事务基础设施，但不能将三者揉成一个不受控的通用 Repository；各自事务和线性化边界须分别定义。
- GOV-CTR-006 已明确 policy_owner=quant、MVP subject_ref=Researchflow service principal、resource_ref=result_id、purpose_code=quant_analysis、content_level=full；Owner/主体映射不是待决项。仍缺 Quant Owner 的实际策略定义/存储/版本快照签发、当前策略复核和撤销并发实现，以及审计保留/失败处置实现。不得默认 Allow、缓存旧 allowed 或伪造策略快照。

### 6.5 实施顺序与当前判定

1. Quant 实现模块自有 `internal/quant/storage`（仅在正式开始生产实现时创建），提供 Repository SQL Adapter 和版本化 Migration；本轮不先建空目录/空 namespace。
2. Server 只注册 `quant` namespace 的 Quant Migration，并在 Root 构造 Quant Repository；连接池及 migration runner 复用 Platform。
3. 授权策略决议明确后，再实现 AuthorizedResultReader 的事务一致性、PrincipalResolver 注入和 AccessAuditor Adapter。
4. 完成 MariaDB 并发/冲突/重启/损坏/撤销竞态/审计失败 Integration，再把 QNT-013 生产闭环标记通过。
