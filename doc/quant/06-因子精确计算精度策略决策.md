# 因子精确计算精度策略决策

- 适用契约：QNT-CTR-003（Factor Request/Result）、QNT-CTR-004（Factor QuantMetric）、GOV-CTR-001（公共 JSON 数值规则）
- 适用因子：MADistance20（`ma20_distance`）、Momentum5（`momentum_5d`）、Momentum20（`momentum_20d`）
- 决策日期：2026-11-26
- 状态：Quant 内部计算精度策略决策；经 DEC-PLAT-002-057 授权已 additive 修订 003/004 1.0.0 Schema（见第 5 节进度更新），项目级契约状态未变，QNT-CTR-003 继续 `deferred`
- 实现位置：`internal/quant/factor/decimal_factor.go`

## 1. 决策背景

首批 Close-only Factor 复用 Data 已授权的 Close Series Snapshot，其 Close 是十进制字符串（Provider 原始精度证据随 Payload 保存）。QNT-CTR-003 登记簿第 51/79 行的解锁条件明确要求"Decimal Factor Registry Entry / 算法精度策略"。但项目内存在两条不同的精度路线，必须先明确比率因子走哪条，否则后续 Schema/Golden/Registry 会建错方向。

- SMA20 生产链：`indicator.DecimalSMA` 用 `big.Rat` 精确计算，`finiteDecimalString` 只接受分母质因数仅为 2/5 的有限小数，否则返回 `ErrNonTerminatingDecimal`；Registry 精度策略为 `RoundingMode="exact"`、`Tolerance="0"`。它能精确是因为 `sum/20`（sum 为两位小数、20=2²×5）必为有限小数。
- 现有 Factor 纯函数：`factor.Result.Value` 是 `float64`，Golden 用 `tolerance=1e-12` 的浮点容差比较。
- 登记簿事实：公共 GOV-CTR-001 已冻结"Decimal 语法与 number 精度/舍入原则"，但明确"字段级 scale、单位、范围、舍入、tolerance 由对应领域 CTR 负责"。

## 2. 核心事实：比率因子不能用 exact

MADistance20 = `last / (Σlast20 / 20) - 1`，Momentum = `last / base - 1`。两者都是两个十进制数相除。除数（均值或 base）含 2/5 以外的质因数时，结果是无限循环小数。例如：

- `MADistance20(19×"3", "1")`：均值 = 58/20 = 2.9，`1/2.9 - 1 = -0.655172413793...`（循环）。
- `Momentum5(95..100)`：`100/95 - 1 = 1/19 = 0.052631578947...`（循环）。

若照抄 SMA 的 `exact`/0 tolerance，这些合法输入会被全部拒绝，等于让精度策略反过来破坏业务可用性。因此比率因子必须定义"精确中间计算 + 明确舍入输出 + 声明容差"，而不是"精确表示"。

## 3. 决策

| 项 | 取值 | 依据 |
|---|---|---|
| 中间运算 | `math/big.Rat` 有理数，全程不经 `float64` | 与 SMA 生产链一致，避免浮点误差累积；满足"精确 Close 输入"初衷 |
| 输入 | 十进制字符串 `[]string`，格式 `^-?(0|[1-9][0-9]*)(\.[0-9]+)?$`，价格必须 > 0，单值 ≤128 字节，样本 ≤10000 | 复用与 `decimal_sma.go` 相同的输入边界，拒绝 float/指数/前导零/空格 |
| 输出 | 固定 `scale=12` 的十进制字符串，去掉尾部零 | 与现有因子 Golden 的 `1e-12` 量级相当，不降低既有精度口径 |
| 舍入模式 | `half_even`（银行家舍入） | Registry 已支持该模式（`registry/entry_test.go` 采用），金融比率通行做法，无正向偏置 |
| 样本不足 | `Value=""`（后续投影为 JSON `null`），`SampleCount=实际根数` | 不用 0 代替缺失，遵循 GOV-CTR-001 空值语义 |
| Registry 精度策略（第②组已落地） | `ValueType=decimal_string`、`MaxIntegerDigits=128`、`MaxFractionDigits=12`、`RoundingMode="half_even"`、`Tolerance="0.000000000001"`（12 位末位，JSON string） | 与 SMA 的 `exact/0` 区分；已注册于 `internal/quant/registry/production_factor.go`，生产 Facade 必须读取并断言该 Entry，不得硬编码 |

## 4. 与现有 float64 因子的关系

- 本决策新增 `DecimalResult`（`Value string`）与三个 `DecimalXxx` 函数，**与现有 `factor.Result`（float64）并存**，不删除、不修改现有纯函数与其 Golden。
- `TestDecimalFactorsAgreeWithFloatWithinTolerance` 证明：新 Decimal 实现转回 float 后，与现有 float64 纯函数在既有 `1e-12` 容差内一致。这既验证新实现正确，也保证现有 Golden 口径不被破坏。
- 后续把 Factor 接入生产 Facade 时，计算输入必须来自已授权 Close Series Snapshot 的十进制字符串，并消费本层的 `DecimalResult`；不得把 float64 结果反向格式化伪装成精确值。

## 5. 本决策的边界

- 精度路线仍为 Decimal + big.Rat / 固定 scale=12 / half-even；本层与既有 float64 纯函数并存，不修改其 Golden。
- **进度更新（2026-11-26，第②组）**：经项目负责人明确授权对冻结契约做 additive 修订（决策留痕 `DEC-PLAT-002-057`），本路线已推进到 Schema/Golden/Registry 层：`QNT-CTR-004`/`QNT-CTR-003` 1.0.0 已 additive 放宽以承载 `ma20_distance`、`momentum_5d` 的 decimal_string 表示；`factorPeriod` 已追加两个 code；`DecimalQuantMetric` DTO、3 条 Decimal Registry Entry、算法级与结果级 Golden 均已落地。现有 float64 因子与其 Golden 未受影响。
- 本决策及第②组均不改变项目级契约状态：QNT-CTR-004 仍 `frozen`、QNT-CTR-003 仍 `deferred`；尚不代表 Factor 可生产发布。仍**未接入** Application Facade、Stage、持久化 Payload、Researchflow 结果校验与 Server 装配，也未取得端到端真实质量输入证据与 Contract Test——这些属后续逻辑工作组，完成后再按登记簿重新核验 QNT-CTR-003 的重新进入条件。
