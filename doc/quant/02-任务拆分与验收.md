## 执行批次

1. Q0：先完成旧资产盘点、契约核对和 Golden 设计；Q0 未完成前不批量迁移旧代码。
2. P0：QNT-001~003；QNT-003 与 QNT-002 不建立强制串行依赖。
3. P1：QNT-004~010；市场/行业/个股按契约并行，策略和回测后置。
4. P2：QNT-011/012，等待足够历史样本和回测验收。
5. 存储可与对应领域能力并行设计；QNT-013 不得修改根 Migration 注册入口。

## 完成门禁

- 单测覆盖公式、窗口边界、缺失/异常、单位、精度和时区。
- 固定样本可重复运行，差异有解释。
- PIT/复权有独立测试。
- 回测交易制度和成本假设有边界测试。
- 真实数据验收记录 Provider、证券、日期、样本数、快照和质量。
- CI 精确关联当前 SHA；Mock/Fixture/构建通过不能代替真实数据验收。
- 诊断结果至少区分 PASS、DEGRADED、FAIL、INSUFFICIENT_DATA、NOT_COMPARABLE、UNKNOWN；这些是诊断分类，不得直接扩展或映射替代 quality_status、metric_status、result_status。对外诊断字段须由对应 DTO Schema/Golden 明确，不允许把 unknown/null 转为零或有效排序值。

### 2026-11-12 Factor QuantMetric Schema 边界修正

Review 发现 Factor QuantMetric Schema 对 `insufficient_data` 状态的周期和样本数约束弱于 Go 构造器：原 Schema 只在 `available` 时检查 period 和最低样本数，导致不足样本结果可能使用错误 period，或以达到可用门槛的 sample_count 仍标记为 insufficient_data。

本轮修正：
- 三种首批 Factor metric_code 无论 metric_status 如何，都固定 period：momentum_20d=20d、momentum_60d=60d、volatility_20d=20d。
- available 状态的最低样本数保持 21/61/20。
- insufficient_data 状态的最高样本数分别固定为 20/60/19。
- 新增正确边界和错误周期/错误计数负例，防止 Schema 与 Go 构造器门槛漂移。
- 不改变 FactorResultPayload 注册状态；Factor Metric 子对象 Schema 不等于完整 Factor Payload。DATA-CTR-005 真实输入门禁及 FactorResultPayload 仍按项目契约保持 deferred/fail closed。

验收：Quant Workflow `43152597197`，SHA `7f6dcfd0582d3b505d8b45688bc1b74055a1866f`，gofmt、Quant 单测、Manifest Fuzz、Race、Vet 全部通过。
