### Data v1 数值精度链路核验（只读证据）

本轮只读核对 `feat/data`，没有修改 Data 分支：

- `internal/marketdata/app/port.go`（blob SHA：`40c0c1576de597383f8aefc6f09adccf7d1fb9f9`）：DailyBar 的 OHLC、Amount、ChangePercent 使用 `float64`；QuoteSnapshot 的价格/金额/比率字段使用 `*float64`；Volume 使用 `*int64`。FundamentalMetric.Value 也是 `float64`。
- `internal/marketdata/httpapi/openapi.yaml`（blob SHA：`95c6ee71850c4e50f3265e78fd979f5fd409b4a1`）：Quote、DailyBar 的价格、金额和百分比字段声明为 JSON `number`；Volume 声明为 `integer/int64`。
- 这与项目登记簿中 DATA-CTR-005 的现状一致：当前 v1 HTTP number / InProcess float64；DailyBars Decimal v2 尚未形成 Schema/Golden，DATA-CTR-005 仍为 deferred。

#### 对 Quant 的直接影响

1. JSON number 进入 Go `float64` 后，精度限制已经存在于应用 DTO；即使后续把结果格式化为 JSON String，也不能恢复已丢失的十进制信息。
2. SMA、EMA、MACD、ATR、Bollinger 等价格派生指标若要求精确十进制结果，必须等输入链路提供可保真的 Decimal 值；不能把现有 float64 结果转字符串后标记为 Decimal。
3. Return、Volatility、RSI 等统计指标可以评估 Number 路径，但必须逐 `metric_code` 明确误差预算、舍入规则和固定样本；不能因为它们是小数就统一决定类型。
4. 成交量/样本数继续使用整数语义；标识符、证券代码继续使用 String。不得将所有字段统一改成 JSON String。
5. 现有 v1 契约保持不变。Decimal v2 需要由 Data Owner 按 DATA-CTR-005 重新进入条件定义原始精度保留、Decimal scale、舍入、单位、缺失语义、bar interval 和交易日历版本引用。

**本轮结论：** Quant 采用项目已冻结的按 `metric_code` 固定 JSON 类型策略；价格/金额精确十进制与统计 Number 分流。价格派生指标的 Decimal 正式 Entry/计算路径受 DATA-CTR-005 阻断；不在 Quant 分支复制 Data DTO，也不做 float64→String 的表面转换。

### Return / Volatility / RSI 统计指标审计（QNT-001）

本轮只读核对 `internal/quant/indicator/indicator.go`、`indicator_test.go`、三份 Indicator synthetic Golden、QNT-CTR-002 参数 Schema、QNT-CTR-004 Indicator Payload Schema、GOV-CTR-001 与项目级决策 DEC-PLAT-002-045/052。没有修改算法或项目级契约。

| metric_code | 当前公式/实现语义 | value_type / unit 候选 | 数学边界 | sample_count 口径 | 当前阻断 |
|---|---|---|---|---|---|
| return | simple: end/start - 1；log: ln(end)-ln(start)；仅取末尾 N 个相邻 close | number / ratio（Quant 总体设计明确内部收益率使用 ratio） | simple 理论上 (-1,+∞)；log 为有限实数域 | N 个 return，需要 N+1 个正数 close | 生产 tolerance、max_fraction_digits、rounding_mode 未确定；Data v1 输入精度与 PIT/复权/质量链路未闭环 |
| volatility | 对末尾 N 个相邻 close 计算 simple/log return，使用样本标准差，再乘 sqrt(annualization_factor) | number / ratio（收益率标准差仍为比例量） | 非负；无已证明的有限上界 | N 个 return，需要 N+1 个正数 close | 年化因子与 interval/calendar 的权威映射缺失；生产精度/舍入/容差和质量策略未确定 |
| rsi | 首 N 个 close_change 初始化平均涨跌，后续变化按 Wilder 增量递推；平盘=50、仅涨=100、仅跌=0 | number；unit 尚无权威决议，不擅自填 point/index_point/ratio | [0,100] | 实际参与递推的全部相邻 close_change，当前实现为 len(closes)-1；至少 N+1 个 close | RSI unit、生产精度/舍入/容差和质量策略未确定 |

#### 可确认的事实

1. Return 的 unit=ratio 有 Quant 总体设计依据；Return 与 Volatility 均是统计量，按 GOV-CTR-001 的语义使用 JSON number 是候选方向，不是已注册 Entry。
2. Volatility 的输出是样本标准差乘以 `sqrt(annualization_factor)`。算法只接收调用方提供的正整数因子，不知道输入 bar interval、交易日历或年化依据；不得默认把日线因子设为 252。
3. RSI 的公式边界可由实现证明为 [0,100]，但数值范围不能替代 unit 决议。项目级 DTO 字段契约明确 RSI 量纲需在 Registry Entry 前确认。
4. Return/Volatility 的数学范围是单边界（Return simple 下界 -1、Volatility 下界 0），而当前 Registry `NumericRange` 只能表达“双边界”或“完全 unbounded”，不能表达单边界。不能用任意最大值伪造上界；若暂用 unbounded，必须另由算法边界测试守住公式不变量。
5. 三份 Golden 的 tolerance=1e-12 仅是单个 synthetic fixture 的测试断言；现有极端数值测试中的 1e-9 也是局部测试容差。二者都不能直接成为生产 Entry.precision.tolerance。
6. QNT-CTR-004 Indicator Payload Schema 的 `sample_count` 当前为 optional（未列入 quant_metric.required）；DEC-PLAT-002-052 要求 Entry.required_in_metric 与专属 Metric Schema 一致。生产 Entry 不能擅自设 true；应先确认真实 Metric 构造映射是否保证输出该字段，或明确设 false 并保持 Schema 一致。
7. QNT-CTR-002 的 `annualization_factor` Schema 只有 minimum=1，没有 maximum；GOV-CTR-001 对 JSON integer 规定不得超过 JavaScript 安全整数 9,007,199,254,740,991。当前参数 Schema 未显式表达该上限，属于实现符合性核验项；本轮不修改已冻结的 1.0.0 Schema。
8. 当前算法仅接收 `[]float64`，没有交易日期、interval、calendar_version、adjustment、PIT、snapshot_ref 或质量字段；不能据此生成完整 input_requirements/quality_policy。

#### 当前可推进与不可推进的内容

- 可作为候选进入后续 Entry 草案：Return 的 `value_type=number`、`unit=ratio`；Volatility 的 `value_type=number`、`unit=ratio`；RSI 的 `value_type=number`、数学范围 [0,100]。
- 不得正式注册：三者均缺生产数值精度/容差/舍入；RSI 缺 unit；Volatility 缺年化因子与 interval/calendar 映射；Data 输入要求与 quality_policy 未闭环。
- 现有算法和 Golden 不重写、不改 tolerance 冒充生产精度。后续应建立高精度参考实现/独立样本测试，覆盖 simple/log、极端比例、接近零收益、长期 Wilder 递推、全涨/全跌/平盘，并在输入有效范围有权威依据后测定误差预算。
- GOV-CTR-001 规则文件头部仍写 `freeze-ready`，但 PLAT-002 登记簿将 GOV-CTR-001 登记为 `frozen`；状态以登记簿为准。该文件头部不在 Quant 分支修改，交由契约文档 Owner 校准。

**本轮结论：** 统计指标的类型候选已收敛，但没有足够证据确定生产精度、舍入与全部单位/输入质量元数据。QNT-001 继续 IN_PROGRESS，不创建半成品 Entry，不将 synthetic Golden 升格为真实验收。

#### 当前不能凭现有证据填写的字段

1. **value_type**：项目决议规定精确价格/金额使用 decimal string、统计数值使用 number；但各 metric_code 的最终分类和可执行转换仍须逐项确定。当前 Indicator/Factor 纯算法输出 float64，价格类指标不能未经精度策略就直接宣称满足 decimal string。
2. **unit**：项目字段契约列举了 CNY/share、percentage_point、ratio 等可用单位，但明确要求逐 metric_code 注册；RSI、ATR、MACD、Bollinger 的具体单位仍有待确认，不能把 Go float64 或公式名称当作单位决议。
3. **precision**：Golden tolerance 是测试断言容差，不是生产 max_fraction_digits、rounding_mode 或误差预算。
4. **range**：synthetic Golden 的样本极值不是合法值域。数学边界必须逐指标证明，价格类范围还依赖输入与算法约束。
5. **input_requirements**：算法函数只接收数值数组，不掌握 Data 字段版本、Decimal 精度、复权参考日期、PIT、交易日历和真实快照质量。DATA-CTR-005/007 仍 deferred。
6. **quality_policy**：纯计算函数不能识别停牌、缺失交易日、Provider 覆盖率或数据新鲜度；不能统一假设 minimum_coverage=1 或 missing_handling=reject 后冒充业务决议。
7. **parameters_schema**：全局 QNT-CTR-002 Schema 和 Golden 已存在，但 Entry.parameters_schema 要求单个 code 对应的封闭对象 Schema；需要从冻结子契约形成逐 Entry 映射，并确认 Registry 接受的对象层级。
8. **sample_count.required_in_metric**：计数单位/规则可由算法与契约推导，但是否对每个输出字段强制存在仍应与对应 Payload Schema 保持一致；当前 Metric Go 字段为可选指针，Validator 只按 Entry 检查字段存在，尚未验证实际计数与 counting_rule 一致。

## 7. QNT-001 Return 样本数不足分支口径修正（2026-11-18）

### 代码审计发现

- 项目 Quant-Research DTO 将 sample_count 定义为实际参与计算的有效样本数；Indicator 输入为 Close 序列时，Return 的统计样本是相邻 Close 产生的收益，不是 Close 根数。
- Return available 分支返回窗口 N，即 N 个相邻收益样本；不足样本分支此前返回 len(closes)，与 available 分支的计数单位不一致。
- 正确的已观察收益样本数为 max(0, len(closes)-1)。Volatility/RSI 的不足样本分支已经采用相同相邻变化计数口径。
- 已修正 Return 的 insufficient_data SampleCount，并新增空输入、单 Close、窗口不足三种测试。

### 契约边界

- QuantMetric.sample_count 为条件必需，是否必须由 Registry Entry.sample_count.required_in_metric 决定；QNT-CTR-004 1.0.0 当前 optional，与公开 DTO 的条件必需定义一致。
- 当前没有生产 Indicator Metric 构造/注册装配，不能据结构 Golden 决定 required_in_metric=true；Entry 必须与专属 Schema 及未来真实构造器一致。
- 本轮不改变 Schema、Registry Entry、生产精度预算或算法公式；仅修正不足样本分支的计数口径。
