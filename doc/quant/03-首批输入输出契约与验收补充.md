# Quant 首批输入输出契约与验收补充

- 适用任务：QNT-001～003
- 契约范围：QNT-CTR-001～005；公共语义遵循 GOV-CTR-001～006
- 状态：实现输入基线；不代表 Schema、Golden、Contract Test 或 L2 已通过
- 权威关系：项目级契约目录登记编号、状态和公共语义；本文件细化 Quant 生产方/消费者边界，不改变已接受的项目级契约

## 1. 依赖方向

Quant 是确定性计算模块。领域层不依赖其他业务模块；Application 通过端口读取 Data 快照并调用 Platform 公共原语。

- Data 拥有行情、证券主数据、交易日历、行业历史成分、财务和估值事实。
- Quant 只通过自己的 Data Adapter 消费公开 DTO/API，不 import Data Domain、Repository、SQL Model、Provider Adapter 或 HTTP DTO。
- Researchflow 是 Quant Application 的主要编排消费者；Quant 不依赖 Research/Researchflow 内部类型，不调用 LLM、不下单、不执行策略动作。
- Quant 风险事件在本地事务写入 Outbox，按 INT-CTR-001 投递 Notification；不直接依赖 Notification 领域包、Repository 或发送接口，发布失败不得回滚已提交风险事实。

## 2. 计算上下文规范

跨模块 DTO 使用 snake_case，时间字段遵循 GOV-CTR-002。首批请求至少包含 schema_version、request_id、correlation_id、scope、security_id（按场景必需）、system_as_of、trade_date、period、input_snapshot_refs、adjustment_basis（按场景必需）、typed parameters、quality_policy、idempotency_key。

system_as_of 是系统知识截止，不是交易日。Data 旧 API 的 as_of 仅允许在 Data Adapter 内显式映射；Quant 对外 DTO、结果和跨模块调用统一使用 system_as_of。当前分支 services/market-data/openapi.yaml 仍登记 v1 DailyBar（数值字段为 JSON number，PIT 查询参数为 as_of，行级时间字段为 system_observed_at）；未发现已发布的 Data v2 Decimal/system_as_of OpenAPI 路由或 Schema。DATA-CTR-005 仍为 pending_evidence，真实 Data Adapter 不得宣称已接入 v2。

历史输入必须满足：
1. snapshot_ref 不可变，保存来源和 source_version。
2. 严格 PIT 的 available_at 必须有来源证据且不晚于 system_as_of；不得用 published_at、fetched_at 或当前时间推导。
3. 交易日、复权基准/参考日期、证券主数据版本、行业成分版本必须一致。
4. 不同 system_as_of、adjustment_basis、单位或不可比较质量的数据不得混算。
5. null/unknown/unavailable 不得转成 0、false 或空字符串。

## 3. 数值与 Metric Registry

每个 Registry entry 以 `(code, schema_version)` 标识，必须声明 `value_type`、`unit`、`precision`（最大整数位、fractional digits/scale、rounding mode、tolerance）、`range`、`algorithm_version`、`input_requirements`（输入字段、interval、adjustment、PIT、quality、snapshot 要求）、`parameters_schema`、`quality_policy`（coverage、missing handling、quality states、unavailable conditions）和 `supports_interval`。Registry 是指标语义的唯一权威来源；消费者不得自行推断单位、精度或算法版本。

- 精确价格/金额使用 decimal string；禁止 float64 转字符串伪装无损。
- 统计量仅在明确允许浮点误差时使用 JSON number，并声明 tolerance 和舍入策略。
- 百分比区分 percentage_point 与 ratio；转换必须位于明确 Adapter/计算边界并有 Golden。
- 计数使用 integer，遵循 GOV-CTR-001 安全整数上限。
- value=null 时 metric_status 必须说明原因；metric_status=available 时 value 必须非 null。
- quality_status=invalid/unknown 时不得 available；上下界必须同时存在或同时为 null，类型与 value 一致。

SMA/EMA/Return/Volatility/RSI/MACD/ATR/Bollinger 参数 Schema 固定窗口、最小样本、seed、缺失处理、复权要求和精度。首批 Factor 仅为单证券时间序列 momentum_20d、momentum_60d、volatility_20d；不做横截面排序、行业中性化、winsorize/zscore/rank 或其他因子扩展，这些均延期。Factor 不隐式依赖 Indicator Engine。

## 4. 结果与风险契约

QuantResult 使用 result_type + schema_version 判别的强类型 payload，禁止任意 map。Envelope 至少包含 schema_version、result_id、result_type、scope、security_id（按场景必需）、system_as_of、trade_date、period、algorithm_version、parameter_fingerprint、input_snapshot_refs、quality_status、result_status、authorization_ref、payload。

result_status 与 quality_status 独立；completed 不代表 valid。insufficient_data、insufficient_sample、rejected、failed 不得伪装为 completed。未知 result_type/schema_version 必须拒绝，不回退旧版本。

Quant Result Manifest 不可变，直接绑定 result_type、schema_version、system_as_of、input_snapshot_refs 和 result_fingerprint；result_fingerprint 对强类型 payload 计算，payload 内的 algorithm_version/parameter_fingerprint 由该摘要间接绑定。调用主体不属于 Manifest 字段，由 Quant 签发的 GOV-CTR-006 AuthorizationRef 单独绑定 subject_ref 和 resource_ref=result_id：policy_owner=quant、subject_ref 来自可信认证 Context、resource_ref=result_id、purpose_code=quant_analysis、content_level=full。读取时仍须检查当前授权；历史 allowed 不能覆盖当前 denied/expired/unknown。

RiskDecision 只表达 pass/reject/unknown、规则版本、评估时间、system_as_of、输入引用和原因。数据缺失、规则无法评估或质量不足时不得 pass；硬风险结论不能被评分或 LLM 覆盖。风险事件仅在首次形成或 status/硬阻断原因集合实质变化并持久化后发布，遵循 INT-CTR-001。

### 6.2 仍待项目级确认的语义

以下问题只登记在 Quant 专项文档，不擅自修改项目级契约或现有 QNT Schema。已经由最新契约明确的 Registry 字段、首批算法和延期范围不再重复列为待决项。

1. **算法活动版本选择。** Registry 已要求区分 `code`、`schema_version`、`algorithm_version`，但尚未明确同一 code/schema_version 存在多个算法版本时的活动版本切换和历史复算规则。建议公开请求只传 code/schema_version/parameters，由服务端显式选择活动 algorithm_version，结果记录实际版本；历史版本保留供内部复算。不得依赖注册顺序或允许客户端任意指定算法版本。该建议需项目级确认。
2. **use_case 幂等作用域。** QuantAnalysisRequest 字段表没有 use_case，但幂等作用域和请求指纹使用 use_case。建议由 AnalyzeStock/AnalyzeMarket 等 Facade 路由稳定映射内部 use_case，不增加客户端可控字段；需要补充同一键跨用例冲突/隔离测试。
3. **QuantResultRef 与 QuantResult Envelope 关系。** 两者字段高度重叠，需要明确 Reference 是 Envelope 的引用投影/索引视图还是独立 DTO，并明确 GetResult 返回完整 Envelope、引用或受授权的结果投影。
4. **纯函数空快照引用冲突。** Envelope 描述允许白名单纯函数的 input_snapshot_refs 为空，但 QNT-CTR-005 Manifest Schema 当前 minItems=1。需明确纯函数是否能生成可持久化/可引用结果；未决前不放宽 Manifest Schema。
5. **NOT_COMPARABLE 的诊断边界。** 项目级 DTO 已固定 QuantMetric.metric_status（available/insufficient_data/insufficient_sample/not_applicable/unknown）和 QuantResult.result_status（completed/insufficient_data/insufficient_sample/rejected/failed）的枚举；NOT_COMPARABLE 是诊断分类，不得擅自加入上述业务状态，也不得静默映射为 unknown/insufficient_data。若对外暴露诊断明细，需在 QNT-CTR-004 对应 Schema/Golden 中明确诊断字段、关联 Metric 和不可比较原因；在该 Schema 冻结前不实现新的公开状态字段。
6. **ATR 首个 TR 边界。** 已由 `atr-previous-close-boundary.golden.json` 固定：窗口 N 需要 N 根 OHLC bar；首根 TR 使用输入窗口前一交易日的 `previous_close`，不使用窗口首日 close 替代；改变 previous_close 必须改变首个 TR。该 Fixture 为 synthetic，不证明 Data Adapter 提供的前收盘价真实且 PIT 正确。
7. **交易日历版本绑定。** 首批 Factor 需要 21/61/21 个连续有效交易日；必须按 Data 交易日历版本判定，不能按自然日或数组连续性推断。需确认交易日历版本从 Snapshot Manifest/输入元数据的哪个字段取得，并补缺失交易日负例。
8. **Data v2 真实输入证据。** 当前 Data OpenAPI v1.0.2 的 DailyBar 数值字段为 JSON number，PIT 参数为 `as_of`，尚不能证明 Decimal string/`system_as_of` v2 Adapter。DATA-CTR-005 证据完成前，只允许 Fixture 或明确标记的 v1 兼容输入，不得宣称真实 v2 接入。
9. **QNT-CTR-005 运行时证据。** 项目级 Manifest Schema/Golden 和测试矩阵已存在；Quant 仍需补模块内 Schema/Manifest Validator、可信 principal 到 AuthorizationRef 的绑定、结果读取当前授权复核，以及策略变更竞态下 fail-closed 的 CI 证据。

明确不再作为待决项：
- 首批范围为 stock/market/industry；portfolio 属 QNT-012 后续能力。
- 首批 Factor 仅为单证券时间序列 momentum_20d、momentum_60d、volatility_20d；横截面排序/中性化/标准化延期。
- Metric Registry 属 Quant 领域能力，放在 `internal/quant/**`；不新增 Platform 通用 Registry，也不要求复用 `internal/analysis/registry`。

### 6.2.1 QNT-CTR-004 当前可执行边界

根据最新项目级 Quant-Research 字段契约，QNT-CTR-004 的基础 DTO 字段不再整体处于语义待决状态；当前阻塞主要是机器契约和消费者验收证据。

已明确、后续 Schema 必须保持一致的语义：
- `QuantResultRef` 是公开结果引用 DTO，包含 result_id、result_type、scope、system_as_of、period、algorithm_version、parameter_fingerprint、input_snapshot_refs、quality_status、result_status、authorization_ref 和 created_at 等字段。
- `QuantResult` 使用共同 Envelope，必须包含 result_id、result_type、scope、system_as_of、algorithm_version、parameter_fingerprint、input_snapshot_refs、quality_status、result_status、authorization_ref 和强类型 `payload`；payload 按 `result_type + schema_version` 命中唯一子 Schema，禁止 `map[string]any`。
- `QuantMetric` 的 value、lower_bound、upper_bound 类型必须由具体 metric_code 的 Schema 固定；available 必须有非 null value，其他不可用 metric_status 必须显式 null；区间必须成对出现并满足边界约束。
- `TrendResult` 的 direction 与 phase 分离；unknown 不得伪装为 sideways。
- `RiskDecision` 只允许 pass/reject/unknown；数据缺失或规则不可评估时不得 pass，硬门禁不得提供评分或 LLM override。
- `quality_status`、`metric_status`、`result_status` 和诊断分类分域管理，不得直接互相转换。

当前仍不能直接生成完整 QNT-CTR-004 Schema/Golden 的原因：
1. `QuantResultRef` 与 `QuantResult` Envelope 字段高度重叠，但项目级字段表尚未规定 Reference 是 Envelope 的投影/索引视图，还是独立 DTO；GetResult 的返回边界也需明确。
2. Envelope 的 discriminated union 已确定，但各 `result_type + schema_version` 的强类型 payload 子 Schema 尚未齐备；不能用宽泛 object 或任意 map 代替。
3. Metric Registry 尚无正式首批条目，无法为每个 metric_code 固定 value/区间 JSON 类型、单位、精度、舍入、范围和 quality_policy。
4. `NOT_COMPARABLE` 属于诊断分类，不是 `metric_status` 或 `result_status` 的成员。公开诊断字段及与具体 Metric 的关联必须由 QNT-CTR-004 Schema/Golden 明确，不能自行扩展业务状态枚举。
5. QNT-CTR-004 项目级验收还要求覆盖 coverage、sample_count、区间边界及 RiskDecision 的组合约束；这些约束必须落实为 Schema、Golden 和消费者 Contract Test。

因此当前只允许继续实现内部强类型 DTO/Schema 的准备工作和已有语义的验证；在上述缺口解决前，不创建一个看似完整但实际宽松的 QuantResult Schema，也不接入 Researchflow 结果消费。

### 6.4 首批算法口径

- SMA：最近 N 个有效 close 的算术平均。
- EMA：首 window 个 close 的 SMA seed，之后 alpha=2/(window+1)。
- Return：按显式参数计算 simple/log return。
- Volatility：window 个收益样本的样本标准差 ddof=1；年化因子显式提供；首批 Factor volatility_20d 不年化。
- RSI：Wilder 平滑；初始平均涨跌幅使用 SMA seed，需要 window+1 个 close。
- MACD：fast/slow/signal EMA 均按 SMA seed；fast_window < slow_window；histogram=2*(DIF-DEA)。
- ATR：TR=max(high-low, abs(high-prev_close), abs(low-prev_close))；Wilder 平滑、初始 SMA；N 个 TR 对应的 OHLC bar 数及首个 previous_close 来源仍待 Golden。
- Bollinger：middle=SMA；总体标准差 ddof=0；multiplier>0。
- Factor：momentum_20d/60d 为 close_t/close_(t-N)-1；volatility_20d 为 20 个 simple daily return 的样本标准差。
- 首批 Factor 只做单证券时间序列；横截面排序、行业中性化、winsorize/zscore/rank 和其他因子均 deferred。
- 价格窗口必须同一 adjustment_basis/reference_date；缺失不填充；无效价格不得生成有效值。

## 10. QNT-CTR-005 Manifest 领域实现

新增位置：`internal/quant/manifest/`。

- `FingerprintPayload` 使用 RFC 8785 JCS + SHA-256 计算强类型 payload 指纹；调用方只传 payload，不把 AuthorizationRef/Manifest Envelope 混入摘要。
- `Build` 生成 Manifest：限制 result_type/schema_version，要求 UTC system_as_of、非空且唯一的输入快照引用、64 位小写 SHA-256；快照引用排序后参与 fingerprint。

- 测试源码使用项目 QNT-CTR-005 Golden 验证生成结果完全一致，并覆盖 JSON 顺序规范化、缺失/重复快照、非法类型/版本/指纹及篡改检测。

### 10.11 Schema 文档与实例重复 JSON 键拒绝

- `compileJSONSchema` 在 Draft 2020-12 编译前递归检查 Schema JSON 对象键唯一性，避免重复的 `$schema`、`type`、`properties` 等字段被 Go map 解码覆盖后产生歧义。
- `validateJSONSchemaInstance` 在解码为 `any`/map 前递归检查实例对象键唯一性，覆盖顶层重复键和嵌套对象重复键。

- 该检查只收紧 JSON 输入的无歧义性，不改变 QNT Schema 业务约束，也不代替 JCS 指纹计算、强类型 DTO 解码或业务 Schema 校验。

### 10.12 Indicator 参数边界与对数收益数值稳定性

- QNT-CTR-002 首批窗口上限为 1000；SMA/EMA/Return/RSI/ATR/MACD 各窗口参数均限制在 1..1000，Volatility/Bollinger 限制在 2..1000。参数 Schema 与纯计算入口必须执行同一边界，不能只依赖 Application 层校验。
- Volatility 的 `annualization_factor` 按契约为正整数；Schema 使用 integer/minimum=1，Go 参数结构使用整数类型。
- Return/Volatility 使用 log return 时按 `ln(close_t) - ln(close_previous)` 计算，避免先做价格比值导致有限正价格的比值上溢/下溢；simple return 仍按原公式计算，无法用有限浮点数表示的结果拒绝。
- 新增窗口上限、年化因子类型和极端正价格对数收益/波动率回归；代码提交 `7ac030a45a431e25b0db64673c7e226e745e4c39` 的 go-core `gofmt`、`go test`、race detector 和 `go vet` 均通过。



### 10.13 Indicator / Factor 波动率中间数值溢出防护

- Indicator Volatility 与 Factor volatility_20d 均使用样本标准差（ddof=1）。原实现直接累加原始收益率并平方偏差；在每个收益率都有限、但累计和或平方和超过 float64 范围时，会错误拒绝最终仍可表示的标准差。
- 两处实现改为先按收益率最大绝对值缩放，再计算归一化均值与平方偏差，最后还原标准差；若最终标准差本身仍超出 float64 范围，继续返回 ErrInvalidInput。
- 新增 21 个价格交替构造的极端有限输入回归：simple returns 量级约为 1e308 与 -1，标准差仍可表示；Indicator 与 Factor 均应返回有限且符合 ddof=1 的结果。
- 该修复不改变收益率定义、样本母体、ddof 或年化规则；不替代交易日连续性、复权和真实 Data 输入门禁。


### 10.14 Indicator Golden 状态与样本数断言

- 八份 Indicator Golden 自动复算测试除校验数值外，统一校验结果状态为 `available`，并按各算法既定语义核对 `sample_count`：SMA/Bollinger 为窗口长度，EMA/MACD/ATR 为输入序列长度，Return/Volatility 为收益窗口长度，RSI 为价格变化数量。
- 防止算法数值正确但样本口径或状态错误时仍被 Golden 测试放行；Factor Golden 已有对应状态、单位和样本数断言。
- 该补充只强化固定样本验收，不证明输入交易日连续性、复权一致性或真实行情质量。


### 10.15 Indicator 均值与 Bollinger 总体标准差数值稳定性

- 通用 `mean` 改为按最大绝对值缩放后求均值，避免有限同号价格的直接累加溢出；对归一化均值执行理论范围钳制，避免浮点累加误差将结果推到最大输入绝对值之外。
- Bollinger 复用缩放后的标准差辅助函数，并显式使用总体标准差（ddof=0）；不改变窗口、倍数或上下轨定义。
- 新增 SMA/EMA 在均值可表示但直接求和会溢出的输入回归，以及 Bollinger 在偏差平方会溢出但中心线/标准差/上下轨仍可表示的回归。
- 最终均值、标准差或轨道若仍超出 float64 表示范围，继续由现有有限性检查拒绝；该修复不解决 float64 十进制精度，也不替代 Data 输入质量验收。


### 10.16 RSI / ATR Wilder 平滑中间溢出防护

- RSI 初始平均涨幅/跌幅改为缩放均值，避免多个有限价格变化直接累加时中间溢出；仍按初始窗口的算术平均建立 Wilder seed。
- RSI 与 ATR 后续 Wilder 平滑改用增量等价式 `previous + (current - previous) / window`，避免先计算 `previous * (window - 1)` 导致中间溢出。
- 新增有限极端价格变化回归，分别覆盖 RSI seed 累加溢出和 ATR Wilder 平滑乘法溢出；预期结果仍可由 float64 表示。
- 该修复不改变 Wilder 公式、窗口、样本边界或输出语义；最终值不可表示时仍由现有有限性检查拒绝。


## 10.17 首批 Factor QuantMetric 机器契约

### 10.22 Registry decimal_string 词法与精度边界

- `decimal_string` 的 JSON 表示必须是字符串；Go `Entry.Validate` / `ValidateMetric` 使用精确有理数解析，不经过 float64。

### 10.25 Quant 价格序列输入边界审计（2026-11-09）

当前 `indicator` 与 `factor` 的纯计算函数接收 `[]float64`；`WithContext` 包装只校验 CalculationContext（system_as_of、trade_date 格式、snapshot refs、adjustment_basis、quality_policy），不校验每根 Bar 的 trade_date、system_observed_at、available_at、单位、复权参考日、质量状态或交易日连续性。`CalculationContext` 注释中所说的“输入数据 DTO 携带字段”在当前 Quant 目录尚无对应的强类型价格序列 DTO。因此不得把 WithContext 的通过解释为输入行情质量/PIT/连续性已通过。

总规划 DATA-CTR-002/005 明确：Quant 真实日线输入应来自 DailyBars v2；价格采用 decimal string，必须保留 snapshot_ref、authorization_ref、quality_status、adjustment_basis、system_as_of，Bar 按交易日升序且不补非交易日；严格 PIT 复权要求未复权 Bar 与复权因子的时间证据均不晚于 system_as_of。DATA-CTR-005 目前仍为 `pending_evidence`，v2 OpenAPI、Go Decimal Model、Provider 原始精度链路及 Golden 未齐。故真实 Quant Data Adapter 继续阻断，不能改用 v1 float64 DTO 绕过。

后续接入分两层，不把职责塞入纯算法函数：
1. Data/Server Adapter：只消费已冻结的 DailyBars v2；校验响应 `system_as_of` 与请求一致、快照/授权引用存在、quality/warnings 可解释、Bar 顺序与唯一性、日期范围/limit 完整性、Bar 的 PIT 时间证据和复权因子证据；将 Data `percentage_point` 显式转换为 Quant `ratio`（仅适用字段），保留原始 Decimal 字符串和转换证据。
2. Quant 输入边界：接收 Adapter 已验证的强类型序列及其单位/复权/快照元数据；在进入现有 `[]float64` 纯计算前执行有明确误差预算的数值转换，若源精度无法被当前计算表示/误差预算覆盖，则返回不可比较/不可用事实，不得默认为 valid。交易日连续性须基于权威交易日历版本检查，不从自然日差推断。

本项不新增临时 DTO、不接入 v1、不在 Quant 内实现交易日历或 Provider 复权逻辑。待 Data v2 Schema/Go Model/Golden 和精度转换规则冻结后，再按实际 DTO 写 Adapter 与边界测试。


### 10.26 QNT-CTR-004 Envelope / Payload 版本与现有 DTO 对照（2026-11-09）

本轮按项目级契约登记簿、Quant/Research DTO 字段表、现有 Go DTO、Schema 和 Golden 做了逐项对照。QNT-CTR-004 仍为 `pending_evidence`，当前不能直接实现完整 Envelope，发现以下必须先消除的契约差异：

#### 1. 版本字段存在歧义

- DTO 字段表 2.7 将 Envelope 的 `schema_version` 定义为 Envelope Schema 版本。
- QNT-CTR-005 Manifest 的 `schema_version`、Manifest Go Input/Manifest 字段则用于结果 payload Schema 版本。
- DTO 字段表又要求按 `result_type + schema_version` 选择唯一 payload 子 Schema。

因此同一个 `schema_version` 同时承担 Envelope 版本与 payload 版本，无法无歧义地实现兼容路由。需要项目级决议明确采用两个字段（例如 `envelope_schema_version` 与 `payload_schema_version`），或明确现有 `schema_version` 只表示 payload 版本并另行固定 Envelope 版本策略。Quant 分支不自行改变跨模块字段名。

#### 2. 当前 Payload 证据覆盖不完整

| result_type | 当前可复用结构 | 当前 Schema / Golden | 结论 |
|---|---|---|---|
| indicator | 通用 `metric.Metric` | 未发现独立 Indicator Payload Schema/Golden | 不能仅凭 Factor Metric 推断 Indicator 契约 |
| factor | `metric.Metric` | Factor Metric 子 Schema + 三项 Factor Golden | 仅支持首批三个 Factor Metric 子对象；不等于完整 Factor Envelope |
| trend | `trend.Result` | Trend Schema + Golden | 具备领域 DTO 基础，尚未绑定 Envelope 身份字段 |
| risk | `risk.Decision` | RiskDecision Schema + Golden | 具备领域 DTO 基础，尚未绑定 Envelope 身份字段 |
| market / industry / stock / strategy / backtest / evaluation | 尚无可确认的完整强类型 Payload DTO | 未发现对应 Payload Schema/Golden | 不允许使用 `map[string]any` 或通用 JSON 兜底 |

当前 Schema/Golden 只覆盖 Factor Metric、TrendResult、RiskDecision 等局部对象；不能把这几份局部 Schema 直接当作 10 类完整 Payload Registry。

#### 3. Envelope 与 Manifest / Ref 的字段映射未形成单一实现规则

- Manifest 权威提供 `result_id/result_type/schema_version/system_as_of/input_snapshot_refs` 及 payload 指纹绑定。
- Ref 另含 `scope/security_id/trade_date/period/algorithm_version/parameter_fingerprint/quality_status/result_status/authorization_ref/created_at`。
- DTO 字段表 Envelope 包含上述大部分字段和 payload，但没有明确 `created_at`、`result_fingerprint`、`manifest_fingerprint` 的公开位置，也没有逐字段规定 Envelope、Ref、Manifest 不一致时谁是权威、哪些字段必须相等。
- 当前 `BuildRef` 从已验证 Manifest 派生 result_id/result_type/system_as_of/input_snapshot_refs，但其他业务元数据由调用方提供；这不构成完整 Envelope 一致性校验。

#### 4. 本分支可执行与不可执行边界

可独立继续：
- 对现有 Factor Metric、TrendResult、RiskDecision 做 Go DTO 与现有 Schema/Golden 一致性测试；
- 建立现有 DTO 的 Envelope 映射字段清单，测试 Manifest 与 Ref 已有字段的一致性；
- 对已存在 payload 类型采用显式类型注册，不接受未知类型/版本，不允许弱类型兜底。

当前不可擅自实施：
- 不为其余 6 类 result_type 创造空壳或猜测 Payload；
- 不把 Envelope 版本和 payload 版本混为一个版本字段；
- 不将 Manifest/Ref 直接合并或改名为 Envelope；
- 不增加 GetResult、跨模块 Facade 或授权签发逻辑。

#### 5. 后续闭环顺序

1. 项目级 DTO 契约明确 Envelope Schema 版本与 payload Schema 版本的字段语义。
2. 对已实现的 indicator/factor/trend/risk 明确 Payload 类型及每类完整字段；其余类型标记 deferred 或给出真实实现批次。
3. 明确 Envelope、Ref、Manifest 的权威字段与相等性约束，补充序列化 Golden。
4. Quant 实现强类型 Envelope、按 `result_type + payload_schema_version` 显式注册 Payload Validator，并覆盖未知类型/版本拒绝。
5. Researchflow 消费端验证 discriminator、Schema、版本及授权引用；完成双方 Contract Test 后再更新 QNT-CTR-004 状态。

**结论：** 当前最主要阻塞不是 Go DTO 编码工作，而是 Envelope 与 Manifest 的版本字段冲突、Payload 覆盖范围不完整以及三种结果对象的权威字段映射未冻结。本轮不通过臆造 DTO 来制造表面进度。
