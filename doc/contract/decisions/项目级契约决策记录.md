## DEC-PLAT-002-012：Quant Application Facade 设计决议

- 日期：2026-11-10
- 状态：`accepted_design_pending_implementation`
- 规划依据：doc/quant/README.md 明确 Researchflow 是 Quant Application 的直接编排消费者，Research 不直接 import Quant；doc/quant/01-量化引擎总体设计.md 将 Quant 定义为确定性计算引擎；doc/quant/03-首批输入输出契约与验收补充.md 明确 Quant Application 通过端口读取 Data 快照并调用 Platform 公共原语。
- 代码证据：当前 internal/quant/** 有 domain、indicator、factor、manifest、metric、registry、result、risk、trend 等包，但没有 application/Facade 包。现有纯计算、Registry 和 Repository Port 不构成完整模块公开 Application Port。
- 决议：采用**窄 Application Facade + 强类型用例 Port**。在 Quant 模块内新增 internal/quant/application（具体文件按实现拆分），由其提供稳定的跨模块调用边界；首批只暴露有真实消费者的能力，至少按 Metric/Indicator/Factor 计算、Risk Evaluation、Result 查询/授权复核划分强类型用例。Trend 等能力在其用例真实可用且有消费者时加入，不为目录齐全预建空接口。
- 依赖规则：Researchflow 只依赖 Quant Application 公开 Port；不得依赖 Quant 的 Domain、Registry、Repository、Storage Adapter 或算法内部包。Quant 不依赖 Researchflow。Server Composition Root 负责构造 Quant Facade 并注入 Researchflow。Facade 不承载 HTTP Handler，不暴露 SQL/Redis/Provider 类型，不把内部包机械包装成逐方法透传层。
- 请求/结果规则：使用版本化、强类型 Request/Result；禁止 map[string]any 作为跨模块主契约；每个用例明确输入快照、PIT、质量、算法版本选择、诊断和幂等语义。客户端不指定任意算法版本；活动版本由 Quant Registry 的显式配置决定并在结果中回显。
- 授权规则：Quant 是 QuantResult 与其 AuthorizationRef 的资源 Owner。签发、查询和读取结果均由 Quant Application 执行可信 Principal/Scope 校验及当前授权复核；仅有 result_id/Manifest 不构成读取授权。Researchflow 负责传递可信调用上下文和保存引用，不自行重建 Quant 资源授权。
- 验收：Quant 提供 Facade 单测及公开 Port Contract Test；Researchflow 提供真实 Adapter/消费者 Contract Test；Server 提供构造注入与生命周期接线测试。QNT-CTR-001～005 在 Schema、Golden、授权复核、消费者测试齐备前仍保持 pending_evidence，本决议不代表契约已冻结。
- 后续责任：Quant 分支实现 Application Facade 和模块内测试；Researchflow 分支实现 Port Adapter 与消费者测试；Server 分支负责装配。项目级契约目录只维护公共语义和状态。

## DEC-PLAT-002-017：Web Owner 密码登录与服务身份分离

- 日期：2026-11-10
- 状态：`accepted_design_pending_server_web_integration`
- 依据：Platform doc/platform/18-Web登录与Session安全原语设计.md 已明确单一 Owner + Web Session Cookie；PLAT-015～019 的密码、Session、CSRF、限流和安全审计原语已有 Platform L1 实现记录。Server 当前 Bootstrap 仍只创建 Bearer Authenticator，Router 路由策略只注册 Anonymous/Owner Bearer，未接入 owner_session。
- 决议：未来 WebUI 使用 Owner 密码登录，登录后仅持有 HttpOnly Web Session Cookie。Owner Bearer 只用于可信运维；Service Bearer 只用于服务间调用；Data Provider/API Key 只由 Server 或受控 Remote Adapter 持有。三类凭证不得互换、不得下发浏览器。
- Credential：MariaDB 保存 Argon2id encoded hash 与 credential_version；明文密码不落库。首次初始化只接受一次性部署 Secret，初始化成功后不得通过环境变量反复重置。密码修改/受控恢复递增 credential_version，使旧 Session 失效。
- Session：复用 Platform Redis SessionStore，Token 至少 256 bit CSPRNG，服务端仅存 SHA-256 摘要；HttpOnly、SameSite=Lax、HTTPS 下 Secure Cookie；空闲 12 小时、绝对 7 天的当前候选策略，Cookie 生命周期不得超过 Session。Redis 或 MariaDB 权威校验故障时受保护请求 fail closed。
- CSRF/Origin：Cookie 认证的状态变更请求必须校验 Session 绑定 CSRF Token；登录入口校验 Origin/Host；前端 CSRF Token 只保存在运行时内存，不写 localStorage。可信代理头仅接受显式配置的代理来源。
- 路由：每条 Server 路由显式声明 anonymous、owner_bearer、owner_session 或 service 身份策略。owner_session 必须走独立 Session Middleware/授权链，不得伪造 Authorization Header 复用 Bearer Authenticator；Session Principal 保留认证来源，不能自动继承 Owner Bearer 或 Service Scope 权限。
- 资源授权：Owner Session 只证明单一 Owner 的登录身份，不代替 Data/News/Quant/Research 等资源 Owner 的 AuthorizationRef 签发和读取时复核。
- 业务范围：首期仅单一 Owner，不建设注册、多用户、租户、OAuth/OIDC、动态 Service Key 或独立认证微服务。
- 责任分层：Platform L1 提供安全原语；Server A2 实现初始化/登录/退出/密码修改/受控恢复、Session Middleware、路由矩阵、CSRF/Origin、审计和 Credential Version 检查；WebUI A2 实现登录/退出/密码交互与 Cookie/CSRF 请求；部署 A3 验收 HTTPS、可信代理、Secret 注入、Redis 故障和恢复流程。
- Argon2id 生产参数必须在目标部署硬件完成耗时与并发内存基准后确定，不直接把文档候选值当作生产默认值。
- 本决议不宣称 Server A2/WebUI A2/部署 A3 已完成；PLAT-CTR-003、SRV-CTR-001、DATA-CTR-006 等项目契约仍按登记簿保持差异/待证据状态。
