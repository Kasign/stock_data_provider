## DEC-PLAT-002-012：Quant Application Facade 设计决议

- 日期：2026-11-10
- 状态：`accepted_design_pending_implementation`
- 规划依据：doc/quant/README.md 明确 Researchflow 是 Quant Application 的直接编排消费者，Research 不直接 import Quant；doc/quant/01-量化引擎总体设计.md 将 Quant 定义为确定性计算引擎；doc/quant/03-首批输入输出契约与验收补充.md 明确 Quant Application 通过端口读取 Data 快照并调用 Platform 公共原语。
- 代码证据：当前 internal/quant/** 有 domain、indicator、factor、manifest、metric、registry、result、risk、trend 等包，但没有 application/Facade 包。现有纯计算、Registry 和 Repository Port 不构成完整模块公开 Application Port。
- 决议：采用**窄 Application Facade + 强类型用例 Port**。在 Quant 模块内新增 internal/quant/application（具体文件按实现拆分），由其提供稳定的跨模块调用边界；首批只暴露有真实消费者的能力，至少按 Metric/Indicator/Factor 计算、Risk Evaluation、Result 查询/授权复核划分强类型用例。Trend 等能力在其用例真实可用且有消费者时加入，不为目录齐全预建空接口。
- 依赖规则：Researchflow 只依赖 Quant Application 公开 Port；不得依赖 Quant 的 Domain、Registry、Repository、Storage Adapter 或算法内部包。Quant 不依赖 Researchflow。Server Composition Root 负责构造 Quant Facade 并注入 Researchflow。Facade 不承载 HTTP Handler，不暴露 SQL/Redis/Provider 类型，不把内部包机械包装成逐方法透传层。
- 请求/结果规则：使用版本化、强类型 Request/Result；禁止 map[string]any 作为跨模块主契约；每个用例明确输入快照、PIT、质量、算法版本选择、诊断和幂等语义。客户端不指定任意算法版本；活动版本由 Quant Registry 的显式配置决定并在结果中回显。
- 授权规则：Quant 是 QuantResult 与其 AuthorizationRef 的资源 Owner。签发、查询和读取结果均由 Quant Application 执行可信 Principal/Scope 校验及当前授权复核；仅有 result_id/Manifest 不构成读取授权。Researchflow 负责传递可信调用上下文和保存引用，不自行重建 Quant 资源授权。
- 验收：Quant 提供 Facade 单测及公开 Port Contract Test；Researchflow 提供真实 Adapter/消费者 Contract Test；Server 提供构造注入与生命周期接线测试。QNT-CTR-001～005 在 Schema、Golden、授权复核、消费者测试齐备前仍保持 pending_evidence，本决议不代表契约已冻结。
- 后续责任：Quant 分支实现 Application Facade 和模块内测试；Researchflow 分支实现 Port Adapter 与消费者测试；Server 分支负责装配。项目级契约目录只维护公共语义和状态。

## DEC-PLAT-002-017：Web Owner 密码登录与服务身份分离

- 日期：2026-11-10
- 状态：`accepted_design_pending_server_web_integration`
- 依据：Platform doc/platform/18-Web登录与Session安全原语设计.md 已明确单一 Owner + Web Session Cookie；PLAT-015～019 的密码、Session、CSRF、限流和安全审计原语已有 Platform L1 实现记录。Server 当前 Bootstrap 仍只创建 Bearer Authenticator，Router 路由策略只注册 Anonymous/Owner Bearer，未接入 owner_session。
- 决议：未来 WebUI 使用 Owner 密码登录，登录后仅持有 HttpOnly Web Session Cookie。Owner Bearer 只用于可信运维；Service Bearer 只用于服务间调用；Data Provider/API Key 只由 Server 或受控 Remote Adapter 持有。三类凭证不得互换、不得下发浏览器。
- Credential：MariaDB 保存 Argon2id encoded hash 与 credential_version；明文密码不落库。首次初始化只接受一次性部署 Secret，初始化成功后不得通过环境变量反复重置。密码修改/受控恢复递增 credential_version，使旧 Session 失效。
- Session：复用 Platform Redis SessionStore，Token 至少 256 bit CSPRNG，服务端仅存 SHA-256 摘要；HttpOnly、SameSite=Lax、HTTPS 下 Secure Cookie；空闲 12 小时、绝对 7 天的当前候选策略，Cookie 生命周期不得超过 Session。Redis 或 MariaDB 权威校验故障时受保护请求 fail closed。
- CSRF/Origin：Cookie 认证的状态变更请求必须校验 Session 绑定 CSRF Token；登录入口校验 Origin/Host；前端 CSRF Token 只保存在运行时内存，不写 localStorage。可信代理头仅接受显式配置的代理来源。
- 路由：每条 Server 路由显式声明 anonymous、owner_bearer、owner_session 或 service 身份策略。owner_session 必须走独立 Session Middleware/授权链，不得伪造 Authorization Header 复用 Bearer Authenticator；Session Principal 保留认证来源，不能自动继承 Owner Bearer 或 Service Scope 权限。
- 资源授权：Owner Session 只证明单一 Owner 的登录身份，不代替 Data/News/Quant/Research 等资源 Owner 的 AuthorizationRef 签发和读取时复核。
- 业务范围：首期仅单一 Owner，不建设注册、多用户、租户、OAuth/OIDC、动态 Service Key 或独立认证微服务。
- 责任分层：Platform L1 提供安全原语；Server A2 实现初始化/登录/退出/密码修改/受控恢复、Session Middleware、路由矩阵、CSRF/Origin、审计和 Credential Version 检查；WebUI A2 实现登录/退出/密码交互与 Cookie/CSRF 请求；部署 A3 验收 HTTPS、可信代理、Secret 注入、Redis 故障和恢复流程。
- Argon2id 生产参数必须在目标部署硬件完成耗时与并发内存基准后确定，不直接把文档候选值当作生产默认值。
- 本决议不宣称 Server A2/WebUI A2/部署 A3 已完成；PLAT-CTR-003、SRV-CTR-001、DATA-CTR-006 等项目契约仍按登记簿保持差异/待证据状态。

## DEC-PLAT-002-034：GOV-CTR-001 公共 JSON 数值与空值规则版本化

## DEC-PLAT-002-035：GOV-CTR-002 公共时间与 PIT 规则版本化

- 日期：2026-11-11
- 状态：`decided_under_explicit_user_delegation`
- 对应契约：GOV-CTR-002；各领域时间字段映射由对应 CTR 负责。
- 决策依据：项目负责人明确授权由 ChatGPT 对未确认的项目级契约取舍直接 Review 并按最优逻辑裁决；本项目初版不承担旧版兼容负担。
- 决议：
  1. GOV-CTR-002 公共时间与 PIT 规则版本定为 1.0.0。跨模块绝对时间统一使用 RFC3339Nano UTC，必须以 `Z` 结尾；保留来源可证明的精度，不补造小数位，不将未知时区假设为 UTC 或 Asia/Shanghai。
  2. 交易日/业务日期使用 `YYYY-MM-DD`，按对应市场的权威交易日历解释；A 股交易日使用 `Asia/Shanghai` 交易日历。日期不是 UTC 午夜时间戳，不得互相隐式转换。
  3. `occurred_at` 表示现实事件发生时间；`published_at` 表示来源声明发布时间；`available_at` 表示有证据证明外部可获得的时间；`system_observed_at` 表示系统首次观察某个具体不可变来源版本的时间；`system_as_of` 表示系统知识截止时间；`valid_time_start/end` 表示业务事实有效区间。上述字段语义独立，不得互相替代。
  4. `fetched_at` 表示系统/Adapter 从来源抓取或读取的处理时间；`normalized_at` 表示标准化处理时间；`created_at/updated_at` 表示记录审计时间。它们都不能替代 `system_observed_at`、`available_at` 或 `system_as_of`。`provider_time` 属于来源特定时间，必须由生产方显式映射到准确公共语义后才能跨模块暴露。
  5. `system_as_of` 不等于交易日、发布时间、当前时间、抓取时间或执行截止时间。`deadline_at` 是执行截止，与知识截止分离。
  6. Researchflow 在 CreateRun 时确定并持久化唯一 `system_as_of`；所有下游请求、查询、Stage、Attempt、Evidence/Context 和重试必须继承同一值。重试不得刷新知识截止时间；下游返回结果不得晚于 Run 的知识截止边界。
  7. `available_at` 缺少可验证来源证据时必须为 null/unknown；不得从 `published_at`、`fetched_at`、`system_observed_at` 或 Provider 当前时间推导。来源时间冲突/时区不明/精度不可验证时，保留原始来源证据，规范化值置 null，不得伪造。
  8. 严格 PIT 的公开事实必须同时满足 `system_observed_at <= system_as_of`，且 `available_at` 非 null 并满足 `available_at <= system_as_of`。无法证明任一边界时，不得作为该截止时间下已知且公开可得的事实参与严格 PIT；不得自动降级为宽松 PIT。
  9. `valid_time_start/end` 是业务有效时间，与系统知识时间独立；两端必须同时为 null 或同时提供且 start <= end。知识截止与业务有效期必须分别校验，不得混成单一时间轴。
  10. Event 的 `time_normalization_rule_version` 等领域规则版本用于说明来源时间如何选择/规范化，不替代 RFC3339Nano UTC 表示规则，也不与 DTO `schema_version`、Event 版本或 Provider 版本混用。
  11. 旧字段 `as_of` 不得仅凭名称自动映射为 `system_as_of`；Adapter 必须确认旧字段实际语义与知识截止完全一致后显式映射，否则拒绝或保留原语义。
- 明确排除：本公共规则不定义每个领域字段的具体来源优先级、Provider 时间映射、交易日历版本选择或时间规范化算法；这些由 Data/News/Research/Quant 等生产方领域 CTR 定义。规则不要求所有时间字段都存在，required/nullable 由字段 Schema 声明。
- 后续定义要求：各领域 DTO/Schema 显式引用 GOV-CTR-002 1.0.0，并分别定义时间字段适用映射。公共时间/PIT 规则可独立达到 `freeze-ready`；字段映射缺口由对应 CTR 继续跟踪。


## DEC-PLAT-002-036：GOV-CTR-003 公共标识符与幂等作用域规则版本化

- 日期：2026-11-11
- 状态：`decided_under_explicit_user_delegation`
- 对应契约：GOV-CTR-003；具体命令/事件字段映射由各领域 CTR 负责。
- 决策依据：项目负责人明确授权由 ChatGPT 对未确认的项目级契约取舍直接 Review 并按最优逻辑裁决；本项目初版不承担旧版兼容负担。
- 决议：
  1. GOV-CTR-003 公共标识符语义规则版本定为 1.0.0。标识符分为领域对象 ID、request_id、originating_request_id、correlation_id、event_id、idempotency_key 和 trace_id/span_id；它们的用途、生命周期和唯一性作用域不同，不得互相替代。
  2. 领域对象 ID 标识业务对象生命周期，由领域生产方定义格式、版本关系和唯一性范围；消费者只按不透明引用使用，不解析内部格式。
  3. `request_id` 标识一次实际请求/执行，仅用于排障和请求日志关联。同步入口由可信入口策略生成/校验；Worker 每次实际执行或 Attempt 使用独立 request_id。request_id 不作为业务主键、认证身份、授权凭证或幂等键。
  4. `originating_request_id` 标识创建异步任务的来源请求。它从可信 Request Context 注入；纯内部触发且不存在来源 HTTP/外部请求时显式 null，不伪造系统请求 ID。Worker 当前 request_id 不得复用 originating_request_id。
  5. `correlation_id` 标识跨模块业务工作链；在同一 Run/业务链及其 Stage、Attempt、事件和重试中保持稳定。无父业务链时由入口/编排方生成高熵值；消费者只继承可信父 Context，不信任客户端自报值。correlation_id 不用于去重或授权。
  6. `event_id` 标识生产方创建的稳定事件身份，重试/重放同一逻辑事件不得改变。跨模块 Inbox 唯一性按 `(source_module, event_id)` 表达；事件版本（如有）与 event_id 分离。Notification 集成事件的 event_id 属于独立消息身份，不得复用 RunRef、RiskDecision ID 或 ResearchEvent ID；来源领域对象通过 source_event_ref 表达。
  7. `idempotency_key` 标识一次命令/副作用意图，不标识请求或资源。每个有副作用的命令必须在其契约中明确唯一性作用域（至少包含调用主体和操作/use_case）、保留期、请求规范化和 fingerprint 输入。相同 scope+key+相同 fingerprint 返回原结果；相同 scope+key+不同 fingerprint 必须返回稳定冲突，不得静默覆盖。
  8. `correlation_id`、`event_id`、`idempotency_key` 均为 1..128 字节非空不透明字符串；`request_id`/`originating_request_id` 遵循 PLAT-CTR-002 的 X-Request-ID 格式和可信入口规则。各领域 ID 的长度/格式由领域 Schema 定义。
  9. 请求 fingerprint 只覆盖影响命令语义/副作用的规范化业务输入，不覆盖 request_id、correlation_id、originating_request_id、接收时间或传输 Header；每个命令契约必须明确其精确字段集合，不能由消费者自行推断。
  10. 当外部副作用结果不确定（ambiguous outcome）时，不得仅凭 retryable 或相同 correlation_id 盲目重放；必须按该操作的幂等能力、对账接口和状态机处理，必要时保留 unknown。
  11. `trace_id/span_id` 属于分布式追踪元数据，不是业务主键、幂等键或授权凭证。首期不要求 Trace SDK、span_id 或 baggage 全链路传播；只有真实并行调用追踪需求出现时再独立扩展。
  12. `gateway_request_id` 与 `upstream_request_id` 如需保留，必须是独立字段，不能覆盖调用方 request_id 或 originating_request_id。
- 明确排除：本公共规则不规定每个命令/事件的具体幂等 key 格式、fingerprint 字段清单、保留期、数据库唯一约束、重试状态机或 Header/Context 运行时实现；这些由对应业务 CTR/PLAT-CTR-002 定义。
- 后续定义要求：各领域 DTO/Port/事件 Envelope 显式引用 GOV-CTR-003 1.0.0，并补齐自身字段映射。公共标识符语义可独立达到 `freeze-ready`；真实传播、Golden 和幂等执行证据由对应 CTR 验收。


## DEC-PLAT-002-037：GOV-CTR-004 Schema 版本、兼容与废弃规则版本化

- 日期：2026-11-11
- 状态：`decided_under_explicit_user_delegation`
- 对应契约：GOV-CTR-004；各 DTO/Event 的版本映射和兼容矩阵由对应 CTR 负责。

- 决议：
  1. GOV-CTR-004 公共版本兼容规则版本定为 1.0.0。每个独立演进的 DTO、Event Envelope、Payload、Result Manifest、Ref 和 Application Contract 使用自己的 `schema_version`；Schema 版本与模块软件版本、算法版本、Template 版本、Event 业务版本相互独立。
  2. `schema_version` 使用 SemVer 字符串 `MAJOR.MINOR.PATCH`，不带 `v` 前缀。该版本只描述当前 DTO/Schema 自身的序列化结构和公开语义；嵌套且可独立演进的 Payload 必须使用自己的版本字段。DEC-028 已明确 Envelope、Manifest、Payload 版本身份分离。
  3. PATCH 只允许修正文档、描述、注释和非规范性示例，不得改变 Schema 验证结果、字段含义、默认值或运行行为。

  5. MAJOR 用于任何破坏性变化，包括 required/nullable/type/unit/precision/range/default/enum meaning/array ordering/state transition/authorization/PIT semantics 改变，删除字段，或改变既有值的解释。收紧/放宽既有字段的有效值集合如会改变消费者接受行为，也按 MAJOR 处理。
  6. Enum 默认是 closed enum。未知枚举值不得映射为默认值、success 或其他已知值；消费者必须拒绝该 DTO/事件或按该契约明确的 unsupported/degraded 安全路径处理。只有 Schema 明确声明为 open enum 且定义未知值处理方式时，才允许向后兼容新增枚举值。
  7. 每个 Schema 必须明确未知字段策略（忽略或拒绝）和安全敏感字段策略。新增 optional 字段只有在所有直接消费者可安全忽略、且不改变既有行为时才可作为 MINOR；涉及授权、身份、金额、PIT 或状态控制的未知字段不得静默忽略。
  8. 消费者只能解析其明确支持的 `schema_version`，或消费契约明确声明兼容的版本范围。未知 MAJOR、未知必需枚举或不兼容版本必须 fail-safe 拒绝；不得回退到“最新可用”、近似版本或旧 Schema 猜测。
  9. 已发布的 `(schema_id, schema_version)` 定义不可原地改变；Event Registry 使用 `(event_type, schema_version)` 唯一定位 Schema。相同版本的规范 Schema 与 Golden 必须保持不可变；需要语义/结构变更时发布新版本并保留旧版本证据。
  10. 废弃必须记录 `deprecated_since`、replacement、迁移说明、直接消费者清单和 `removal_after`（版本或明确条件）。不设全项目统一的“两次发布周期”最低等待期；实际兼容窗口按部署状态、消费者迁移成本和风险明确声明。仍有活跃消费者时，删除前必须证明所有直接消费者已迁移并通过兼容 Contract Test。
  11. 若初版能力尚无部署消费者、无外部兼容承诺，项目可通过明确决议直接退役旧定义/接口，不强制建设无意义兼容层；必须保留退役记录和替代关系。DEC-018 的旧 Analysis API 直接退役属于此类。
  12. 历史 Run/Event/Delivery/Result 必须保留创建时的 schema_version、algorithm_version、template_version 和输入快照引用；不得静默用当前版本重算、迁移或重解释历史结果。确需迁移时必须生成显式、可审计的迁移产物。
- 明确排除：本规则不维护所有 DTO/Event 的逐项版本表、兼容矩阵、消费者支持范围或迁移状态；这些由登记簿和各领域 CTR 负责。本规则不要求所有模块支持双版本，也不把 CI/部署测试纳入公共语义冻结门禁。
- 后续定义要求：各 DTO/Event Schema 显式声明自身版本、未知字段/枚举策略和兼容级别；各直接消费者维护支持版本矩阵及必要 Golden。GOV-CTR-004 公共规则可独立达到 `freeze-ready`，逐契约兼容证据仍由对应 CTR 验收。

## DEC-PLAT-002-039：PLAT-CTR-001 公共 HTTP Error Envelope 与 Fault 投影

- 日期：2026-11-11
- 状态：`decided_under_explicit_user_delegation`
- 对应契约：PLAT-CTR-001、PLAT-CTR-002、GOV-CTR-004。
- 决议：
  1. 内部 `platform.Fault` 不是 HTTP DTO，不得直接 JSON 序列化。Server 必须显式投影为独立 `ErrorEnvelope`，结构为顶层 `schema_version` 与 `error` 对象。
  2. `ErrorEnvelope.schema_version` 固定表示 ErrorEnvelope 自身 Schema 版本，首版为 `1.0.0`；不得用模块版本、API 路由版本或 Fault.Code 代替。
  3. `error` 必需字段为 `class`、`code`、`message`、`retryable`；`request_id` 为可选兼容字段。若 body 携带 request_id，必须与 PLAT-CTR-002 的响应 `X-Request-ID` 完全一致；响应 Header 是权威值。
  4. `class` 使用 Fault 稳定闭合枚举：validation、unauthenticated、forbidden、not_found、conflict、unavailable、timeout、internal。未知 class 必须拒绝/归一为 internal，不能默认成功。
  5. `code` 是稳定机器码，使用小写 namespaced identifier，匹配 `^[a-z0-9][a-z0-9._-]{0,159}$`；各生产方负责自己的 code namespace。`message` 是安全的人类可读摘要，1..512 字符，不得包含堆栈、内部 Cause、敏感信息或原始 Provider 错误。`retryable` 为必需布尔值。
  6. `retryable=true` 只允许用于 unavailable 或 timeout；该标记不保证副作用可安全重放，调用方仍必须遵守 GOV-CTR-003 幂等作用域、预算和 deadline。
  7. HTTP 状态映射：validation 默认 400；请求体超限可使用 413，媒体类型不支持可使用 415；unauthenticated=401、forbidden=403、not_found=404、conflict=409、unavailable=503、timeout=504、internal=500。不得根据 message/code 文本推断状态。
  8. `Retry-After` 是可选 HTTP Header，仅在 Server 明确给出退避时间时返回；不得仅因 retryable=true 自动推导固定等待时间。`X-Request-ID` 按 PLAT-CTR-002 生成/传播。
  9. HTTP Error DTO 不公开 Fault.Dependency、Cause、堆栈、原始错误、请求体或凭证。错误响应使用 `Content-Type: application/json; charset=utf-8`、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`。
  10. HTTP 状态码是传输层结果；ErrorEnvelope 不重复包含 status 字段。request_id 不作为认证、授权或幂等依据。
- 明确排除：不定义所有领域 Error.Code 的全集，不规定领域错误的业务解释，不把 retryable 变成自动重试命令；领域 Code/消息由对应模块 CTR 维护。
- 后续定义要求：Server HTTP Response、OpenAPI/Schema 和 Golden 统一按 PLAT-CTR-001 1.0.0；现有 Server 实现是否已投影 schema_version、可选 request_id 和全部 Header 属于后续 Server 实现符合性，不阻断本公共 DTO 定义冻结。


## DEC-PLAT-002-040：Principal 必须显式区分认证来源

- 日期：2026-11-11
- 状态：`accepted_by_chatgpt_under_user_authorization`
- 对应契约：PLAT-CTR-002、PLAT-CTR-003、SRV-CTR-001。
- 问题：现有 Principal 只有 Kind/Subject/Scopes，owner_bearer 与 owner_session 都表现为 Kind=owner；若只按 Kind 授权，会把浏览器 Session 与可信运维 Bearer 混为同一权限来源，违反 DEC-PLAT-002-017。
- 决议：
  1. Principal 增加闭合枚举 `AuthMethod`，值为 anonymous、owner_bearer、owner_session、service_bearer；Kind 继续表示 anonymous/owner/service 身份类别。
  2. owner_bearer 的 Subject 固定 owner，Scopes 仅有 platform:admin；owner_session 的 Subject 固定 owner，Scopes 为空，不继承 platform:admin 或 Service Scope；service_bearer 使用稳定 Service Name 和固定 Service Scope。

  4. 新增/完善 `WithPrincipal(ctx, principal)` 作为可信身份 Middleware 的唯一写入入口；它必须校验 Kind/AuthMethod/Subject/Scopes 组合并复制 Scopes。只有完成认证的 Server Middleware 可调用；领域模块不得自行构造或覆盖 Principal。
  5. Server 每条路由显式声明允许的 AuthMethod；owner_session 不自动继承 owner_bearer/service_bearer 权限。领域资源授权继续由资源 Owner 按 GOV-CTR-006 复核，不由 AuthMethod 替代。
- 依据：DEC-PLAT-002-017 的 Bearer/Session 隔离要求；现有 Platform Bearer Router 不解析 Cookie；当前单一 Owner 应用需要 Web Session，但不能把运维凭证下发浏览器。
- 影响：Platform security Principal/Context API、Server Session Middleware/路由矩阵、领域 Application 的可信身份消费。
- 实施边界：本决议冻结公开语义，不在本轮修改 Platform/Server 业务代码；AuthMethod 与 WithPrincipal 的实现属于后续实现符合性工作。



## DEC-PLAT-002-041：Data HTTP API 仅在远程兼容模式使用专用 X-API-Key

- 日期：2026-11-11
- 状态：`accepted_by_chatgpt_under_user_authorization`
- 对应契约：DATA-CTR-006、DATA-CTR-008、PLAT-CTR-003、SRV-CTR-001。
- 决策依据：项目默认架构为 Root Server 与 Data 同进程；既有 Data 服务间认证映射文档已明确同进程使用可信 Principal/Scope Context，远程兼容模式使用独立 Data API Key；用户已授权由 ChatGPT 对未确认的项目级技术取舍按最优逻辑裁决。
- 问题：当前 OpenAPI 顶层将 ApiKey 与 BearerAuth 声明为 OR，Data Handler 又把 Authorization Bearer 当作 X-API-Key 的回退输入，契约测试将 Bearer 作为成功方式。这会把 Data API Key 与 Platform Service Bearer 混为同一凭据，违反 PLAT-CTR-003 的凭据隔离原则，也与默认同进程架构边界不符。
- 决议：
  1. Root Server + Data 同进程是默认模式。Root Server 在外部入口完成认证/路由授权，将可信 Principal/Scope Context 注入 Data Application Port；Data InProcessHandler/Application Port 不使用 Data API Key，不重复认证。
  2. 只有远程兼容/独立部署模式启用 Data HTTP Adapter 时，业务 HTTP API 才使用 Data 专用 `X-API-Key`；该模式只接受此 Header，不接受 `Authorization: Bearer` 别名。
  3. OpenAPI 顶层只保留一个 `ApiKey: []` Security Requirement Object；不得与 BearerAuth 形成 OR。健康接口显式 `security: []`，业务 Operation 继承 ApiKey。
  4. Data API Key、Platform Service Bearer、Owner Bearer、Owner Session Cookie 和 Provider Token 必须隔离；Data API Key 只认证 Remote Adapter，不是逻辑 caller 或资源授权凭证。
  5. `AuthorizationRef.subject_ref` 与 `SnapshotManifest.caller_ref` 必须来自可信逻辑调用主体；不得使用 API Key 值，也不得信任客户端自报主体。跨 HTTP 的可信 caller 传递/绑定机制归 DATA-CTR-008 明确。

## DEC-PLAT-002-045：Quant Metric Registry 身份、复合输出映射与活动算法版本

- 日期：2026-11-11
- 状态：`accepted_by_chatgpt_under_user_authorization`
- 对应契约：QNT-CTR-001、QNT-CTR-002、QNT-CTR-003、QNT-CTR-004、GOV-CTR-001。
- 决策依据：QNT-CTR-001 Entry Schema、`internal/quant/registry.Entry`、`internal/quant/metric.Metric`、首批 Indicator/Factor 计算返回结构；用户已授权按最优逻辑裁决未确认项目级语义。
- 决议：
  1. Registry Entry.code 是 metric_code；Registry 以 (metric_code, schema_version) 标识结构版本，Entry 独立定义单一标量 Metric 的类型/单位/精度/范围/算法/输入/参数/质量语义。
  2. Indicator code 是计算入口，不等于 metric_code。SMA/EMA/Return/Volatility/RSI/ATR 各输出一个同名 metric_code；MACD 输出 macd_dif/macd_dea/macd_histogram；Bollinger 输出 bollinger_middle/bollinger_upper/bollinger_lower。每个输出分别注册 Entry。
  3. 首批 Factor 输出分别使用 momentum_20d、momentum_60d、volatility_20d 作为 metric_code。
  4. 同次 Indicator 计算的复合输出共享 algorithm_version；每个 Metric.calculation_version 必须匹配其 Registry Entry.algorithm_version。
  5. schema_version 只表示 Entry JSON 结构版本；algorithm_version 表示该 metric_code 的公式、seed/window、参数解释、输入要求、单位、value_type、精度、舍入、范围和质量策略语义版本。指标语义变化升级 algorithm_version，Entry 结构变化升级 schema_version。
  6. 公共请求不指定 algorithm_version；服务端从唯一活动版本映射选择。结果记录实际版本，历史复算按实际 algorithm_version 查找，不随活动版本切换改变。
  7. 同一 metric_code/schema_version 最多一个 active algorithm_version；切换必须显式提供 expected previous version，拒绝未知版本和并发冲突；Registry Freeze 后禁止注册或切换。
- 明确排除：不决定各 metric_code 的具体 unit/scale/tolerance/range/quality_policy 数值；不伪造首批 Registry Entry/Golden；不改变首批 Indicator/Factor 算法公式。
- 影响与后续：Quant 责任范围按本决议生成首批 Registry Entry/Golden，并与 QNT-CTR-002/003 参数 Schema、QNT-CTR-004 Metric DTO 一致；完成后重新核验 QNT-CTR-001。
