## 3. Migration 未完成项与风险

Root 在 `MIGRATION_ENABLED=true` 时仍调用 Data Module 公开的 `MigrationRunner.Migrate(ctx)`，随后由 Root Registry 执行其他静态 Migration。本轮已增加显式外部 namespace 登记：`market_data` 不再被 Registry 当作未知 namespace。

外部 namespace 只读校验规则：必须存在至少一条 Migration History，所有版本号非零且状态为 `applied`。这能修复此前 `server.storage.schema_not_ready` 因未登记 namespace 导致的误报；但不校验 Data 预期版本集合和 checksum，属于过渡性校验，不是最终统一 Migration Registry。

仍存在两个代码事实：
1. Data Store.Migrate 在 Platform ApplyMigrations（版本 1～3）返回后，仍在锁外执行 `ensureNonUniqueHistoryIndex`、`ensureColumn`。多 API/Worker 实例可能并发观察到同一索引/列缺失并执行 DDL，存在真实竞态风险。
2. `MIGRATION_ENABLED=false` 时外部 namespace 仅校验 history 存在且所有记录状态 applied，不比较 Data checksum；Data Diagnostics.Ready 仍只验证 DB/Redis Ping，不验证 Data 物理 Schema。

最终方案仍为：Data 公开不可变 Migration 定义并将兼容 DDL 纳入版本 4+；Platform 提供共用 checksum preparation 的只读校验能力；Server 统一注册/调度。Migration 子项维持 IN_PROGRESS，不宣称多实例启动安全。

## 5. WebUI 与独立 Data Service 切换边界

当前 WebUI 尚未切换到 Root Data Handler：`web/src/api.js` 的行情 API 默认基路径仍为 `/market-api`，行情请求仍携带 `X-API-Key`；`web/default.conf.template` 的 `/market-api/` 仍代理到独立 `MARKET_DATA_SERVICE_NAME:8091`。Root Data Handler 则挂载在 `/api/v1/...` 明确路径前缀，并由 Owner Bearer 保护，不接受旧的 `X-API-Key` 请求，也不会自动把 Owner Session Cookie 映射为 Owner Bearer。

因此本轮只删除 Server 内部旧的 `internal/adapters/marketdata/**` HTTP Client/Collector，不删除 `cmd/market-data`、`services/market-data`、Nginx `/market-api/` 代理或独立 Data 部署资产。WebUI 认证/代理切换和旧独立服务下线必须由 Web/Data/部署任务单独完成并有真实验收；在此之前保留旧服务是必要的兼容边界。

## 6. 验收口径

- PASS：共享资源唯一；启用 Provider 的 HTTP/TCP 出口均受控；Application/HTTP/Diagnostics/Lifecycle 真实集成通过；Migration 执行和只读校验并发安全；精确 SHA CI 和真实 MariaDB/Redis Bootstrap 测试通过。
- DEGRADED：仅可选 Provider 明确 skipped/degraded，必需存储、Schema、路由和生命周期仍健康，且有 reason_code/evidence。
- FAIL：必需资源/Schema 不可用、受控出口缺失、Migration 失败或存在未控制的并发 DDL 风险、认证上下文不可信、无法安全关闭。
- NOT_COMPARABLE：无真实 Provider 样本或没有可比较来源；不能将 CI Fixture/Mock 记为真实行情验收。
