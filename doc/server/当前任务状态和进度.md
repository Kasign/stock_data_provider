## 3. 实施前置问题

以下问题必须在代码实施前明确，不得靠临时增加接口或复制公共能力绕过。

### 3.1 Data MigrationRunner 与 Server Registry 对接

- Data Module 的公开 MigrationRunner 只有 Migrate(ctx) error。
- Server Registry 当前接收 []platformstorage.Migration，并通过 ValidateApplied 做只读版本校验。
- Data MigrationRunner 没有向 Server 暴露 Migration 定义或独立 ValidateApplied 方法。
- Data Store.Migrate 中版本化 Migration 由 Platform ApplyMigrations 执行，但后续兼容索引/补列逻辑在该调用之后继续执行。

实施前需确定：由 Data 提供完整且可验证的公开 Migration 能力，还是 Server 在不访问 Data 私有 SQL/Repository 的前提下增加有明确调用场景的 Runner 适配。还必须明确 MIGRATION_ENABLED=false 时如何只读验证 Data Schema，以及多 API/Worker 实例同时启动时兼容 DDL 如何保证安全。

### 3.2 BaoStock/Pytdx TCP 受控出站

- Platform 当前提供 HTTP Client/BoundDoer；未发现可直接复用的公共 TCP BoundDialer。
- Data Module 需要 BaoStockDialContext 和 PytdxDialContext。
- 先核实是否有 Data 以外的真实模块消费者；没有跨模块复用场景时，不新增 Platform 公共 API。
- 生产实现必须绑定允许的目标 Host/Port、解析并校验目标地址、限制重定向/重新解析绕过，并且在缺少注入时 fail-closed。

## 5. 验收标准

- PASS：Data Module 使用唯一 Root 共享资源；启用 Provider 的 HTTP/TCP 出口均有明确受控执行器；Migration 可重复且并发安全；Data Readiness/路由/Lifecycle 正常；真实 MariaDB/Redis 测试通过。
- DEGRADED：仅可选 Provider 被明确标记 skipped/degraded，必需资源、Schema 和核心路由仍健康；诊断必须给出 reason_code 和证据引用。
- FAIL：必需资源或 Schema 不可用、受控出口缺失、Migration 失败/并发不安全、身份上下文不可信、Lifecycle 无法安全关闭；启动或 Readiness 必须 fail-closed。
- NOT_COMPARABLE：Provider 未配置、没有真实样本或无法核对真实上游行为；只能记录不可比较，不能记为真实 Provider 验收通过。
