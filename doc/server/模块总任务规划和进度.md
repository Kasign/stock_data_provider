## 1. 模块目标与边界

Server 是唯一应用组合根和对外 HTTP 宿主，负责配置 Bootstrap、共享资源创建、模块构造与依赖注入、路由注册、认证接入、Migration 汇总、Worker 生命周期、Health/Readiness/Diagnostics 和优雅关闭。

Server 不实现 Data/News/Research/Quant/Researchflow/LLM/Notification 的领域规则，不复制 Platform 的 HTTP Client、Fault、Security、Storage、Migration Runner 或 Diagnostics Runner，不直接访问其他模块私有 Repository/SQL/Domain。

## 5. 后续整体执行顺序

### P0：SRV-009 Data M3/M4 Root 装配

这是当前最明确、可以在 Server 分支推进的主线。

1. 复核 Data Module 公开 Config、Dependencies、Application、InProcessHandler、Diagnostics、Migration 定义和 Start/Stop/Close，不重新实现 Data Bootstrap。
2. Root 使用现有 Platform Resources：MariaDB、Redis、HTTP Client；不得在 Data Module 外再创建第二套连接池。
3. 对实际启用的 Provider 能力构造精确 DestinationPolicy/BoundDoer，并启用 RequireEgressDependencies；禁止缺少受控出口时静默回退。
4. 等待 Data 公开 Migration 定义及兼容 DDL 版本化、Platform 只读 checksum 校验能力就绪，再接入根 Migration 生命周期。
5. 挂载 Data InProcessHandler，按 DATA-CTR-006 和明确的路由认证矩阵注入可信身份；不把 API Key 下发到 WebUI。
6. 将 Data Diagnostics.Ready 接入 Server Diagnostics/Readiness；将 Data Module Start/Stop/Close 纳入 Server Lifecycle。
7. 用真实 MariaDB/Redis 验证 API/Worker 角色、迁移、路由、Provider 出站、Readiness、关闭和并发启动。

### P1：SRV-008 Owner Session 目标环境验收

不再安排新的 Owner Session 功能开发。目标环境具备访问条件后，完成 Nginx/Compose/HTTPS、Cookie Secure/Path/SameSite、Origin/Host、刷新 CSRF、登出和密码修改后重新登录的真实浏览器验收。SRV-CTR-002 的 freeze-ready 状态由契约治理流程决定，Server 不自行改写。

### P2：真实外部依赖具备后再接入

- SRV-010：先取得真实 Gateway 版本、Generate/Structured Output/SSE/取消/超时能力证据、SecretRef 和出口策略，再复用现有 Server/Platform 资源装配。
- SRV-011：先由产品确定真实渠道和权威 Recipient Directory，再装配模块已有 Fanout/Delivery 能力；不使用 Fake Provider 或虚构接收人验收生产投递。
- 两项均未满足前保持 BLOCKED，不创建占位 Provider、接口或空 Worker。

### 暂缓：SRV-012/SRV-013

Researchflow HTTP API 继续 deferred。没有正式契约和 WebUI 消费场景前，不开放公网 CreateRun/GetRun/CancelRun；旧 Analysis API/Worker 不提前删除，避免出现无替代入口或双路径 fallback。

### 后续：SRV-014 Data 部署与最终验收

Data Root 装配代码通过后，再执行部署切换、旧 Market Data 入口停用、浏览器同源访问、回滚验证及真实数据验收。CI/Fixture 不等同真实 Provider 数据验收。

## 6. 生产装配准入与诊断标准

- 只装配模块已公开且可构造的 Application Port、Handler、Worker、Migration 和 Check。
- 所有 Config 在 Bootstrap 读取并校验，作为不可变快照注入。
- 共享资源由 Server 创建并拥有；模块借用，不提前关闭。
- 关闭顺序：先停止消费者/Worker/Relay/模块后台任务，再关闭共享 HTTP Client、Redis、DB。
- 业务模块之间通过公开 Application Port 或冻结 Outbox/Inbox 契约交互，不直接访问彼此数据库。
- 模块没有真实 Provider、Schema 或消费者时，不创建空 Registry、空 Adapter 或占位 Worker。
- 诊断统一使用 Platform Diagnostics Runner；Server 只做模块 Check Adapter，不复制 Runner。

每项新增诊断必须在任务设计中明确：
- PASS：必需依赖和必需检查均 healthy，且有当前检查时刻的真实证据。
- DEGRADED：必需链路仍可用，但可选 Provider/能力被明确跳过或部分不可用；必须保留 reason_code/evidence，不得包装成 PASS。
- FAIL：必需依赖、Schema、受控出口或必需检查失败；Required 检查不健康时 Readiness 必须拒绝流量。
- NOT_COMPARABLE：未配置可比较来源、无真实样本或缺少可验证证据；不得将其记为健康或真实数据验收通过。

进程 Readiness 与领域数据质量分开：Provider 无配置/无样本不必然导致进程不可启动，但不能据此宣称数据质量 PASS。Required/Optional 必须在每个 Check 注册时说明。

## 7. Owner Session 专项边界

- Owner Bearer 与 Owner Session 必须独立验证；浏览器只使用 HttpOnly Cookie Session，不下发 Bearer。
- Platform 提供 CredentialStore、SessionStore、CSRF、Login RateLimit、Hasher 和安全原语。
- SRV-CTR-002 定义 Owner Session 登录/登出/轮换/密码修改 HTTP DTO、路由和安全边界；当前项目契约状态仍以 PLAT-002 登记簿为准。
- 当前已完成 Schema/Golden/OpenAPI、真实 MariaDB/Redis HTTP 生命周期和 WebUI 消费代码；剩余是目标环境部署/浏览器验收和契约治理冻结，不重复开发已有 Handler。
- 不新增匿名初始化或匿名密码重置接口；生产 Argon2id 参数必须经目标硬件基准。
