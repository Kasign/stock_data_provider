# FLOW-006 结果综合与校验实施说明

## 1. 职责与边界

Researchflow 是跨模块结果综合的编排者。Quant 拥有数值计算及 Quant Risk Payload 语义；Research 拥有 Evidence/Claim/Context 语义；LLM 只提供辅助解释。Composer 另接收一个独立的编排层 RiskDecision 输入，但它与 Quant risk.Decision 的来源关系和字段映射尚未冻结。Researchflow 不重算 Quant 指标、不改写 Research 证据、不让 LLM 覆盖事实或硬风险结论。

`resultvalidation` 当前是纯校验/组合层：不主动读取 Quant/Research Repository，不签发授权，不调用模型，不持久化最终研究结果，也不创建 ResultRef。

## 2. Quant Result Envelope 精确契约

Quant Owner 当前公开 Envelope：

- 权威 Schema：`doc/quant/schema/QNT-CTR-004-quant-result-envelope-1.0.0.schema.json`
- ResultRef 是独立资源契约：`doc/quant/schema/QNT-CTR-004-quant-result-ref-1.0.0.schema.json`
- Envelope `schema_version` 表示 Envelope 自身版本，当前固定为 `1.0.0`。
- Envelope `payload_schema_version` 表示 Payload 版本，必须与 `schema_version` 分开治理。
- 当前 Envelope `result_type` 联合只支持 `trend`、`risk`；ResultRef/Registry 中可能存在其他领域类型，不代表这些类型已进入 Envelope 联合。
- `created_at` 属于 QuantResultRef，不属于 QuantResultEnvelope；Researchflow 不得把 ResultRef 元数据伪装成 Envelope 字段。
- `result_id` 使用 `quant_result:sha256:<64位小写hex>` 内容寻址格式。

本轮修复前，Researchflow 曾把 Envelope `schema_version` 当作 Payload Registry 版本、将 `created_at` 放进 Envelope、并允许 indicator/factor 等未进入 Quant Envelope 联合的类型。现已纠正：

1. `QuantResultEnvelope` 显式区分 `SchemaVersion` 和 `PayloadSchemaVersion`，移除不存在的 `CreatedAt`。
2. Registry 键固定为 `(result_type, payload_schema_version)`，未知版本不回退。
3. 当前仅允许 `trend` / `risk`；默认 `NewQuantPayloadRegistry` 精确注册两者 1.0.0。
4. Payload Validator 委托 Quant Owner 的 `quantresult.DecodePayload`，不复制 Quant Schema 或自行解析成任意 map。
5. `FromQuantEnvelope` 先执行 Quant Envelope.Validate，再映射到 Researchflow 内部组合 DTO，并保持两种 Schema 版本独立。
6. Quant Envelope 的 SystemAsOf 必须是规范 UTC，且与 Run.SystemAsOf 完全相等。

**授权边界**：`FromQuantEnvelope` 只验证/映射 Envelope，不执行当前授权或 Manifest 查询。生产调用必须先通过 Quant Application `GetResult`；该 Use Case 负责当前授权复核、Result Manifest 绑定校验和读取审计。不得绕过 Application Facade 直接读取 Quant Repository 后调用本 Adapter。

## 3. Quant Registry 与可用性

- `Registry.Register(result_type, payload_schema_version, validator)` 只接受当前 Envelope 联合支持的类型，重复注册失败。
- `Registry.Validate` 先验证 Envelope 版本，再按 Payload 版本查找精确 Validator。
- Envelope 版本当前必须等于 Quant 的 `EnvelopeSchemaVersion`；Payload 版本必须存在精确注册。
- `result_status != completed` 的结果保留但标记不可用。
- `quality_status=invalid/unknown` 不可用；`degraded` 仅在 Template 显式允许时可用。
- 纯函数空输入仅在 Template 显式 `AllowEmptyInputs` 时允许。
- `SystemAsOf` 与 Run 完全一致；输入快照引用必须非 nil、无重复、稳定排序。
- 当前默认 Registry 不注册 indicator/factor/market/industry/stock/strategy/backtest/evaluation 等未进入 Quant Envelope 联合的类型。

## 4. Result Composer

`ComposeResult` 分别接收 Research Context/Evidence/Claim DTO、Quant Envelope 内部 DTO、LLM ModelResponse 和可选 RiskDecision：

- Research/Quant/Risk/LLM 的 SystemAsOf 必须与 Run 完全一致；Evidence 的知识截止允许早于 Run，但不得晚于 Run。
- Claim 的支持/反证引用必须能在本次 Evidence 集合中闭环；Evidence 派生引用必须存在。
- Quant 不可用结果保留为 `Usable=false + ReasonCodes`，不丢弃、不升级成有效事实。
- LLM 只接受 completed 且无 Tool Call/Refusal 的文本输出；文本单独放在 Explanation，明确标记 `non_authoritative`。
- RiskDecision 独立保留；block triggered/unknown 与 pass 冲突时组合失败；输入引用必须闭环到已纳入 Context 来源或本次 Quant 结果/快照。
- RiskDecision=pass 不得引用本次已判定为不可用的 Quant Result。
- 不计算总分、不合并事实/解释、不生成行动建议状态；不持久化最终研究结果。
- Research DTO 深拷贝，避免调用方后续修改切片影响已组合结果。

### RiskDecision 来源与语义边界（待契约决议）

当前存在两个结构不同的风险对象，不能默认视为同一 DTO：

- Quant Owner 的 `quant/risk.Decision`：权威定义见 `internal/quant/risk/decision.go` 和 `doc/quant/schema/QNT-CTR-004-risk-decision-1.0.0.schema.json`。Reason 包含 code、severity、status、safe_message、evidence_refs。
- Researchflow 的 `resultvalidation.RiskDecision`：见 `internal/researchflow/resultvalidation/risk.go`。Reason 额外包含 rule_ref、observed_value、expected_range、remediation_code；时间使用 `time.Time`。

两者的校验语义也不等价：

- Quant `Decision.Validate` 要求 EvaluatedAt 不早于 SystemAsOf、Reason Code 唯一，并要求 Decision.Status 等于 `AggregateStatus(Reasons)`；AggregateStatus 至少需要一条 block 规则，所有 block 明确 not_triggered 才能 pass。
- Researchflow `ValidateRiskDecision` 已拒绝空 Reasons、`EvaluatedAt < SystemAsOf`，并防止 block triggered/unknown 与 pass 冲突；但尚未强制 Reason Code 唯一，也没有复用 Quant 的完整 `AggregateStatus` 规则。
- Composer 将 Researchflow RiskDecision 作为独立输入，与 QuantResultEnvelope 分开接收；当前没有从 Quant `risk.Decision` 到该类型的正式 Adapter。

**处理原则**：在 Owner/项目契约决议明确前，不将 Quant 的 risk Payload 自动映射成 Composer 的独立 RiskDecision，也不擅自把两套规则合并。需要先决定该对象是 Quant RiskDecision 的跨模块投影，还是 Researchflow/某个 Gate Provider 独立拥有的编排层风险结论；随后冻结唯一字段、聚合规则、时间和引用映射，并补充真实消费者测试。详见 `RF-BLOCK-008`。此外，Template 的 `HardRiskGateRegistry` 当前只是 `Contains(stageCode string) bool` 的存在性注册接口，不负责执行 Gate 或产生 RiskDecision；目前没有生产 Gate Provider 证明 Composer RiskDecision 的真实来源。

## 5. 生产接入未完成项

1. Server/Worker 生产 Adapter 尚未调用 Quant Application `GetResult`、Research Context/Evidence/Claim Facade 和 LLM Provider。
2. 生产调用必须从同一 Run 继承 `SystemAsOf` 和 `DeadlineAt`；不得用 Context.CreatedAt、模型调用当前时间或本机时钟重新生成。
3. 需要把真实 Quant Envelope 通过 `FromQuantEnvelope` 转换，并使用 `NewQuantPayloadRegistry` 验证；禁止直接读 Quant Repository。
4. Research Owner 当前授权和 Quant Owner 当前授权均在读取时复核；AuthorizationRef 非空不等于授权有效。
5. `ComposedResearchResult` 目前没有持久化 Store/ResultRef；Run 的 `ResultSummaryRef` 只表示执行摘要，不是完整研究报告。**建议由 Researchflow 持有按 RunRef 唯一关联的 `RunResult` 子资源**，只持久化组合输出、解释和来源引用，不复制 Research/Quant 原始资源；`ResultSummaryRef` 保持原义，不增加 Run Schema 1.0.0 字段。该归属需项目架构确认后再实现。
6. LLM 的真实 ModelRequest/ModelResponse 调用、Tokenizer 预算和结果引用闭环需要 Server 端到端测试。

## 6. 验收

- Quant Envelope/ResultRef Schema 与 Go 类型字段逐项一致。
- Envelope schema_version 与 payload_schema_version 独立测试；Registry 只按 payload_schema_version 精确查找。
- Quant Payload 由 Quant DecodePayload 验证；未知 result_type/schema 不回退。
- Result ID 内容寻址格式、SystemAsOf、授权/Manifest 边界和输入快照引用校验通过。
- Composer 纯函数测试不代表真实 Facade/授权/模型调用验收。
