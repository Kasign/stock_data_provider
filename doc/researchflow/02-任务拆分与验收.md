### 状态机验收补充（FLOW-CTR-001/002；历史别名 CONTRACT-006/007）

- Run 状态统一为 created/queued/running/cancelling/succeeded/partial/failed/cancelled；不得出现 Run.degraded 或 Run.timed_out。结果质量单独表达。
- Template 对每个 Stage 固定 on_degraded、on_skipped、on_failed、on_timed_out、on_blocked 传播策略，并纳入 fingerprint；归并优先级 fail > partial > succeeded。
- Stage degraded 表示有输出但质量受限；可按模板 accept 后 Run succeeded（结果质量仍 degraded），也可传播为 partial/failed。partial 必须附带缺失 Stage、降级/阻断原因和 coverage。
- required Stage 运行期失败、blocked 或 timed_out 不得用 skipped/no_impact 掩盖；硬风险门禁不能忽略失败、降级或未执行。
- blocked 不创建 Attempt；skipped 仅用于模板裁剪/不适用。Attempt 创建后不可变，重试必须创建新 Attempt。
- RetryStage 只允许 Run=running、未取消且未过 deadline；依赖输出、重试次数和总预算均需复核，重试不得改变 Run.system_as_of、输入快照或 Template 版本。
- cancel 先原子进入 cancelling，停止派发并取消在途 Attempt；所有 Attempt 收敛后 Run 才 cancelled。完成与取消通过 CAS 决胜；已提交终态不得被覆盖。
- Run deadline 是硬边界；到期后停止派发，在途工作记录 timed_out 并按模板归并，不增加 Run.timed_out；若 deadline 前已接受用户取消，保持 user_cancelled 终止原因。
- Executor 必须有界并发/队列、持久化 queued 状态、执行租约、租约回收和 fencing token；容量满时拒绝创建 Run，不得无界排队。

### FLOW-CTR-001/002 项目决议与验收补充（历史别名 CONTRACT-006/007，2026-11-06）

本节为项目统一决议。FLOW-CTR-001/002 的设计决策已关闭，当前状态为 pending_evidence；实现与自动化验收仍未完成，不以个人 Owner 签字作为门槛。

- Stage 增加非终态 retry_wait；Template 固定有限 max_attempts、retryable_reason_codes、backoff_policy、attempt_timeout。仅白名单错误自动重试；预算耗尽后 Stage.failed/timed_out 才参与 Run 聚合。
- RetryStage 仅推进 retry_wait，不得重开终态 Stage、修改 system_as_of/输入快照/Template 或扩大预算；命令必须幂等。
- created/queued 无运行中 Attempt 时可直接取消；queued Worker claim 与取消使用 CAS；running 取消进入 cancelling。
- deadline 使用数据库 UTC 时钟；db_now >= deadline_at 时 deadline 优先。未启动 Stage 记 timed_out/run_deadline_exceeded，在途 Attempt 停止或 fencing 后 timed_out，禁止重试。
- Run 终态要求所有 Stage 终结、无 running Attempt、结果摘要固定；聚合在事务内使用 Run.version CAS。
- 硬风险门禁使用 Registry stage_code + gate_type=hard_risk 双重标识；门禁执行失败/跳过/阻断/超时/降级导致 Run.failed。RiskDecision=reject/unknown 是有效分析结果但 actionability_status=blocked；Template 声明 requires_hard_risk_gate；纯观察/研究模板 actionability_status=not_evaluated；可执行结论模板必须配置至少一个适用硬风险门禁，且全部明确 pass、Run 完整成功才允许 actionable。
- 租约 fencing 只保护本地写入；有副作用工具必须有下游幂等键，结果不确定且下游不支持幂等时禁止自动重试。

## 首批实现的关键语义与待补证据

- CreateRun 指纹作用域为可信 authenticated caller + CreateRun；包含模板引用/版本、system_as_of、deadline_at、规范化快照引用和规范化 parameters；排除 originating_request_id/correlation_id。caller_ref 不允许来自请求体。
- Template fingerprint 纳入参数 Schema 引用、Output Registry 版本、资源策略、Stage DAG、Applicability 版本、传播策略和重试策略；模板解析按拓扑依赖和稳定优先级排序。
- Applicability 由接口提供；被排除 Stage 必须带 rule_version/reason_code，不创建运行 Stage；空 DAG 和依赖被排除 Stage 均拒绝。
- Retry 只允许精确 reason code 白名单；max_attempts 包含首次执行；退避使用 exponential_full_jitter_v1；失败 Attempt 保留并追加新 Attempt。
- Cancel/Deadline 对在途 Stage 不直接伪造停止成功；必须在停止确认或 fencing 后才允许 Run 收敛。
- Hard Risk Gate 必须注册、required、fail closed；RiskDecision=reject/unknown 是有效业务结果但 actionability_status=blocked；门禁未执行不得 actionable。
- 当前状态机函数是领域决策层，不提供数据库事务、CAS 或跨进程互斥。任何调用方不得将其单独视为竞态安全实现。

### 2026-11-06 RFC 8785 JCS 指纹规范化

- RequestFingerprint 与 WorkflowTemplate.Fingerprint 统一使用 `github.com/gowebpki/jcs` 的 RFC 8785 Transform，再执行 SHA-256；不再将 `encoding/json.Marshal` 输出直接作为哈希输入。
- RequestFingerprint 保留已约定的调用主体/操作/模板版本/UTC 时间/快照引用/parameters 范围；快照引用按集合语义排序，parameters 作为 RawMessage 交由 JCS 规范化。
- JCS 对重复对象键、非法 UTF-8/代理项和不符合规范的 JSON 拒绝；数值统一按 ECMAScript binary64 规则规范化，包含负零语义。
- Template fingerprint 继续先对 Stage、Dependencies、RetryableReasonCodes 等集合语义字段排序，再对完整执行语义对象执行 JCS。
- 依赖版本固定为 `v1.0.2`，其模块声明 Go 1.21，与本项目 Go 1.22 兼容；仍需在 CI 执行 RFC 8785 Golden/边界测试确认。
