### 状态机验收补充（FLOW-CTR-001/002；历史别名 CONTRACT-006/007）

- Run 状态统一为 created/queued/running/cancelling/succeeded/partial/failed/cancelled；不得出现 Run.degraded 或 Run.timed_out。结果质量单独表达。
- Template 对每个 Stage 固定 on_degraded、on_skipped、on_failed、on_timed_out、on_blocked 传播策略，并纳入 fingerprint；归并优先级 fail > partial > succeeded。
- Stage degraded 表示有输出但质量受限；可按模板 accept 后 Run succeeded（结果质量仍 degraded），也可传播为 partial/failed。partial 必须附带缺失 Stage、降级/阻断原因和 coverage。
- required Stage 运行期失败、blocked 或 timed_out 不得用 skipped/no_impact 掩盖；硬风险门禁不能忽略失败、降级或未执行。
- blocked 不创建 Attempt；skipped 仅用于模板裁剪/不适用。Attempt 创建后不可变，重试必须创建新 Attempt。
- RetryStage 只允许 Run=running、未取消且未过 deadline；依赖输出、重试次数和总预算均需复核，重试不得改变 Run.system_as_of、输入快照或 Template 版本。
- cancel 先原子进入 cancelling，停止派发并取消在途 Attempt；所有 Attempt 收敛后 Run 才 cancelled。完成与取消通过 CAS 决胜；已提交终态不得被覆盖。
- Run deadline 是硬边界；到期后停止派发，在途工作记录 timed_out 并按模板归并，不增加 Run.timed_out；若 deadline 前已接受用户取消，保持 user_cancelled 终止原因。
- Executor 必须有界并发/队列、持久化 queued 状态、执行租约、租约回收和 fencing token；容量满时拒绝创建 Run，不得无界排队。

- 租约 fencing 只保护本地写入；有副作用工具必须有下游幂等键，结果不确定且下游不支持幂等时禁止自动重试。

- CreateRun 指纹作用域为可信 authenticated caller + CreateRun；包含模板引用/版本、system_as_of、deadline_at、规范化快照引用和规范化 parameters；排除 originating_request_id/correlation_id。caller_ref 不允许来自请求体。

- 当前状态机函数是领域决策层，不提供数据库事务、CAS 或跨进程互斥。任何调用方不得将其单独视为竞态安全实现。

### 2026-11-06 RFC 8785 JCS 指纹规范化

- RequestFingerprint 与 WorkflowTemplate.Fingerprint 统一使用 `github.com/gowebpki/jcs` 的 RFC 8785 Transform，再执行 SHA-256；不再将 `encoding/json.Marshal` 输出直接作为哈希输入。
- RequestFingerprint 保留已约定的调用主体/操作/模板版本/UTC 时间/快照引用/parameters 范围；快照引用按集合语义排序，parameters 作为 RawMessage 交由 JCS 规范化。

### 2026-11-09 FLOW-004 Retry Policy 执行门禁

- Worker 对 Provider 请求 retry_wait 的结果不直接信任 RetryAt；按不可变执行快照中的 Template RetryPolicy 重新计算。
- 重试必须同时满足 attempt_no 未达到 max_attempts（首次执行计入次数）且 ReasonCodes 命中精确 allowlist；不满足时将 Stage 收敛为 failed，不创建后续 Attempt。
- 退避算法固定为 exponential_full_jitter_v1，按 BaseDelayMS 指数增长并封顶 MaxDelayMS，使用 crypto/rand 生成 full jitter，避免 Provider 控制重试时点或同步重试风暴。
- 新增纯函数测试覆盖允许/拒绝 reason code、max_attempts 边界和退避上限。当前 CI 尚未执行到该最新提交。

### Worker 时钟与模板重试策略一致性

- Worker 在 Claim 前读取 Stage 的不可变 RetryPolicy，并将其 max_attempts 传给 ClaimAttempt；Claim 后重新读取执行快照并比较完整 RetryPolicy，避免配置漂移。
- RetryAt 使用 DatabaseClock.NowUTC 计算，避免多 Worker 节点本地时钟偏差。
- 以上能力只定义 Application Port；具体 resolved_template_snapshot 的加载和校验由 Server Composition Root Adapter 实现。


### Worker 配置收敛

- 移除 Worker 级 max_attempts 配置，ClaimAttempt 的最大次数唯一来源为 Run 快照中的 Stage RetryPolicy，避免全局配置与版本化模板策略冲突。
- 增加 Worker 集成单测：Provider 只能返回 retry_wait 意图，Worker 根据白名单决定是否重试，并自行生成 RetryAt；非白名单原因强制落为 failed。


### FLOW-004 Attempt Timeout

- Worker 执行上下文使用 min(Run.deadline_at, Attempt.started_at + RetryPolicy.attempt_timeout_ms) 作为单次 Attempt 截止时间；租约心跳仍由 Run deadline 控制，不会因单次 Attempt 超时而提前停止。
- Attempt 超时被归一化为 Attempt=timed_out、reason_code=attempt_timeout，再按模板 allowlist/max_attempts 决定进入 retry_wait 或 Stage=timed_out；不会把单次超时误记为 Run deadline。

## 27. Storage 并发安全 Review（2026-11-10）

本轮按实际 SQL 事务逐项复核 Claim、Lease Renew、Attempt Result、取消确认/过期 fencing、Begin Cancellation、Deadline Expire、FinalizeRun 与 Outbox。

### 锁顺序结论

- Run 状态变更和 Attempt 生命周期事务统一先锁 Run；涉及 Stage 时按 Stage 主键/StageRef 顺序锁定；涉及 Attempt 时在 Stage 后锁定对应 Attempt，或按 stage_ref、attempt_no 顺序锁定整组 Attempt。
- ClaimAttempt、RenewAttemptLease、CommitAttemptResult、ConfirmAttemptCancellation、FenceExpiredCancellationAttempt 均遵循 Run -> Stage -> Attempt。
- BeginRunCancellation、ExpireRunDeadline、FinalizeRun 均遵循 Run -> ordered Stages -> ordered Attempts（FinalizeRun 在全部 Stage 后锁 Attempt）。
- 由于同一 Run 的写路径首先竞争同一 Run 行锁，后续 Stage/Attempt 行锁不会与另一条同 Run 写路径形成反向获取顺序。不同 Run 的锁定资源按 run_ref 隔离。
- Outbox Claim/Lease/Ack/Retry 只锁或更新 Outbox 行，不再请求 Run/Stage/Attempt 锁；FinalizeRun 在持有 Run 锁时插入新 Outbox 行，但 Outbox Worker 不回锁 Run，因此本轮未发现该组路径构成锁等待环。

### 事务失败与上下文取消

- 上述多行状态变更均在单个 SQL 事务中执行；任何中途 SQL 错误、RowsAffected 不符合预期或 Commit 前 context 取消，都会由事务回滚路径撤销本事务内已完成的写入。
- 方法均通过 BeginTx 绑定调用 context，SQL 操作可响应取消；Commit 已开始后的结果不应由调用方仅凭 context 状态推断，遇到提交错误应按持久化状态重新读取，不应盲目重复生成新的业务身份。
- 本结论来自代码路径 Review；仍需 MariaDB 故障注入和取消时序测试证明驱动/数据库环境下的行为。

### Outbox 交付语义

- FinalizeRun 在同一事务内写入 ResultSummary、Outbox 和 Run 终态；事务提交后消息才对 ClaimOutbox 可见。
- ClaimOutbox 先取得消息租约并递增 lease_generation；发布动作发生在领取事务提交之后；发布成功后由当前 owner/generation Ack。
- 若发布端已接受消息但进程在 Ack 前崩溃，租约到期后消息会被重新 Claim 并再次发布。因此这是至少一次投递，不是 exactly-once。
- 消费端必须使用 Outbox 的稳定 idempotency_key 做幂等去重；下游副作用若不支持幂等，不能依靠本地 lease_generation 消除重复副作用。
- 旧 Worker 的 Ack/Retry/Renew 由 owner + generation + 未过期租约门禁拒绝；已补对应 MariaDB 集成断言，但尚未实测。

### Review 结论与遗留验证

- 当前代码未发现 Run/Stage/Attempt 写事务之间的反向锁顺序；Outbox 与 Run 写事务之间未发现需要反向获取 Run 锁的路径。
- 未发现多行事务在中途错误时主动提交部分写入；统一依赖 SQL 事务回滚。
- 尚缺真实 MariaDB 执行证据：并发死锁/锁等待压力测试、事务中途失败回滚、context cancel 注入、Outbox 发布成功后 Ack 前崩溃并重投、消费端幂等去重。
- 此 Review 不替代 MariaDB 版本、隔离级别、索引/执行计划和生产负载验证；Server Publisher Adapter 与 Worker 生命周期仍由 Server 集成负责。


## 28. Storage 查询索引与执行计划 Review（2026-11-10）

本轮对照 v1/v2 Migration 的索引与主要查询谓词、排序字段进行静态核对。当前没有目标 MariaDB 版本上的 EXPLAIN/ANALYZE 输出，因此不凭索引存在就宣称查询已走索引或性能达标。

| 查询路径 | 已有索引 | 静态判断 | 必须补充的实测 |
|---|---|---|---|
| Run Deadline 候选 | runs(status, deadline_at) | status IN 多值并按 deadline_at、run_ref 排序；可能需要额外排序，且 EXISTS Stage 子查询依赖 stages(run_ref,status) | 不同状态分布下 EXPLAIN/ANALYZE、候选扫描行数与排序成本 |
| Outbox Claim | outbox(published_at,next_attempt_at,lease_expires_at,created_at) | IS NULL 与两个 OR 可降低复合索引的连续范围利用率；ORDER BY created_at,outbox_ref 可能 filesort；按 run_ref 限定时当前索引也不以 run_ref 开头 | 全局/单 Run 两种 Claim 查询的 EXPLAIN/ANALYZE、待投递/延迟/租约过期比例下的扫描行数 |
| Attempt 租约回收 | attempts(status,lease_expires_at) | 适合按状态与租约到期时间筛选；具体回收 SQL 仍需核对是否同时带 run/stage 限定 | EXPLAIN/ANALYZE 与大规模历史 Attempt 下的扫描量 |
| Run 下 Stage 列表 | stages(run_ref,status) | run_ref 等值过滤可利用索引；按 stage_ref 排序或全量阶段读取需结合具体 SQL 判断 | GetRun/Deadline/Cancel 快照查询的实际计划 |
| Stage 历史 Attempt | attempts(stage_ref,attempt_no) 唯一索引 | 可支持 stage_ref 等值、attempt_no 倒序取最新 Attempt | EXPLAIN 与大量重试历史下的读取成本 |

### 当前不做的变更

- 不盲目增加覆盖索引：会增加 Attempt/Outbox 高频写入成本、磁盘占用和锁竞争。
- 不在没有目标 MariaDB 版本及真实数据分布时改写 Claim/Deadline SQL。
- 不将静态索引匹配等同于执行计划验收。

### 本轮发现并修复的 Attempt 回收一致性缺口

- ClaimAttempt 回收过期 running Attempt 时，原实现只写入 timed_out/finished_at，未清空 lease_owner、lease_expires_at，也未推进旧 Attempt 的 fencing_token。
- 现已在同一 Claim 事务中将旧 Attempt 标记 timed_out、fencing_token + 1，并清空租约字段；对 token 溢出 fail-closed。新 Attempt 的 token 基于该 Stage 历史最大 token 再加一，因此旧 token=1 的回收后，新 Attempt token=3。
- MariaDB 集成测试增加断言：旧 Attempt 必须无 owner、无 expiry、token 已推进；新 Attempt 使用更高 token；旧 Worker 仍无法提交结果。
- 该测试尚未在真实 MariaDB 执行。
