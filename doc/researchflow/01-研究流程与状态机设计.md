# Researchflow 研究流程与状态机设计

## 1. 职责

接收 ResearchRequest，选择版本化 Workflow Template，创建 Run/Stage/Attempt，按 DAG 调用 Quant/Research/LLM/Notification Ports，管理 deadline/并发/取消/重试/恢复，校验引用和结构化输出，综合并归档结果。

不实现指标算法、Event 规则、模型协议或通知渠道。Platform Task Runner 提供执行基础设施；Researchflow 管理研究 Run/Stage 领域状态。

## 2. 标准研究阶段

0 受理和范围解析；1 输入快照与质量门禁；2 市场环境；3 行业/主题；4 个股量化；5 事件研究；6 Context/假设；7 策略/情景验证；8 硬风险门禁；9 结果综合和校验；10 持久化与跟踪。

模板：market_review、industry_review、stock_research、event_research、strategy_evaluation、portfolio_simulation。模板声明 required/optional stages；裁剪阶段必须记录 skipped 和 reason_code。

## 3. 状态模型与结果归并

### 3.1 状态定义
- Run 非终态：created、queued、running、cancelling；终态：succeeded、partial、failed、cancelled。
- Stage：pending、ready、running、succeeded、degraded、skipped、failed、timed_out、cancelled、blocked。
- Attempt：running、succeeded、degraded、failed、timed_out、cancelled。

Run 不使用 degraded/timed_out：degraded 表示阶段输出质量，timed_out 表示一次执行预算耗尽；整体完成度由 Run.succeeded/partial/failed 表达，Run 结果摘要另带 quality_status。Stage blocked 是依赖/前置条件不满足，不创建 Attempt；skipped 只表示模板预先裁剪或明确不适用。运行期依赖失败不得伪装 skipped。

### 3.2 Stage 传播策略
Workflow Template 必须对每个 Stage 固定以下策略，并纳入 template fingerprint：
- on_degraded：accept / partial / fail；
- on_skipped：no_impact / partial / fail；
- on_failed、on_timed_out、on_blocked：partial / fail。

归并顺序：任一 Stage 传播为 fail，则 Run failed；否则任一传播为 partial，则 Run partial；否则 Run succeeded。Stage degraded 可配置为 accept，此时 Run 可 succeeded，但结果摘要 quality_status 必须为 degraded，并保留 degraded_stage_codes/reason_codes。可选 Stage 的 intentional skipped 只有策略为 no_impact 时不影响完成度。required Stage 不得以 no_impact 忽略运行期失败或跳过。硬风险门禁 Stage 不允许忽略失败、降级或未执行；RiskDecision=unknown 不得通过。

Run partial 的 result_summary 必须包括 stage_outcomes、missing_stage_codes、degraded_stage_codes、blocked_stage_codes、reason_codes 和 coverage，不得仅返回布尔值。failed 只有重试预算耗尽后才参与最终归并；deadline 到达产生的 timed_out 直接参与归并。

### 3.3 合法迁移与重试
Run：created → queued/cancelled；queued → running/cancelling/cancelled；running → cancelling/succeeded/partial/failed；cancelling → cancelled（user_cancelled）或 failed/partial（deadline_exceeded 收敛）。终态不可重开。

Stage：pending → ready/skipped/blocked/cancelled/timed_out；ready → running/blocked/cancelled/timed_out；running → succeeded/degraded/failed/timed_out/cancelled；failed/timed_out → ready（仅显式 RetryStage 校验通过后）。Stage skipped/blocked/cancelled 为本次 Run 终态；failed/timed_out 在重试预算尚有剩余且 Run deadline 未到达时可重试。Run deadline 到达产生的 timed_out 不得重试。Stage degraded 默认不重试，除非模板显式允许。

Attempt：running → succeeded/degraded/failed/timed_out/cancelled；创建后只允许一次终态写入，不能覆盖或重开。每次重试创建 attempt_no + 1。

RetryStage 必须校验 Run=running、未取消、deadline 尚有效、Stage 失败可重试、依赖输出仍有效、次数和总预算未耗尽。重试复用原 Run.as_of、输入快照和 Template 版本。终态 Run 必须创建新 Run 才能重跑。

### 3.4 取消、deadline 与竞态
Run.deadline_at 是 UTC 绝对截止时间；Stage deadline 取阶段预算与 Run deadline 的较早者，重试不得延长 Run deadline。

显式取消在 deadline 前通过原子状态迁移将 Run 置为 cancelling，并记录 termination_reason=user_cancelled；此后拒绝新 Stage/Attempt 和 RetryStage，未开始 Stage 标记 cancelled，向在途 Attempt 传播 context cancellation。Run 等待所有在途 Attempt 收敛后才转为 cancelled。

deadline 到达且此前没有被接受的 user_cancelled 请求时，设置 termination_reason=deadline_exceeded，停止派发并取消在途执行；超时的 Stage/Attempt 记录 timed_out，随后按 Stage 传播策略归并为 failed 或 partial。Run 不增加 timed_out 终态。若 user_cancelled 在 deadline 前先被接受，取消原因保持不变；deadline 之后只负责强制回收仍未停止的 Worker。

取消与正常完成竞争，以数据库事务/CAS 的成功提交作为线性化点：正常终态先提交则后续 Cancel 返回 terminal_conflict；cancel 先进入 cancelling 则正常归并不得再提交其他终态。Attempt 终态同样采用 compare-and-set；取消后迟到输出不得覆盖已写入的 cancelled 或其他终态。context cancellation 是协作信号，不代表执行已停止；超过有界取消宽限期，由租约回收和 fencing token 拒绝旧 Worker 的迟到写入。

## 4. DAG 与资源预算
DAG 必须无环。独立市场/行业/个股子分析可并行。Executor 至少限制全局 Worker 数、全局排队容量、单 Run 并行 Stage 数、单 Stage 执行预算和 Run 总 deadline。

排队容量满时 CreateRun 返回可重试的 capacity_exceeded，不创建 queued Run。queued 状态持久化并可在进程重启后恢复。running Attempt 通过 owner/fencing token/lease_expires_at 租约管理并定期续租；租约过期由唯一回收者原子收敛 Attempt，按策略决定是否创建新 Attempt，旧 Worker 的迟到写入必须被 fencing token 拒绝。

重试由 Researchflow Application 单点负责；Executor/Adapter 不得叠加业务重试。队列不得无界缓存或无限创建 goroutine。缓存键包括 as_of、snapshot、复权、算法和质量版本。首期不建设可视化 DAG 编辑器或分布式工作流平台。
## 4. DAG 与资源

DAG 必须无环。独立市场/行业/个股子分析可并行。每个 Run 设置总 deadline、阶段并发、模型调用和数据请求预算。重试有限且带退避，不允许 Adapter/业务层/Runner 多层叠加。缓存键包括 as_of、snapshot、复权、算法和质量版本。首期不建设可视化 DAG 编辑器或分布式工作流平台。

## 5. Context 和 Tool Policy

Research 定义 Context/Evidence 模型；Flow 负责按模板组装、排序、Token Budget 和裁剪。工具 Registry/Allowlist/Scope、参数 Schema、权限、预算、超时和幂等由 Flow 管理。模型返回的工具参数必须再次校验，LLM Adapter 不直接执行工具。

## 6. 结果综合

结果必须分层展示事实、Quant 数值、Research 证据/假设、LLM 辅助解释、unknown/degraded/limitations 和硬风险门禁。模型不得修改数值事实、引用或风险状态。

## 7. Persistence / Diagnostics / Integration

Researchflow 拥有 Run/Stage/Attempt/WorkflowResult Repository 和 Migration。Platform 提供连接池、事务和 Migration Runner。Flow 提供领域 Check，注册到 Platform Diagnostics。模块分支只提供 Application Facade；根 HTTP 路由、DI、Worker 启动和 OpenAPI 在集成批次处理。
