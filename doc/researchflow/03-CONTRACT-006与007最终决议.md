## 2. FLOW-CTR-001：状态和结果归并

### 2.1 状态枚举

| 对象 | 状态 | 终态 |
|---|---|---|
| Run | created、queued、running、cancelling、succeeded、partial、failed、cancelled | succeeded、partial、failed、cancelled |
| Stage | pending、ready、running、retry_wait、succeeded、degraded、skipped、failed、timed_out、cancelled、blocked | succeeded、degraded、skipped、failed、timed_out、cancelled、blocked |
| Attempt | running、succeeded、degraded、failed、timed_out、cancelled | succeeded、degraded、failed、timed_out、cancelled |

Run 不设置 degraded/timed_out。Run.partial 表示研究覆盖不完整；quality_status 单独表达数据/结果质量。Stage.retry_wait 是非终态，表示当前 Attempt 已终结、存在符合策略的后续尝试。

blocked 表示运行期依赖/前置条件无法满足，不创建 Attempt。skipped 只表示在创建 Run 时按版本化适用性规则判定不适用或裁剪，必须带 reason_code；运行期失败不得映射为 skipped。

### 2.2 Template 传播矩阵

每个 Stage 的策略由 stage_code + template_version 固定并参与 Template fingerprint：

| Stage 结果 | 允许策略 | 说明 |
|---|---|---|
| degraded | accept / partial / fail | accept 时 Run 可 succeeded，但质量摘要保留 degraded |
| skipped | no_impact / partial / fail | no_impact 只允许 optional Stage |
| failed | partial / fail | 仅在重试预算耗尽/不可重试后参与 |
| timed_out | partial / fail | 仅在重试预算耗尽或 Run deadline 时参与 |
| blocked | partial / fail | 运行期依赖/前置条件无法满足 |

required Stage 的适用性必须在 CreateRun 前由版本化 applicability rule 解析：
- 适用：进入 resolved DAG，不能配置 on_skipped=no_impact。
- 不适用：写入 resolved_template_snapshot.excluded_stages（stage_code、rule_version、reason_code），不创建 Stage。
- optional Stage 可被标记 skipped；只有 no_impact 才不降低完成度。
- resolved DAG 至少有一个适用 Stage；空 DAG 拒绝创建，防止空流程直接 succeeded。

归并规则：
1. 先处理自动重试；retry_wait 不参与 Run 归并。
2. 所有 Stage 到终态且无运行中 Attempt 后才可归并。
3. 任一最终 Stage 的传播结果为 fail，则 Run.failed。
4. 无 fail、至少一个传播结果为 partial，则 Run.partial。
5. 所有传播结果均为 accept/no_impact，则 Run.succeeded。
6. Run.result_summary 至少包含 stage_outcomes、excluded_stages、missing_stage_codes、degraded_stage_codes、blocked_stage_codes、reason_codes、coverage、quality_status、risk_gate_decisions、actionability_status。

### 2.3 硬风险门禁

硬风险门禁必须同时满足：
- stage_code 在受控 HardRiskGate Registry 注册；
- Workflow Template 对该 Stage 声明 gate_type=hard_risk；
- Stage 在适用时必须 required；
- on_degraded/on_skipped/on_failed/on_timed_out/on_blocked 全部为 fail。

门禁执行结果和门禁业务结论分开：
- Stage 成功执行并返回 RiskDecision=pass：门禁明确通过。
- Stage 成功执行并返回 RiskDecision=reject：分析有效，门禁拒绝。
- Stage 成功执行并返回 RiskDecision=unknown：分析有效，但无法证明通过。
- 门禁未执行、Stage 执行失败/降级/超时/阻断/跳过：属于流程门禁失败，Run.failed，不得输出 actionable。

因此，RiskDecision=reject/unknown 不必把分析 Run 置为 failed，但在要求硬风险门禁的模板中 actionability_status=blocked。Workflow Template 必须显式声明 requires_hard_risk_gate：true 表示模板产出可执行建议，resolved DAG 必须至少包含一个适用的 HardRiskGate Registry 阶段；缺少适用门禁时 CreateRun 拒绝。false 表示纯观察/研究，actionability_status 固定为 not_evaluated，不能因没有配置门禁而被视为通过。actionability_status 枚举为 actionable / blocked / not_evaluated。只有 requires_hard_risk_gate=true、Run=succeeded、所有适用硬风险门禁均已执行且明确 pass、并满足其他结果质量门槛时，actionability_status=actionable。对于 requires_hard_risk_gate=true 的模板，RiskDecision=reject/unknown 或 Run.partial 时为 blocked；门禁未执行/执行层失败时 Run.failed 且 actionability_status=not_evaluated。对于 requires_hard_risk_gate=false 的模板，无论 Run 完成度如何均保持 not_evaluated，不得映射为 blocked 或 actionable。

## 3. 重试决策

每个 Stage 的 retry_policy 固定 max_attempts（包含首次）、retryable_reason_codes、backoff_policy 和 attempt_timeout。仅白名单错误可重试；Stage.degraded 在 MVP 不自动重试。

- 可重试 Attempt 失败/超时且预算可用：Attempt 终结，Stage 进入 retry_wait。
- 退避时间到达后，Scheduler 通过 RetryStage 推进 retry_wait → ready 并创建下一 Attempt。
- 非白名单错误、预算耗尽或 Run deadline 到达：Stage 终结为 failed/timed_out，参与 Run 传播。
- RetryStage 仅允许 retry_wait，不得重开终态 Stage、增加预算、改变 Run.system_as_of、输入快照或 Template 版本；命令必须有独立 idempotency_key。
- Attempt 唯一键为 (run_id, stage_id, attempt_no)，历史追加保存。

## 4. FLOW-CTR-002：取消、deadline 与竞态

- Run=created/queued 且无运行中 Attempt 时可直接取消；queued Worker claim 与 Cancel 使用 CAS，先提交者获胜。
- Run=running 取消先进入 cancelling；拒绝新派发，将 pending/ready/retry_wait Stage 标记 cancelled，并向运行中 Attempt 发送 context cancellation。已在取消线性化点前提交的结果保留，之后的迟到输出拒绝写入。
- Run.deadline_at 为绝对 UTC 时间；CreateRun 拒绝已过期 deadline。截止判断统一使用数据库 UTC 时钟，db_now >= deadline_at 时 deadline 优先。
- Attempt deadline=min(attempt_started_at+attempt_timeout, Run.deadline_at)，所有重试共享 Run.deadline_at。
- Deadline 时 queued/running Run 进入 cancelling；pending/ready/retry_wait Stage 标记 timed_out/run_deadline_exceeded；在途 Attempt 确认停止或 fencing 后记 timed_out；deadline 超时禁止重试。
- deadline_exceeded 收敛后按传播策略得到 Run.partial/failed；user_cancelled 若先于 deadline 被接受则保留原原因。
- Run 终态必须满足所有 Stage 终结、无 running Attempt、结果摘要固定；事务内使用 Run.version CAS。状态变更采用固定锁顺序 Run → Stage → Attempt。

## 5. Executor、租约和副作用

- 全局 Worker、队列容量、单 Run 并行 Stage 数有上限；容量满时 CreateRun 返回 capacity_exceeded，不创建 queued Run。容量检查与队列名额预留必须在同一事务/CAS 中完成，避免并发 CreateRun 超卖容量。
- queued Run/Stage 持久化并支持重启恢复；就绪队列稳定排序。队列恢复不得绕过 Run 状态、deadline 和 retry_policy 检查。
- Attempt lease 包含 lease_owner、lease_expires_at、单调 fencing_token；所有输出提交校验 token、Attempt=running、Run 仍允许执行。每次重新 claim/接管都递增 token，旧 token 永久失效。
- Lease 过期不代表 Worker 已停止；恢复器先原子递增 fencing_token 并撤销旧 lease，再决定是否重试。只有旧 Attempt 已终结、被确认停止或被 fence 后，才能创建下一 Attempt。
- Fencing 只保护本地写入，不能撤销外部副作用。有副作用的 Tool/Adapter 必须传递稳定下游幂等键；下游不支持幂等且结果不确定时禁止自动重发并进入诊断对账。
- 纯读取或下游幂等的操作才允许自动重试；LLM 上游可能已接收且无幂等保证时，超时后不得透明重发。

### 5.1 取消、deadline、claim 与重试的线性化规则

- `CancelRun`、Worker claim、Scheduler retry 和 deadline sweep 必须通过同一 Run.version CAS/事务门禁协调；不得只依赖进程内锁。
- 对 created/queued Run：若取消事务先成功，Run 直接 cancelled，后续 Worker claim 必须失败；若 Worker claim 先成功并将 Run 转为 running，取消必须转为 cancelling，再收敛在途 Attempt。
- 对 running Run：只有 `running -> cancelling` CAS 成功的时刻是用户取消线性化点。线性化点之前已提交的 Stage/Attempt 结果保留；之后到达的结果不得覆盖状态或写入最终结果。
- Run 已进入终态时，CancelRun 不得改写终态或 termination_reason；相同幂等命令返回当前终态，不同命令返回明确的 already_terminal 结果。
- Scheduler 推进 `retry_wait -> ready` 时，必须在同一事务确认 Run=running、`db_now < deadline_at`、重试预算仍可用且取消未被接受；创建下一 Attempt 与状态推进必须原子完成。
- Deadline sweep 与用户取消使用数据库 UTC 时钟和 Run.version CAS：`db_now >= deadline_at` 时 deadline 优先；若 user_cancelled 已在 deadline 前成功提交，则后续 deadline sweep 不得改写原 termination_reason。
- 进入 cancelling 后禁止新 Stage 派发和新 Attempt 创建。取消请求发出不等于 Attempt 已停止；Run 只有在所有在途 Attempt 收到停止确认，或其 lease 已被 fence 且本地写入权撤销后，才能进入 cancelled/partial/failed 终态。
- Attempt timeout 与 Run deadline 共用上述停止/确认流程；超时后不得在旧 Attempt 尚未停止或 fence 时并发启动下一次尝试。

### 6.1 Run Execution Context 字段契约

Run 创建时必须固定并持久化：
- `system_as_of`：必填 RFC3339Nano UTC 时间，必须不晚于服务端可信 UTC 当前时间，表示本次运行的系统知识截止值；所有 Stage、Attempt、下游 Data/News/Quant/Research/LLM 请求及重试必须原样继承。
- `deadline_at`：必填的绝对 RFC3339Nano UTC 执行截止时间；调用方必须显式传入，不设置隐式默认值，也不由模板静默生成；与 system_as_of 完全独立，不得互相推导。
- `template_ref`、`template_version`、`template_fingerprint`：固定执行定义。
- `input_snapshot_refs`：固定本次运行使用的输入快照引用；无输入快照的纯函数用例必须在 Template 声明白名单，不得用空数组掩盖数据缺失。
- `originating_request_id`：可空，追溯创建 Run 的同步 HTTP Request；纯内部触发为 null，不得伪造。
- `correlation_id`：必填，关联本次 Run 的异步工作链；从可信父 Context 继承，否则由 Researchflow 生成。

跨模块 DTO 统一使用字段名 `system_as_of`。Data 现有 API 查询参数 `as_of` 属于 Data 传输层兼容命名，由 Data Adapter 显式映射自 system_as_of；不得把它解释为 trade_date、published_at 或业务 valid_time。

### 6.2 FLOW-CTR-001/002/003 字段级命令与执行契约

**CreateRunCommand**

| 字段 | JSON 类型 | 必填/nullable | 约束 |
|---|---|---|---|
| schema_version | string | 必填 / non-null | 命令 DTO 独立版本 |
| idempotency_key | string | 必填 / non-null | 在调用主体 + CreateRun 操作范围内唯一；相同键、相同请求指纹返回原 Run，不同指纹返回 idempotency_conflict |
| template_ref | string | 必填 / non-null | 不透明模板引用 |
| template_version | string | 必填 / non-null | 显式指定，不允许默认 latest |
| system_as_of | RFC3339Nano UTC | 必填 / non-null | 必须不晚于服务端可信 UTC 当前时间；创建时固定，所有 Stage/Attempt/下游请求原样继承 |
| deadline_at | RFC3339Nano UTC | 必填 / non-null | 必须晚于数据库当前 UTC 时间 |
| input_snapshot_refs | array<string> | 必填 / non-null | 无输入纯函数模板必须在模板注册时声明 allow_empty_inputs=true |
| parameters | object | 必填 / non-null | 按 template_version 对应 typed Schema 校验；无参数使用空对象，不允许任意 map |
| originating_request_id | string/null | 必填字段 / nullable | 从可信服务端 Request ID Context 注入；纯内部触发显式 null，不伪造 system-origin Request ID |
| correlation_id | string | 必填 / non-null | 从可信上游业务 Context 继承；没有父链路时由 Researchflow 生成高熵 ID；不得直接信任客户端自报 Header |

调用主体从可信认证 Context 获取，不作为客户端可填写 DTO 字段。CreateRun 的 idempotency_key 作用域为 `(authenticated_caller_ref, CreateRun)`。请求指纹覆盖调用主体、template_ref/version、system_as_of、deadline_at、规范化 input_snapshot_refs 和 parameters；不覆盖 originating_request_id、correlation_id、request_id、接收时间。相同 idempotency_key 重放时，指纹相同返回原 Run，指纹不同返回冲突。

**Run / Stage / Attempt 读取模型**

- Run：run_ref、schema_version、status、单调递增 version、system_as_of、deadline_at、template_ref/version/fingerprint、input_snapshot_refs、result_summary_ref、created_at/started_at/finished_at、termination_reason。
- Stage：stage_ref、run_ref、stage_code、status、version、required、dependency_stage_refs、retry_policy_ref、output_ref、quality_summary_ref、diagnostic_refs、reason_codes、created_at/started_at/finished_at。
- Attempt：attempt_ref、stage_ref、attempt_no、status、lease_owner、lease_expires_at、单调递增 fencing_token、started_at/finished_at、fault_ref、output_ref。

所有 Ref 为不透明非空字符串；version、attempt_no、fencing_token 为正整数；时间均为 RFC3339Nano UTC。无结果引用显式 null；无诊断/依赖使用空数组。状态字段不可省略或以空字符串表达 unknown。

**Stage Provider Result Envelope**

| 字段 | 类型 | 责任方 | 约束 |
|---|---|---|---|
| run_ref / stage_ref / attempt_ref | string | Orchestrator | 由调用边界注入，Provider 不得输入或覆盖 |
| stage_code / template_version | string | Orchestrator | 必须与已解析模板快照一致 |
| output_type / schema_version | string | Domain Provider | 必须在 Provider Output Registry 注册 |
| payload | object | Domain Provider | 由 output_type + schema_version 对应 Schema 校验，不允许任意 map |
| quality_summary | typed object | Domain Provider | 质量语义由领域生产方定义，不映射 Stage status |
| diagnostic_refs | array<string> | Platform/Domain | Observation/evidence 不透明引用 |
| completed_at | RFC3339Nano UTC | Orchestrator | 执行边界完成时间 |

Provider 技术错误走 Platform Fault；合法业务 reject/unknown 作为领域 payload。输出 Schema 不匹配是执行契约错误，不得保存为成功业务结果。

**Retry Policy**

- max_attempts 为正整数且包含首次执行；retryable_reason_codes 是稳定白名单，不支持通配符。
- backoff 必须显式声明 algorithm、base_delay_ms、max_delay_ms；时间单位统一为 integer milliseconds，base_delay_ms>0、max_delay_ms>=base_delay_ms。MVP algorithm 固定为 exponential_full_jitter_v1：第 n 次 Attempt 失败后的上限 delay=min(max_delay_ms, base_delay_ms*2^(n-1))，实际等待从 [0,delay] 均匀抽取。attempt_timeout_ms 为正整数；Run deadline 是所有 Attempt 的共同上限。
- MVP 不设置隐式全局重试默认值；每个 Stage 显式声明 retry_policy；禁止重试使用 max_attempts=1。
- degraded、业务 reject/unknown、参数校验失败、Schema 不匹配、权限失败不可自动重试；仅白名单技术错误可重试。
- retry_wait -> ready 与新 Attempt 创建必须同事务提交；人工重跑必须是独立授权命令，不得复用 RetryStage。

### 2026-11-09 FLOW-007 Attempt Claim 持久化边界

- ClaimAttempt 的事务锁顺序固定为 Run → Stage → 最新 Attempt；Run/Stage 行锁是 fencing token 单调递增的并发串行化基础。
- Claim 在数据库 UTC deadline 内允许 Run=created/queued/running，Stage=ready/retry_wait；retry_wait 必须到达 retry_at。当前有效租约只允许同 owner 幂等重放，其他 owner 不得抢占。
- 租约过期的 running Attempt 在创建下一 Attempt 的同一事务中转为 timed_out；新 Attempt 的 attempt_no 与 fencing_token 均严格递增，Stage 转为 running 并 CAS 式递增版本，Run 首次运行时同步推进 running。
- 本切片仅完成 Claim 和 lease reclaim。迟到 Worker 的结果写入必须在后续接口中同时校验当前 fencing_token、lease_owner、Attempt=running、lease_expires_at > DB UTC now，并与 Stage/Run 的更新处于同一事务；不得只依赖普通 Stage.version CAS。

### 2026-11-09 FinalizeRun 持久化边界

- FinalizeRun 是 Domain AggregateRun 之后的持久化边界；Application 必须先校验传播策略、硬风险门禁和完整 ResultSummary，再传入终态。

- ResultSummary 资源（使用独立 SummarySchemaVersion）、run.finalized Outbox 事件和 Run 终态在一个事务内提交；Run.version CAS 是最终并发保护。Outbox 幂等键使用 Run Ref + Event Type 的 SHA-256 派生值，避免超过列长度；唯一约束防止同一 Run 重复生成摘要/终态事件。
- 该原语不实现 Outbox Worker，也不自动完成 cancelling Run 的在途 Attempt 停止确认；取消必须先等待 Worker 确认或租约 fencing，再调用 FinalizeRun。
