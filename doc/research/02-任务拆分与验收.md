## 2. RSC-001 Context 第一批实现

### 2.1 字段来源和语义

字段依据项目级 `03-模块接口契约/Quant-Research公开DTO字段级契约.md` 第 3.1、9.1、9.2、9.8 节。

| 字段 | 数据来源 | 语义 |
|---|---|---|
| schema_version | Research DTO 版本 | SemVer |
| context_id | Research ID 生成器 | 不透明 Context 标识 |
| context_version | Research 版本管理 | 从 1 开始单调递增；不可原地覆盖 |
| research_question | 可信调用方 | 研究问题 |
| scope | 可信调用方 | market/industry/stock/event |
| subject_refs | 调用方及已验证实体引用 | 证券/行业/Event 引用 |
| system_as_of | Researchflow CreateRun | Run 唯一系统知识截止时间 |
| section_refs | Research 分区评估结果 | 全部分区及版本、来源、Evidence、质量和时间 |
| quality_summary | Research 领域质量归纳 | 仅描述 Context/Evidence 完整性 |
| included_sections | section_refs | 必须等于 included=true 的 section_id 集合 |
| omitted_sections | section_refs + 省略原因 | 必须等于 included=false 的分区及原因 |
| builder_version | Research | 语义构建规则版本 |
| created_at | Research 创建记录时钟 | 创建时间，不替代 system_as_of |

### 2.2 必须满足的不变量

- context_version 从 1 开始单调递增；重新装配或改变证据集合必须产生新版本。
- section_refs 内 section_id 唯一；source_refs/evidence_refs 使用非 null 数组，引用不得重复。
- 非 Research 自身派生分区必须有 source_refs；纯 Research 派生分区可为空。
- section_refs 中每个 system_as_of 必须与 Context.system_as_of 完全一致。
- included_sections 必须精确等于 included=true 的 section_id；omitted_sections 必须精确对应 included=false 的分区。
- 每个 omitted section 必须具有稳定 reason_code、required、source_refs、safe_message、retryable。
- QualitySummary 计数为非负整数，reason_codes 去重并按字典序排序；missing_required/optional_count 必须与 omitted_sections 对应。
- required=true 的分区被省略时 Context 不得标 valid；是否阻断 Run 由 Researchflow Template 决定。

## 4. 跨模块边界决议与待决项

### RSC-DEC-001：Quant 来源引用不等于 Research 直接依赖 Quant

Quant-Research DTO 允许 Evidence.source_owner=quant 和 Scenario.quant_evaluation_ref，但项目级依赖 DAG 明确 Research 不直接依赖 Quant。Quant 结果如需进入 Research，由 Researchflow 通过公开 Quant Port 获取并完成调用主体、资源归属和当前 AuthorizationRef 复核，再把已授权的强类型 DTO 或不透明引用传入 Research。Research 仅保留引用及来源授权元数据，不直接读取 Quant Repository/Domain，不把历史 allowed 当作持续读取许可。

### RSC-OPEN-007：Evidence 不可变存储与授权快照续期语义

RSC-CTR-001 的 content_fingerprint 明确排除 authorization_ref；当前 Research Migration 的 payload_sha256 则针对完整 JSON payload，包含 authorization_ref。因此，同一 evidence_id 在内容完全不变但 Owner 重新签发 AuthorizationRef 时，会出现 content_fingerprint 相同、payload_sha256 不同的情况。

在项目契约明确前，Repository 采用完整 payload 不可变策略：相同 evidence_id + 相同完整 payload 幂等；相同 evidence_id + 不同完整 payload 冲突，不覆盖旧授权快照，也不自动生成替代 ID。该策略意味着不能用更新 Evidence 行的方式续期授权；读取时当前授权复核必须由来源 Owner 完成。若未来需要保存多次授权签发记录，应由契约明确独立授权记录/关联模型，而不是修改 Evidence 内容指纹规则。


RSC-007 Port 追加约束：Context/Event/Claim 的 Append 必须在同一数据库事务中锁定 aggregate head、校验当前最新版本、执行领域 ValidateNextVersion、插入版本快照并更新 head；相同 ID+版本+完整 payload 重放为幂等成功，不同 payload 冲突，版本跳号拒绝。Evidence 按 evidence_id 不可变写入，相同完整 payload 重放幂等、不同完整 payload 冲突；RSC-OPEN-007 的授权续期语义未决前不得按 content_fingerprint 单独放宽幂等。


### 2.12 RSC-007 Context/Event/Claim SQL Adapter 第一批实现

本轮新增 `internal/research/storage/repository.go` 及三个 typed Adapter 文件：

- `ContextRepository` 实现 `context.Repository`；`EventRepository` 实现 `event.Repository`；`ClaimRepository` 实现 `claim.Repository`。
- 构造函数接收 `*sql.DB` 和可选 `Clock`，只组装 Repository，不连接数据库、不自动执行 DDL；Migration 仍由组合根显式注册到 Platform Storage Runner。
- Append 在一个 InnoDB 事务内执行：INSERT IGNORE 初始化 aggregate head → SELECT ... FOR UPDATE 锁定 head → 检查版本连续性/幂等重放 → 读取上一版本并执行领域 ValidateNextVersion → 插入不可变快照 → CAS 更新 head → Commit。
- 相同 ID+版本+完整 JSON payload SHA-256 一致时幂等成功；同版本不同 payload、版本跳号或版本回退返回冲突。事务中途错误依赖 Rollback，不会先推进 head。
- GetVersion 只按 ID+精确版本读取；解码后重新执行领域 Validate，并检查 payload 内 ID/version 与查询键一致。缺失记录返回 `storage.ErrNotFound`。
- PIT 索引列使用 初版 Migration v1 的 RFC3339Nano 文本格式；created_at/updated_at 使用应用 Clock，不参与 PIT 比较。
- SQL 标识符只来自 Adapter 内常量，所有业务值均使用参数绑定。

当前实现状态：代码已写入；环境变量门禁的 MariaDB 集成测试覆盖首次写入、连续追加、相同 payload 重放、冲突 payload、跳号、精确读取、并发相同/冲突追加、插入失败后的 aggregate head 回滚和 Context Cancel。尚未执行仓库级 gofmt/go test，也没有真实 MariaDB 验证；未完成前不将 RSC-007 标记为验收通过。本节记录当时 Evidence Adapter 尚未实现；后续已补齐基础 Append/Get，RSC-OPEN-007 仅保留授权续期历史留档语义，不再阻断基础存储。

## 本轮整体交付盘点与收敛结论（2026-11-09）

### 已具备的模块内能力
- Context：领域模型、完整结构校验、版本连续性、内部 Golden、Draft 2020-12 Schema Validator、SQL 事务 Repository。

- Storage：Research 初版 Migration v1、聚合头锁、事务追加、完整 payload 幂等、摘要校验、精确版本读取及 MariaDB 故障注入测试代码。

### 尚未达到模块交付的事项
1. **Application Port / Facade**：Context/Evidence 的 Create/Add/Get 首批用例和 Application 自有 DTO 已实现；仍缺 ListEvidence 游标查询、Context 更新/修订用例（若后续契约需要）及 Researchflow 实际调用接线。
2. **Scenario**：主体 DTO 语义已有，Condition/ConditionGroup 的联合结构和 expected_value 类型映射仍未形成机器契约；暂不实现猜测型结构。
3. **Event Outbox**：INT-CTR-001 首批 Payload 映射、Schema/Golden Contract Test、Event/Outbox 原子提交和 Research 侧 Claim/Confirm/Retry/Reject 已实现；专用 MariaDB 验收及 Server→Notification PublishEvent 联调未完成，不能把 Outbox 已入队误报为 Notification 已接收。

6. **授权闭环**：Research 本地快照验证不能替代 Data/News/Quant Owner 当前策略复核、撤销检查和内容读取 TOCTOU 保护。

### 本轮 Research Outbox 可靠投递边界（2026-11-09）

- 新增 Application-owned NotificationEventEnvelope 和 OutboxDeliveryPort；Server 可通过 Claim / Confirm / Retry 驱动 Outbox，不需要依赖 Research Storage 具体实现。
- 历史方案曾通过 Migration v5 为 Outbox 增加 pending / leased / retry_wait / delivered 状态、可领取时间、租约所有者/截止时间、尝试次数、稳定错误码和确认时间。
- Storage Claim 使用事务行锁批量领取，租约过期可重新领取；每次领取递增 attempt_count，重试继续返回原始不可变 Envelope。
- Confirm 仅允许当前租约所有者确认；重复确认幂等。Retry 仅允许当前租约所有者设置下一次可领取时间，并只记录稳定 reason_code，不保存底层错误文本。
- 领取时重新校验 Envelope 必需字段和 JCS fingerprint，损坏记录 fail-closed，不发送给 Notification。
- 新增 MariaDB 集成用例覆盖 Claim → Retry → 到期重领 → Confirm → 重复确认及不再领取；仍需在专用 MariaDB 环境实际执行。
- Research 不依赖 Notification 模块；Server 后续通过 Application OutboxDeliveryPort 连接 Notification PublishEvent。

- Outbox 投递状态中的成功终态统一命名为 published（已被 Notification 接收并确认），永久拒绝进入 rejected，不再无限重试；临时错误由 Server 决定退避时间并调用 Retry。Research 不记录 Notification Delivery/Channel 状态。
- 每次 Outbox 领取都会生成独立 128-bit lease token；确认、重试、拒绝必须同时匹配 worker_id 与 lease token，避免同一 worker 在租约过期重领后，旧执行回调误确认新租约。lease token 只在 Research 内部返回给 Relay，不进入 Notification Envelope。

### 本轮 Outbox 投递接口和租约并发安全（2026-11-09）

- Application 暴露 NotificationEventEnvelope 与 OutboxDeliveryPort；Server 可 Claim、Confirm、Retry、Reject，Research 不依赖 Notification 包。
- Outbox 状态为 pending / leased / retry_wait / published / rejected；published 表示 Notification 已确认接收，不代表任何渠道已发送。
- 每次 Claim 生成独立 lease token；Confirm/Retry/Reject 同时校验 worker_id、token 和租约未过期，避免旧执行在重领后误操作新租约。
- Envelope 的 event_id、idempotency_key、occurred_at、published_at、correlation_id、fingerprint 和 payload 在重试期间不变；LeaseToken 不进入 Notification Envelope。
- Retry 只保存稳定 reason_code，不保存原始错误详情；永久拒绝进入 rejected，不再自动领取。
- 以上为 Research 模块能力；实际调用 Notification PublishEvent 的 Relay Worker 由 Server 负责装配，仍待跨模块联调。

### 2026-11-12 RSC-002 独立推进：News Application Port 消费 Adapter

**调用场景：** Researchflow 或其他可信同进程调用方已选定一条 News 不可变版本，需要将其登记为 Research Evidence；Research 写入前及后续读取时均需由 News Owner 重新检查当前授权。

**实现范围：**
- `internal/research/adapters/news` 只依赖 News 公开的 `app.ResearchEvidenceQuery` 和 Research 公开 `application.Port`，不访问 News Repository、Domain 或 SQL。
- Importer 通过 GetEvidence 指定 `caller_ref/purpose_code/content_level/system_as_of/news_id/version_id`，仅导入明确指定的不可变版本，不触发搜索或采集。
- 映射规则：`source_ref=News SourceRef`、`source_locator=NewsID`、`source_version=VersionID`；`evidence_type=reported_fact`，不把来源陈述升级为独立核实事实；News DTO 未提供可验证主体引用时 `subject_refs=[]` 并保留限制说明。

- News 当前授权状态必须为 allowed；Research Authorizer 在每次 Add/Get 前再次调用 News Query，绑定可信 caller、用途、NewsID、VersionID、内容级别及 PIT 时点。历史 AuthorizationRef 只留作来源审计，不作为 bearer token。
- News quality 与 business_quality 合并：任一 invalid => invalid；任一 unknown/未知枚举 => unknown；degraded/stale => degraded；只有两者均 valid 才为 valid。不得把 stale 或 unknown 静默标为 valid。

## 2026-11-12 RSC-CTR-002 Event 跨字段校验补齐

对照项目级冻结登记簿与 Quant/Research DTO 字段契约第 3.3、9.6.1、9.9 节，本轮按冻结语义补齐 Event 时间证据校验，不等待其他模块：

- `source_times` 中同一 `evidence_ref + time_type` 组合只能出现一次，避免同一来源同一时间类型重复记录造成歧义。
- `occurred_at/published_at/available_at` 非 null 时，必须存在对应类型的来源时间证据，且所有该类型来源时间值必须与规范化值完全一致。
- 多来源同类时间存在冲突时，允许保留全部 `source_times`，但规范化字段必须为 `null`；不允许任选一个来源值作为规范化结果。
- 增加重复来源时间、规范化值不匹配、多来源冲突、冲突时 null、多个来源一致等固定测试。
- 复核确认 Event `derived_from_refs` 的精确版本存在性和递归无环检查已在 SQL Repository 追加事务内执行；该检查不能仅靠 Application 预查替代，否则会有并发竞态。
- `time_normalization_rule_version` 当前 Domain 只校验 SemVer 格式。契约要求历史 Event 保留规则版本、冲突/精度/null 处理可复核；本轮不虚构规则 Registry，也不把格式校验冒充规则执行验收。
