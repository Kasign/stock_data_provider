## 1. 当前模块版图与拆分原则

当前已登记的主模块包括：

| 模块 | 当前职责 | 是否建议继续独立 |
|---|---|---|
| Platform | 公共技术原语、安全上下文、Fault、Diagnostics Runner、HTTP Client、Storage/Config | 是；禁止承接业务领域规则 |
| Data | A 股基础数据、行情、财务、日历、行业、Snapshot、PIT、数据质量 | 是；Provider 与数据域暂不拆成多个服务 |
| News | 新闻来源、Provider、授权、采集、版本、Evidence 查询 | 是；来源策略与内容权利保持同一 Owner |
| Quant | Indicator、Factor、Metric、Trend、Signal、Strategy、Backtest、Risk、Evaluation | 是；首期保持一个确定性计算域 |
| Research | Context、Evidence、Event、Claim、Hypothesis、Scenario | 是；负责研究语义，不重复计算 Quant 指标 |
| Researchflow | Run、Stage、Attempt、DAG、执行上下文、工具治理、结果传播与恢复 | 是；唯一跨业务流程编排者 |
| LLM | 模型协议、Provider Adapter、请求/响应/流/Usage | 是；不执行工具、不做业务决策 |
| Notification | 事件注册、Inbox、Subscription、Delivery、Channel Adapter | 是；只负责投递，不判断业务告警条件 |
| Server | 唯一组合根、依赖装配、启动/关闭和 Worker 装配 | 是；不拥有业务规则 |
| WebUI/API 消费端 | 页面、交互、API 消费与展示 | 是；不在前端复制领域规则 |

拆分规则：

1. 按业务事实和生命周期拆，不按页面、表、Provider 或代码目录拆。
2. 一个领域对象只能有一个写入 Owner；其他模块通过公开 API/Port/事件消费。
3. 新模块必须有独立生命周期、独立规则或独立演进压力。仅有独立页面、独立表或独立 Adapter 不足以拆模块。
4. 首期优先逻辑模块化、同进程公开 Port；只有部署、安全、扩缩容或故障隔离确有需要时才拆独立服务。
5. 任何新模块不得绕过 Researchflow 直接编排多个业务模块；不得反向依赖 Server、Platform 或 Notification 的业务实现。
6. 当前不建设交易下单、券商账户连接或自动交易执行域。

## 2. 建议新增的候选功能域

### 2.1 Portfolio：投资组合与持仓观察

<badge label="建议优先评审" color="success" />

**解决的问题：** 当前 Data 管证券事实，Quant 做计算，Research 管研究证据，但没有明确 Owner 管理用户自己的观察组合、持仓快照、成本/数量和组合维度的研究上下文。

**建议职责：**
- 自选股分组、排序、备注和观察状态。
- 用户手工维护的持仓/现金/成本等个人投资组合事实。
- 组合快照、持仓变更历史和组合维度汇总。
- 将证券/组合引用提供给 Researchflow、Quant 和 WebUI。

**明确不负责：**
- 不拥有证券主数据、行情、财务数据（归 Data）。
- 不负责指标、因子、回测和风险算法（归 Quant）。
- 不负责研究结论（归 Research）。
- 不连接券商、不下单、不托管资金、不做自动交易。
- 不把 Portfolio 持仓数据写入 Data 的市场事实表。

**建议依赖：** Portfolio → Platform、Data；Researchflow 消费 Portfolio 的公开组合快照。Quant 如需组合风险计算，由 Researchflow 传递标准化组合输入，不允许 Quant 直接读取 Portfolio 内部表。

**拆分判断：** 自选股基础 CRUD 可以先由现有 WebUI/Data API 完成，但持仓、成本、交易流水、组合快照和审计历史应由独立 Portfolio Owner 管理。若当前仅有自选股，不急于建立独立服务；先形成领域模型和 Port。

### 2.2 Alert：规则告警与触发状态

<badge label="建议优先评审" color="success" />

**解决的问题：** Quant 可以计算 Signal，Notification 可以投递消息，但“什么条件触发、触发后如何去重、何时恢复、何时静默”目前没有清晰的唯一领域 Owner。不能把告警判定塞进 Notification，也不能让 WebUI 定时轮询并自行判断。

**建议职责：**
- 用户定义的价格、涨跌幅、指标、因子、风险和事件触发规则。
- 规则版本、启停、有效期、触发窗口和冷却策略。
- Trigger/Resolve 状态机、重复事件抑制、告警历史。
- 将已确认的 Alert Event 发布给 Notification。

**明确不负责：**
- 不计算行情/指标/因子（归 Data/Quant）。
- 不抓取新闻或判断来源授权（归 News）。
- 不负责渠道模板和实际投递（归 Notification）。
- 不把“通知发送成功”视为“告警条件成立”。

**建议依赖：** Alert → Platform、Data、Quant、Research（仅在明确需要研究事件规则时）；Alert → Notification 通过版本化事件/命令契约。跨模块批量计算仍由 Researchflow 或明确的 Alert Evaluation Application 协调，不能形成循环依赖。

**拆分判断：** 告警规则与触发状态具备独立生命周期，建议作为独立逻辑模块评审；首期可以由 Server 装配 Worker，不需要独立部署。

### 2.3 Report：研究报告与发布快照

<badge label="第二批评审" color="info" />

**解决的问题：** Researchflow 的 WorkflowResult 是一次执行结果，Research 的 Evidence/Event/Claim 是可复用研究对象，WebUI 的报告页需要稳定、可追溯、可再次读取的报告产物。三者不能混成一个对象。

**建议职责：**
- 报告模板、章节结构、报告版本和渲染快照。
- 绑定 Run、Research 对象、Quant Result、News Evidence 的引用。
- 报告生成时的 system_as_of、内容来源、授权引用和内容级别记录。
- 报告版本比较、重新生成、撤回/失效状态和只读查询。

**明确不负责：**
- 不执行分析流程（归 Researchflow）。
- 不创建或改写 Evidence/Claim 等研究事实（归 Research）。
- 不重算 Quant 结果（归 Quant）。
- 不绕过来源 Owner 当前授权读取受限内容。
- 不负责通知投递（归 Notification）。

**建议依赖：** Report → Researchflow、Research、Quant、News、Platform；Server 负责装配。报告内容读取必须保留每个来源的授权链，不能因为 Report 自己保存了快照就获得新的内容许可。

**拆分判断：** 先作为 Researchflow/Research 上方的独立逻辑模块设计；待报告持久化、版本和权限需求明确后再分支实施。短期仅展示 Run 结果时不必创建独立服务。

## 3. 暂不拆分的功能域

| 功能域 | 暂不独立的原因 | 归属 |
|---|---|---|
| Provider 管理/采集调度 | Provider 是数据/新闻领域的接入适配，不是独立业务事实；策略和质量规则由领域 Owner 管理 | Data、News |
| Indicator/Factor/Strategy/Backtest/Risk | 都围绕确定性数值分析和同一套 Metric/数据版本演进；过早拆分会增加版本和计算链复杂度 | Quant 内部子域 |
| Context/Evidence/Event/Claim/Hypothesis/Scenario | 共享研究语义、来源引用和追加式版本；应保持 Research 一个 Owner | Research 内部子域 |
| Run/Stage/Attempt/Tool Policy | 同属执行生命周期和恢复状态机；不能拆成多个互相协调的调度服务 | Researchflow |
| LLM Tool Runtime | 工具权限、参数校验和执行必须由 Researchflow 控制；LLM 只做模型协议适配 | Researchflow + LLM |
| Notification Channel | 邮件、Webhook、站内消息等属于投递 Adapter，不是独立领域模块 | Notification |
| Scheduler/Worker | 先作为 Server 装配与 Researchflow/Alert 的执行机制；没有独立业务事实，不单独建 Scheduler 服务 | Server + 各业务模块 |
| User/Auth/RBAC | 当前个人使用场景不需要用户中心、组织、租户和复杂 RBAC；先用 Platform owner/service 身份原语 | Platform |
| Trading/Broker | 明确不在个人研究助手当前范围内，避免误把研究信号变成交易授权 | 不纳入当前规划 |

## 5. News → Research 授权链复审

### 5.1 已核对的 News 侧材料

本次只读检查了 `feat/research-news-ingestion` 分支的：
- `doc/news/新闻来源授权矩阵.md`
- `doc/整体任务规划/golden/NEWS-CTR-002-authorization-binding.golden.json`

确认：
1. News 明确区分 Provider 输出使用权和原始发布来源内容权利，要求两者分别判断。
2. Provider Output、Source、Endpoint 适用策略进入同一 PolicySnapshot；Endpoint 默认只能收紧 Source。
3. 请求内容级别高于策略许可时直接拒绝，不允许静默降级。
4. conditional 不是授权许可；满足条件后必须重新签发新的 allowed 引用，旧 conditional 不可读取。
5. Golden 明确 `decision=conditional`、`conditions=[attribution_required]`、`expected_content_returned=false`，因此不能把 conditional Evidence 正文交给 Research。

### 5.2 Research 派生内容必须满足的强制规则

对所有派生 Evidence，必须执行以下规则；Research 自身签发 allowed 只代表 Research 对其新建对象的管理决策，不会扩大上游授权：

1. **全来源授权（all-of）：** 派生内容涉及的每一个直接上游 Evidence 都必须存在可追溯的 Owner AuthorizationRef；任何一个来源为 denied、conditional、unknown、expired、revoked、unavailable 或引用缺失，均不得将其受限内容纳入派生结果。
2. **内容级别取交集：** 派生内容允许级别不得高于所有上游来源允许级别的最严格交集。不能用一个 full 来源提升另一个 snippet 来源的内容；不能把 metadata/snippet 来源的原文拼接后标为 full。
3. **授权用途取交集：** 派生对象用途必须同时满足每个来源的 purpose 许可；不能把 user_display 授权转用为 research_analysis。
4. **引用链传递闭包：** `derived_from_refs` 必须覆盖所有直接内容来源；对每条直接来源继续解析其上游来源链，直至原始 Data/News/Quant/Research Owner 资源。不得只保存最末级 Research Evidence 引用而丢失原始 Owner 授权。
5. **撤销传播：** 任一上游撤销、到期、收紧或当前授权服务不可用时，所有依赖该来源的派生 Evidence/Report 进入不可披露状态；若能证明剥离受影响片段并重新计算内容与 fingerprint，则可生成新的派生版本；否则拒绝整个派生对象。
6. **读取时复核：** 历史 allowed 与历史内容缓存都不能绕过 Owner 当前策略；读取前对所有上游 Owner 执行当前授权复核，并确保授权检查和内容读取处于可证明一致的版本边界。
7. **最小披露：** 不允许把 conditional/denied/unknown 来源的正文、snippet 或可还原片段写入派生内容、Prompt、日志、报告缓存或 WebUI 响应。允许返回的最小公开元数据必须由来源策略明确许可，不能从 conditional 推导出默认 metadata 可披露。

### 5.3 当前契约覆盖与待补测试

现有 GOV-CTR-006 已覆盖 conditional 不可读取、Research 来源链保留、混合来源撤销、当前读取复核和 TOCTOU fail-closed 原则；RSC-CTR-001 测试矩阵已包含派生链、超范围派生、上游撤销和 PIT 场景。

仍需在 Research Owner 的实际 DTO/Validator/Contract Test 中明确以下断言，不能只靠文档文字：

| 建议测试 ID | 场景 | 必须断言 |
|---|---|---|
| RSC001-AUTH-04 | 两个上游来源分别允许 full 与 snippet | 派生内容级别不得超过 snippet；不得把 full 来源作为提升依据 |
| RSC001-AUTH-05 | 多来源中一个来源为 conditional/unknown/denied | 该来源内容不得进入派生对象；若无法可靠隔离，整个派生请求拒绝 |
| RSC001-AUTH-06 | 只保留直接 Research Evidence ref，但上游授权链缺失 | Validator 拒绝不完整 provenance；必须追溯到每个原始 Owner 授权 |
| RSC001-READ-02 | 派生 Evidence 已缓存，任一上游撤销/过期 | 缓存不可直接返回；剥离并重新计算新版本，或拒绝整个对象 |
| RSC001-RACE-02 | 多个 Owner 并发复核，其中一个 Owner 在读取前撤销 | 整个读取操作 fail closed；不得返回其他来源拼接后的残留内容 |

**内容级别比较不能只按枚举序号实现。** Validator 必须按显式允许集合/策略交集计算；若不同来源的级别语义或用途不兼容，结果应为拒绝，而不是取最小字符串或默认值。

## 6. 本轮决议建议

1. 将 Portfolio、Alert 列为下一批优先评审的候选模块；Report 列为第二批。
2. 当前先完成逻辑边界与契约设计，不立即创建服务、不立即拆分仓库或分支。
3. 对 Research 授权链按本文件 5.2 的 all-of、级别交集、用途交集、传递闭包、撤销传播和读取复核补充机器可执行测试。
4. 在 Research 实际 Schema/Golden/DTO/Validator 路径未确认前，不改写其权威 Schema，不宣称 RSC-CTR-001 完成。
5. 本文的候选模块编号和契约编号留空；待项目总规划确认后再统一登记，禁止各模块自行分配编号。
