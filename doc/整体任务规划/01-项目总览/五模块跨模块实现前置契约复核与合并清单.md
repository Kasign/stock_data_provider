- 日期：2026-11-06
- 规划分支：`feat/design_doc`
- 覆盖模块：Quant、Research、Researchflow、LLM、Notification
- 目的：将跨模块 Review 发现转成可合并、可执行的实现约束和验收清单

## 1. 本轮复核范围与结论口径

本轮以当前规划分支 HEAD 为基线，复核以下权威文档：

- `doc/整体任务规划/跨模块契约目录与冻结状态.md`
- `doc/整体任务规划/跨模块统一契约制定规范与治理基线.md`
- `doc/整体任务规划/Quant-Research公开DTO字段级契约.md`
- `doc/notification/03-ApplicationPort与投递状态契约.md`
- `doc/notification/05-首批业务事件映射决议.md`
- `doc/researchflow/03-CONTRACT-006与007最终决议.md`
- `doc/platform/08-公共平台契约规范.md`

本清单区分三种状态：

1. **语义已决议**：不再重复讨论设计，模块按现有契约实现。
2. **实现证据待补**：设计已有结论，但仍需 DTO/Schema/Golden/Contract Test 或运行时证据。
3. **需要项目决策**：现有权威文档没有明确约束；本清单中的建议在批准前不视为冻结契约。

不得把“语义已决议”误写成“实现完成”，也不得把“实现证据待补”重新包装成设计未决。

## 3. 仍需补齐的跨模块实现约束

### 3.1 P0：Notification Envelope 输入资源上限

**发现**

当前 Notification 文档已约束 Schema 校验、JCS 指纹、模板渲染大小/深度和渠道 `max_payload_bytes` 能力，但尚未明确统一的原始 Envelope 字节数、Payload 字节数及 JSON 嵌套深度上限。只限制模板渲染或渠道发送大小，不能防止超大输入在解析、规范化和计算指纹阶段消耗资源。

**实现要求**

1. 在 JSON 解析和 JCS 规范化之前检查原始 Envelope 字节数；超限直接 fail closed。
2. 解析后单独检查 Payload 字节数、最大嵌套深度；拒绝重复对象键、非法 UTF-8、非法 JSON 和超限结构。
3. 限制必须作用于 `ValidateEvent(raw []byte)` 的入口，不得只在 HTTP Handler 或渠道 Adapter 处理。
4. 超限返回稳定 validation Fault/reason_code；不得截断、降级、跳过 Schema 校验或继续计算 fingerprint。
5. 增加刚好达到上限、超过 1 字节、深层嵌套、超大字符串、超大数组和恶意重复键测试。

**待项目决策**

建议先以 Envelope 1 MiB、Payload 768 KiB、最大嵌套深度 32 作为初始上限，并确保不超过 Platform 对应入口的请求体限制。该数值目前只是 Review 建议，未经项目统一决策不得标记为 frozen；若 Platform 已有更严格上限，应服从更严格值。

### 3.2 P1：命令请求 Fingerprint 规范统一

**发现**

QuantAnalysisRequest、Researchflow CreateRun 等已定义幂等作用域和参与指纹的业务字段；Data Manifest、Quant Result Manifest、AuthorizationRef、Notification Payload 也已使用 JCS。但项目级普通命令 Request Fingerprint 尚未形成统一的可执行规范，存在不同模块各自使用 `json.Marshal`、字段拼接或自定义排序的风险。

**建议统一规则**

1. 先按版本化 DTO 完成类型校验和语义规范化，再对参与指纹的业务对象执行 RFC 8785 JCS，使用规范化 UTF-8 字节计算 SHA-256。
2. 指纹输入只包含该命令契约声明的业务字段；request_id、correlation_id、originating_request_id、接收时间、重试次数等传输/执行元数据不得混入，除非该命令权威契约明确要求。
3. Decimal 必须保持 JSON string；不得将精确 Decimal 转为 number。number 字段按 JCS/IEEE-754 语义处理，不允许 NaN/Inf。
4. 对声明为集合的数组，先按契约规定的稳定键排序并拒绝重复项；对有序序列，保留原顺序。不得对所有数组一律排序。
5. UTC 时间在 DTO 边界规范为 RFC3339Nano `Z` 后参与指纹。
6. 幂等唯一键作用域与 fingerprint 是两个概念：唯一键相同且 fingerprint 相同返回原结果；唯一键相同但 fingerprint 不同返回冲突。

**必须补充的 Golden**

对象键顺序、数组顺序/集合排序、`1` 与 `1.0`、负零、指数表示、Unicode、转义字符、Decimal string、null/缺失、时间偏移转 UTC、重复集合元素。Quant 与 Researchflow 至少共用同一组规范化测试向量；不要求它们共享业务 DTO。

### 3.3 P1：LLM Clock 与 Deadline 传播

**实现要求**

1. LLM 能力探测、时间戳生成和 deadline 判断通过可注入 Clock 获取当前时间，禁止在核心逻辑中散落直接 `time.Now()`。
2. 单次调用有效截止时间取以下边界中最早者：ModelRequest.deadline_at、调用 Context deadline、ProviderConfig.request_timeout。
3. Generate 与 Stream 必须使用同一有效截止时间；SSE 读取、等待下一事件和最终响应收尾均受 Context 取消约束。
4. deadline 已过时不得发起 Provider 请求；调用超时后不得把不完整流伪装为 completed。
5. 测试使用固定/可推进 Clock，覆盖 deadline 相等、已过期、Context 更早、Provider timeout 更早和流读取中取消。

Researchflow 继续以数据库 UTC 时钟作为 Run/Attempt 状态竞争的权威时钟；不得将 LLM 本地 Clock 扩大为跨模块状态机时钟。

### 3.4 P1：Notification DeliveryPlan 持久化前双重校验

**实现要求**

DeliveryPlan 的结构合法性校验与 fingerprint 一致性校验是两个独立步骤。Application 层在创建/更新 Delivery 前必须同时执行：

1. `DeliveryPlan.Validate()`：验证必填字段、版本、状态、渠道能力、Recipient Scope 和字段边界。
2. `DeliveryPlan.VerifyFingerprint()`：重新计算规范化 fingerprint 并与请求/持久化值比较。
3. 两者全部通过后才允许 Repository 写入；失败不得创建部分 Delivery 或启动 Worker。
4. 增加错误 fingerprint、合法字段但伪造 fingerprint、字段变更未重算 fingerprint、相同唯一键不同 plan fingerprint 的拒绝测试。

### 3.5 P1：时间序列化与输入边界测试

GOV-CTR-002 的时间语义已经接受，不再重新讨论时区策略。五模块需要补齐同一组边界测试：

- 输出绝对时间统一为 RFC3339Nano UTC `Z`；不得输出本地时区或固定偏移格式。
- 输入 DTO 按权威 Schema 的格式要求校验；内部 `time.Time` 可有不同 Location，但序列化边界必须规范化。
- 保留纳秒精度，不得无依据截断或补造源时间精度。
- system_as_of、system_observed_at、available_at、published_at、occurred_at、created_at、deadline_at 不得混用。
- system_as_of 是知识截止，deadline_at 是执行截止；Run 重试不得刷新 system_as_of。

### 3.6 P1：Research 授权复核必须落在真实读取路径

Research Evidence 的 authorization_ref 和 derived_from_refs 语义已经明确。实现验收必须证明：

- 写入时验证来源 Owner、subject/resource、purpose、content_level 与引用归属。
- 读取受限内容时向来源 Owner 重新执行当前授权检查。
- 上游授权 revoked/expired/denied/unknown 时，派生 Evidence 不得因 Research 自身 allowed 而放行。
- 授权检查失败时只返回允许的元数据/引用和限制说明，不返回受限正文。
- 覆盖授权在写入后撤销、过期、策略版本变化和并发读取竞态。

## 4. 五模块开发顺序与验收切片

| 模块 | 可并行实施项 | 跨模块接入前置门槛 | 不得宣称完成的条件 |
|---|---|---|---|
| Quant | Metric/Indicator/Factor Registry、强类型参数与 Payload、纯计算 Fixture、Result Manifest | Data v2 Decimal Adapter、输入快照引用校验、QNT-CTR-005 授权读取 | 仅有纯计算单测不能代表结果持久化、Manifest 和授权读取完成 |
| Research | Context/Evidence Domain、PIT 过滤、引用完整性、授权链验证 | DATA-CTR-007 DailyBarsV2 Consumer DTO；RSC-CTR-001 授权复核；ResearchEvent 状态迁移提交时间 | 有 Evidence 模型不代表真实来源授权复核或 lifecycle_changed 生产映射完成 |
| Researchflow | Template、状态机、Repository/CAS、Worker、租约/fencing、Outbox | FLOW-CTR-001~004 Schema/Golden、Provider Adapter、命令指纹规范 | 纯状态迁移函数不代表并发 Worker、崩溃恢复和终态事件可靠发布完成 |
| LLM | Responses Adapter、SSE Parser、错误映射、Capability Registry、Clock 注入 | Provider 请求/响应字节限制、有效 deadline 传播、JSON/SSE Golden | DTO/Fixture 不代表真实 HTTP Adapter、流式取消和 Gateway E2E 完成 |
| Notification | Envelope Registry、Inbox 幂等、DeliveryPlan、Delivery Worker、Fake Channel、对账 | Envelope/Payload/Depth 上限、双重校验、JCS Fingerprint、Outbox/Inbox Contract Test | Domain/Fake Channel 不代表真实渠道送达或 ambiguous outcome 对账完成 |

## 5. 跨模块集成验收顺序

1. **输入与授权**：Data v2 → Quant；Data v2/News Evidence → Research；检查 Decimal、单位、PIT、snapshot_ref、authorization_ref。
2. **组合执行**：Researchflow 调用 Quant、Research、LLM；检查同一 system_as_of、deadline 传播、幂等、CAS、租约和 fencing。
3. **结果与事件**：Quant RiskDecision、ResearchEvent lifecycle、Researchflow Run terminal 经 Outbox 发布到 Notification；检查 changed_at/occurred_at、事件版本、fingerprint、Inbox 去重。
4. **失败恢复**：模拟进程重启、重复投递、唯一键冲突、授权撤销、Provider 超时、SSE 中断、渠道 ambiguous outcome；确认不丢事实、不重复副作用、不把 unknown 当成功或普通可重试失败。
5. **统一证据**：每项验收记录测试命令、Fixture/Golden、执行分支 HEAD、结果和失败明细；未执行的项目标记 pending，不得写成通过。

## 6. 合并与维护约束

- 本清单及本轮 Review 补充只在 `feat/design_doc` 维护；业务模块分支合并后，由各模块在自己的 `doc/<module>/` 维护实现进度和测试证据。
- 各模块合并时只吸收本模块相关的约束和验收项，不复制整份项目规划，也不擅自修改其他模块文档。
- 本清单不改变契约目录中的状态，不替代项目统一决策。需要新增冻结语义时，先更新唯一 canonical path，再更新契约目录状态。
- 不把未执行的测试、未验证的外部 Provider、未完成的真实渠道或未完成的集成验收标记为通过。
- 当前没有要求修改 Go 代码、Schema、Golden 或其他业务分支；后续实现应在对应模块分支按本清单推进。
