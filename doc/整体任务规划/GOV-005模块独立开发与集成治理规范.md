# GOV-005 模块独立开发与集成治理规范

- 所属治理任务：GOV-005
- 规划分支：`feat/design_doc`
- 修订日期：2026-11-05
- 状态：治理方案草案，待评审；本文件不授权创建分支或启动代码修改。
- 适用范围：Quant、Research、Researchflow、LLM、Notification 五个模块及其共同集成分支。

## 1. 目标与基本原则

GOV-005 的目标是让五个模块可以在明确边界下独立设计、开发、测试和交付，同时避免公共接口漂移、共享入口冲突和集成阶段集中返工。

必须遵守以下原则：

1. **模块独立验收优先**：模块自身的编译、单测、静态检查和模块内集成测试，以该模块当前分支及其明确依赖契约为准。
2. **不要求所有依赖分支同时编译**：Quant 不需要等待 News、LLM、Notification 全部编译；Research 也不需要等待 Data、Platform、Researchflow 的业务分支同时构建成功。
3. **契约与实现分开验收**：消费者可以依赖已评审、版本化的公开契约开发 Adapter，不要求提供方必须先完成全部生产实现；提供方的真实实现仍须在其自身验收和后续集成中通过。
4. **集成失败归属明确**：某个依赖模块编译失败，只阻断包含该模块的组合构建或端到端集成验收，不反向否定其他模块已通过的独立验收。
5. **禁止用 Mock 冒充生产验收**：Mock/Fixture 可验证消费者行为和契约，但不能证明 Provider、数据库、模型服务、通知渠道或部署网络真实可用。
6. **共享入口集中治理**：根 DI、HTTP 路由、Worker 启动、根 Migration 注册、部署文件等由集成阶段统一修改，不由多个模块分支抢占。
7. **先冻结最小契约，再并行开发**：不追求一开始冻结所有未来字段；只冻结当前开发批次必需的公开接口和语义。新增能力通过契约变更流程演进。

## 2. 三层就绪状态

不得再使用一个笼统的“GOV-004 通过/不通过”表达所有模块是否能开工。项目级状态分为三层：

| 层级 | 状态 | 含义 | 允许的工作 |
|---|---|---|---|
| L1 | Design Ready | 模块职责、依赖方向、核心领域边界和首批任务已明确 | 设计评审、任务拆分、测试方案 |
| L2 | Module Ready | 当前开发批次所需公开契约已评审并版本化；模块可使用契约和测试夹具独立开发 | 创建模块分支、模块内实现和独立验收 |
| L3 | Integration Ready | 提供方实现、消费者 Adapter、组合根、存储/网络/真实外部依赖及跨模块测试均已通过 | 合入集成分支、端到端验收和发布准备 |

状态可以按模块和按能力分别记录。例如 Quant 的 Indicator/Factor 可以达到 Module Ready，而 Quant Data Adapter 仍处于等待 Data 输入契约的状态；不得因此把整个 Quant 标为不可开工。

## 3. GOV-004 与 GOV-005 的职责分工

### 3.1 GOV-004：公共契约基线

GOV-004 负责：
- 五模块职责、依赖 DAG 和禁止 import 方向；
- 模块间公开 DTO/Port 的字段、类型、required/optional/nullable、单位、时间、质量和版本语义；
- Data、News 等外部输入的消费者边界；
- 错误、超时、取消、幂等、重试和部分成功语义；
- Repository/Migration 所有权；
- 契约版本和兼容策略。

GOV-004 不负责要求所有模块业务实现已经完成，也不以所有依赖分支同一时刻编译通过作为契约冻结条件。

### 3.2 GOV-005：开发与集成治理

GOV-005 负责：
- 模块分支创建源、命名和 PR 目标；
- 模块目录和文件修改边界；
- 任务认领、提交颗粒度和并行协作；
- 契约变更审批；
- 模块独立验收和集成验收的区分；
- 共享文件和组合根的变更流程；
- 集成批次、冲突处理、回滚和关闭条件。

## 4. 模块开工门禁

模块进入 L2 Module Ready 必须满足：

- [ ] 模块职责和禁止职责明确。
- [ ] 本模块首批任务及其验收标准明确。
- [ ] 当前批次直接依赖的公开 DTO/Port 已有字段级定义；未确定字段明确标为 optional、deferred 或暂不支持，不允许靠猜测实现。
- [ ] 时间、单位、质量、空值、错误和版本语义已有可执行约定。
- [ ] 本模块允许修改的目录和禁止修改的共享入口明确。
- [ ] 模块测试策略明确，至少包含领域单测、Application 测试和契约测试。
- [ ] 依赖未就绪部分有隔离边界：接口/Adapter 可先定义，生产连接和真实集成单独登记为阻断项。
- [ ] 模块 Owner 和集成协调责任明确。

**以下事项通常不阻断模块独立开工**，但可能阻断具体 Adapter 或最终集成：
- 其他模块当前分支的编译状态；
- 其他模块真实 Provider 的凭据和线上连通性；
- Platform 真实 MariaDB/Redis 部署验收；
- 最终根 DI、HTTP 路由、Worker 和 Migration 总注册入口；
- 尚未进入当前批次的高级功能、Metrics、审计或生产通知渠道；
- 跨模块端到端流程尚未接通。

若某项缺失会改变当前模块的公开 DTO 或领域语义，则它仍是该模块当前批次的契约阻断项，不能用临时字段猜测绕过。

## 5. 五模块首批开工范围与局部阻断

| 模块 | 可先独立推进 | 局部阻断项 | 不应等待的事项 |
|---|---|---|---|
| Quant | 计算上下文、Indicator、Factor、纯算法和固定样本测试 | Data Adapter 的字段映射、PIT/复权/单位细节未冻结时，不接入真实 Data | News/LLM/Notification 的实现和 CI |
| Research | Context、Evidence 基础领域模型、事实/推断分类、版本与引用规则 | News Query Facade 未定稿时，不实现 News 生产 Adapter 和历史证据读取 | Quant 业务实现；通过 Researchflow 传递的 Quant 结果可先用契约样例 |
| Researchflow | Request/Run/Stage/Attempt、状态机、DAG 纯逻辑和模板校验 | 真实模块 Facade 未就绪时，不接生产调用；Platform Task Queue 不得直接替代研究状态机 | 所有底层模块的生产实现同时完成 |
| LLM | 现有模型服务协议盘点、Provider/Adapter 抽象和响应 Schema 测试 | 真实服务地址/凭据缺失时，真实调用验收标记 blocked，不得标记通过 | Research/Quant/Flow 的领域实现 |
| Notification | Event、Subscription、Template、Delivery 领域模型和幂等规则 | Platform Secret/HTTP 接口未验收时，不做真实渠道投递验收 | Researchflow 的 DAG 实现和上游告警规则实现 |

说明：
- 上表表示可以拆分批次推进，不代表这些模块当前已全部达到 L2。
- 模块是否达到 L2，应由对应模块的首批契约与任务验收表给出结论；不再依赖其他模块的 CI 状态。
- Data/News/Platform 仍由各自分支负责实现。模块消费者可先基于已评审的契约编写 Adapter 和契约测试，但生产集成需等待提供方实现验收。

## 6. 分支与 PR 规则

### 6.1 分支命名

新模块分支统一使用短名称：
- `feat/quant`
- `feat/research`
- `feat/researchflow`
- `feat/llm`
- `feat/notification`

现有 `feat/research-analysis-flow-native-go` 保留为历史集成分支名称，不重命名。后续如确需新建集成分支，优先考虑 `feat/analysis`，创建前检查冲突并确认。

### 6.2 创建源与共同基线

- 五个模块分支必须从同一个已确认的分析集成基线创建，避免各分支带入不同的旧代码状态。
- 共同基线应包含已评审的规划文档和必要的稳定骨架；不要求 Data、News、Platform 的全部业务实现合并到该基线。
- 共同基线 SHA 只在创建分支前记录一次，并写入模块分支矩阵；不能把某个其他业务分支的最新 HEAD 自动当作共同基线。
- GOV-005 本文件不授权创建分支；创建操作须在模块开工门禁通过并得到明确执行指令后进行。

### 6.3 PR 方向

- 五模块 PR 目标统一为分析集成分支，不互相直接合并。
- 模块分支不得直接向 Data、News、Platform、WebUI 分支提交代码。
- 每个模块 PR 只包含本模块目录、测试、Migration 和本模块文档；跨模块契约变更必须先走第 7 节流程。
- PR 可以保持 Draft；模块内部验收完成后再请求 Review。
- 合并顺序遵循依赖 DAG，但不要求所有模块同时完成。

## 7. 契约变更流程

当模块实现发现契约缺失或不合理时：

1. 提交契约变更提案，写明当前契约版本、问题场景、消费者、兼容性和替代方案。
2. 契约 Owner 审查字段所有权、语义和版本影响；涉及多个模块时由相关 Owner 共同确认。
3. 在规划/契约文档中更新字段表、示例 JSON、Schema 和兼容策略。
4. 由契约 Owner 批准后，模块分支按新版本实现；不得在多个模块中各自复制一份定义。
5. 破坏性变更必须升级契约主版本或采用显式迁移期；禁止静默改字段含义、单位、枚举或空值语义。
6. 契约提案未通过前，模块可以继续不依赖该接口的工作；受影响的 Adapter/调用点保持隔离，不得自行假设。

契约变更记录至少包含：变更 ID、Owner、消费者、旧/新 Schema、兼容策略、迁移步骤、测试证据和生效基线。

## 9. 模块独立验收与跨模块集成验收

### 9.1 模块独立验收（Module CI）

每个模块按自己的 SHA 执行：
- 格式化、静态检查、单元测试；
- 本模块 Application/Repository/Adapter 测试；
- 本模块 Migration 测试（使用隔离测试数据库）；
- 公开 DTO/Schema 契约测试；
- 必要时使用契约 Fixture 验证消费者/提供者行为。

报告必须记录模块分支、精确 SHA、命令、测试范围、通过/失败/跳过和失败归属。

模块 CI 的通过结论只对该模块 SHA 和该模块覆盖范围有效。不得将其描述成真实外部依赖或系统端到端验收。

### 9.2 依赖模块验收（Provider CI）

Provider 自身的构建、单测、集成测试独立记录。Provider CI 失败：
- 阻断 Provider 自身合格状态；
- 阻断依赖该 Provider 的组合构建和真实集成验收；
- 不阻断不依赖该 Provider 的模块开发；
- 不推翻其他模块此前通过的 Module CI。

### 9.3 跨模块集成验收（Integration CI）

只在集成分支执行组合验证，至少记录：
- 参与模块的精确 SHA 列表；
- 公共契约版本；
- 组合构建、跨模块契约测试、真实存储/网络/模型/渠道验收；
- 故障、超时、取消、重试、幂等和降级测试；
- 集成问题归属和回归结果。

集成失败只将该组合标记为 Integration Blocked。定位到单模块缺陷后，由对应模块分支修复，再更新集成基线；不得为修复一个模块问题而在其他模块分支复制补丁。

### 9.4 状态表达

统一使用：
- `passed`：该验收范围有证据通过；
- `failed`：该范围执行失败；
- `blocked`：因明确依赖或环境缺失无法执行；
- `skipped`：按设计不适用或主动跳过，并记录原因；
- `not_run`：尚未执行。

不得把 blocked/skipped/not_run 记为 passed。一个模块可同时出现 Module CI passed、Provider Integration blocked。

## 10. 提交与协作规则

- 提交信息使用中文，格式建议：`<类型>(<模块>): <变更摘要>`，例如 `feat(quant): 增加指标计算上下文`、`test(research): 补充证据版本边界`、`docs(governance): 明确模块独立验收门禁`。
- 按完整逻辑功能批次提交，不按文件逐个提交，也不把互不相关的大量功能混成一个提交。
- 一次任务可先集中修改多个相关文件，完成自检后再提交。
- 提交前确认当前分支、HEAD、工作范围和文件路径；GitHub 更新使用当前 SHA/expected SHA，冲突时重新读取，不强制覆盖。
- 每个模块维护自己的任务状态、实现记录和测试证据；项目总览只维护跨模块里程碑，不复制其他分支的逐次提交日志。
- 发现无关问题先登记，不顺手扩展本次修改范围；安全或数据正确性高风险问题除外。

## 11. 集成阶段与顺序

1. **模块基础并行**：Quant、Research、LLM、Notification 先完成各自最小领域模型和公开 Application Port；Researchflow 同步完成 Run/Stage/Attempt、状态机和模板骨架。
2. **Adapter 接入**：按 Data、News、Platform 已冻结契约实现各自 Adapter；提供方尚未就绪时使用契约测试，真实接入状态单独标 blocked。
3. **模块存储**：各模块实现自有 Repository/SQL/Migration；只依赖 Platform Storage 稳定原语，不共享业务表。
4. **流程组合**：Researchflow 通过公开 Application Facade 组合 Quant、Research、LLM、Notification；禁止直接引用对方 Domain/Repository/Adapter。
5. **根入口集成**：集成 Owner 统一修改 DI、HTTP 路由、Worker、Migration 总注册、配置和部署。
6. **端到端验收**：以参与模块的明确 SHA 组成集成基线，执行真实数据库、Data/News、模型服务和通知渠道验收。
7. **旧链路退役**：按 MIG 清单切换调用方、差分验证、监控回滚窗口，最后删除旧 Bridge/Fallback/运行时。

## 13. 当前结论

GOV-005 的治理规则已形成文档草案，但尚未完成 Owner 确认、GOV-004 最小契约基线评审和共同基线确认。因此当前状态为 **Design Ready（治理草案）**，不是 Module Ready，也不代表可以自动创建分支。

本规范明确废止“所有依赖分支必须同时编译通过，五模块才能开工”的隐含要求。正确门禁是：
- 当前模块依赖的公开契约足够明确，模块即可独立开工；
- 真实 Provider/Storage/模型/渠道的缺失，只阻断相应真实 Adapter 或集成验收；
- 跨模块组合构建只在 Integration CI 验收，不反向覆盖各模块的独立验收结论。

本轮只新增治理文档，不创建分支、不修改业务代码、不合并 PR、不修改默认分支。
