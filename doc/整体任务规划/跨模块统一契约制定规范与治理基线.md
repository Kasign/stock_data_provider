# 跨模块统一契约制定规范与治理基线

- 仓库：`Kasign/stock_data_provider`
- 权威维护位置：`feat/design_doc`
- 文档路径：`doc/整体任务规划/跨模块统一契约制定规范与治理基线.md`
- 文档性质：项目级治理规范与跨模块契约制定基线
- 适用范围：Platform、Data、News、Quant、Research、Researchflow、LLM、Notification、Server，以及实际消费这些接口的 API/WebUI
- 状态：`accepted`（治理规则基线）；本文件不表示其中所有领域契约已冻结
- 修订日期：2026-11-06

> 本文是项目级跨模块契约治理的唯一规范入口。项目总规划决定跨模块语义、责任边界、契约编号、冻结状态和阻断范围。模块专项文档负责其领域契约的字段级定义和实现证据，不得另行创造冲突的公共语义。

---

## 1. 目标、原则与适用范围

### 1.1 目标

建立一套可以直接指导模块独立开发、联调和验收的跨模块协议基线，确保：

1. 每条真实跨模块调用关系都有明确的生产方、消费者、责任模块和公开契约。
2. 同一个字段、状态、错误码、事件或单位只有一个权威定义。
3. 契约可以落实为 DTO、JSON Schema、Golden、Contract Test 和兼容性检查。
4. 契约冻结只约束实际依赖它的调用点，不将跨模块协作变成全仓串行等待。
5. 设计决议、模块实现、真实环境集成分别验收，不混淆完成状态。
6. 统一协议，不统一内部实现；共享必要原语，不建设巨大共享 Domain 或万能 Repository。

### 1.2 强制原则

- **项目总规划唯一权威**：跨模块公共语义、编号、依赖方向、状态和门禁只能由项目总规划决定。
- **单一事实来源**：字段、枚举、状态、错误码、事件结构和单位只允许一个权威定义位置。
- **生产方负责契约**：生产方负责公开 DTO、语义、版本和 Schema；消费者负责确认实际消费语义、适配和契约测试。
- **职责不越界**：Platform 提供技术原语，不定义业务语义；Server 负责组合装配，不拥有业务规则。
- **证据驱动冻结**：文档写明不等于契约冻结；接口可调用不等于语义正确；包级测试通过不等于真实集成通过。
- **独立开发优先**：一个未冻结契约只阻断真实依赖它的调用点，不阻断无关模块开发。
- **向后兼容优先**：已发布契约优先通过新增可选字段、显式版本或新接口演进，不静默改变既有字段语义。
- **安全默认拒绝**：身份、授权、数据质量、风险门禁和未知状态不得通过隐式默认值放行。

### 1.3 术语

| 术语 | 定义 |
|---|---|
| 契约（Contract） | 跨模块可观察、可验证、可版本化的协议约束 |
| 生产方（Producer） | 对公开字段、语义和版本负责的模块 |
| 直接消费者（Consumer） | 通过公开 Port/API/事件直接读取或调用契约的模块 |
| Owner Role | 对契约负责的模块责任角色，不代表具体人员 |
| 权威文档（Canonical） | 唯一可以修改该契约定义的文档位置 |
| 引用文档（Reference） | 仅引用契约编号和权威文档，不复制定义 |
| 冻结（Frozen） | 语义、版本、样例、Schema、消费者确认及必要测试证据齐备 |
| L2 Module Ready | 当前模块实际调用点依赖的契约已冻结且模块自身验收证据齐备 |
| L3 Integration Ready | 真实外部依赖和端到端流程通过集成验收 |

## 2. 文档权威性与模块职责边界

### 2.1 文档权威层级

| 层级 | 权威位置 | 负责内容 | 禁止事项 |
|---|---|---|---|
| 项目级 | `doc/整体任务规划/**` | 跨模块语义、依赖 DAG、统一编号、契约目录、冻结状态、阻断范围、L1/L2/L3 | 不替代模块内部算法设计和实现文档 |
| Platform | `doc/platform/**` | Fault、身份原语、Request Context、Diagnostics Runner、HTTP Client、Storage Bootstrap 等技术原语 | 不定义 Data/News/Quant/Research/Flow 的业务状态、领域错误或业务 DTO |
| Data | `doc/api/**` | Provider 标准化、数据 API、证券/日历/行业、单位、复权、PIT、质量和数据诊断 | 不定义 Quant/Research 的领域模型 |
| News | `doc/news/**` | 来源授权、采集、新闻版本、检索、Evidence 查询 Facade 和内容访问策略 | 不定义 Research Event/Claim，不允许消费者访问内部存储 |
| Quant | `doc/quant/**` | Indicator、Factor、Metric、Strategy、Backtest、Risk、Evaluation | 不把计算语义转移给 Research 或 LLM |
| Research | `doc/research/**` | Context、Evidence、Event、Claim、Hypothesis、Scenario | 不直接访问 News 内部 Repository，不重算 Quant 指标 |
| Researchflow | `doc/researchflow/**` | Run、Stage、Attempt、DAG、执行上下文、工具治理、结果传播与恢复 | 不拥有各业务模块内部领域模型和算法 |
| LLM | `doc/llm/**` | 模型请求/响应、Stream、Usage、协议错误适配 | 不拥有工具权限、研究状态、事实和风险决策 |
| Notification | `doc/notification/**` | 事件消费、订阅、模板、渠道、投递、幂等和重试 | 不拥有上游业务规则和告警判定 |
| Server | 当前服务端组合根/启动文档；由项目总规划索引 | 依赖装配、配置注入、启动/关闭、资源生命周期和 API 暴露 | 不承载业务领域规则，不创建重复共享基础设施实例 |
| WebUI/API 消费端 | `doc/web/**`、接口协作清单 | API 消费、展示、交互、客户端兼容 | 不推断服务端缺失字段，不复制服务端业务规则 |

### 2.2 唯一权威规则

1. 项目总规划拥有跨模块契约的**语义决策权**和**编号分配权**。
2. 契约的字段级权威定义可以位于生产模块专项文档，但必须由项目总规划目录登记唯一 canonical path、生产方、消费者和版本。
3. 若项目总规划与专项文档冲突，以项目总规划已批准的决议为准；专项文档必须按同步清单修订。
4. 若专项文档存在项目总规划尚未决策的新语义，标记为 `pending_decision`，不得自行作为消费者必须遵循的已冻结协议。
5. 引用文档只允许写“使用 `<契约编号>`，详见 <权威路径>”，不复制字段表、状态迁移表或错误码表。
6. 为便于阅读可以展示摘要，但摘要必须注明“非权威摘要”，并链接到唯一权威定义；摘要不得独立变更。
7. 同一契约可以有多个消费者，但不得有多个 Owner；消费者可以提出变更，不可单方面改变生产方语义。
8. 跨模块变更由项目总规划记录决策和影响范围，再由各模块按职责同步；不要求同一提交跨越所有分支。

### 2.3 责任角色

Owner 使用模块责任角色，例如：

- `Platform Owner`
- `Data Owner`
- `News Owner`
- `Quant Owner`
- `Research Owner`
- `Researchflow Owner`
- `LLM Owner`
- `Notification Owner`
- `Server/Integration Owner`
- `Consumer Owner`

不得虚构具体人员姓名。跨模块契约由生产方 Owner 负责定义，直接消费者 Owner 必须确认消费语义；项目总规划负责裁决跨模块冲突。

## 3. 目标架构与依赖方向

### 3.1 模块职责摘要

| 模块 | 唯一领域职责 | 主要公开产物 |
|---|---|---|
| Platform | 通用技术基础设施 | Fault、身份上下文、Diagnostics Runner、HTTP Client、Storage Bootstrap、配置/日志/Trace 原语 |
| Data | A 股数据事实、来源和质量 | Security、MarketData、Financial、Calendar、Industry、Snapshot、PIT、Data Quality |
| News | 新闻来源、内容和授权证据 | Source、News Item/Version、Search、Evidence Query、Authorization Reference |
| Quant | 确定性数值分析 | Indicator、Factor、Metric、Trend、Signal、Backtest、Risk、Evaluation |
| Research | 研究语义与证据组织 | Context、Evidence、Event、Claim、Hypothesis、Scenario |
| Researchflow | 研究任务编排和执行生命周期 | Run、Stage、Attempt、WorkflowResult、Context Assembly、Tool Policy |
| LLM | 模型协议适配 | ModelRequest、ModelResponse、Stream Event、Usage、Model Error Mapping |
| Notification | 通知订阅与外部投递 | Notification Event、Subscription、Delivery、DeliveryAttempt |
| Server | 组合根与运行生命周期 | Bootstrap、依赖装配、HTTP Server、Worker 装配和资源关闭 |

### 3.2 依赖 DAG 规则

- Quant 不依赖 Research、Researchflow、LLM、Notification。
- Research 不依赖 Quant 或 Researchflow；通过公开证据/数据契约消费 Data、News。Quant 结果由 Researchflow 转换为 Research 所需上下文。
- Researchflow 是跨业务模块的编排者，通过公开 Application Port 调用 Data、News、Quant、Research、LLM、Notification。
- LLM 不依赖业务模块；不执行工具调用，不决定工具权限。
- Notification 不依赖 Researchflow；通过事件或公开命令消费通知请求。
- News 不依赖 Research；Research 不得访问 News 内部 Repository/SQL。
- 所有业务模块依赖 Platform 的公开技术接口，不依赖 Platform 内部实现。
- Server 依赖各模块公开 Bootstrap/Application Facade，负责装配，不允许业务模块反向依赖 Server。
- API/HTTP Handler 调用 Application Facade，不直接访问 Repository 或 Domain 内部对象。
- 模块间 DTO 转换放在明确的 Adapter/Assembler 边界；不得为图省事直接 import 对方 internal 包。
- 禁止循环依赖；禁止跨模块读取对方数据库表作为集成协议。

### 3.3 跨模块调用目录

项目总规划必须维护调用关系矩阵。首期至少登记：

| 契约域 | 生产方 | 直接消费者 | 主要方向 | 权威模块 |
|---|---|---|---|---|
| Platform 基础原语 | Platform | 所有服务端模块 | 各模块调用 Platform | Platform |
| Security/Calendar/Market/Financial/Industry/Snapshot | Data | Quant、Researchflow；必要时 Research | 消费公开 Data API/Facade | Data |
| Data Quality/Provider Observation | Data | Researchflow、WebUI/API | 数据质量与诊断输出 | Data |
| News Search/Evidence Query | News | Research、Researchflow | 只读查询 | News |
| Indicator/Factor/Metric/Trend/Risk | Quant | Researchflow | 计算与结果读取 | Quant |
| Context/Evidence/Event/Claim/Hypothesis/Scenario | Research | Researchflow | 研究对象创建、读取与综合 | Research |
| Run/Stage/Attempt/WorkflowResult | Researchflow | Server、API、WebUI、Worker | 任务生命周期 | Researchflow |
| Model Request/Response/Stream | LLM | Researchflow | 模型协议调用 | LLM |
| Notification Event/Delivery | Notification | Researchflow及业务事件生产方 | 事件消费与投递 | Notification |
| Server Bootstrap/Composition | 各模块公开 Bootstrap；Server 组合 | Server | 依赖装配 | Server 组合根 |

每新增一个跨模块调用，必须先登记生产方、消费者、调用方式、DTO/事件、超时/取消、错误映射和验收证据，再进入实现。

## 4. 契约编号与登记规则

### 4.1 编号体系

历史 `CONTRACT-001...` 在不同分支已出现编号语义冲突。自本规范生效后：

1. 不再分配新的无领域前缀 `CONTRACT-xxx`。
2. 使用领域前缀编号，编号由项目总规划统一分配。
3. 旧 `CONTRACT-xxx` 作为历史别名保留，只用于追溯，不再作为新决策编号或新文件主编号。
4. 不因模块分支独立而独立发号；所有分支必须先从项目总规划取得编号。
5. 编号一经分配永久不复用；废弃编号保留 tombstone 和替代关系。

| 前缀 | 归属 | 适用范围 |
|---|---|---|
| GOV | 项目治理 | 编号、门禁、文档权威、整体架构治理 |
| PLAT | Platform | 公共技术原语 |
| DATA | Data | 数据事实、数据 API、质量、PIT |
| NEWS | News | 新闻来源、证据查询、授权、分页 |
| QNT | Quant | Indicator、Factor、Metric、Risk、Backtest |
| RSC | Research | Evidence、Event、Claim、Hypothesis、Scenario |
| FLOW | Researchflow | Run、Stage、Attempt、执行上下文、结果传播 |
| LLM | LLM | Model Request/Response、Stream、Usage |
| NTF | Notification | Event、Subscription、Delivery |
| INT | 跨模块集成 | 多模块共同参与且无法归属于单一生产方的集成协议 |
| SRV | Server | 组合根、启动/关闭和运行装配契约 |

### 4.2 编号格式

- 决策/契约主编号：`<PREFIX>-NNN`，例如 `DATA-001`、`FLOW-006`。
- 子条款：`<PREFIX>-NNN.a` 或文档章节，不另行占用全局编号。
- 文档文件名可包含编号，但必须与总规划登记表一致。
- 一项契约覆盖多个字段时仍使用一个主编号；不同生产方、不同生命周期或不同版本策略的协议应拆分编号。
- 纯任务编号（如 QNT-001）与契约编号必须区分登记类型，不得发生编号碰撞；建议任务使用独立任务目录登记，契约编号在契约目录中唯一。

### 4.3 历史编号迁移

历史编号不直接删除。迁移表至少包含：

| 历史编号 | 历史定义 | 新编号 | 权威文档 | 迁移状态 |
|---|---|---|---|---|
| CONTRACT-001 | Platform 数值类型与精度候选方案 | GOV/PLAT/DATA/QNT 等拆分后按责任分别登记 | 项目公共基础契约及各生产方专项文档 | 待字段级拆分，不视为冻结 |
| CONTRACT-002 | Indicator | QNT-xxx（分配前不得猜号） | Quant 专项文档 | 待迁移 |
| CONTRACT-003 | Factor | QNT-xxx（分配前不得猜号） | Quant 专项文档 | 待迁移 |
| CONTRACT-004 | AuthorizationRef | NEWS/INT-xxx（按最终生产方与消费关系拆分） | News/项目级文档 | 待迁移 |
| CONTRACT-005 | system_as_of | GOV/INT/FLOW/DATA/NEWS 等按语义分层登记 | 项目公共时间契约及生产方文档 | 待迁移 |
| CONTRACT-006 | Researchflow 结果传播 | FLOW-xxx | Researchflow 专项文档 | 已有决议，编号映射待登记 |
| CONTRACT-007 | Researchflow 取消、重试、fencing | FLOW-xxx | Researchflow 专项文档 | 已有决议，编号映射待登记 |
| CONTRACT-008 | LLM Responses/SSE | LLM-xxx | LLM 专项文档 | 待迁移 |
| CONTRACT-009 | Notification 幂等 | NTF-xxx | Notification 专项文档 | 待迁移 |
| CONTRACT-010 | Notification Schema | NTF-xxx | Notification 专项文档 | 待迁移 |
| CONTRACT-011 | News PIT/授权/Cursor | NEWS-xxx | News 专项文档 | 待迁移 |
| CONTRACT-012 | Data OpenAPI/Go JSON | DATA-xxx | Data 专项文档 | 待迁移 |
| CONTRACT-013 | Server 组合根 | SRV-xxx | Server/项目规划 | 待迁移 |
| CONTRACT-011（规划分支旧用法） | 公共基础类型最终决议 | GOV-xxx | 项目总规划 | 与 Platform 历史编号冲突，停止使用旧编号 |
| CONTRACT-012（规划分支旧用法） | 五模块首批 Port 最终决议 | GOV/INT/FLOW 等按生产方拆分 | 项目总规划与模块专项文档 | 与 Platform 历史编号冲突，停止使用旧编号 |

## 5. 每项契约的最低定义要求

任何契约只有在下列适用项全部明确后，才允许进入 `accepted`；不适用项必须写明原因。

### 5.1 契约元信息

- 契约编号、名称、版本、状态、目的、适用范围。
- 生产方、直接消费者、Owner Role、Consumer Role。
- 权威文档路径、引用文档、关联决策记录。
- 调用方式：同步 API、进程内 Port、异步事件、持久化引用等。
- 数据所有权、授权边界、信任边界和依赖方向。
- 兼容范围、废弃策略和迁移批次。

### 5.2 请求与响应结构

每个字段至少定义：

| 属性 | 必须明确的内容 |
|---|---|
| 名称 | JSON snake_case 名称；Go 字段与 JSON Tag 对照 |
| 类型 | JSON 类型及允许的结构/枚举 |
| 必填性 | required / optional |
| Nullable | 是否允许显式 null |
| 单位 | 货币、数量、时间、比例等单位 |
| 精度 | 小数位、最大整数位、舍入、误差容忍 |
| 范围 | 最小/最大值、长度、枚举集合 |
| 默认值 | 默认值及生效条件；无默认值也需明确 |
| 语义 | 业务含义、来源、责任方和禁止解释方式 |
| 版本 | 所属 schema_version 和兼容规则 |

必须分别定义字段缺失、显式 null、零值、空字符串、空数组、未知枚举和无效值的含义。不得用 Go 零值或 JSON omitempty 的偶然行为代替协议语义。

### 5.3 数值与单位

- 金额、价格、单价、成本和费用等要求精确十进制表达的字段，跨模块 JSON 优先使用 decimal string。
- 股数、样本数、计数使用 integer，并明确安全范围；跨 JSON/JavaScript 使用的整数不得超过安全整数边界，超界必须改用字符串或专用编码。
- 比例、收益率、波动率、概率等使用 number 时，必须明确 `ratio` 或 `percentage_point`，禁止仅写“百分比”。
- 成交量、成交额、价格必须声明单位；不得从字段名猜单位。
- Decimal 禁止科学计数法、千分位和货币符号；声明最大整数位、小数位、scale、范围和舍入规则。
- 任何精度敏感的转换不得先转 float64 再格式化为 Decimal；无法无损转换时必须显式失败或输出质量降级，不得伪称精确。
- NaN、Infinity、-Infinity 不得进入 JSON。
- Number 字段应声明舍入方法和容差；没有业务理由时统一采用明确的十进制舍入策略，不允许各模块自行选择。
- lower_bound/upper_bound 与 value 使用同一类型、单位和精度规则。
- 每个 Metric/Indicator/Factor 的单位、精度、舍入、容差和算法版本由其生产模块 Registry 管理，消费者不得自行解释。

### 5.4 缺失与质量语义

以下概念必须区分：

| 表达 | 含义 | 禁止行为 |
|---|---|---|
| 字段缺失 | 生产方未提供该字段，可能因版本或条件不适用 | 不得自动补零 |
| null | 字段存在但值明确为空/未知，含义按字段定义 | 不得等同缺失 |
| 0 | 有效的数值零 | 不得当作缺失 |
| empty string | 空字符串，除非字段明确允许，否则通常无效 | 不得当作 null |
| empty array | 已知集合为空 | 不得等同字段缺失 |
| unknown | 已评估但无法确定 | 不得当作 false、0 或 success |
| unavailable | 依赖或能力当前不可用 | 不得当作无数据 |
| not_supported | 当前实现不支持 | 不得伪装成空结果 |
| not_configured | 必需配置尚未提供 | 不得标记为成功 |
| missing | 应存在的数据缺失 | 不得自动降级为正常 |
| degraded | 有结果但质量/覆盖存在已知限制 | 不得隐去限制 |
| invalid | 输入或输出不满足契约 | 不得继续作为有效事实传播 |

质量状态与执行状态分离。请求成功、HTTP 200、任务 completed 不代表数据 valid。质量状态只能由数据/结果生产方产生，消费者不得自行升级。

### 5.5 时间、交易日和 PIT

- 跨模块绝对时间使用 RFC3339，明确时区；存储和比较统一 UTC。
- 交易日期使用 `YYYY-MM-DD`，并明确按 `Asia/Shanghai` 交易日历解释。
- 区分 `published_at`、`available_at`、`valid_from/valid_to`、`provider_time`、`observed_at/system_observed_at`、`fetched_at`、`normalized_at`、`system_as_of`、`created_at/updated_at`。
- 没有来源证据的 `available_at` 必须保持 unknown/null，不得由发布时间、抓取时间或观察时间推导。
- `system_as_of` 是系统知识截止时间，不是交易日、发布时间或当前时间。
- Researchflow 创建 Run 时确定并持久化唯一 `system_as_of`；所有下游请求、查询、Evidence/Context 和重试继承同一值。
- Stage 重试不得刷新 `system_as_of`；下游数据可见性按各自 PIT 规则校验。
- 任何字段不得在不同模块中复用同一名称表达不同时间口径。

### 5.6 ID 与请求关联标识

至少区分：

| 标识 | 作用域 | 用途 | 不得替代 |
|---|---|---|---|
| entity/business ID | 领域对象生命周期 | 业务对象身份 | Request ID |
| request_id | 单次请求/执行 | 请求排障与日志关联 | 业务主键、幂等键 |
| originating_request_id | 异步任务创建来源 | 追溯创建 Run 的原始请求 | Worker 当前 request_id |
| correlation_id | 跨模块工作链 | 关联一次业务流程 | event_id 去重 |
| event_id | 单个事件 | 事件身份和 Inbox 去重基础 | correlation_id |
| idempotency_key | 命令意图范围 | 防止重复执行副作用 | request_id |
| trace_id/span_id | 分布式追踪 | 调用链追踪 | 业务身份或授权凭证 |
| source_ref/evidence_ref | 外部来源/证据引用 | 追溯来源和内容 | 可直接访问的 URL 或授权本身 |

ID/Ref 使用不透明、稳定、非空字符串；消费者不得解析内部格式。格式、生成方、唯一性范围和保留期限由生产方明确。Request ID 不得作为身份或权限依据。

### 5.7 错误、重试和依赖故障

- 定义稳定错误分类、领域错误码、safe_message、dependency 和 retryable。
- `retryable=true` 仅表示技术层面可作为重试候选，不代表调用方必须重试。
- 重试还必须校验幂等性、请求体可重放性、重试预算、deadline、取消状态和领域策略。
- 错误码由产生该领域错误的模块拥有；Platform 不统一接管业务错误码。
- 原始 SQL、DSN、Token、Secret、堆栈和上游敏感响应不得进入外部 safe_message。
- Cause 仅内部错误链，不序列化。
- HTTP 状态映射由 Transport 层负责；领域错误码不能与 HTTP 状态码混为一谈。
- 未知错误码不得默认成功或可重试。

### 5.8 幂等、唯一性与重复处理

每项有副作用的命令/事件必须定义：

- 幂等键生成方、唯一性作用域、保留期和请求规范化方式。
- 相同 key + 相同请求的响应行为。
- 相同 key + 不同请求的冲突行为。
- 并发重复请求的线性化点和唯一约束。
- 重复事件、乱序事件、迟到事件的处理方式。
- 失败后重试是否复用幂等键，是否产生新 Attempt/DeliveryAttempt。
- 外部渠道不具备 exactly-once 能力时的重复投递风险和对账机制。

Correlation ID 不用于去重。不能证明外部投递未发生时，不得盲目重发；需要 `unknown` 状态与对账流程。

### 5.9 分页、排序与一致性

适用分页的契约必须明确：

- page_size 默认值、最小/最大值和超限行为。
- 稳定排序字段、唯一 tie-breaker、升降序。
- Cursor 是否不透明、防篡改，以及绑定的过滤条件、排序版本、快照、PIT 时间和租户/调用方范围。
- 游标过期、非法、跨过滤条件复用时的错误。
- 并发新增/删除/更新时分页一致性保证。
- 是否使用 snapshot/版本化读取；不得仅依赖 OFFSET 声称强一致分页。
- 无更多数据时的 next_cursor 表达。

不适用时标注“单对象查询，无分页”。

### 5.10 版本兼容与废弃

- DTO、Event Payload 和可独立演进的 Application Contract 必须有明确 schema_version。
- Schema 版本与模块软件版本分离。
- 新增可选字段通常可向后兼容；新增 required 字段、改变类型/单位/精度/枚举含义、改变默认值或状态迁移均属于破坏性变更。
- 未知字段默认忽略还是拒绝，必须按契约明确；安全敏感字段不得静默忽略。
- 未知枚举不得默认成功。
- 废弃必须给出替代字段/接口、双读/双写或迁移策略、最早移除版本和消费者迁移清单。
- 已发布 Schema/Golden 作为历史版本保留；不得直接覆盖旧版本样例而失去回归能力。

## 6. Platform 公共技术契约边界

### 6.1 Fault

Platform 只定义通用错误原语，不定义业务领域错误语义。

通用结构至少包含：

- `class`：validation、unauthenticated、forbidden、not_found、conflict、unavailable、timeout、internal 等稳定类别。
- `code`：稳定机器标识；领域模块保留自己的命名空间。
- `safe_message`：可展示、已脱敏的安全摘要。
- `dependency`：可选逻辑依赖名，不包含 URL、IP、DSN、Secret 或用户输入。
- `retryable`：默认 false，仅表示技术层面可能可重试。
- `cause`：仅内部错误链，不序列化。

业务模块负责定义业务错误码、领域原因和状态映射。Platform 负责统一序列化/传输原语及安全约束。字段 JSON 名称必须在 Schema 和 Go JSON Tag 中一致，禁止在文档中混用 Go 字段名和 JSON 字段名。

### 6.2 身份、授权、ServiceKey 和 Secret

- Platform 提供身份上下文、认证原语和默认拒绝的 Route Policy。
- 业务模块负责资源级、数据级、内容级和用途级授权。
- Owner 管理凭证、内部 Service Secret、Data API Key、Provider Token、News Source Credential、LLM Key 和 Notification Channel Credential 必须隔离。
- 凭证只能由其所属 Adapter/服务端持有；不得传递到浏览器、模型上下文、日志或不可信业务模块。
- Service Identity 不自动拥有 Owner/Admin 权限。
- 凭证不得作为普通 DTO 字段在模块间透传；使用可信调用上下文或受控 Secret 注入。
- 授权引用只作为审计/策略引用，不自动代表当前仍有访问权限；读取时仍需执行撤销、过期、用途和内容级别检查。

### 6.3 Diagnostics

Platform 提供通用 Check Contract、有限并发 Runner、Deadline/Timeout 和基础聚合；领域模块拥有诊断规则、领域状态、reason_code、证据和质量解释。

Observation 至少定义：

- `status`
- `reason_code`
- `safe_message`
- `checked_at`
- `duration`
- `evidence_ref`（可选）
- `attributes`（可选）

约束：

- reason_code 由领域模块命名并解释。
- evidence_ref 是不透明引用；证据 Owner 负责访问授权、生命周期和解释。
- attributes 必须有界、白名单、低敏感结构化标量。
- 不承载正文、snippet、原始响应、凭证或无界调试信息。
- required 依赖缺失不得伪装 skipped；optional 未配置可 skipped，但必须有 reason。
- Data Probe/Validation/Freshness/Coverage 的业务状态归 Data，不被 Platform Observation 取代。
- Diagnostics 状态与业务质量状态不能混为一个枚举。

### 6.4 HTTP Client 与 SSRF

- Platform 实现网络层安全执行：Host/Port/协议策略、DNS A/AAAA 校验、私有/loopback/link-local/reserved IP 拦截、受控 Dial 防 DNS rebinding、重定向逐跳校验、HTTPS 不降级、代理策略、Deadline、超时、响应体上限和并发限制。
- 调用方模块负责目的地授权策略和业务用途；News 负责新闻来源授权，Data 负责 Provider 授权。
- 默认禁止重定向或必须显式允许并逐跳重新校验。
- 不可信来源默认禁用环境代理。
- 仅对明确幂等、请求体可重放的请求有限重试。
- 连接成功不等于 Provider 数据质量通过；单测通过不等于部署出口 SSRF 集成验收通过。

### 6.5 Storage、Repository 和 Migration

- Platform 拥有 DB/Redis 连接生命周期、连接池、Ping、事务基础能力和 Migration Runner 等技术原语。
- 各领域模块拥有自己的 Repository、SQL、表结构、Migration、保留策略、领域审计和数据所有权。
- 禁止 Platform 建设公共万能 Repository 或拥有业务表。
- Redis 不得成为唯一事实存储，除非项目总规划另行批准具体用途和恢复策略。
- Migration namespace/version 必须唯一；已发布 Migration 不可修改，修复通过新增版本完成。
- Server/集成根负责 Migration 注册与启动顺序，领域模块不得擅自改根注册、全局 DI 或启动入口。
- DB 连接实例由 Server/Bootstrap 装配并按依赖注入复用；模块不得各自创建重复共享连接池。
- 包级 Storage 测试不等于真实数据库集成验收。

## 7. Data 与业务模块的数据契约

### 7.1 Data 公开数据语义

Data 对证券主数据、行情、财务、估值、交易日历、行业分类、复权、Provider 来源、PIT 和数据质量负责。

跨模块输出必须能表达：

- 数据类型、证券/范围、交易日或时间区间。
- 来源/provider、source_version/provider_time。
- 单位、精度、复权口径、分类/主数据版本。
- available_at、system_observed_at、fetched_at、normalized_at（具备证据时）。
- snapshot_ref、quality_status、coverage、missing/reason_codes。
- 数据是否为全市场、样本、分页结果或局部覆盖。

### 7.2 Provider 原始值标准化

- Provider Adapter 负责保留原始来源标识、原始单位、精度、时间戳和错误上下文。
- 标准化映射必须有字段级来源表，明确源字段、目标字段、转换公式、单位、精度、空值处理和口径差异。
- 禁止以字段名相似作为等价依据。
- Provider 原始数值转标准 Decimal 不得经过有损 float64 中间转换。
- 不同 Provider 的字段只有在语义、单位、复权口径和时间口径一致后才可归一为同一标准字段。
- 无法无损转换时返回明确错误或 degraded/unknown，并附 reason_code；不得伪造精度。
- Adapter 必须有原始样例、标准输出 Golden 和边界值测试。

### 7.3 行情、复权与交易日

- 价格字段明确 raw/前复权/后复权/不复权口径。
- 复权因子、公司行动和历史成分必须可追溯版本。
- 交易日必须依据 Data 交易日历，不以自然日或服务器时区推断。
- 停牌、未上市、退市、无成交、Provider 缺报、权限不足等情况必须区分。
- 成交额、成交量、换手率、涨跌幅和资金流字段必须明确单位、分母、口径与来源。
- 成交额/成交量不得被当作净资金流入；不同数据源资金流算法不可无说明混用。

### 7.4 Data API 与 Go DTO 验收

- 从实际 Handler/OpenAPI 与 Go Model/JSON Tag 做双向差异核对。
- 逐字段审查 required、optional、nullable、类型、单位、精度、枚举和嵌套引用。
- 用真实 Handler JSON Golden 验证，而不只对单个 Model marshal。
- nil slice、空数组、null、字段缺席和零值必须有明确约定。
- Schema 字段必须有真实响应来源；Go 字段必须确认是否对外公开。
- Adapter 对外转换应有精度无损测试；无法保证时显式失败或降级。
- Data API 当前字段类型不要求为了新模块而无条件重写；由 Adapter 在边界转换，但不得掩盖源数据精度不足。

## 8. News → Research 证据契约

### 8.1 所有权与访问路径

- News 拥有新闻来源、授权、采集、原文、标准化记录、新闻身份/版本、关系断言和内容级别。
- News 提供只读 Evidence Query Facade。
- Research 通过公开 Facade 获取证据，不访问 News 私有 Domain、Repository、SQL、内部 Adapter。
- Research 负责将 News DTO 转为自己的 Evidence Domain。
- Researchflow 传递可信 caller、用途、内容级别和 Run 的 system_as_of。
- 不允许消费者通过任意 URL、SQL、动态字段名或抓取指令绕过 News 授权。

### 8.2 Evidence 查询最低语义

- GetEvidence：按稳定 news_ref 和可选 version_ref 查询。
- ListEvidence：按受控过滤条件、知识时间、业务时间和内容级别分页。
- 请求明确 caller_ref、purpose、requested_content_level、system_as_of（历史研究必需）。
- 返回来源标识、版本、时间字段、内容级别、授权引用、质量和证据引用。
- Cursor 不透明、防篡改，绑定过滤指纹、排序版本、快照、system_as_of 和稳定唯一排序键。
- 分页会话读取同一知识快照，不能仅依赖 OFFSET 保证并发一致性。
- 历史授权引用仅用于审计；每次实际读取仍检查当前撤销、过期、用途和内容级别。
- 未授权全文不得复制给 Research、LLM 或 WebUI。

### 8.3 PIT 语义

对 system_as_of=T：

1. 先过滤 T 时系统已观察到的 Observation、Version、Identity、Classification、Relation。
2. 再按 published_at、valid_from/valid_to 等业务时间解析。
3. 不得先解析当前关系，再伪装成历史状态。
4. 不得由 published_at 早于 T 推导系统当时已知。
5. 不得用当前版本覆盖历史版本。
6. available_at 无来源证据时保持 unknown。

## 9. Quant → Researchflow/Research 数值结果契约

### 9.1 Indicator、Factor、Metric

- Indicator、Factor、Metric 由 Quant 定义并维护唯一 Registry。
- Registry 对每个 code 声明 schema_version、参数 Schema、输入要求、单位、JSON 类型、精度、舍入、范围、容差、算法版本和质量规则。
- Indicator 参数使用 typed/versioned Schema；禁止无约束任意 map。
- Factor 必须绑定 universe_ref、交易日、分类版本、PIT 可用时间和样本范围。
- 结果区间 lower/upper 与 value 使用一致的类型和单位。
- 每项结果包含样本数、覆盖率、缺失/排除原因和质量状态。
- 结果状态与质量状态分离；completed 不等于 valid。
- 计算版本变化必须可追溯，历史结果不可静默覆盖。

### 9.2 Research 消费规则

- Research/Researchflow 只消费 Quant 公开 DTO 和 Registry 元数据。
- 消费者不得隐式转换 Decimal、number、ratio、percentage_point 或单位。
- 消费者不得根据字段名推断单位、复权或算法版本。
- 无法识别 metric_code/schema_version 时按明确兼容策略拒绝或标记 unsupported，不得猜测。
- 质量不足时保留质量状态和 reason_codes，不得自行升级为 valid。
- 概率、收益分布、MAE/MFE、校准和样本外评估由 Quant 负责；Research 负责情景语义和证据解释。

## 10. Researchflow 执行与状态机契约

### 10.1 层级和责任

- Run：一次完整研究执行。
- Stage：Run 内一个逻辑阶段。
- Attempt：Stage 的一次实际执行。
- 每次重试创建新的 Attempt，不覆盖历史 Attempt。
- Researchflow 拥有状态机、DAG、执行上下文、调度、取消、重试、超时、恢复和结果传播。
- 各业务模块只实现自己的公开 Application Port，不感知其他模块内部状态机。

### 10.2 状态语义基线

当前已形成的 Researchflow 决议应以 `doc/researchflow/03-CONTRACT-006与007最终决议.md` 为专项细节输入，并在完成编号迁移后由项目总规划登记新的 FLOW 编号。不得由 Platform 文档维护第二套状态机。

当前设计决议摘要：

- Run 非终态：created、queued、running、cancelling；终态：succeeded、partial、failed、cancelled。
- Stage：pending、ready、running、succeeded、degraded、skipped、failed、timed_out、cancelled、blocked。
- Attempt：running、succeeded、degraded、failed、timed_out、cancelled；Attempt 终态不可重开。
- retry_wait 是等待重试的非终态调度状态；其归属和 DTO 表达按 FLOW 权威决议执行，不得在不同状态层级混用。
- blocked 表示调度前置条件或依赖不满足；skipped 只用于模板明确裁剪/不适用，必须有 reason_code。
- degraded 是结果质量，不等同执行失败；timed_out 是执行结果，不新增 Run.degraded 或 Run.timed_out 终态。
- Run 的结果传播按模板策略归并；必需阶段失败不得伪装成功。

### 10.3 并发、取消、重试和 fencing

- Run 状态竞争使用数据库事务/CAS 作为线性化点。
- Cancel、Worker claim、Retry、Deadline sweep 必须在同一版本/状态门禁下协调。
- queued Run 取消先提交则 Worker claim 必须失败；Worker claim 先提交则取消进入 cancelling。
- retry_wait → ready 与新 Attempt 创建必须原子完成。
- 进入 cancelling 后拒绝新 Stage 派发、新 Attempt 和新 Retry。
- Context cancellation 只是协作信号，不代表 Worker 已停止。
- Attempt lease/fencing token 每次接管递增，旧 token 永久失效；旧 Worker 迟到写入必须被拒绝。
- Run 进入终态前，活动 Attempt 必须已确认停止，或被 fence 且写入权撤销。
- deadline 优先规则和 user_cancelled 的竞争关系按 Researchflow 权威决议执行；deadline 不得覆盖已先提交的 user_cancelled termination_reason。
- Executor 容量检查和名额预留必须原子化，防止并发超卖。
- 队列重启恢复必须重新检查 Run 状态、deadline、retry_policy 和 fencing token。
- 以上决议不等于实现已通过并发、数据库或 Worker 集成测试。

### 10.4 执行上下文和结果关联

- Run 创建时确定 system_as_of、输入快照、模板版本、算法/模型版本、请求关联 ID 和 deadline。
- Stage/Attempt 必须继承 Run 的 PIT 截止时间和必要输入引用。
- Stage 输出、诊断、Evidence/Context 和最终报告必须能通过 run_ref/stage_ref/attempt_ref 追溯。
- 下游模块不得刷新 system_as_of。
- 运行诊断与业务结果分离；诊断失败不得伪装成业务风险结论。
- LLM 输出不能覆盖 Quant 硬风险门禁。
- 纯观察模板不执行硬风险门禁时，actionability 必须保持 not_evaluated；不得仅凭 Run succeeded 推导 actionable。

## 11. LLM 与 Notification 契约

### 11.1 LLM

LLM 负责模型协议适配，不拥有工具权限、研究状态或业务事实。

契约必须定义：

- ModelRequest：model/provider、instructions/input、response format、sampling/limit、deadline、request_id/correlation_id、必要元数据。
- ModelResponse：响应状态、结构化输出、usage、latency、model/provider 版本、request_id 和错误信息。
- Stream：事件类型、事件顺序、增量字段、终止事件、取消、断流和恢复语义。
- Tool Call：仅作为结构化建议/请求返回；真正授权和执行由 Researchflow 负责。
- Usage 缺失必须表达 unknown，不得默认零。
- 合法 incomplete/failed 协议响应不自动等同 Platform Fault。
- Platform Fault 到 ModelErrorInfo 的映射必须字段级唯一，Cause 不序列化。
- stream_interrupted、terminal event、重复/乱序 chunk 和客户端取消必须有样例及测试。
- 不记录不必要的敏感 Prompt/Response；日志和诊断必须脱敏。

### 11.2 Notification

Notification 拥有订阅、模板、渠道、Dispatcher、Delivery 和 DeliveryAttempt。

契约必须定义：

- Event 注册键：`event_type + schema_version`。
- 事件生产方、消费方、事件 ID、关联 ID、发生时间和 payload Schema。
- Inbox/PublishEvent/Delivery 各自幂等范围和唯一键。
- Delivery 状态至少覆盖 queued、sending、retry_wait、sent、failed、skipped、blocked、unknown；状态含义和合法迁移由 Notification 唯一维护。
- unknown 表示外部副作用结果无法确认，必须先对账，不得盲目重发。
- 每次重试产生新的 DeliveryAttempt，保留原始投递历史。
- 外部渠道不承诺 exactly-once；明确 at-least-once 风险、重复通知去重和人工对账策略。
- 业务事件到通知事件的映射由事件生产方和 Notification 共同确认，Notification 不负责计算业务触发条件。
- Secret 由 Platform 安全原语管理，渠道业务配置和投递策略由 Notification 管理。

## 12. Server 组合根与运行生命周期契约

### 12.1 唯一组合根

- Server 是服务端依赖装配、启动和关闭的唯一组合根。
- 每个可执行服务必须只有一个明确 Bootstrap/Composition Root。
- 模块向组合根暴露公开构造器/Bootstrap 接口，不在模块内部自行创建共享 DB、Redis、HTTP Client、Logger、Metrics、Worker Pool 或全局 Registry 实例。
- Handler/Worker 依赖 Application Facade/Port，不直接创建 Infrastructure 实例。
- 业务模块不得反向 import Server。

### 12.2 生命周期

必须定义：

1. 配置加载与校验。
2. Logger/Telemetry 初始化。
3. DB/Redis/HTTP Client 等共享资源初始化与健康检查。
4. Repository、Adapter、Application Service 装配。
5. Worker/Dispatcher/Consumer 初始化。
6. HTTP Server 和后台任务启动。
7. Readiness 变为可接流量的条件。
8. Shutdown 时停止接收新请求/新任务。
9. Worker drain、取消传播、租约/fencing 收敛。
10. HTTP Server 关闭。
11. Repository/DB/Redis/HTTP Client 等资源按依赖逆序释放。

每个步骤必须明确失败处理、超时、重试策略和资源回滚。启动失败不得留下后台 goroutine 或未释放连接。

### 12.3 配置与共享资源

- 每个模块拥有自己的 Config Struct、字段 Schema 和 Validate。
- 环境变量只在 Bootstrap/Config 装载边界读取；装载后作为不可变配置快照。
- Secret 由部署环境或 Platform 安全原语注入；不得进入普通配置日志。
- DB/Redis 连接池、HTTP Client、Logger 和 Worker Pool 的实例所有权必须唯一。
- 模块可以拥有 Repository/事务，但不能私自创建同一共享数据库的重复连接池，除非有明确隔离理由和项目总规划批准。
- Server 负责依赖装配，不负责业务默认值、业务状态或业务策略。
- 包级初始化不得产生不可控网络访问、数据库连接或后台 goroutine。

## 13. 契约状态与冻结分级

### 13.1 状态定义

| 状态 | 含义 | 是否允许消费者据此实现 |
|---|---|---|
| `pending_decision` | 语义、责任、边界或方案尚未确定 | 不允许猜测；只允许不依赖该语义的独立工作 |
| `accepted` | 生产方与直接消费者已确认语义和边界 | 可按已确认语义开展设计/实现，但不能声称冻结 |
| `pending_evidence` | 语义已确认，Schema/Golden/Contract Test/必要实现证据尚不齐 | 允许在明确风险范围内实现；调用点不能宣称 L2 |
| `frozen` | 语义、版本、样例、Schema、消费者确认及必要契约测试证据齐备 | 可作为稳定实现基线 |
| `deferred` | 明确延期，记录理由、目标批次和不阻断范围 | 不阻断声明范围之外的开发 |
| `rejected` | 方案否决，记录理由和替代方案 | 不得继续引用为有效协议 |

### 13.2 状态迁移规则

- `pending_decision → accepted`：决策记录完成，生产方和直接消费者确认。
- `accepted → pending_evidence`：语义稳定，开始补齐可执行证据；也可在语义确认时直接进入 pending_evidence。
- `pending_evidence → frozen`：Schema、Golden、消费者确认和必要 Contract Test 全部通过。
- `pending_decision/accepted/pending_evidence → deferred`：明确延期理由、目标批次和不阻断范围。
- 任一非冻结状态可转 `rejected`，必须提供替代方案。
- `frozen` 发生破坏性变更时，不得直接覆盖原版本；创建新版本和新决策，旧版本进入 deprecated/compatibility 维护流程。
- 状态回退必须保留原因、影响模块和原证据，不得直接改状态字段掩盖问题。

### 13.3 冻结证据清单

每项标记 `frozen` 的契约至少有：

- 字段级请求/响应/事件 Schema。
- 正常、边界、异常和兼容性 Golden 样例。
- required/optional/nullable/default/unit/precision/time semantics 明确。
- 状态机/错误/重试/幂等/分页等适用规则。
- 生产方 Owner 和所有直接消费者确认。
- Schema Validation 或生成校验。
- 至少一组可执行 Contract Test；有并发/幂等/状态机时必须有对应竞态测试。
- 版本兼容与废弃策略。
- 权威路径和引用关系已登记。
- 不存在未解决的同字段/状态/错误码冲突。

只有文档，没有 Schema/Golden/Test 证据，不得 frozen。

## 14. L1 / L2 / L3 独立开发门禁

### 14.1 L1 Design Ready

模块达到 L1 必须具备：

- 模块职责和禁止职责明确。
- 依赖 DAG 无循环，依赖方向明确。
- 首批 Application Port、DTO、状态机草案和 Owner Role 明确。
- 真实调用点与生产方/消费者清单已登记。
- 对未决契约标记状态、阻断调用点和延期策略。
- 不要求其他模块先完成代码、编译或 CI。
- L1 不代表契约冻结或模块可以对外集成。

### 14.2 L2 Module Ready

模块达到 L2 必须满足：

- 当前模块实际调用点所依赖的契约均为 frozen。
- 模块自己的公开 DTO/Schema、Golden 和 Contract Test 齐备。
- 模块内部单元测试、边界测试、错误映射、超时/取消/幂等测试通过。
- Adapter 对生产方协议的映射可验证，精度、单位、PIT、质量状态不丢失。
- 未冻结契约不被调用，或相关调用点明确禁用/隔离。
- 使用 Mock/Fake/Contract Fixture 可完成模块独立验收。
- 不要求其他模块实现、分支编译、CI 通过或真实 Provider 可用。
- 不自动授权创建分支、修改业务代码、创建 PR 或合并。

### 14.3 L3 Integration Ready

L3 必须在真实集成环境验证：

- 真实 Provider/数据源和网络出口。
- 真实数据库、Redis 和 Migration。
- 真实 Worker 并发、取消、重试、恢复和租约/fencing。
- 真实模型服务、Stream、超时和限流。
- 真实通知渠道、投递结果和对账。
- Server 组合根、启动/关闭和资源释放。
- 端到端 PIT、权限、质量、结果关联和可追溯性。
- 生产部署配置、安全和容量约束。

L2 不能被 L3 反向阻断。真实 Provider 暂不可用时，模块仍可使用契约 Fixture 完成 L2；但必须明确标记 L3 未验收。

### 14.4 阻断范围算法

对任一未冻结契约 C：

1. 找到 C 的直接消费者。
2. 找到消费者当前实际调用点。
3. 只阻断依赖 C 未决语义的调用点。
4. 对不依赖 C 的其他功能、模块和测试继续推进。
5. 若可通过 Adapter 隔离、Feature Flag、Mock Contract 或暂不启用调用点规避，则记录规避方式和风险，不扩大阻断范围。
6. 只有依赖方向、数据安全或共享协议本身存在系统性冲突时，才允许扩大阻断，并由项目总规划记录依据。

## 15. Schema、Golden 与 Contract Test 组织

### 15.1 组织规则

- 项目级维护契约目录、Schema 索引和 Golden 索引。
- 具体领域 Schema 优先放在生产方模块目录；项目级公共原语 Schema 放在 Platform 或项目公共契约目录，按权威表登记。
- Golden 文件与 Schema 同版本、同契约编号。
- 消费方维护 Adapter/Consumer Contract Test，不复制生产方 Schema 作为第二权威。
- 跨模块 INT 契约由项目总规划登记，涉及的生产模块分别维护其侧的测试。
- 不因统一而将所有 Schema 堆入一个巨大目录；保持领域归属清晰。

### 15.2 最低样例类型

每项契约至少提供：

1. 正常请求/响应。
2. 边界值：最大/最小、空集合、缺失可选字段、精度边界。
3. 异常：非法类型、越界、未知枚举、未授权、依赖超时。
4. 缺失语义：字段缺失、null、0、空字符串、空数组。
5. 兼容性：旧版本消费者读取新版本输出；新版本消费者面对旧版本输出。
6. 状态/并发：适用时覆盖重复请求、并发冲突、取消/重试/超时、迟到写入。
7. PIT：适用时覆盖 system_as_of 前后边界、available_at unknown 和历史版本。

### 15.3 测试边界

- Schema Validation 证明结构，不证明业务语义。
- Golden 证明具体序列化样例，不证明所有状态转换。
- Contract Test 证明生产方与消费者的公开交互，不证明真实外部服务可用。
- Integration Test 证明真实依赖连接和协同行为。
- E2E Test 证明端到端路径，不替代模块内部测试。
- CI 必须按模块责任分层；L2 不依赖其他模块未完成的 CI。

## 16. 决策记录与变更治理

### 16.1 决策记录必需字段

每项决策至少记录：

- 决策编号、标题、状态、日期。
- 背景与待解决问题。
- 候选方案及取舍。
- 最终决策和不采用方案的理由。
- 生产方、直接消费者、Owner Role。
- 影响契约、字段、状态、Schema 和调用点。
- 影响分支/文档路径。
- 版本策略、兼容/迁移方式。
- L1/L2/L3 影响和阻断范围。
- 验收证据和待补事项。

### 16.2 变更流程

1. 提出变更：说明问题、现状、目标和兼容要求。
2. 影响分析：检索所有引用、Schema、Golden、消费者和调用点。
3. 生产方提出方案：字段、类型、语义、版本、默认值、错误、状态迁移。
4. 直接消费者确认：验证是否满足真实消费场景。
5. 项目总规划裁决：处理冲突、分配编号、确定权威路径和冻结状态。
6. 先修订权威文档与证据，再同步引用文档。
7. 按模块分支提交同步变更；不得跨分支伪造一次性完成。
8. 通过兼容性和 Contract Test 后更新状态。
9. 对外发布后保留旧版本和迁移记录。

### 16.3 变更分类

| 类型 | 示例 | 处理 |
|---|---|---|
| Patch | 文档错字、示例修正，不改变语义 | 更新文档，保留版本说明 |
| Minor | 新增 optional 字段/新枚举且旧消费者可安全忽略 | 新 Schema 版本或兼容小版本，补 Golden/测试 |
| Major | 改字段类型/单位/精度、required、状态、默认值或错误语义 | 新主版本/新契约编号，迁移计划和双版本支持 |
| Security | 授权、Secret、内容级别、SSRF、身份边界变化 | 安全 Review，默认按破坏性变更处理 |
| Emergency | 必须立即修复的安全或数据完整性问题 | 先止损，随后补决策、版本和消费者同步记录 |

### 16.4 分支同步规则

- 项目级语义先在 `feat/design_doc` 决策并更新权威文档。
- 各专项分支按归属更新其领域文档和实现证据。
- Platform 分支不得独立创建新的跨业务 CONTRACT 编号或改变领域状态。
- 专项分支遇到冲突先登记，不得自行复制一份替代契约。
- 不要求所有模块分支同时提交，也不要求跨模块分支编译通过后才开始独立开发。
- 未经明确授权，不因契约冻结自动创建开发分支、修改业务代码、创建 PR 或合并。

## 17. 强制 Review 流程

Review 必须按以下顺序进行；每轮发现问题先修订权威文档/相关专项文档，再进入下一轮。不得只列问题不落实修正。

### Review 1：完整性

检查：

- 当前架构中的所有真实跨模块调用关系是否登记。
- 是否遗漏同步 Port、HTTP API、事件、持久化引用、Worker 和 Server 装配关系。
- 每条调用是否有生产方、消费者、DTO、错误、超时/取消和版本。
- 未登记的调用是否属于内部实现误用。

通过标准：调用关系矩阵覆盖当前已知调用点；未知项有明确调查任务和阻断范围。

### Review 2：一致性

检查：

- 同一字段的类型、单位、精度、required、nullable、默认值是否一致。
- 时间、时区、PIT、system_as_of 是否一致。
- ID、Request ID、Correlation ID、Event ID、Idempotency Key 是否混用。
- 状态、终态、错误码、reason_code、质量状态是否重复定义。
- JSON Tag、OpenAPI、Schema、Golden 是否一致。
- 是否存在跨分支重复编号。

通过标准：同一语义只有一个权威定义；冲突有决议和同步清单。

### Review 3：可实现性

检查：

- DTO 能否无歧义生成 Go 类型和 JSON。
- 缺失/null/零值/空字符串/空数组是否可区分。
- 默认值是否有明确生效条件。
- 单位和精度转换是否可实现且可验证。
- 时间/PIT 是否存在双重数据来源或推导错误。
- 幂等、重试、分页、取消和超时是否存在未定义边界。

通过标准：生产方和消费者能独立实现相同语义，不需要口头补充或猜测。

### Review 4：依赖合理性

检查：

- 是否引入循环依赖或 internal 包跨模块引用。
- 是否绕过公开 Facade 直接访问其他模块数据库。
- Platform/Server 是否承担了业务领域职责。
- 是否存在重复创建共享基础设施实例。
- 数据、授权、Secret 和证据是否越权流转。

通过标准：依赖 DAG 无环，数据所有权和安全边界清晰。

### Review 5：独立开发验证

检查：

- 每个模块是否能仅依赖自身已冻结调用契约完成 L2。
- 未冻结契约是否被错误扩大成全仓阻断。
- 是否可用 Fixture/Mock/Adapter 隔离未完成依赖。
- 是否把真实 Provider、网络、Worker、模型和渠道验收错误塞入 L2。
- 是否把 L2 错误理解为创建分支/PR/合并授权。

通过标准：每个模块都有可独立推进任务和精确阻断清单。

### Review 6：验收验证

检查：

- 每个 frozen 契约是否有 Schema、Golden、Contract Test。
- 边界、异常、兼容性和状态机竞态是否有可执行用例。
- 测试是否覆盖真实公开边界，而非仅内部 Model marshal。
- L2 与 L3 证据是否分开。
- 冻结状态是否有消费者确认和可追溯证据。

通过标准：冻结结论可以被 CI/测试重复验证，不依赖口头确认。

### 18.4 可延期且不应全局阻断的事项

除非某模块当前调用点确实依赖，否则以下事项可延期：

- 未来可能使用但当前无消费者的通用事件总线。
- 多租户、远程配置中心、动态策略引擎。
- 尚无真实需求的跨模块万能 Repository。

- 真实 Provider/模型/通知渠道的 L3 环境验收。
- 不影响当前 DTO 语义的未来扩展字段和非必要性能优化。

延期项必须标记 `deferred`，说明目标批次、Owner Role 和不阻断的调用范围，不得作为隐性前置条件。

### 19.1 各模块 L2 的具体阻断规则

- Platform：只阻断依赖未冻结技术原语的实际调用点；不阻断业务模块使用 Mock/Fake 完成领域逻辑。
- Data：未冻结的数据字段/单位只阻断依赖该字段的转换和消费；不阻断其他 Provider、数据集和独立 API。
- News：未冻结的 Evidence 授权/PIT 只阻断对该证据的跨模块读取；不阻断独立采集、来源管理和内部质量能力。
- Quant：未冻结的某个 Indicator/Factor 参数只阻断该 code 的公开消费；不阻断其他已冻结算法。
- Research：未冻结的来源 DTO 映射只阻断相关 Evidence 导入；不阻断内部领域对象和独立 Repository。
- Researchflow：未冻结的某个 Port 只阻断对应 Stage Adapter；不阻断状态机纯逻辑、队列机制和其他已冻结 Stage。
- LLM：未冻结的 Stream 事件不阻断已冻结的非流式 Generate 调用。
- Notification：未冻结的某类业务事件不阻断 Delivery Engine 和其他已冻结事件类型。
- Server：未完成的某个模块装配不阻断模块独立 L2；集成入口的真实运行属于 Server/L3 验收。

### 19.2 开发顺序原则

允许并行推进：

1. Platform 技术原语和独立测试。
2. Data Provider/标准化/API/质量能力。
3. News 采集/来源/检索内部能力。
4. Quant 不依赖外部未决 DTO 的确定性算法。
5. Research Domain 和独立持久化设计。
6. Researchflow 状态机纯逻辑与 Fixture 驱动测试。
7. LLM 协议 Adapter 和 Mock Stream。
8. Notification 状态机、模板和模拟渠道。
9. Server 组合根设计和生命周期测试骨架。

只有实际跨模块调用点需要的契约达到 frozen，才进入该调用点的 L2 实现/验收。不得要求所有模块先全部完成，才开始任何一个模块的开发。

## 22. 结论与执行约束

1. 项目总规划是跨模块统一契约的唯一语义权威和编号分配入口。
2. Platform 只负责公共技术原语；Data、News、Quant、Research、Researchflow、LLM、Notification 各自拥有领域语义；Server 只负责组合装配。
3. 每项契约必须字段级、状态级、错误级和证据级可实现、可验收。
4. `accepted` 不等于 `frozen`；设计决议完成不等于实现验收完成。
5. L1、L2、L3 分层独立；模块 L2 不依赖其他模块分支编译、CI 或真实 Provider 可用性。
6. 未冻结契约按真实调用点精确阻断，不扩大为全仓阻断。
7. 现有专项文档作为输入材料保留有效细节；冲突由项目总规划裁决，专项文档按同步清单修改。
8. 新增或变更契约必须先完成影响分析、生产方定义、消费者确认、项目总规划登记和证据更新。
9. 未经明确授权，不因契约规划或 L2 达成而创建分支、修改业务代码、创建 PR 或合并。
10. 最终目标是让每个模块能基于稳定边界独立开发，并在真实依赖具备时按 L3 完成集成，而不是让所有模块排队等待一个全仓冻结时刻。

**最终原则：统一协议，不统一实现；冻结必要边界，不冻结所有细节；明确责任，不虚构 Owner；以真实调用关系确定阻断范围。**
