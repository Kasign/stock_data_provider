## 1. 项目目标与边界

### 1.1 最终目标

建设可持续运行、可复算、可追溯、可评估的 A 股研究工作台，回答市场环境、行业轮动、个股趋势、财务估值、事件影响、策略有效性、未来情景和风险边界等问题；每次研究均可留档、复查、比较、跟踪和评估。

### 1.2 不做的事情

- 不接入券商下单、自动交易或实盘资金托管。
- 不以 LLM 代替行情事实、量化计算、数据质量判断或硬风险门禁。
- 不把自选股/当前分页统计称为全市场结论。
- 不用成交额/成交量代理净资金流入。
- 不把新闻情绪分数直接当作事件影响结论。
- 不把策略候选信号等同交易计划或交易指令。
- 不因模块拆分提前微服务化或建设通用工作流平台。
- 不虚构服务端字段、分析结果或 UI 流程节点。
- A 股主线稳定前不扩展海外市场体系。

### 1.3 成功标准

- 数据具有来源、单位、口径、时间、覆盖范围、质量状态和版本。
- 历史研究遵守 PIT，避免未来数据泄漏。
- Quant 结果确定性、可复算；Research 事实/推断/假设分离；Researchflow 可追踪。
- 策略经过交易制度、费用滑点、样本外和稳定性验证。
- 概率输出有样本量、校准和失效监控；样本不足时拒绝伪精确。
- 硬风险门禁不能被评分、模型或人工解释覆盖。
- 每次 Run 可还原输入快照、阶段、算法/模型版本、证据、质量和失败原因。
- WebUI 只消费已确认 API；Python 生产调用逐项切换、验收和退役。

## 2. 总体架构与职责

### 2.1 目标架构

```text
Data / Security Master / Calendar       News
                │                         │
                └──── 输入契约与快照引用 ──┘
                              │
             ┌────────────────┴────────────────┐
             ▼                                 ▼
        Quant Engine                     Research Domain
  指标/因子/趋势/市场/行业/个股       Context/Evidence/Event
  策略/回测/风险/评估                 Claim/Hypothesis/Scenario
             │                                 │
             └────────────────┬────────────────┘
                              ▼
                         Researchflow
              Run/Stage/DAG/Context Assembly
              Tool Policy/Result Validation
              Failure Recovery/Diagnostics
                              │
                  ┌───────────┴───────────┐
                  ▼                       ▼
              LLM Adapter             Notification
                  │                       │
                  └───────────┬───────────┘
                              ▼
                  Result / Evidence / Version
                              │
                         API / WebUI
```

Platform 横向提供安全、配置、日志、Trace、HTTP Client、存储连接、通用任务执行和诊断 Runner，不承载业务领域规则。

### 2.2 五模块唯一职责

| 模块 | 主责 | 关键输出 |
|---|---|---|
| Quant | 确定性数值分析、策略、回测、风险和评估 | Metric、Factor、TrendState、Market/Industry/Stock Snapshot、Signal、Backtest、RiskDecision |
| Research | 研究语义、事实证据、事件、假设和情景 | Context、Evidence、Event、Claim、Hypothesis、Scenario |
| Researchflow | 研究任务生命周期、阶段调度、工具治理、结果综合 | ResearchRun、Stage、Attempt、WorkflowResult、运行诊断 |
| LLM | 模型服务协议适配和响应校验支持 | ModelResponse、StructuredOutput、Usage、InvocationMetadata |
| Notification | 订阅、模板、渠道和投递生命周期 | Subscription、Notification、Delivery、DeliveryAttempt |

### 2.3 依赖规则

- Quant 不依赖 Research、Researchflow、LLM、Notification。
- Research 不依赖 Quant 或 Researchflow；消费 Data/News 契约，量化结果通过 Researchflow 适配为上下文/证据。
- LLM 不依赖业务模块；只处理模型协议，不管理工具权限和研究状态。
- Notification 不依赖 Researchflow；通过通知命令/事件契约接收请求。
- Researchflow 依赖其他模块的公开接口，是流程编排和结果综合层。
- API/Bootstrap 依赖 Application Facade，不直接访问 Domain/Repository。
- 禁止循环 import；模块间转换在调用方 Adapter/Assembler 完成。
- Context/Evidence/Event 属于 Research；一次 Run 的上下文装配和 Token 裁剪属于 Researchflow。
- 概率分布、MAE/MFE、校准属于 Quant；情景语义和证据解释属于 Research。
- 硬风险规则由 Quant 计算；Researchflow 必须保证模型输出不能覆盖 block。

## 4. 契约、数据所有权和横向能力

### 4.1 契约所有权

| 契约 | 所有者 | 消费者 |
|---|---|---|
| Security、MarketData、Financial、Calendar、Industry、PIT、Snapshot、Data Quality | Data | Quant、Research、Researchflow |
| Article、Source、News Search、Raw Evidence Reference | News | Research、Researchflow |
| Metric、Factor、Trend、Signal、Backtest、Risk、Evaluation | Quant | Researchflow |
| Context、Evidence、Event、Claim、Hypothesis、Scenario | Research | Researchflow |
| Model Request/Response/Usage/Stream Event | LLM | Researchflow |
| Subscription、Notification、Delivery | Notification | Researchflow 和其他业务模块 |
| Run、Stage、Attempt、Workflow Template、Tool Policy | Researchflow | API、Worker、WebUI |
| Auth、Config、Logger、Fault、Trace、HTTP Client、Storage Bootstrap、Diagnostics Runner | Platform | 所有服务端模块 |

不建设一个巨大共享 Domain 包。各模块拥有自己的模型和公开接口；只共享必要、稳定、版本化的引用和基础契约。

### 4.2 时间与质量语义

研究输入至少表达 `as_of`、`provider_time`、`available_at`、`fetched_at`、`system_observed_at`、`source_version`、`snapshot_id`、`quality_status`、`coverage` 和 `reason_codes`。

- 历史研究按 PIT/available_at 约束，不以当前最新值还原历史事实。
- missing、unknown、not_configured、not_supported、degraded、invalid 不得静默转零或转成功。
- 不可比较数据不得强行计算差值。
- 复权、单位、交易日历、行业分类和证券主数据必须携带口径/版本。
- 快照和结果版本不可变，重算产生新版本。

### 4.3 Persistence 不独立拆分支

Persistence 由领域拥有数据模型和 Repository：
- Quant：策略、回测、评估。
- Research：事件、证据、假设、情景；新闻原文仍归 News。
- Researchflow：Run、Stage、Attempt、WorkflowResult。
- LLM：仅保存必要调用元数据，不默认保存完整敏感 Prompt/Response。
- Notification：订阅、模板配置、投递记录。
- Platform：DB/Redis 连接、事务基础组件和 Migration Runner，不拥有业务表。

各模块可维护自己的 Migration 文件；编号/命名空间唯一。根 Migration 注册和执行顺序由集成分支协调。

### 4.4 Diagnostics 不独立拆分支

- Platform：通用 Check Contract、Registry、Runner、超时/并发和安全聚合。
- Data：Provider、字段、Freshness、Coverage、数据集质量。
- News：来源授权、搜索、抓取、解析、去重和存储。
- Quant：算法输入、覆盖、指标有效性、样本量、回测和评估。
- Research：Context/Evidence/Event 完整性、来源和事实/推断质量。
- LLM：模型依赖、超时、限流、Schema 和响应校验。
- Researchflow：Run/Stage/Attempt、DAG、依赖、恢复和结果一致性。
- Notification：渠道可用性、投递失败、重试积压和幂等。

模块提供领域 Check，接入 Platform Runner，不复制通用诊断框架。

## 5. 五模块职责和任务索引

### 5.1 Quant（`feat/quant`）

职责：Indicator、Factor、Trend、Market、Industry、Stock、Strategy、Backtest、Risk、Evaluation。确定性计算，不调用 LLM，不访问 Provider/SQL/Redis。

关键约束：MA20 仅为特征；市场统计明确全集/分母/覆盖；行业成分历史版本化；成交额不等于净流入；回测纳入 T+1、涨跌停、停牌、ST、上市退市、费用滑点和公司行动；硬风险 block 不可被评分覆盖。

任务：QNT-001 计算契约；002 Indicator；003 Factor；004 Trend；005 Market；006 Industry；007 Stock；008 Strategy；009 Backtest；010 Risk；011 Evaluation/概率；012 组合研究；013 Quant Repository/Migration。详见 `doc/quant/02-任务拆分与验收.md`。

### 5.2 Research（`feat/research`）
职责：Context、Evidence、Event、Claim、Hypothesis、Scenario。消费 Data/News/Quant 引用，但不采集新闻、不重算量化指标。

关键约束：事实/报道事实/推断/假设/未知分离；证据包含来源、时间、版本和正反立场；事件生命周期追加版本；假设可验证可证伪；情景概率由 Quant 提供。

任务：RSC-001 Context；002 Evidence；003 Event；004 实体关联/影响路径；005 Claim/Hypothesis；006 Scenario；007 Repository；008 领域诊断。详见 `doc/research/02-任务拆分与验收.md`。

### 5.3 Researchflow（`feat/researchflow`）

职责：Request/Run/Stage/Attempt、流程模板、DAG、状态机、超时/取消/重试/恢复、Context 装配、工具权限、结果综合、运行诊断和 Application Facade。

关键约束：不实现算法/事件规则/模型协议/通知渠道；必需阶段失败不能伪装成功；可选失败可 degraded；skipped 必须有原因；重试不覆盖 Attempt；首期不建设可视化 DAG 编辑器。

任务：FLOW-001 运行契约；002 模板；003 状态机；004 DAG；005 Context/Tool Policy；006 结果综合；007 持久化；008 诊断；009 Facade；010 旧流程切换。详见 `doc/researchflow/02-任务拆分与验收.md`。

### 5.4 LLM（`feat/llm`）

职责：现有模型服务协议适配、超时/限流/错误分类、结构化输出、流式事件、用量/延迟元数据和脱敏。

关键约束：复用现有独立模型服务，不重建推理 Gateway；Tool Registry/权限/预算归 Researchflow；不执行模型工具调用；不修改 Quant 事实或硬风险门禁。

任务：LLM-001 协议盘点；002 Adapter；003 可靠性；004 结构化输出；005 流式；006 元数据；007 安全限制；008 多模型路由（有真实需求后）。详见 `doc/llm/02-任务拆分与验收.md`。

### 5.5 Notification（`feat/notification`）

职责：Notification Event、Subscription、Template、Channel、Dispatcher、Delivery、Attempt、幂等、重试、投递诊断。

关键约束：业务规则由上游模块计算；Notification 不依赖 Researchflow；发送失败不回滚业务结果；测试发送明确目标；Secret 由 Platform 管理。

任务：NTF-001 领域契约；002 模板；003 渠道；004 Dispatcher；005 Retry；006 Repository；007 Diagnostics/API。详见 `doc/notification/02-任务拆分与验收.md`。

## 11. 验收门禁

### 数据

Evidence 来源、时间、版本、正反立场完整；Event 有实体、生命周期、影响路径和不确定性；Hypothesis 可验证可证伪；LLM 输出经过 Schema、引用、数值来源、权限和脱敏校验。

DAG 无环；必需/可选阶段明确；deadline、取消、超时、重试、幂等、恢复有测试；部分结果标记 incomplete/degraded；Run/Stage/Attempt 可追溯。

### Notification
幂等、有限重试、渠道限流和投递记录齐全；通知失败不回滚业务结果；测试发送目标显式指定；Secret 和敏感内容脱敏。

### 集成与产品
模块接口和 API/OpenAPI 一致；CI 精确关联当前 SHA；真实 Provider/DB/模型/通知按要求验收；WebUI 明确展示空数据、错误、超时、取消和部分结果；Python 调用链和部署依赖全部审计后才退役。

### 14.1 GOV-001：Go Module 与实际部署入口核查

**状态：已完成文档审查**

核查基线：本分支当前 HEAD 与规划提交 `6218768e160c20f282f76104bf3e49fb08528708` 一致。核查对象包括根 `go.mod`、`cmd/analysis-api/main.go`、根 `Dockerfile`、根 `docker-compose.yml`、`internal/service/wiring.go`、根 Python API Adapter、`go-core/go.mod`、`go-core/cmd/analysisd/main.go` 和 `go-core/Dockerfile`。

**核查事实**

1. 根目录是独立 Go Module：`example.com/stock-analysis-flow`，Go 1.22。根 `cmd/analysis-api` 通过 `service.NewRunnerWithMarketDataStores` 创建分析 Runner，随后启动异步 Task Queue 和 HTTP API，默认监听 `:8092`。
2. 根 `docker-compose.yml` 的 `stock-analysis-server` 使用根 `Dockerfile` 构建；根 Dockerfile 编译 `./cmd/analysis-api`。统一 Compose 将服务端口绑定到本机 8092，并依赖 `stock-analysis-data`。因此，当前仓库统一部署入口明确指向根 Go Module。
3. 根 `internal/service/wiring.go` 当前仍直接依赖 `internal/analysis/{app,domain,modules,registry}`，并通过 `internal/adapters/pythonapi` 调用既有 Python API。根 `pythonapi.Client` 明确封装旧 Python API 的行情、历史、Profile 和数据概览请求。因此，`internal/analysis` 不是纯历史闲置目录，而是当前根 API 的运行时依赖，不能直接删除或整体搬迁。
4. `go-core` 是第二个独立 Go Module：`github.com/Kasign/stock_data_provider/go-core`，Go 1.23。它有独立 `cmd/analysisd` 和 Dockerfile，可构建独立进程，但当前根 `docker-compose.yml` 没有定义或启动该服务。
5. `go-core/cmd/analysisd` 仍要求配置 Python Bridge Token/URL，并创建 Python Bridge Client；Analyzer、Persistence、Notification 和旧 News Search 均通过 Bridge Adapter 接入。它虽然将行情数据切到 Go 数据服务，但并非完全脱离 Python 的独立最终架构。
6. 部署说明将 `go-core/`、`python_bridge/` 描述为兼容/计算模块，并明确以当前 Compose 和服务配置决定启用范围；本次实际 Compose 核查未发现 go-core 服务项。

**架构结论**

- 五个新模块的目标落位继续采用根 Go Module 下的 `internal/{quant,research,researchflow,llm,notification}`，与当前统一部署入口保持一致。
- 当前分析 HTTP 服务仍通过根 `internal/service` 和 `internal/analysis` 运行；模块拆分必须通过后续集成批次逐步替换调用链，不能把新增模块误认为已接管现有 API。
- `go-core/internal/**` 与根 `internal/analysis/**` 都作为迁移参考资产，按能力逐项标记 `reuse / rewrite / retire / defer`。优先复用经过测试的算法、数据边界、异常处理和固定样本，不照搬整套流程，也不保留两套并行领域实现。
- `go-core` 的流程骨架可作为迁移参考，但在其 Python Bridge 尚未退役、且未进入统一 Compose 部署前，不将它认定为最终运行入口。
- GOV-001 不授权本轮改动 `cmd/**`、DI、HTTP 路由、根 Migration 注册、部署文件或旧目录；这些改动留待模块接口冻结后的集成阶段。

### 14.2 GOV-002：五模块职责与 Go import DAG 审查

**状态：架构审查已完成；接口包路径与具体 Schema 留待 GOV-003/004 冻结。**

本次对五模块 README、详细设计、任务拆分和跨模块架构索引进行交叉审查。模块职责总体可成立，没有发现必须推翻五模块拆分的循环依赖；但必须区分“数据/业务调用关系”和“Go 包 import 关系”。

#### 目标 import 方向

```text
                    Platform
                  /    |     \
                 /     |      \
               Data   News   LLM / Notification
                 \     /       ^       ^
                  \   /        |       |
                 Quant       Research  |
                    \          /      |
                     \        /       |
                       Researchflow
                            |
                    API / Worker Bootstrap
```

以上是职责层级示意，不表示所有模块必须直接 import Platform、Data 或 News 的内部包。具体约束如下：

1. **Quant**：只消费 Data 的稳定数据契约，并在 Infrastructure Adapter 中接入 Platform 提供的存储/日志等基础能力。Domain/算法包不得 import Data 服务实现、Platform 具体 Adapter、HTTP、SQL Driver 或 Redis Client。
2. **Research**：拥有 Context/Evidence/Event/Claim/Hypothesis/Scenario 模型。可使用 Data/News 的来源引用；Quant 结果只能由 Researchflow 装配为受版本约束的输入/证据引用，Research 不得 import Quant 包。RSC-006 对 Quant Evaluation 的依赖是数据/语义依赖，不是 Go import 依赖。
3. **Researchflow**：唯一的跨模块组合层，通过各模块公开 Application/Port 调用 Quant、Research、LLM、Notification；可通过明确的输入 Adapter 获取 Data/News 快照和引用。其他四个业务模块不得 import Researchflow。
4. **LLM**：只依赖标准库和必要 Platform 基础能力；不得 import Researchflow、Research 或 Quant。模型请求中的业务上下文由调用方转换成 LLM 自有协议类型。
5. **Notification**：只依赖自己的领域契约及必要 Platform 基础能力；上游以通用、版本化 Notification Command/Event 调用，不得 import Researchflow 或具体业务模块的领域类型。
6. **API/Worker Bootstrap**：在集成层依赖 Researchflow Application Facade 和 Platform；不直接拼接 Quant/Research/LLM/Notification 的内部实现。

#### 必须落实的边界

- 禁止循环 import；跨模块只依赖稳定公开接口，不引用对方的 `internal` 子目录或私有实现。
- 领域模型归各自模块所有，不建立承载所有业务类型的共享 Domain/Common 巨型包。
- Repository 由领域模块拥有接口和数据语义；数据库实现放在模块自己的 Infrastructure Adapter，底层连接池/事务/迁移执行器由 Platform 提供。Quant 等模块可以有 Repository/Migration，但 Domain/Application 不直接操作 SQL/Redis。
- Platform Task Runner 只提供通用执行基础设施；Researchflow 自己拥有 Run/Stage/Attempt 状态机和研究流程语义。
- Research 定义 Context/Evidence 的领域含义；Researchflow 负责单次 Run 的上下文装配、Token Budget、裁剪和工具授权。
- Quant 负责概率、收益分布和风险数值；Research 负责情景语义和证据；Researchflow 负责装配；LLM 只能辅助解释，不可改写数值或风险状态。

#### 审查发现与后续处理

- Research 设计中“消费 Quant 结果”与“不依赖 Quant”容易被误读为直接依赖。按本节规则，必须经 Researchflow Adapter/Assembler 传递，后续 GOV-004 冻结输入 DTO 和引用 Schema 时落实。
- RSC-006 对 Quant Evaluation 的依赖保留为结果引用依赖，不增加 Research → Quant import。
- Quant 的 Repository/Migration 与“不直接访问 SQL/Redis”并不冲突：前者是领域端口/Adapter，后者禁止领域逻辑耦合具体存储驱动。
- 各模块 README/设计文档的接口包路径、依赖箭头和 DTO 命名在 GOV-004 统一校准；本次不修改其他模块文档，不提前创建共享契约包。
- GOV-002 通过条件：后续静态 import 检查与代码 Review 均符合本节方向；任何例外须先修改本总览并说明理由。

#### 1. Data：Quant 可消费的现有数据能力

**模块边界与部署**

- **当前代码现状：** 行情数据仍位于独立 Go Module `services/market-data`，Root Server 通过 HTTP/OpenAPI 调用；这只是迁移前的代码与部署事实。
- **目标架构：** Data 迁入根 Go Module 的 `internal/marketdata`，Root Server/业务消费者通过 Data Public Application Port 调用；Data HTTP Adapter 保留为兼容/远程边界，不作为同进程内部调用路径。
- Data 保留唯一领域 Owner；其他模块不得 import Data 的 Provider、Repository、Domain/Model 等私有实现。Data 合并后可依赖 Platform 公开技术 package（尤其受控 HTTP Client），但不得依赖 Platform 私有实现或其他业务模块的 internal。
- 当前 Data HTTP API 的 `X-API-Key` 是迁移前传输认证事实；目标同进程调用使用 Root Server 可信 Principal/Scope Context。远程兼容 Adapter 可保留独立 Key 认证，不能与 Owner Token、Platform Service Secret 或 Provider Token 混用。

**已存在的主要数据契约**

- 实时行情与批量行情、日 K、行情 Bundle。
- 证券搜索、证券档案、交易日历、交易时段、指数目录/行情/成分/历史日线。
- 市场宽度、市场情绪及历史、行业/概念排行、涨跌停池、龙虎榜、人气榜。
- 证券公告、财务指标/报表、估值、个股/市场资金流、筹码分布、所属板块。
- 历史交易状态、涨跌幅规则、公司行动及复权相关数据。
- 日 K 支持 `as_of` 系统观察时点查询；必须保留 point-in-time 语义，不能把当前 Provider 数据当作历史事实。

**Quant 必须保留的数据元信息**

- 标准单位：价格 CNY/股、成交量 shares、成交额 CNY；百分比采用百分点表示。
- 时间必须区分源端时间、`fetched_at`、`normalized_at`、`system_observed_at`，不得互相补位。
- 复权口径：`none / forward_adjusted / backward_adjusted / unknown`；unknown 是响应状态，不是请求口径。
- 质量状态：`valid / degraded / stale / invalid / unknown`；HTTP 200 不能推导为 valid，unknown/null 不能转换为 0。
- 数据来源、来源版本、标准化版本、回退来源/原因、质量原因和字段校验报告应在 Quant 数据快照或输入引用中可追溯。
- PIT 查询的证券状态、交易日历、复权因子、公司行动、财务报告可用时间必须与研究时点一致；不能只保存最终数值而丢弃观察时间和版本。

**Data 已有诊断能力，禁止 Quant 重建**

- Provider 主动 Probe：按 capability 检查 connectivity、contract、quality、freshness、cross-provider、storage 等维度。
- Provider 被动请求熔断诊断与主动 Probe 分开；前者来源于真实业务请求观测，后者是显式探测。
- 字段级 Validation Report：stage、field、provider_field、code、expected、actual_type/preview、severity、message，以及可选证券/日期/行号。
- Coverage：总体分母、返回/校验/缺失/排除数量和比例；市场宽度还支持 quote_response、price_classification、quote_timestamp、amount 等独立覆盖维度。
- Freshness SLA、数据源能力声明、跨 Provider 对账、Probe 历史与质量状态由 Data 自己负责。
- Probe 的 `skipped`、`not_supported`、`failed`、`unknown` 等领域语义不得被 Quant 或 Platform 简化为统一“健康/不健康”。

**对五模块的使用规则**

- Quant 通过 Data Public Application Port（或未来受控 Remote Adapter）消费稳定领域 DTO；Adapter 负责 DTO 映射，不让 Quant Domain 依赖 Data HTTP 传输结构。
- Research 通常只引用 Quant/Researchflow 装配好的数据快照和来源证据，不直接成为 Data API 客户端。
- Researchflow 负责研究 Run 的输入快照与质量门禁；Data 的 Probe/Quality 结果仅作为质量证据，不代替研究流程自己的阶段状态。
- 数据接口当前有不少成熟能力，但“接口存在”不等于所有 Provider 实时可用或已完成真实黄金样例验收。必须按 Data 的真实运行验收记录判断可用范围。

#### 2. News：新闻事实与证据输入

**当前实现与边界**

- News 已在根 Go Module 建立 `internal/news/domain`、`internal/news/app`、`internal/news/adapters/provider`、`internal/news/adapters/parser`。
- 已有 Provider 搜索适配、候选标准化、RSS/Atom 与 HTML 离线解析、内容分层、来源/入口授权、身份识别、观察幂等和跨来源转载关系等业务能力。
- News 是随根 `stock-analysis-server:8092` 部署的模块化单体；当前不建设独立 News HTTP 服务、端口、Token 或专属公网路由。
- 当前代码树尚未出现完整 News Repository/持久化 Adapter/Migration；N6 仍等待 Platform Storage 契约接入。不能把 Domain/Application 首批代码说成新闻存储闭环已完成。

**Research 可消费的语义**

- Search Candidate/Observation：搜索结果只是发现线索，不自动成为发布者事实。
- Source / Endpoint / Policy Version：发布来源身份、采集入口和授权策略版本必须分别记录。
- News Item / Identifier / Version：来源原生 ID、规范 URL、主体身份和不可变元数据版本可追溯。
- Content Payload：正文/附件是否允许提取、存储、展示和保留，取决于 Provider 与 Publisher/Endpoint 授权交集。
- News Relation：转载/跨来源关系是带证据的关系断言，不应直接合并不同发布来源的主体。
- 时间必须区分 `published_at`、`available_at`、`observed_at`、`fetched_at`、`normalized_at`；缺失时间不得用抓取时间补成发布时间。
- 质量状态包含 valid/degraded/invalid/unknown 等业务质量判断；来源未识别、授权不足、身份冲突、发布时间缺失不能由 LLM 自动补全成事实。

**Research 的边界**

- Research 拥有 Event/Hypothesis/Claim/Scenario；News 只提供新闻对象、来源、版本、Observation 和关系证据，不负责事件聚合、影响方向、价格验证或研究结论。
- Research 可消费 News Application 的稳定用例/输出契约，但不能 import News 的私有 Domain/Adapter 包；跨模块传递引用与快照 DTO，后续 GOV-004 冻结。
- Research 不复制 News 原文、不自行重建 News Provider 或来源授权体系。Evidence 应引用 News 的稳定标识、版本和证据定位，并遵守授权与保留规则。
- News 业务质量规则由 News 负责；Platform Diagnostics 只提供统一执行/Observation 契约，不替代 News 质量判断。

#### 3. Platform：根 Go Module 公共基础能力

**当前代码包**

- `internal/platform/config`：环境配置读取、类型化值与 Secret 脱敏。
- `internal/platform/security`：owner/service/anonymous 身份与访问模式基础。
- `internal/platform/observability`：Request ID 生成/传播和日志基础。
- `internal/platform/fault`：稳定错误类别、Code、安全摘要、Dependency、Retryable。
- `internal/platform/diagnostics`：Check、Observation、超时/并发限制与结果聚合。
- `internal/platform/httpclient`：受控 Destination Policy、DNS/IP 校验、受控 Dial、重定向策略、禁用环境代理、响应大小/超时/并发和有限幂等重试。
- `internal/platform/storage`：SQL/Redis 连接生命周期、Ping 与 namespace/version Migration Runner。
- `internal/platform/httpapi`：根服务 HTTP 基础能力。
- `internal/platform/taskqueue`：当前仍存在历史分析领域耦合，不能直接认定为通用任务框架。

**可以复用的稳定基础契约**

- Fault：`class/code/safe_message/dependency/retryable`；Cause 仅内部使用。Retryable 是技术候选提示，不代表业务可无条件重试。
- Diagnostics Observation：`status/reason_code/safe_message/checked_at/duration/evidence_ref/attributes`。非 healthy 必须提供 reason_code；evidence_ref 是不透明引用，由证据所有者解释和授权。
- Check：ID、名称、Required、Timeout、Run；可选依赖未配置应 skipped，必需依赖缺失不能伪装 skipped。
- HTTP Client：调用方必须提供明确 DestinationPolicy；重试受幂等声明、次数、Deadline 和请求体可重放能力约束。News 来源授权由 News 持有，Platform 只负责网络目标安全执行。
- Storage：Platform 提供连接生命周期和 Migration 执行原语；领域拥有自己的 Repository、SQL、表结构、namespace 和迁移清单。
- Config/Secret：业务配置归业务模块；Platform 不建立全局业务配置中心、不做热更新。
- Request ID/日志：传播关联标识、统一安全字段；不把平台诊断记录当领域证据仓库。

**真实验收限制**

- Platform 包级测试/race/vet 与专项 CI 已有通过记录，但真实 MariaDB/Redis 集成和现有分析 Store 接入尚未完成验收。
- HTTP Client 的受控 DNS/IP、重定向和代理防护已有测试，但生产出口网络和完整 SSRF 攻击矩阵仍待部署环境验收。
- Platform Diagnostics 首期不建设通用诊断历史库；Data Probe、News Ingestion、Research Run、Notification Delivery 的历史与证据仍由各领域拥有。
- Data 迁入根 Go Module 后，可依赖 `internal/platform` 的公开技术 package；Provider 出站请求必须复用受控 HTTP Client。Data 不得依赖 Platform 私有实现或其他业务模块 internal。跨模块业务调用仍只能经公开 Application Port/DTO，不得因同 Module 而直接引用对方内部实现。
- Platform 不负责业务领域模型、领域 SQL、Research Run/Stage 状态机、News 来源质量或 Quant 计算规则。

#### 5. GOV-003 审查发现与需要进入 GOV-004 的事项

1. **数据契约需要拆成领域输入快照，而不是复制 Data DTO。** 至少冻结 Quote/DailyBar/TradingCalendar/SecurityStatus/CorporateAction/Fundamentals/MarketContext 的必要字段、单位、时间、复权、质量和版本引用。
2. **PIT 需要端到端贯通。** Researchflow 的 Run 必须固定 `as_of`；Quant 所有输入与特征计算必须遵守同一信息截止时间；Research Evidence 必须保留 `available_at/observed_at`，不可把未来修订数据泄漏进历史判断。
3. **Data 认证契约按迁移目标分层。** 同进程模式由 Root Server 在入口认证并向 Data Application 注入可信 Principal/Scope Context，不使用 Data API Key；仅远程 HTTP Adapter 保留 Data API Key。Platform Service Secret、Owner Token、Provider Token 与 Data API Key 语义分离。浏览器不得持有任何服务端 Secret。
4. **News 目前没有完整持久化闭环。** Research 的 Evidence Repository 不能依赖 News 已经落库；先冻结稳定引用模型，并将 News N6 与 Platform Storage 真实集成作为依赖门禁。
5. **Diagnostics 与领域质量分层。** Platform Observation 是执行结果外壳；Data/News/Quant/Research/Researchflow/Notification 保留各自领域质量状态、规则、证据和历史。
6. **Platform Task Queue 不作为 Researchflow 的直接基础。** 当前代码与分析领域耦合，需由 GOV-004/Researchflow 设计确定首期领域自有 Run 持久化与 Worker 策略；除非出现多个真实调用方，不抽象通用队列。
7. **Platform Storage 不能标记为生产可用完成。** 先完成真实 MariaDB/Redis 集成和迁移故障演练，再允许领域模块接入其 Migration Runner；Redis 仅缓存/短期辅助，不存唯一事实。
8. **HTTP Client 的 SSRF 安全门禁必须在 News 在线采集前通过。** 当前单测通过不等于生产 DNS/出口验收完成。
GOV-003 通过条件：五模块可以准确指出每项数据/质量/基础设施能力的权威所有者、调用边界和缺失依赖；不重复实现 Data/News/Platform 已有能力；未验收的能力不被描述为已可用。
