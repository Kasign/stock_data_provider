## 1. 项目目标与交付边界

### 1.1 最终目标

形成一套能够持续回答以下问题的 A 股研究工作台：

1. 当前市场处于什么环境，市场风险偏好和赚钱效应如何？
2. 哪些行业/主题正在走强、走弱或发生切换？
3. 单只股票的趋势、量价、资金、估值、财务和事件情况如何？
4. 当前结论有哪些数据和事实证据，数据是否完整、及时、可信？
5. 如果形成策略信号，历史上类似条件的表现如何，风险边界在哪里？
6. 后续走势可能有哪些情景，概率和风险区间如何，而不是只给一个目标价？
7. 研究结论如何留档、复查、跟踪和评估？

### 1.2 不做的事情

- 不做券商交易、自动下单和实盘资金托管。
- 不以 LLM 输出代替行情事实、量化计算或风险门禁。
- 不保留 Python 生产服务作为长期架构组成；所有 Python 业务能力均须迁移到 Go，完成验收后删除 Python 服务、Bridge 和运行时依赖。
- 迁移期间禁止新增 Python 生产依赖。存量 Python 生产调用允许暂时保留，但必须登记调用方、触发条件、配置开关、日志/指标、负责人和替换期限；不得把存量 fallback 视为 Go 迁移完成。Go 替代能力完成契约、数据质量、真实环境和回归验收后，才可关闭对应 Python 调用。Python 固定样本对照环境必须与生产网络、数据库写权限和服务发现隔离，不得参与生产请求。
- 不把模拟数据、Fixture、Mock、CI Live Probe 的工作流通过等同于真实 Provider 数据验收。
- 不把当前已加载分页的本地筛选称为全市场策略扫描。
- 不用成交额、成交量或其他代理字段冒充资金净流入。
- 国内 A 股主线稳定前，不扩展海外市场数据体系。
- 不为了页面完整而虚构服务端能力、数据字段或策略结果。

### 1.3 关键成功标准

- 数据有来源、时间、单位、口径、覆盖范围和质量状态。
- 历史研究遵守 PIT（Point-in-Time）约束，避免未来数据泄漏。
- 市场、行业、个股使用统一且可解释的分析口径。
- 量化引擎负责可重复计算，AI 研究引擎负责解释和研究辅助，职责不冲突。
- 策略必须经过历史回测、样本外验证和风险约束，不能仅凭规则写完即认定有效。
- WebUI 只展示服务端事实和分析结果，不自行复制服务端策略逻辑。
- 每项任务有负责人、依赖、完成标准、测试证据和真实数据验收边界。

## 2. 总体架构与职责边界

### 2.1 逻辑架构

```text
数据采集与标准化
    │
    ├── Provider / API / 数据库 / Redis
    ├── 数据质量 / 统一诊断 / Freshness
    └── PIT / 历史版本 / 来源与时间追溯
    │
    ▼
统一研究数据快照与契约
    │
    ├──────────────────────┐
    ▼                      ▼
Go 量化分析引擎             Go 原生研究引擎 + 外部模型服务
    │                      │
    ├─ 市场环境             ├─ 新闻检索与事实归纳
    ├─ 行业强度             ├─ 事件去重与事件解释
    ├─ 个股趋势/因子        ├─ 财务/公告/产业链解释
    ├─ 策略信号             ├─ 研究假设与情景分析
    ├─ 风险门禁             └─ 报告生成与结论解释
    └─ 回测/统计
    │                      │
    └──────────┬───────────┘
               ▼
统一分析结果、证据链与版本记录
               │
               ▼
WebUI 个股研究与市场观察工作台
               │
               ├─ 市场总览 / 行业观察 / 个股研究
               ├─ 选股 / 分析任务 / 研究归档
               └─ 诊断 / 告警 / 设置
```

### 2.2 两条分析引擎的唯一职责

| 引擎 | 唯一主责 | 不应承担 |
|---|---|---|
| Go 量化分析引擎 | 数值指标、市场/行业/个股状态、策略信号、风险规则、回测和统计 | 不依赖 LLM 决定数值事实；不允许模型绕过硬风险门禁 |
| Go 原生研究引擎 | 新闻与事件理解、公告/财务解释、产业链关联、研究假设、报告与自然语言解释 | 不独立再造趋势指标或风险规则；不把模型推断当作已核实事实；不依赖 Python Bridge |
| 统一结果层 | 统一数据快照、时间语义、指标口径、结论、证据、算法/模型版本、质量状态 | 不允许两个引擎各自定义互相矛盾的公共字段和状态 |
| WebUI | 页面、请求编排、交互、本地工作区、结果呈现和证据导航 | 不在浏览器复制 Provider 选择、数据清洗、策略计算或风险门禁 |

### 2.3 统一分析结果的最低要求

每次分析结果至少应能追溯：

- 证券代码、市场、分析时间和数据 as_of。
- 行情/财务/估值/事件等各数据域的源端时间、采集时间、可用时间和质量状态。
- 数据快照或输入版本标识。
- 指标、策略、规则和算法版本。
- 结论、支持证据、反向证据、未知项和限制条件。
- 风险门禁结果及拒绝原因。
- LLM 模型标识、提示词/流程版本（适用时）和引用来源。
- 任务 ID、运行状态、失败阶段和可复现所需参数。


### 2.4 Go 原生模块分工与职责边界

本节定义目标模块职责，供数据侧分支按现有代码结构逐步落位。它是逻辑边界，不要求为了匹配名称而立即大规模搬迁目录；实施前必须先核对当前包结构，优先复用已有实现。

| 模块 | 核心职责 | 输入 / 输出边界 | 明确不负责 | 主要归属 |
|---|---|---|---|---|
| 服务入口与配置（Bootstrap） | 进程启动、配置加载、依赖装配、生命周期、优雅关闭 | 将配置和依赖注入应用服务 | 不写业务规则、不直接实现 Provider | 数据侧分支 |
| API / Transport | HTTP 路由、参数校验、鉴权、DTO、错误码、OpenAPI | DTO 转应用层请求；应用结果转响应 | 不直接访问 Provider/数据库，不计算指标 | 数据侧分支；WebUI 只消费契约 |
| 领域模型与公共契约（Domain / Contracts） | 证券、行情、财务、估值、事件、分析任务、质量状态、时间语义等稳定模型 | 定义跨模块请求/响应和领域约束 | 不承载外部 SDK、HTTP、SQL 细节 | 数据侧分支；跨端需同步 |
| 行情数据（Market Data） | Quote、DailyBar、复权、交易日历、停复牌/交易状态、行情标准化 | Provider 原始响应 → 标准行情模型及质量报告 | 不负责趋势结论、新闻解释和页面展示 | 数据侧分支 |
| 财务数据（Fundamentals） | 财务报表、指标映射、公告/报告期、PIT、修订历史 | Provider 原始财务数据 → 统一字段、单位、available_at/as_of | 不自行推断缺失公告时间，不承担估值策略 | 数据侧分支 |
| 估值数据（Valuation） | PE/PB/PS/PCF 等估值字段、分母口径、TTM/静态/动态语义 | 行情快照 + 财务可用数据 → 有口径的估值结果 | 不混淆财务事实与模型预测，不在 WebUI 重算 | 数据侧分支 |
| 证券与市场基础数据（Security / Market / Industry） | Security Master、指数、市场宽度、行业分类/成分及历史版本 | 证券主数据、交易状态、指数/行业数据和覆盖率 | 不用当前成分冒充历史成分，不用成交额冒充资金净流入 | 数据侧分支 |
| Provider 适配（Provider Adapters） | 各数据源鉴权、限流、请求、响应解析、能力声明、错误分类 | 统一接口输出原始/标准数据及来源元信息 | 不把某个 Provider 的字段口径泄漏为公共契约；不做静默补零 | 数据侧分支 |
| 统一诊断与数据质量（Diagnostics / Quality） | Probe、Validator、Reporter、Freshness、Coverage、质量等级和诊断历史 | 对 Provider、字段、数据集和任务给出可解释诊断 | 不将 skipped/not_configured 记为通过；不与业务数据混存 | 数据侧分支 |
| 研究采集与新闻（Research Ingestion / News） | 新闻源接入、搜索、采集、标准化、去重、来源可信度和原始证据留存 | 外部新闻/公告 → 带来源、时间和原文引用的标准记录 | 不直接输出未经核验的交易信号；不把模型摘要当原始事实 | Go 服务端研究模块 |
| 事件研究（Event） | 事件识别、聚合、生命周期、事实/推断标记、证券/行业关联、影响路径 | 新闻/公告事实 → 可追踪事件及版本化关联 | 不与新闻原文混为一体；不把情绪分数当影响结论 | Go 服务端研究模块 |
| LLM 接入（LLM Gateway / Model Adapter） | 多模型适配、请求/响应协议、超时、重试、限流、结构化输出校验、脱敏和成本记录 | 研究任务上下文 → 模型请求 → 受校验的模型结果 | 不持有业务主流程、不直接修改核心业务表、不决定量化风险门禁 | Go 服务端研究模块；模型推理由外部/本地模型服务承担 |
| 研究编排（Research Orchestrator） | 任务状态机、上下文组装、工具调用、阶段编排、结果合并、失败恢复 | 调用数据、事件、量化和 LLM 模块，产出统一研究结果 | 不复制 Provider 逻辑；不绕过数据质量和风险门禁 | Go 服务端研究模块 |
| 量化分析与回测（Quant / Backtest） | 指标、因子、趋势、策略、风险规则、回测、样本外评估 | 统一快照 → 可复算指标/信号/回测结果 | 不调用 LLM 决定数值事实；不允许评分覆盖硬风险规则 | Go 量化引擎 |
| 持久化（Persistence） | Repository、事务、迁移、幂等、历史版本、任务/研究记录存储 | 应用层定义接口，存储适配层实现 MariaDB/Redis 等 | 不让各业务模块散落 SQL；不把缓存当事实数据源 | Go 服务端基础设施 |
| 通知（Notification） | 渠道适配、订阅、模板、发送、重试、幂等、投递记录 | 业务事件/告警 → 渠道消息及投递状态 | 不负责告警规则计算，不在通知失败时丢失业务事件 | Go 服务端基础设施 |
| 可观测性与安全（Observability / Security） | 结构化日志、指标、Trace、审计、密钥管理、脱敏、访问控制 | 全链路统一 trace/task ID 和错误分类 | 不记录密钥、完整敏感上下文或未脱敏个人数据 | 全服务端共用 |

#### 模块依赖方向

目标依赖方向如下，禁止循环依赖：

```text
API / Transport
      ↓
Application / Use Cases
      ↓
Domain / Contracts ← Quant / Event / Research（领域能力实现）
      │
      ├── Ports：MarketData / Repository / LLM / Notification
      │
      ▼
Adapters：Provider / Persistence / Model API / Notification Channel
```

实施约束：

1. 领域模型和公共契约不依赖 HTTP、SQL、Redis、Provider SDK 或具体 LLM SDK。
2. API 层只做协议适配和输入校验；业务流程放在应用服务/用例层。
3. Provider 适配器只负责数据源接入与标准化，不决定业务分析结论。
4. LLM 适配器只负责模型协议；研究编排负责上下文、工具调用、状态机和结果校验。
5. 持久化通过 Repository/Store 接口使用；业务模块不得各自建立互相耦合的数据库访问链路。
6. 量化模块、事件模块和研究模块共享统一时间、证券身份、快照和质量契约，不各自发明同义字段。
7. 模块拆分以职责和依赖为先，不为追求微服务化而拆成多个进程；首阶段允许同一 Go 进程内模块化部署。
8. 任何新模块落位前先列出当前实现路径、目标职责、调用方、被调用方和迁移/删除范围；不允许只改包名或目录就标记迁移完成。

公共平台由 `feat/platform-foundation` 独立分支开发，避免与数据、新闻、分析分支并行修改公共包和平台组件。该分支负责公共组件、平台管理能力及其契约测试；不直接承载各业务模块。数据侧、新闻侧和分析侧分别按冻结契约接入，最终由服务端集成分支协调公共平台分支合入及启动装配、路由和 Migration 集成。平台分支不直接改写业务分支；跨分支集成前必须核对共同祖先、HEAD、目录差异、接口兼容和 Migration 冲突。WebUI 只消费确认后的 Server API。

### 2.6 Python 全量退役原则

- 最终生产架构只保留 Go 业务服务；禁止新增 Python 生产服务、后台 Worker、定时任务、数据 fallback 或业务 Bridge。迁移期存量调用按 MIG-003 登记、监控和限期替换。
- Python 旧实现可在迁移期保留必要的存量生产调用，但不得扩张调用范围；固定样本对照必须使用独立隔离环境，与生产网络、数据库写权限和服务发现隔离。
- Python 能力按模块迁移，不按“整个 Bridge 一次性替换”处理；每项能力先确定 Go 所属模块、契约、数据所有权、验收样本和删除条件。
- LLM 迁移目标是 Go 实现模型适配和研究编排；模型本身可以由兼容 API 的外部或本地模型服务提供，不要求 Go 实现模型推理。
- 删除 Python 前必须完成调用链扫描、部署配置扫描、依赖扫描、数据兼容核验和回滚方案确认。

## 3. 任务状态与更新规范

### 3.1 完成字段定义

每个任务必须有独立的完成字段：

- **完成：否**：未完成、只完成部分代码、只通过 Mock/单测、缺少必要验收证据、被阻塞或尚未核验。
- **完成：是**：任务定义中的代码/文档、自动化测试、契约验证及该任务要求的真实数据/部署验收均已完成；有可追溯证据。
- **不适用/暂缓**：只用于明确暂不进入当前项目范围的任务，不得把它写成完成。

禁止将“代码已写”“本地能跑”“CI 通过”“真实数据正确”混为同一状态。

### 3.2 建议同时维护的进度字段

| 字段 | 填写要求 |
|---|---|
| 完成 | 只填“是”或“否” |
| 当前状态 | 未开始 / 设计中 / 开发中 / 待测试 / 待联调 / 待真实验收 / 阻塞 / 已完成 / 暂缓 |
| 已完成内容 | 只写已有实现和证据，不写愿望 |
| 未完成内容 / 下一步 | 写成可执行动作 |
| 依赖 | 标明任务编号、接口、Provider 凭据、数据库或用户决策 |
| 代码基线 | 实际检查的分支和 HEAD SHA |

### WebUI 实施约束

1. 前端只消费服务端数据、质量状态和分析结果；不补零、不推断缺失时间、不重算 Provider 数据口径。
2. 当前分页本地筛选不能命名为全市场扫描；服务端能力未完成时明确标注边界。
3. 真实 Provider 诊断与历史持久化未验收时，只展示已有事实和阻塞状态，不以 Fixture 宣称联调完成。
4. 浏览器本地数据必须明确标注本地范围，不伪装成服务端持久化或跨设备同步。
5. 复杂交互、持久化 schema 或服务端模型调整，先提交方案并取得用户确认。
6. 维持原生 HTML/CSS/JavaScript ES Modules，不引入 React；按功能批次提交，不为小修复频繁提交。

## 7.1 市场—行业—个股三层分析

不得混淆三层范围：

- **市场层：** 全市场或明确市场指数成分范围；统计分母、停牌/退市/新股处理和覆盖率必须说明。
- **行业层：** 行业成分及历史分类口径；要区分行业涨幅、行业广度、成分贡献和资金净流入。
- **个股层：** 个股多周期趋势、量价、波动、相对强度、财务估值、资金和事件。

自选股或当前分页的 MA20 占比，只能描述对应股票集合，不得命名为全市场宽度。

## 7.2 趋势模型拆分

趋势方向与趋势阶段是两个维度，不应混成一个互斥枚举：

- 方向：bullish / neutral / bearish / unknown。
- 阶段：strong / advancing / pullback / consolidating / rebound / weakening / reversal_watch。
- 输出必须同时包含周期、证据指标、数据质量和置信边界。
- 不允许仅凭 MA20 单一指标认定完整趋势，更不能把 MVP 规则称为成熟策略。

## 7.3 新闻与事件分析原则

新闻/事件不能只输出情绪分数。至少区分：

1. 原始新闻和权威来源。
2. 同一事件的多篇报道去重。
3. 已确认事实、媒体表述、模型推断和未知信息。
4. 事件发生时间、公开时间、采集时间和有效期。
5. 关联公司、行业、上下游和可能受影响标的。
6. 影响方向、传导路径、潜在持续时间和不确定性。
7. 事件发生前后市场价格/成交/行业表现验证。
8. 历史事件样本和事后评估，避免只挑成功案例。

# 9. 阶段准入与退出门禁

## 9.1 数据可信度门禁

下列条件未满足，不进入依赖这些数据的策略/预测正式验收：

- 证券身份、交易日历和交易状态可解释。
- DailyBar 复权口径真实可验证。
- 财务/估值 PIT 与单位/口径明确。
- Provider 来源、源端时间和服务端采集时间分离。
- 数据质量报告能区分缺失、异常、降级、未知和不可比较。
- 关键数据域有真实样例，或明确列出因权限/数据源导致的阻塞。

## 9.2 策略准入门禁

- 策略规则、输入字段和参数版本固定。
- 使用无未来函数的数据快照。
- A 股交易制度和交易成本纳入回测。
- 样本内、样本外、滚动验证和基准对比齐全。
- 报告收益、回撤、胜率、盈亏比、交易次数、暴露、换手和稳定性。
- 关键风险规则为硬约束，任何总分或 LLM 解释都不能覆盖。

## 9.3 预测准入门禁

- 不以单个目标价作为唯一输出。
- 输出收益区间/分布、方向概率、MAE/MFE 和样本量。
- 有样本外评估、概率校准和不同市场状态分层结果。
- 预测置信度与数据质量、样本覆盖、模型版本关联。
- 发现漂移或表现失效时可降级或关闭预测能力。

## 9.4 WebUI 验收门禁

- 当前 HEAD 的 WebUI Checks 和 Chromium Browser Smoke 通过。
- 关键页面完成窄屏到桌面视口检查。
- 加载、空数据、错误、超时、取消、旧响应、未知字段和损坏本地数据均有明确状态。
- 敏感配置不回显，外链/文本/CSV 有安全处理。
- Fixture 只证明前端行为，不证明真实数据源质量。

# 10. 强制执行规则：防止任务发散

以下规则适用于后续所有数据侧、WebUI 和跨端开发任务。

### 10.1 开始任务前必须做

1. 确认用户授权的目标分支；没有授权不得修改其他分支。
2. 读取目标分支最新 HEAD、最近提交和相关 Git Tree/文件。
3. 读取本文及对应专项计划、协作清单，核对任务是否已完成或被替代。
4. 先检查现有代码、测试和 API，不允许按规划标题直接重写。
5. 写出本批任务编号、目标、范围、明确不做事项、依赖、验收标准。
6. 若涉及新架构、新数据库模型、新策略模型、复杂 UI 或破坏性变更，先提交设计方案并等待用户确认。

### 10.2 开发过程中必须遵守

1. 一批只围绕一个明确目标，可并行的独立子任务可以并行，但不能扩大任务边界。
2. 不顺手重构无关模块，不临时增加未规划功能。
3. 数据侧只修改数据侧允许目录；WebUI 只修改 `web/**` 及获准的 WebUI 文档。
4. 先契约后接入：服务端字段尚未确定时，WebUI 不自行定义临时业务字段。
5. 不通过 Mock、Fixture 或静态假数据掩盖后端缺口。
6. 不把测试通过当成业务正确；数据正确性需要真实样本和口径核验。
7. 发现新问题先判断是否属于当前任务；无关问题登记任务池，不擅自插队。
8. 不为了“任务有进展”而制造无意义提交；按完整功能批次集中提交，提交说明使用中文。
9. 所有 GitHub 写操作必须以最新 SHA 为基线；更新引用时使用 expected SHA/lease，冲突后重新读取再处理。
10. 不创建新分支、不合并、不关闭 PR，除非用户明确授权。

### 10.3 任务完成时必须做

1. 代码审查：检查改动范围、异常路径、兼容性和安全边界。
2. 测试：执行与本批相关的格式检查、单测、集成测试、契约测试或浏览器测试。
3. CI：记录对应提交 SHA 的运行结果；取消、跳过、未触发均不能写通过。
4. 真实验收：需要 Provider/数据库/部署的任务单独执行；未执行明确记录。
5. 文档：更新本文对应任务的完成字段、证据、依赖和下一步；专项细节写入专项文档。
6. 汇报：说明当前阶段、完成项、未完成项、阻塞、提交 SHA 和下一任务。
7. 若任务未完全满足验收标准，`完成` 必须保持“否”。

### 10.4 每轮“继续任务”的固定执行节奏

```text
读取最新 HEAD
  ↓
核对任务编号与完成状态
  ↓
检查现有代码/文档/测试
  ↓
确定一个最小可交付批次
  ↓
开发与自审
  ↓
自动化测试 / CI / 真实数据验证（按任务要求）
  ↓
更新任务进度与证据
  ↓
集中提交
  ↓
报告当前状态和下一项
```

不得跳过“核对现状”直接按旧计划继续开发；不得把下一项任务自动扩大为整个阶段。

本节是对前文架构、分支和执行顺序的补充约束；与旧章节存在不一致时，以本节和《公共平台基础能力建设方案.md》为准。

公共平台由 feat/platform-foundation 独立分支开发，数据侧 Go 服务分支负责最终服务端集成；News、Research 按冻结契约接入。公共平台专项文档统一位于 doc/platform/。

### 14.2 公共平台目标和边界

公共平台采用“组件优先、管理能力按需集中、服务谨慎拆分”的方式：

- Go 公共组件：Security Middleware、Config/Secret、Logger、Error、Trace、HTTP Client、DB/Redis Bootstrap、Diagnostics SDK、Metrics、Idempotency。
- 集中管理能力：服务身份/Key 管理、诊断聚合、必要的任务元数据和审计查询。
- 业务能力：Notification 仍是独立业务模块；Data、News、Research 保留各自领域模型、Repository 和业务诊断规则。
- 基础设施：MariaDB 作为事实持久化，Redis 用于缓存、短期协调和经验证需要的队列；复用现有 LLM 服务。

公共平台不等于所有能力独立部署。认证中间件、日志、配置和 HTTP Client 首期作为 Go 包嵌入各服务；只有存在独立生命周期、跨进程共享状态或集中管理需求时，才考虑独立服务。

### 14.3 必须遵守的公共原则

1. 外部用户、管理员、内部服务、Provider 凭证和后台任务身份严格区分。
2. 内网地址不能替代应用认证；内部 Service Key 按服务和环境隔离，具备 Scope、过期、轮换、撤销和审计。
3. 默认拒绝、最小权限；客户端传入的身份 Header 不可信，身份只能由认证中间件建立。
4. Secret 不写日志、不进入普通配置响应；首期使用部署环境注入，避免提前建设复杂配置中心。
5. 统一 Request ID、Trace、错误分类和日志脱敏。
6. 诊断统一 healthy、degraded、unavailable、skipped、failed；连通性检查不能替代数据质量检查。
7. HTTP 重试必须受总 Deadline 和幂等约束，禁止多层重试风暴。
8. MariaDB 保存任务和研究等事实状态；Redis 不能成为唯一事实源。
9. 各领域拥有自己的表和 Repository；Migration 文件可按领域拆分，但注册和执行顺序统一协调。
10. Notification 只负责通知请求、模板、渠道和投递；不复制平台安全、配置、日志、HTTP 和任务底座。
11. Quant 纯计算可先行；Context/Evidence 先定义模型、来源、时间和质量校验，再接入 Data/News。
12. LLM Gateway 暂缓重建，后续通过 Adapter 复用现有独立服务。
