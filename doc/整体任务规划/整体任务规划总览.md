# A 股研究助手整体任务规划与执行约束

- 仓库：`Kasign/stock_data_provider`
- 本文所在分支：`feat/design_doc`
- 文档路径：`doc/整体任务规划/整体任务规划总览.md`
- 规划版本：v1.0
- 规划日期：2026-11-04
- 项目范围：国内 A 股个人研究助手；日线优先；不接入券商下单；暂缓海外市场。
- 本文性质：项目级唯一总路线、跨侧任务分工、依赖关系和执行约束。本文不替代数据侧、WebUI 侧专项计划和 API 契约。

> **状态说明：** 本文初始状态根据 2026-11-04 可读取的数据侧与 WebUI 专项规划整理，不代表本次已对两个开发分支最新 HEAD 逐文件复核。凡需要最新代码、CI 或真实 Provider 证据的任务，均应先核验对应分支后再更新状态。历史记录不能自动代表当前 HEAD。

## 1. 项目目标与交付边界

### 1.1 最终目标

形成一套能够持续回答以下问题的 A 股研究工作台：

1. 当前市场处于什么环境，市场风险偏好和赚钱效应如何？
2. 哪些行业/主题正在走强、走弱或发生切换？
3. 单只股票的趋势、量价、资金、估值、财务和事件情况如何？
4. 当前结论有哪些数据和事实证据，数据是否完整、及时、可信？
5. 如果形成策略信号，历史上类似条件的表现如何，风险边界在哪里？
6. 后续走势可能有哪些情景，概率和风险区间如何，而不是只给一个目标价？
7. 研究结论如何留档、复查、跟踪和评估？

### 1.2 不做的事情

- 不做券商交易、自动下单和实盘资金托管。
- 不以 LLM 输出代替行情事实、量化计算或风险门禁。
- 不把模拟数据、Fixture、Mock、CI Live Probe 的工作流通过等同于真实 Provider 数据验收。
- 不把当前已加载分页的本地筛选称为全市场策略扫描。
- 不用成交额、成交量或其他代理字段冒充资金净流入。
- 国内 A 股主线稳定前，不扩展海外市场数据体系。
- 不为了页面完整而虚构服务端能力、数据字段或策略结果。

### 1.3 关键成功标准

- 数据有来源、时间、单位、口径、覆盖范围和质量状态。
- 历史研究遵守 PIT（Point-in-Time）约束，避免未来数据泄漏。
- 市场、行业、个股使用统一且可解释的分析口径。
- 量化引擎负责可重复计算，AI 研究引擎负责解释和研究辅助，职责不冲突。
- 策略必须经过历史回测、样本外验证和风险约束，不能仅凭规则写完即认定有效。
- WebUI 只展示服务端事实和分析结果，不自行复制服务端策略逻辑。
- 每项任务有负责人、依赖、完成标准、测试证据和真实数据验收边界。

## 2. 总体架构与职责边界

### 2.1 逻辑架构

```text
数据采集与标准化
    │
    ├── Provider / API / 数据库 / Redis
    ├── 数据质量 / 统一诊断 / Freshness
    └── PIT / 历史版本 / 来源与时间追溯
    │
    ▼
统一研究数据快照与契约
    │
    ├──────────────────────┐
    ▼                      ▼
Go 量化分析引擎             go-core + LLM 研究引擎
    │                      │
    ├─ 市场环境             ├─ 新闻检索与事实归纳
    ├─ 行业强度             ├─ 事件去重与事件解释
    ├─ 个股趋势/因子        ├─ 财务/公告/产业链解释
    ├─ 策略信号             ├─ 研究假设与情景分析
    ├─ 风险门禁             └─ 报告生成与结论解释
    └─ 回测/统计
    │                      │
    └──────────┬───────────┘
               ▼
统一分析结果、证据链与版本记录
               │
               ▼
WebUI 个股研究与市场观察工作台
               │
               ├─ 市场总览 / 行业观察 / 个股研究
               ├─ 选股 / 分析任务 / 研究归档
               └─ 诊断 / 告警 / 设置
```

### 2.2 两条分析引擎的唯一职责

| 引擎 | 唯一主责 | 不应承担 |
|---|---|---|
| Go 量化分析引擎 | 数值指标、市场/行业/个股状态、策略信号、风险规则、回测和统计 | 不依赖 LLM 决定数值事实；不允许模型绕过硬风险门禁 |
| go-core + LLM 研究引擎 | 新闻与事件理解、公告/财务解释、产业链关联、研究假设、报告与自然语言解释 | 不独立再造一套趋势指标或风险规则；不把模型推断当作已核实事实 |
| 统一结果层 | 统一数据快照、时间语义、指标口径、结论、证据、算法/模型版本、质量状态 | 不允许两个引擎各自定义互相矛盾的公共字段和状态 |
| WebUI | 页面、请求编排、交互、本地工作区、结果呈现和证据导航 | 不在浏览器复制 Provider 选择、数据清洗、策略计算或风险门禁 |

### 2.3 统一分析结果的最低要求

每次分析结果至少应能追溯：

- 证券代码、市场、分析时间和数据 as_of。
- 行情/财务/估值/事件等各数据域的源端时间、采集时间、可用时间和质量状态。
- 数据快照或输入版本标识。
- 指标、策略、规则和算法版本。
- 结论、支持证据、反向证据、未知项和限制条件。
- 风险门禁结果及拒绝原因。
- LLM 模型标识、提示词/流程版本（适用时）和引用来源。
- 任务 ID、运行状态、失败阶段和可复现所需参数。

## 3. 任务状态与更新规范

### 3.1 完成字段定义

每个任务必须有独立的完成字段：

- **完成：否**：未完成、只完成部分代码、只通过 Mock/单测、缺少必要验收证据、被阻塞或尚未核验。
- **完成：是**：任务定义中的代码/文档、自动化测试、契约验证及该任务要求的真实数据/部署验收均已完成；有可追溯证据。
- **不适用/暂缓**：只用于明确暂不进入当前项目范围的任务，不得把它写成完成。

禁止将“代码已写”“本地能跑”“CI 通过”“真实数据正确”混为同一状态。

### 3.2 建议同时维护的进度字段

| 字段 | 填写要求 |
|---|---|
| 完成 | 只填“是”或“否” |
| 当前状态 | 未开始 / 设计中 / 开发中 / 待测试 / 待联调 / 待真实验收 / 阻塞 / 已完成 / 暂缓 |
| 已完成内容 | 只写已有实现和证据，不写愿望 |
| 未完成内容 / 下一步 | 写成可执行动作 |
| 依赖 | 标明任务编号、接口、Provider 凭据、数据库或用户决策 |
| 代码基线 | 实际检查的分支和 HEAD SHA |
| 测试证据 | 命令、CI Run、测试范围和结果 |
| 真实验收 | Provider、证券、日期、字段、数据量、环境和结果 |
| 更新日期 | YYYY-MM-DD |

### 3.3 任务编号

- `GOV`：项目治理、架构与统一契约。
- `DATA`：数据侧任务，只能在 `feat/full-go-data-providers-api-switch` 开发。
- `WEB`：WebUI 任务，只能在 `feat/webui-market-data-console` 开发。
- `CROSS`：跨端任务，需双方确认接口契约和联调结果。
- `RESEARCH`：策略研究、回测与预测方案任务。
- 编号一经分配不复用；任务拆分时保留父编号并增加子编号。

### 3.4 进度更新模板

每次只更新实际推进的任务，不重写整张表：

| 字段 | 更新内容 |
|---|---|
| 任务编号 | DATA-xxx / WEB-xxx / CROSS-xxx |
| 完成 | 是 / 否 |
| 当前状态 | 当前枚举值 |
| 已完成内容 | 本批真实完成的工作 |
| 未完成内容 / 下一步 | 下一项最小可执行任务 |
| 依赖与阻塞 | 明确依赖编号或“无” |
| 分支 / HEAD | 实际核对的分支与 SHA |
| 测试证据 | 测试命令、CI Run、结果 |
| 真实验收 | 通过 / 失败 / 未执行 / 跳过，并说明原因 |
| 更新日期 | YYYY-MM-DD |

## 4. 项目阶段路线图

阶段顺序代表依赖顺序，不代表每个阶段必须串行完成所有无关工作。允许数据侧和 WebUI 侧并行推进各自独立任务，但不得越过跨端契约和质量门禁。

| 阶段 | 目标 | 数据侧主责 | WebUI 主责 | 阶段出口 |
|---|---|---|---|---|
| 0 工程与治理基线 | 代码、文档、契约和状态可信 | Go 构建、模块、数据质量与诊断基线 | 页面与浏览器回归基线 | 两侧 HEAD 和验收证据可核验 |
| 1 数据可信度 | 行情、财务、估值和历史数据可追溯 | DailyBar、PIT、单位、Freshness、Provider 验收 | 正确展示质量/来源/时间/空数据 | 数据可信度达到可研究标准 |
| 2 市场/行业/个股分析 | 形成统一分析事实 | 市场环境、行业强度、个股指标和结果契约 | 市场观察、行业研究、个股统一视图 | 三层分析口径统一且可解释 |
| 3 基础策略与回测 | 验证策略是否有统计价值 | 策略信号、风险门禁、回测和样本外验证 | 策略结果、证据、风险和历史展示 | 策略经过历史和样本外验收 |
| 4 新闻与事件 | 把新闻变成可验证研究事件 | 事件数据契约、关联与历史存储 | 新闻/事件时间线、影响证据展示 | 事件与价格表现可追溯 |
| 5 未来走势研究 | 输出概率分布和风险区间 | 预测样本、统计模型、校准与监控 | 情景、区间、概率和风险呈现 | 有样本外预测评估，拒绝伪精确目标价 |
| 6 组合与模拟跟踪 | 从单股研究扩展到组合风险 | 仓位、风险预算、组合回测/模拟 | 组合观察、持仓假设和告警 | 模拟闭环，不接真实下单 |
| 7 研究工作台收口 | 长期使用、审计与维护 | 服务稳定性、历史结果、告警接口 | 研究归档、任务历史、告警和全站体验 | 可持续研究和回溯 |

### 数据侧任务边界

1. 先核对已有实现和测试，再补明确缺口；不得因规划列出任务就重写已有 Probe、Reporter、Validator、Freshness。
2. 真实 Provider 未配置凭据时记为“跳过/未配置”，不能记为通过，也不能伪报失败。
3. 真实数据对账必须记录 Provider、证券、交易日/报告期、请求参数、源端时间、采集时间和样本数量。
4. Provider 取回数据不等于数据准确；CI Live Probe 通过不等于全部 capability 通过。
5. 对跨 Provider 数据，只在证券、日期、单位、复权、指标定义和质量状态一致时比较；否则标记 not_comparable。
6. PIT 不可证明时必须标记 unknown/不可判定，不能推断或回填历史可用时间。

### WebUI 实施约束

1. 前端只消费服务端数据、质量状态和分析结果；不补零、不推断缺失时间、不重算 Provider 数据口径。
2. 当前分页本地筛选不能命名为全市场扫描；服务端能力未完成时明确标注边界。
3. 真实 Provider 诊断与历史持久化未验收时，只展示已有事实和阻塞状态，不以 Fixture 宣称联调完成。
4. 浏览器本地数据必须明确标注本地范围，不伪装成服务端持久化或跨设备同步。
5. 复杂交互、持久化 schema 或服务端模型调整，先提交方案并取得用户确认。
6. 维持原生 HTML/CSS/JavaScript ES Modules，不引入 React；按功能批次提交，不为小修复频繁提交。

## 7.1 市场—行业—个股三层分析

不得混淆三层范围：

- **市场层：** 全市场或明确市场指数成分范围；统计分母、停牌/退市/新股处理和覆盖率必须说明。
- **行业层：** 行业成分及历史分类口径；要区分行业涨幅、行业广度、成分贡献和资金净流入。
- **个股层：** 个股多周期趋势、量价、波动、相对强度、财务估值、资金和事件。

自选股或当前分页的 MA20 占比，只能描述对应股票集合，不得命名为全市场宽度。

## 7.2 趋势模型拆分

趋势方向与趋势阶段是两个维度，不应混成一个互斥枚举：

- 方向：bullish / neutral / bearish / unknown。
- 阶段：strong / advancing / pullback / consolidating / rebound / weakening / reversal_watch。
- 输出必须同时包含周期、证据指标、数据质量和置信边界。
- 不允许仅凭 MA20 单一指标认定完整趋势，更不能把 MVP 规则称为成熟策略。

## 7.3 新闻与事件分析原则

新闻/事件不能只输出情绪分数。至少区分：

1. 原始新闻和权威来源。
2. 同一事件的多篇报道去重。
3. 已确认事实、媒体表述、模型推断和未知信息。
4. 事件发生时间、公开时间、采集时间和有效期。
5. 关联公司、行业、上下游和可能受影响标的。
6. 影响方向、传导路径、潜在持续时间和不确定性。
7. 事件发生前后市场价格/成交/行业表现验证。
8. 历史事件样本和事后评估，避免只挑成功案例。

# 9. 阶段准入与退出门禁

## 9.1 数据可信度门禁

下列条件未满足，不进入依赖这些数据的策略/预测正式验收：

- 证券身份、交易日历和交易状态可解释。
- DailyBar 复权口径真实可验证。
- 财务/估值 PIT 与单位/口径明确。
- Provider 来源、源端时间和服务端采集时间分离。
- 数据质量报告能区分缺失、异常、降级、未知和不可比较。
- 关键数据域有真实样例，或明确列出因权限/数据源导致的阻塞。

## 9.2 策略准入门禁

- 策略规则、输入字段和参数版本固定。
- 使用无未来函数的数据快照。
- A 股交易制度和交易成本纳入回测。
- 样本内、样本外、滚动验证和基准对比齐全。
- 报告收益、回撤、胜率、盈亏比、交易次数、暴露、换手和稳定性。
- 关键风险规则为硬约束，任何总分或 LLM 解释都不能覆盖。

## 9.3 预测准入门禁

- 不以单个目标价作为唯一输出。
- 输出收益区间/分布、方向概率、MAE/MFE 和样本量。
- 有样本外评估、概率校准和不同市场状态分层结果。
- 预测置信度与数据质量、样本覆盖、模型版本关联。
- 发现漂移或表现失效时可降级或关闭预测能力。

## 9.4 WebUI 验收门禁

- 当前 HEAD 的 WebUI Checks 和 Chromium Browser Smoke 通过。
- 关键页面完成窄屏到桌面视口检查。
- 加载、空数据、错误、超时、取消、旧响应、未知字段和损坏本地数据均有明确状态。
- 敏感配置不回显，外链/文本/CSV 有安全处理。
- Fixture 只证明前端行为，不证明真实数据源质量。

# 10. 强制执行规则：防止任务发散

以下规则适用于后续所有数据侧、WebUI 和跨端开发任务。

### 10.1 开始任务前必须做

1. 确认用户授权的目标分支；没有授权不得修改其他分支。
2. 读取目标分支最新 HEAD、最近提交和相关 Git Tree/文件。
3. 读取本文及对应专项计划、协作清单，核对任务是否已完成或被替代。
4. 先检查现有代码、测试和 API，不允许按规划标题直接重写。
5. 写出本批任务编号、目标、范围、明确不做事项、依赖、验收标准。
6. 若涉及新架构、新数据库模型、新策略模型、复杂 UI 或破坏性变更，先提交设计方案并等待用户确认。

### 10.2 开发过程中必须遵守

1. 一批只围绕一个明确目标，可并行的独立子任务可以并行，但不能扩大任务边界。
2. 不顺手重构无关模块，不临时增加未规划功能。
3. 数据侧只修改数据侧允许目录；WebUI 只修改 `web/**` 及获准的 WebUI 文档。
4. 先契约后接入：服务端字段尚未确定时，WebUI 不自行定义临时业务字段。
5. 不通过 Mock、Fixture 或静态假数据掩盖后端缺口。
6. 不把测试通过当成业务正确；数据正确性需要真实样本和口径核验。
7. 发现新问题先判断是否属于当前任务；无关问题登记任务池，不擅自插队。
8. 不为了“任务有进展”而制造无意义提交；按完整功能批次集中提交，提交说明使用中文。
9. 所有 GitHub 写操作必须以最新 SHA 为基线；更新引用时使用 expected SHA/lease，冲突后重新读取再处理。
10. 不创建新分支、不合并、不关闭 PR，除非用户明确授权。

### 10.3 任务完成时必须做

1. 代码审查：检查改动范围、异常路径、兼容性和安全边界。
2. 测试：执行与本批相关的格式检查、单测、集成测试、契约测试或浏览器测试。
3. CI：记录对应提交 SHA 的运行结果；取消、跳过、未触发均不能写通过。
4. 真实验收：需要 Provider/数据库/部署的任务单独执行；未执行明确记录。
5. 文档：更新本文对应任务的完成字段、证据、依赖和下一步；专项细节写入专项文档。
6. 汇报：说明当前阶段、完成项、未完成项、阻塞、提交 SHA 和下一任务。
7. 若任务未完全满足验收标准，`完成` 必须保持“否”。

### 10.4 每轮“继续任务”的固定执行节奏

```text
读取最新 HEAD
  ↓
核对任务编号与完成状态
  ↓
检查现有代码/文档/测试
  ↓
确定一个最小可交付批次
  ↓
开发与自审
  ↓
自动化测试 / CI / 真实数据验证（按任务要求）
  ↓
更新任务进度与证据
  ↓
集中提交
  ↓
报告当前状态和下一项
```

不得跳过“核对现状”直接按旧计划继续开发；不得把下一项任务自动扩大为整个阶段。
