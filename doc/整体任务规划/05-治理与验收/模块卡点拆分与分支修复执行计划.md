## 1. 盘点结论

本轮核对 repair_all 的九份模块卡点文档、RepairAll 跨模块修复记录、模块文档目录及远端分支。

- 所有模块分支均已存在，不新建分支。
- 模块分支负责模块自身实现和文档；`integration` 是唯一集成入口，负责接收各模块 PR、跨模块冲突协调、联调和集成验收。`repair_all` 仅作为聚合修复工作分支，不得绕过 `integration` 向模块分支或最终目标分支合并。
- 卡点不等于模块代码任务。必须区分模块内可执行、上游/下游协作、项目契约决策、真实外部环境证据。
- 不把 `repair_all` 的代码盲目复制到模块分支；先以 `integration` 为共同集成基线核对实现和提交差异，只将有明确归属的模块改动通过 PR 提交到 `integration`。模块分支之间禁止直接合并。
- 本轮只建立任务拆分计划，未修改生产代码。

## 4. 模块任务包细化

## 6. 分支执行与合并规则（以 integration 为唯一集成入口）

1. 各模块只在自己的 `feat/<module>` 分支完成模块内代码、测试和文档；开始任务前核对该分支最新 HEAD、模块规划、卡点和契约。
2. 每个模块分支向 `integration` 提交 PR；PR 的 base 必须是 `integration`。禁止模块分支直接合并到另一个模块分支。
3. `repair_all` 是聚合修复工作分支，不是集成入口。其变更如需进入集成基线，必须通过 `repair_all → integration` PR；不得直接合并到任一 `feat/*` 分支或最终目标分支。
4. `integration` 是唯一跨模块共同基线。模块依赖同步只能从 `integration` 出发，并通过目标模块分支的受控 PR/同步变更完成；不得以模块 A 直接向模块 B 合并的方式传递依赖。
5. 跨模块任务先指定唯一主责模块和契约 Owner，再拆为生产者契约/实现、消费者适配、Server 装配三个模块交付；各交付分别 PR 到 `integration`，按生产者→消费者→Server 的顺序集成。
6. PR 前先比较源分支与 `integration` 的 merge-base、ahead/behind、文件差异和目标文件当前实现。存在大幅分叉时不得直接全量合并；先识别已被集成、已被替代、仍有价值的独有提交，再选择性整理。
7. 所有 PR 均记录源分支 SHA、PR head/base SHA、冲突处理、合并提交 SHA、目标分支 SHA、CI Run 和精确被测 SHA。代码 CI 与真实 Provider/Gateway/生产环境证据分开判定；文档提交不冒充代码 CI。
8. `integration` 的集成 CI 通过后，才允许将 `integration` 推进到最终目标分支；不得绕过 `integration`。
9. 既有历史 PR（例如本计划前已完成的模块间依赖 PR）只作为历史记录，不构成后续可绕过本规则的先例。
