## 1. 本次治理目标

本次治理不是重写模块设计，也不是把模块重新规划为从零开发。目标是以各模块当前分支的代码、测试、契约和 CI 证据为准，清除过时的当前状态描述、重复规划入口和失效 TODO，同时保留有追溯价值的任务历史。

模块统一采用三层文档结构：

1. `模块总任务规划和进度.md`：模块目标、边界、已有能力、完整剩余任务、依赖与总体进度。
2. `当前任务状态和进度.md`：唯一当前执行入口，记录当前任务、分支/基线、问题、阻塞、下一步和最新验证证据。
3. `任务历史/`：每个已完成子任务的完成记录；保留目标、改动、测试/CI、Commit、验收结论和遗留项。

README 仅作为文档索引，不再维护第二份任务状态。契约、Schema、Golden、运行手册和必要设计说明不强制塞进三层结构，继续按职责保留并从总规划链接。

## 3. 已发现的文档问题

### 3.1 多份文档同时承担当前进度

- 项目总览、模块 README、模块任务拆分文档、交接文档均可能出现“当前状态/下一步/阻塞”。
- 例如 Research README 有模块状态表，`02-任务拆分与验收.md` 又有详细进度表和大量按日期追加记录；二者有必要区分为当前快照与历史证据。
- Researchflow README 和任务拆分文档也同时描述当前能力/缺口，容易在更新不同步时产生冲突。
- WebUI README 已声明 `Web整体规划.md` 是唯一规划入口，这是可复用的维护方式，但文档仍需纳入三层结构并校准当前状态。

处理原则：每个模块只允许 `模块总任务规划和进度.md` 维护总体任务状态，`当前任务状态和进度.md` 维护当前执行状态；README 只做索引。

### 3.2 长任务文档混入大量执行历史

Research、Researchflow、Data、Server/Integration 等任务文档包含大量按日期追加的执行记录。历史记录本身有价值，不应整体删除；问题在于它们与当前任务表、现行阻塞和旧待办混排。

处理原则：保留有证据价值的历史内容，按子任务拆入 `任务历史/`；旧文档保留必要的历史索引或迁移说明，不能继续作为当前任务入口。迁移后删除重复正文，不删除契约、Golden、Schema、测试样例和不可替代的审计证据。

### 3.3 存在旧目录/旧命名并行

当前同时存在：
- `doc/research/` 与 `doc/research-analysis-flow-native-go/`
- 项目级整体规划、模块任务拆分文档、模块 README、专项 Review/验收报告
- Data 的 `doc/api/` 与项目级跨模块契约/治理文档

这些目录不应仅因名字旧就直接删除。需要逐份确认是否仍承载唯一设计决策、迁移映射或历史依据。确认已被新文档完整吸收后，才删除重复副本；否则转入历史归档并保留链接。

### 3.4 状态语义需要统一

后续统一使用：
- `DONE`：有代码/文档范围明确且满足验收证据。
- `IN_PROGRESS`：已有实现，但任务验收条件尚未全部满足。
- `BLOCKED`：有明确外部依赖或证据门禁阻塞。
- `DEFERRED`：明确决定暂不做，不进入当前迭代。
- `SKIPPED`：本次执行因条件不满足而跳过，不能当作完成。
- `NOT_STARTED`：尚未开始。
- `NOT_COMPARABLE`：缺少可比较依据，不得误报 PASS/FAIL。

“代码存在”“单测通过”“契约冻结”“CI 通过”“真实生产链路通过”是不同证据等级，不得相互替代。

## 5. 清理和迁移规则

1. 不删除契约、OpenAPI、Schema、Golden、Migration 设计依据、数据样例和真实验收证据。
2. 不因为历史文档中的旧 TODO 仍存在，就将其重新列为当前任务。
3. 不因为新 README/新规划存在，就直接删除旧文档；先做引用和内容去重检查。
4. 同一事实只保留一个当前权威位置；其他文档改为链接或历史说明。
5. 任务历史必须注明当时的分支、SHA、Run ID、验证范围和边界；旧 SHA/旧 CI 不能代表当前 HEAD。
6. 不将 skipped、fixture、mock、静态审查或单元测试写成真实生产验收通过。
7. 代码分支的模块文档由对应模块分支维护；项目级规划和跨模块契约由 `feat/design_doc` 维护；`integration` 只维护获授权的聚合验收证据。
8. 文档清理不得顺手改业务代码、契约语义或模块边界。
