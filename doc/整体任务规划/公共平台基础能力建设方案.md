## 1. 建设目标与基本判断

公共平台的目标不是建设一个包含所有技术功能的“大型平台服务”，而是为所有 Go 业务模块提供一致、可复用、可诊断、可治理的基础能力，避免 Data、News、Research 分别实现认证、配置、日志、HTTP 调用、任务和诊断。

公共平台需要解决六类问题：

1. **统一身份和访问边界**：明确外部用户、管理员、内部服务和任务执行身份，避免仅依赖内网地址或自定义请求头判断可信。
2. **统一运行规范**：配置、Secret、日志、错误、Trace、超时、重试和资源关闭方式一致。
3. **统一依赖治理**：MariaDB、Redis、HTTP 外部依赖的连接、超时、健康状态和错误分类可控。
4. **统一诊断**：服务存活、依赖可用、业务能力和数据质量分层诊断，避免把 HTTP 200 等同于业务可用。
5. **统一异步任务语义**：任务状态、取消、超时、重试、幂等和恢复行为一致。
6. **统一审计和可观测性**：能回答谁在什么时间通过什么身份调用了什么能力，调用链在哪里失败，是否影响业务数据。

### 1.1 非目标

当前阶段不建设：

- 独立的微服务注册中心、服务网格或复杂 API Gateway。
- 自研 OAuth/OIDC 身份平台或完整多租户 IAM。
- Kafka、RabbitMQ 等新消息基础设施，除非现有 MariaDB/Redis 经验证无法满足任务需求。
- 通用工作流引擎、通用规则引擎或复杂 Agent Runtime。
- 独立的日志、指标、Trace 存储平台；先统一埋点和导出接口，复用现有部署能力。
- 所有模块共享一套巨大 Domain 模型或万能 Repository。
- 让每个公共能力都成为一个独立部署进程。

### 1.2 核心原则

- 先盘点、再抽象、后实现；已有实现优先复用。
- 组件优先于服务；只有存在独立生命周期、状态管理或管理入口时才考虑独立部署。
- 默认最小权限；认证与授权分开。
- 内部网络不等于可信网络；内部服务调用也必须有身份。
- Secret 不落日志、不进入普通配置响应、不以明文持久化。
- 业务事实以 MariaDB 等持久化事实源为准，Redis 只承担缓存、短期协调或队列能力。
- 失败必须显式分类；禁止静默补零、静默降级或把未执行标记为成功。
- 公共接口保持小而稳定，业务模块通过接口接入，不反向依赖具体基础设施实现。
- 公共平台不接管 Data、News、Research 的领域规则和数据所有权。

## 2. 目标架构：公共组件与公共服务分层

### 2.1 组件层

组件层以 Go package / SDK 形式存在，由各业务进程内嵌使用。组件和公共管理能力统一在独立分支 `feat/platform-foundation` 开发、测试和维护；经契约验收后再集成到服务端主线。首期建议覆盖：

| 组件 | 职责 | 是否需要独立进程 |
|---|---|---|
| Security Middleware | 认证、授权、身份上下文、路由策略 | 否 |
| Config | 类型化配置、默认值、环境变量、校验 | 否 |
| Secret Provider | Secret 读取接口、脱敏、轮换适配 | 否 |
| Logger | 结构化日志和字段规范 | 否 |
| Trace | Request ID、Trace Context 传播 | 否 |
| Error | 统一错误分类、错误码和映射 | 否 |
| HTTP Client | 超时、请求限制、重试、并发控制、调用记录 | 否 |
| DB / Redis Bootstrap | 连接池、生命周期、基础健康检查 | 否 |
| Diagnostics SDK | 检查项注册、执行上下文、标准结果 | 否 |
| Metrics | 请求量、错误率、耗时和业务指标接口 | 否 |
| Idempotency | 幂等键、执行状态和重复请求保护 | 否 |

组件不得直接导入业务模块。公共组件只依赖 Go 标准库或少量经过评估的基础库，不依赖 News、Quant、Research 等业务包。

### 2.2 公共管理能力

首期只保留必要的集中管理能力：

| 能力 | 首期形态 | 后续是否可能独立部署 |
|---|---|---|
| 服务身份与 Key 管理 | 管理 API + 持久化 Repository | 视服务数量和运维需求决定 |
| 诊断聚合 | 统一注册与查询入口 | 是，若跨进程诊断和历史查询需要独立生命周期 |
| 配置管理 | 环境配置 + 类型化加载；敏感配置由 Secret Provider 提供 | 暂不需要 |
| 任务执行 | 进程内 Runner + MariaDB 状态记录，必要时 Redis 协调 | 任务量和跨进程需求达到阈值后再拆 |
| 可观测性 | 统一埋点与导出接口 | 不自建存储，复用现有监控设施 |

### 2.3 推荐逻辑结构

~~~
外部调用方
   │
   ▼
Server API / Transport
   ├── Request ID / Trace
   ├── Recovery / Body Limit
   ├── Authentication
   ├── Authorization
   ├── Rate Limit
   └── API Handler
          │
          ▼
Application / Use Cases
   ├── Data
   ├── News
   ├── Research
   └── Notification
          │
          ▼
Platform Components
   ├── Config / Secret
   ├── Logger / Trace / Error / Metrics
   ├── HTTP Client
   ├── Diagnostics
   ├── DB / Redis Bootstrap
   ├── Task / Idempotency
   └── Audit
          │
          ▼
MariaDB / Redis / External Providers / Existing LLM Service
~~~

图示是逻辑依赖，不要求把每个方框拆成独立服务。业务模块只能通过明确的 Port / Interface 使用公共能力，不得跨模块直接访问对方的 Repository。

## 3. 代码归属、分支协作与集成原则

### 3.1 当前分支约束

本项目已有数据、新闻、分析和 WebUI 多条开发线。公共平台不能被默认塞入新闻或分析业务分支，也不能让各业务分支复制一份实现。

当前建议：

| 分支 | 主要职责 | 与公共平台的关系 |
|---|---|---|
| feat/design_doc | 项目级架构、任务、边界和验收规则 | 维护本方案，不承载业务代码 |
| feat/full-go-data-providers-api-switch | Go 服务端公共基线、数据服务和最终服务端集成 | 公共平台首期唯一实现归属，避免多分支重复改公共入口 |
| feat/research-news-ingestion | 新闻采集、标准化、存储、搜索和新闻诊断 | 按冻结接口接入；不自行实现认证、日志、HTTP Client 和公共诊断框架 |
| feat/research-analysis-flow-native-go | Quant、Context、Evidence、研究编排和 Notification | 按冻结接口接入；不自行实现公共基础设施 |
| feat/webui-market-data-console | WebUI | 只消费 Server API，不直接调用内部服务或公共组件 |

上述归属遵循现有项目总览中“服务端公共基线集中治理”的约束。新闻和分析分支可以先完成领域代码，但在平台接口尚未冻结前，不应各自创建另一套公共实现。

### 3.2 是否新建 platform-foundation 分支

当前不创建新分支，也不把它作为开发前置条件。

理由：

1. 多条分支已有不同基线，新增分支会增加共同祖先、同步和冲突治理成本。
2. 当前总览已经将服务端公共基线和最终集成归入数据侧 Go 服务分支。
3. 公共平台首批改动集中在新增包和少量启动装配，能够通过目录所有权降低冲突。
4. 如果后续公共平台工作量明显超过数据分支可承载范围，再以已同步的共同基线评估独立分支；不能先创建分支再解决基线问题。

### 3.3 高冲突文件保护

以下文件视为公共集成区，非必要不修改：

- cmd/**/main.go
- 各服务 bootstrap / wiring / DI 注册入口
- internal/domain/** 和跨模块 contracts
- internal/ports/** 公共接口
- HTTP 路由总注册
- Migration 总注册入口
- Docker Compose、根部署文件和 CI 主工作流

平台首批实现应优先新增 internal/platform/** 下的独立包。确需改启动入口时，按一个完整集成批次修改，不要分支之间同时编辑同一入口。

### 3.4 分支接入规则

1. 平台先发布接口契约和最小接入示例。
2. News / Research 可以先用本模块 Adapter 或测试替身开发，但不得复制平台实现。
3. 公共平台合入共同服务端基线后，再统一替换临时 Adapter。
4. 接入方必须提供自己的路由策略、诊断检查项和业务错误映射。
5. 平台接口变化必须记录兼容策略和受影响模块；禁止未经协调修改公共结构体字段语义。

## 4. 公共安全体系（PLAT-003 / PLAT-004）

安全是首个必须统一的公共能力。新闻分支已提出安全中间件需求，因此需要先定义适用于所有内部模块的安全契约。

### 4.1 身份类型必须分开

| 身份类型 | 用途 | 凭证 | 不允许的混用 |
|---|---|---|---|
| 外部用户身份 | 用户访问 Server API | 由当前实际用户认证方案提供 | 不得用服务 API Key 伪装用户登录 |
| 管理员身份 | 管理服务 Key、配置和敏感操作 | 独立管理凭证或受保护管理会话 | 不得把管理 Key 作为普通业务 API Key |
| 内部服务身份 | Server 调用 News、任务 Worker 调用内部模块 | 独立 Service Key / 服务身份 | 不得复用用户 Cookie |
| 外部 Provider 凭证 | Tushare、新闻源、通知渠道等上游认证 | 各 Provider Secret | 不得作为内部服务身份 |
| 任务执行身份 | 后台任务代表哪个服务/用户发起 | 任务创建时记录的主体与授权快照 | 不得丢失发起者和权限来源 |

当前若尚无完整用户体系，外部用户认证可以暂由现有反向代理或 Server 认证方案承担，但必须明确边界；公共 Security SDK 不应擅自创建一套新的用户登录系统。

### 4.2 认证机制

首期内部服务认证建议采用独立 Service Key：

- 每个服务、每个环境使用独立 Key，不共享一个全局万能 Key。
- Key 由随机高熵材料生成，使用 Key ID 定位；服务端只持久化不可逆摘要，不存明文。
- 创建时只展示一次明文 Key，后续只能轮换或撤销。
- 支持启用、禁用、过期、轮换和短暂双 Key 过渡。
- Key 必须绑定服务身份、允许的 audience、scope 和环境。
- 比较摘要时使用常量时间比较；错误响应不泄露 Key 是否存在。
- Key 不进入 URL、日志、Trace、错误消息或诊断详情。
- 服务间调用使用专用 Header；不得信任客户端直接传入的 X-User-ID、X-Service-Name 等身份头。
- 只有通过认证的主体才能由中间件写入可信 Context。

若内部服务未来跨越不可信网络或需要抵抗重放攻击，再增加短时 HMAC 请求签名（method、path、timestamp、nonce、body digest）或 mTLS。首期不要同时引入 JWT、HMAC、mTLS 三套机制，避免实现复杂度超过实际威胁模型。

### 4.3 授权模型

首期使用基于 Scope 的最小授权，避免一开始建设复杂 RBAC：

- data:read、data:diagnose
- news:read、news:search、news:ingest
- research:run、research:read
- notification:send、notification:manage
- platform:diagnose、platform:service-key:manage
- platform:config:read、platform:config:write

实际 Scope 必须按路由和操作逐项核对，不应直接把表中示例全部开放。

授权规则：

1. 默认拒绝，显式授权。
2. 认证通过不等于授权通过。
3. 读、写、管理、诊断操作分开。
4. 管理凭证不得自动拥有所有业务权限。
5. 任务执行时记录主体、scope、发起来源和授权快照。
6. 内部服务不能仅凭 service identity 获得所有资源权限。
7. 管理操作必须产生审计事件。

### 4.4 中间件顺序

推荐统一 HTTP 中间件顺序：

1. Request ID / Trace Context 提取或生成。
2. Panic Recovery。
3. 请求体大小限制、Header 和超时限制。
4. 安全访问日志（先脱敏）。
5. CORS（仅对浏览器入口配置，不作为认证机制）。
6. Authentication。
7. Authorization。
8. Rate Limit / 并发限制。
9. Idempotency（仅对需要幂等的写操作）。
10. Handler。

公开路由只允许明确列入白名单的 health/readiness 或必要的公开 API；管理接口不能因为位于 /internal 或 /admin 路径就自动豁免认证。

### 4.5 网络与部署边界

- 公网只暴露 Server API / WebUI 所需入口。
- News、诊断管理、内部 Worker 等接口默认只绑定内网或 Docker 私有网络。
- 反向代理负责 TLS 终止、基础来源限制和必要的边缘防护；应用中间件仍必须验证身份。
- 容器网络隔离不能替代应用层认证。
- 禁止把内部管理端口映射到公网。
- 生产 Secret 不写入镜像、Compose 明文仓库文件或 Git。
- 管理接口必须有独立路由策略和审计。
- 代理转发的身份头必须由可信代理覆盖，应用不得盲信外部传入值。

### 4.6 安全审计

至少记录：

- actor_id / service_id
- credential_id（不记录 Secret）
- action / resource
- request_id / trace_id
- source_ip（按隐私和部署策略处理）
- result / deny_reason
- timestamp / duration
- key lifecycle operation（创建、轮换、撤销、禁用）

不得记录 Authorization、Cookie、完整请求体中的 Secret、Provider Key 或用户敏感内容。

### 4.7 安全失败策略

- 认证组件初始化失败：受保护路由启动失败或全部拒绝，不能静默降级为匿名访问。
- Key 存储不可用：已有可验证的短期缓存可按明确策略使用；缓存过期后 fail closed。
- 授权信息缺失：拒绝访问。
- 时钟偏差、过期、签名无效：拒绝并给出不泄露细节的错误。
- 安全审计暂时不可写：敏感管理操作应失败关闭；普通只读请求可按审计等级和本地缓冲策略处理，但必须有可观测告警。

## 5. 配置与 Secret 管理（PLAT-005）

### 5.1 配置分类

| 类型 | 示例 | 管理方式 |
|---|---|---|
| 非敏感运行配置 | HTTP 地址、超时、并发数、开关 | 类型化配置 + 环境变量 |
| Secret | DB 密码、Service Key、Provider Token、Webhook Secret | Secret Provider；首期可由部署环境注入 |
| 业务配置 | Provider 优先级、新闻源启停、通知订阅 | 归属对应业务模块，不混入 Platform 全局配置 |
| 动态运营配置 | 限流阈值、任务并发上限 | 只有确有热更新需求时才引入管理 API |

### 5.2 加载优先级

建议固定为：

默认值 < 配置文件（如启用） < 环境变量 < 部署平台 Secret 注入。

不允许业务代码在运行时随意读取 os.Getenv。环境变量读取集中在配置装载层，其他模块接收已校验的配置结构体。

### 5.3 启动校验

- 必填项缺失时明确报错并阻止依赖该配置的能力启动。
- URL、端口、超时、并发、TTL、枚举值进行类型和范围校验。
- 未配置的可选 Provider 标记 not_configured / skipped，不伪装成连接失败。
- Secret 日志统一显示是否配置，不显示值、长度或可逆片段。
- 配置快照记录版本/摘要，不记录 Secret 明文。
- 首期不做全局热更新；确需动态更新的配置按模块明确一致性和生效时点。

### 5.4 Secret 生命周期

1. 创建：随机生成或由外部密钥系统注入。
2. 保存：生产环境优先使用部署 Secret；若必须存 DB，只存不可逆摘要或加密后的密钥材料，并明确密钥加密主密钥来源。
3. 使用：通过 Secret Provider 获取，限制调用范围。
4. 轮换：支持新旧凭证短期并行，验证新 Key 后撤销旧 Key。
5. 撤销：立即阻断新请求，清理缓存并审计。
6. 泄露处置：撤销、轮换、检查日志/CI/镜像/备份，不能只改环境变量后认为结束。

## 6. 日志、错误、Trace 与审计（PLAT-006 / PLAT-012）

### 6.1 统一日志字段

结构化日志至少包含：

- timestamp、level、service、environment、version
- request_id、trace_id、span_id（有 Trace 时）
- route、method、status_code、duration_ms
- actor_id 或 service_id（脱敏/稳定标识）
- error_code、error_category
- task_id、run_id（适用时）
- dependency、provider、attempt（外部调用适用时）

日志分级：

- DEBUG：开发期细节，生产默认关闭或采样。
- INFO：关键业务阶段、状态变化。
- WARN：降级、可恢复错误、质量不足。
- ERROR：请求或任务失败。
- FATAL：仅进程无法安全启动或继续运行的致命错误。

禁止记录密钥、Cookie、完整 Authorization、数据库 DSN、未经脱敏的用户数据和大段原始新闻/模型上下文。

### 6.2 统一错误模型

建议错误结构包含：

- code：稳定机器可读错误码。
- category：validation / authentication / authorization / configuration / dependency / timeout / rate_limit / data_quality / conflict / internal。
- message：面向调用方的安全摘要。
- retryable：是否允许重试。
- dependency：失败依赖（适用时）。
- request_id / trace_id。
- details：受控字段，不得包含 Secret 或内部堆栈。

HTTP 映射要稳定：参数错误 400、未认证 401、无权限 403、资源不存在 404、冲突 409、限流 429、依赖超时 504、服务内部错误 500/503。不能把所有错误都包装成 200 或 500。

### 6.3 Trace 传播

- HTTP 使用标准 traceparent；没有上游 Trace 时生成 Request ID。
- 内部服务调用、异步任务和通知投递要传播 trace/task/run 关联 ID。
- 不允许将用户可控的任意 Trace ID 当作身份或授权依据。
- Trace 采样策略可配置；高错误率和慢请求可提高采样。
- 不把完整业务数据、新闻全文、Prompt 或模型响应写入 Span Attribute。

### 6.4 审计与普通日志分离

安全审计、业务事件和调试日志是不同数据类型：

- 普通日志用于排障。
- 审计记录用于回答主体、操作、资源和结果。
- 业务事件用于通知和异步处理。

审计记录需要持久化、不可随普通日志轮转策略丢失；首期可复用 MariaDB，但应有独立表、保留期限和访问权限。

## 7. 统一诊断框架（PLAT-007）

诊断是横向公共能力，不由 Platform 替业务模块判断业务正确性。每个模块注册自己的检查项，公共框架负责调度、状态归一、结果保存和聚合展示。

### 7.1 诊断层级

| 层级 | 检查内容 | 示例 |
|---|---|---|
| L1 Liveness | 进程是否存活 | healthz、goroutine/主循环状态 |
| L2 Readiness / Dependency | 是否具备基本服务条件 | DB、Redis、内部 API |
| L3 Capability | 业务能力能否执行 | Provider 查询、新闻搜索、通知测试发送 |
| L4 Data Quality | 结果是否可信 | 覆盖率、日期、字段完整性、时间新鲜度、异常值 |

L1 不应因可选 Provider 不可用而失败；L2 应按关键依赖判定；L3/L4 允许模块级 degraded。

### 7.2 统一状态

- healthy：检查通过且满足定义的质量要求。
- degraded：可工作但存在降级、覆盖不足或质量限制。
- unavailable：关键能力无法提供。
- skipped：未执行，通常是未配置或前置条件不满足。
- failed：检查本身执行失败或发现明确错误。

skipped 不是成功，也不能算作失败；not_configured 应作为明确原因。

### 7.3 Check 契约

每个 Check 至少声明：

- check_id、module、name、description
- level、criticality
- required_config / dependencies
- timeout、执行成本和是否有副作用
- input parameters（受限、脱敏）
- result status、reason codes
- checked_at、duration_ms
- evidence / sample summary
- implementation_version

主动 Probe 必须有并发限制、超时、速率限制和副作用说明。默认诊断不应触发大规模全市场采集或发送真实通知。

### 7.4 执行模式

- 被动诊断：读取运行状态、最近调用结果和缓存指标，成本低。
- 主动 Probe：真实调用依赖，验证当前能力。
- 数据质量检查：检查样本和数据集的字段、时间、覆盖率和异常。
- 历史诊断：保留运行结果，支持比较变化和定位回归。

### 7.5 聚合规则

不能简单对所有 Check 做 AND：

- 关键依赖失败可使服务 unavailable。
- 可选 Provider 未配置应为 skipped，不拖垮整体 readiness。
- 关键 Provider 全部失败时，相关数据能力 unavailable。
- 多 Provider 仅部分可用时，按能力覆盖和质量标为 degraded。
- 数据质量失败不能被网络连通成功覆盖。
- 聚合结果必须展示原因和受影响能力。

### 7.6 诊断安全

诊断接口需要鉴权和 scope；Provider Probe 有资源限制；结果中的 URL、错误和响应片段需要脱敏；任何检查都不能返回 Secret。

## 8. HTTP Client 与外部依赖治理（PLAT-008）

所有跨进程 HTTP 和外部 Provider 调用应通过统一 Client Policy 或经过审查的适配器，不要求把所有业务请求塞进一个万能 Client。

### 8.1 必须统一的策略

- connect / TLS / response header / total timeout。
- 最大响应体和最大 Header。
- 最大并发、每依赖并发隔离。
- 重试次数、退避、随机抖动。
- 429 / Retry-After 处理。
- 请求和响应脱敏。
- Request ID / Trace 传播。
- 错误分类和耗时统计。
- 连接池与优雅关闭。

### 8.2 重试规则

- 只对明确可重试错误重试，如临时网络错误、部分 5xx、429。
- 默认只自动重试幂等请求。
- POST 写操作只有在支持 Idempotency-Key 或业务幂等时才能重试。
- 不对参数错误、认证失败、授权失败、数据质量错误重试。
- Provider 级重试预算必须受总任务 deadline 约束。
- 禁止 HTTP Client、业务 Adapter、任务 Runner 三层各自重试造成重试风暴。

### 8.3 故障隔离

首期先实现每依赖并发上限、超时和有限重试。熔断器只有在有稳定指标、明确恢复策略和测试覆盖后再启用；不要为了架构完整提前引入难以调参的复杂熔断状态机。

## 9. MariaDB、Redis 与 Migration 规范（PLAT-009）

### 9.1 数据所有权

- 各领域拥有自己的表和 Repository。
- Platform 只拥有服务身份、审计、必要任务元数据、诊断历史等平台数据。
- News 不直接写 Research 表；Research 不直接写 News 内部表。
- 跨模块数据通过 API、Port 或只读查询契约获取。
- 不建立一个跨领域万能 Repository。

### 9.2 MariaDB

- 统一连接池配置和生命周期；每个进程避免重复创建多个无管理连接池。
- 事务边界由应用用例或领域 Repository 明确控制。
- 所有 Migration 有唯一编号/命名空间、版本记录和可重复执行策略。
- 破坏性 Migration 必须有备份、兼容窗口和回滚/前滚方案。
- 禁止多个分支同时改同一个 Migration 注册入口。
- Schema 变更必须包含索引、唯一约束、数据量和查询路径评估。
- MariaDB 是业务事实源；缓存失效不能导致事实数据丢失。

### 9.3 Redis

- 统一 Key 前缀：环境 / 服务 / 领域 / 资源 / 版本。
- 每个 Key 必须有 owner、用途、数据类型、TTL 和失效策略。
- 缓存 Key 与任务协调 Key 分区命名。
- 除明确需要外，禁止无 TTL 的临时 Key。
- 分布式锁必须有租约、唯一持有者标识和安全释放逻辑；不能只靠 SETNX 后永久持有。
- Redis 故障时，缓存可降级；如果任务协调或限流依赖 Redis，则应按该能力的关键性明确拒绝或降级。
- 禁止把 Redis 缓存当作唯一研究结果或财务事实存储。

### 9.4 Migration 协作

- 先盘点现有 Migration 机制，不引入第二套迁移工具。
- 每个领域维护自己的 Migration 文件，但统一注册、执行顺序和版本记录。
- 分支开发期间可新增独立 Migration 文件；合入时统一核对编号冲突。
- 禁止启动时多个模块并发执行相互依赖的 Schema Migration。
- 数据迁移与代码发布分阶段进行，优先 Expand → Migrate → Contract。

## 10. 异步任务、幂等和调度（PLAT-010）

异步任务是研究分析、新闻采集、诊断和通知的共同需求，但首期不建设通用工作流平台。

### 10.1 首期任务抽象

任务接口需要明确：

- task_id、task_type、owner_module
- submitted_by / actor / service identity
- payload_version、payload reference
- status、priority
- created_at、started_at、finished_at
- deadline、timeout
- attempt、max_attempts
- idempotency_key
- cancel_requested_at
- error_code、error_summary
- trace_id、parent_task_id

状态建议：

- queued
- running
- succeeded
- failed
- retry_wait
- cancel_requested
- cancelled
- timed_out

状态转换必须由状态机控制，禁止业务模块随意写任意状态。

### 10.2 执行模型

首期采用轻量 Runner：

- MariaDB 保存任务事实状态和执行历史。
- Redis 可用于短期队列、租约或并发协调，但不作为唯一任务事实源。
- Worker 有并发上限、租约和超时。
- 任务执行需要 context cancellation。
- 进程退出后能够识别过期 running 任务并按策略恢复。
- 重试采用有限次数和退避。
- 同一 idempotency_key 在约定范围内只产生一次有效业务效果。

### 10.3 任务与业务事件解耦

通知、研究完成、新闻入库等业务事件不应直接依赖一个 HTTP 请求持续存活。

需要评估 Outbox Pattern：业务事务内写入业务记录和 Outbox 事件，后台投递后标记完成。首期若任务量较小，也必须至少保证“先持久化业务状态，再投递”的可恢复性。

### 10.4 不在首期建设

- 任意 DAG 工作流编辑器。
- 多租户任务调度平台。
- 跨地域分布式调度。
- Kafka 消费组式通用事件平台。

## 11. Metrics 与运行可观测性（PLAT-011）

首期统一指标名称、标签和导出接口，不要求自建监控数据库。

### 11.1 基础指标

- HTTP 请求数、状态码分布、P50/P95/P99 延迟。
- 依赖调用成功率、超时率、重试次数。
- DB/Redis 连接池状态和错误数。
- Worker 队列长度、任务等待时长、执行时长、失败数。
- Diagnostics 各状态数量和最近执行时间。
- Notification 投递成功率、失败和积压。
- Provider 请求量、限流、数据覆盖率和质量状态。

### 11.2 标签约束

- 标签必须有界；禁止把 symbol、request_id、task_id、用户输入等高基数字段作为 Metrics Label。
- 高基数标识放日志或 Trace。
- 关键错误要能通过 request_id / trace_id 关联日志。
- 业务指标需要注明统计口径、时间窗和分母。

### 11.3 告警

先覆盖服务不可用、关键依赖故障、任务积压、通知持续失败、诊断连续 degraded/unavailable 和错误率异常。告警投递通过 Notification，不在 Metrics 组件里实现渠道发送。

---

## 12. Notification 的边界

Notification 是公共业务能力，不是 Security / Config / Logger 这类底层组件。它可以被 Data、News、Research 和 Platform 诊断共同调用，但应保留自己的业务模型和投递生命周期。

Notification 首期可在分析分支独立开发，使用接口隔离公共基础依赖：

- Notification Request / Event。
- Template Renderer。
- Channel Adapter。
- Dispatcher。
- Delivery Repository。
- Retry / Idempotency。
- Delivery Status API。

平台负责提供认证、配置、日志、Trace、HTTP Client、任务和审计组件；Notification 自己负责渠道、模板、订阅、投递状态和发送语义。

通知发送必须考虑幂等、渠道限流、超时、失败重试和敏感内容脱敏。诊断测试发送必须显式指定测试目标，不得默认群发真实订阅者。

## 14. 独立分支开发、集成与协作策略

### 14.1 分支职责

- `feat/platform-foundation`：公共平台唯一实现分支，负责 PLAT 任务代码、公共契约、组件测试、平台自身文档和版本变更；不负责 Data、News、Research 的领域业务。
- `feat/full-go-data-providers-api-switch`：数据服务与 Provider 主线，同时承担公共平台的最终服务端集成；负责在平台能力稳定后集成公共组件、启动装配、路由和 Migration 注册，不再独占平台组件实现。
- `feat/research-news-ingestion`：按已冻结契约接入平台安全、配置、日志、HTTP 和诊断能力；不得复制平台实现，也不得直接依赖平台分支的临时内部路径。
- `feat/research-analysis-flow-native-go`：按已冻结契约接入平台能力；Notification 仍由分析领域负责，LLM Gateway 继续复用现有独立服务。
- `feat/webui-market-data-console`：只消费服务端最终确认的 API，不直接依赖平台内部接口。

### 14.2 开发与集成规则

1. 平台分支从当前服务端主线的明确基线创建；每次开始工作先记录平台分支 HEAD 和服务端集成分支 HEAD。
2. 平台分支优先交付可独立编译、可单测的组件和契约，不直接修改业务分支文件。
3. 公共 API、错误码、身份上下文、诊断状态、配置结构和 Migration 约定必须通过契约测试固定；未冻结的内部实现不得成为跨分支依赖。
4. 平台分支不直接修改服务端主线的启动入口、全局 DI、路由总表和 Migration 总注册入口；由服务端集成分支在集成批次统一完成。
5. 业务分支可以并行开发领域代码和 Adapter，但只能依赖已冻结的公共接口；接口未冻结时先使用本地 Port/Adapter 隔离，不复制平台实现。
6. 集成采用平台分支 → 服务端集成分支 → News/Research 接入分支的顺序；先集成组件，再接入管理 API 和持久化变更，最后完成跨模块验收。
7. 每次集成前检查共同祖先、双方 HEAD、冲突文件、Go module/import 路径、Migration 编号、路由和 DI 重复注册。
8. 平台分支的合并不等于 PLAT 任务全部完成；每项任务仍需完成对应业务接入与验收。
9. 禁止平台分支与数据侧分支同时重构同一个公共入口；遇到入口级变更先由集成分支确定唯一修改批次。

## 15. 实施阶段与依赖顺序

### 阶段 0：现状盘点和接口冻结

目标：明确已有实现、重复实现、缺口和真实接入方。

- 检查 Go Core、行情服务、新闻分支、分析分支的当前 HEAD。
- 盘点认证、配置、日志、错误、Trace、HTTP Client、DB/Redis、诊断、任务和 Migration。
- 列出每个组件的路径、调用方、依赖方、测试、运行状态和缺口。
- 明确 News 安全中间件需求对应的路由、身份类型和 Scope。
- 冻结最小公共接口，先不做目录大搬迁。

出口：形成现状矩阵和公共契约；没有明确归属的组件不进入实现。

### 阶段 1：P0 安全与运行规范

并行但按接口先后推进：

1. Security Middleware / Service Identity。
2. Config / Secret。
3. Logger / Error / Request ID / Trace。
4. Diagnostics Contract / Registry。
5. News 接入安全中间件的契约验证。

出口：受保护路由默认拒绝；日志脱敏；诊断状态统一；News 能按最小权限调用内部 API。

### 阶段 2：外部依赖与存储规范

1. HTTP Client Policy。
2. MariaDB / Redis Bootstrap 与 Key 规范。
3. Migration 统一约定。
4. Metrics 基础指标。
5. 现有 Data / News / Research 逐步接入。

出口：外部调用超时、重试、并发、错误分类一致；DB/Redis 生命周期和故障行为明确。

### 阶段 3：异步任务和可恢复执行

1. Task Contract / State Machine。
2. MariaDB Task Repository。
3. Redis 协调（若验证需要）。
4. Worker Lease / Timeout / Retry / Cancel。
5. Outbox 与 Notification 对接。

出口：任务可追踪、可重试、可取消、可恢复；重复提交不会造成重复业务效果。

### 阶段 4：可观测性和治理完善

1. Metrics 导出。
2. 诊断历史和趋势。
3. 审计查询和保留策略。
4. 故障演练。
5. 安全配置、Key 轮换和恢复流程文档。

出口：能从一次请求追踪到依赖、任务和结果；关键异常有指标和告警。

### 15.1 首批交付边界

首批只交付：

- PLAT-001：现状盘点。
- PLAT-002：最小契约与边界。
- PLAT-003：Security Middleware。
- PLAT-004：Service Key 生命周期的必要部分。
- PLAT-005：Config / Secret 规范。
- PLAT-006：Logger / Error / Trace。
- PLAT-007：Diagnostics 基础契约和注册。

首批不要求实现完整 IAM、动态配置中心、独立诊断集群、复杂任务系统或全套 Metrics 平台。

### 15.2 与其他任务的关系

- News 的安全中间件接入依赖 PLAT-003/004，不要求 News 自己实现 Key 管理。
- Data 现有诊断能力应复用 PLAT-007 的状态和 Check 契约，不要求重写 Provider Probe。

- Context / Evidence 的领域模型不依赖平台具体实现，但持久化和跨服务组装依赖 PLAT-009/010 及领域契约。
- LLM Gateway 暂缓；先保留既有独立服务，后续由 Analysis Adapter 接入，不纳入本批平台建设。

## 16. 验收矩阵

### 16.1 安全验收

- 无凭证访问受保护路由返回 401。
- 有效身份但缺少 Scope 返回 403。
- 已撤销、过期或禁用 Key 不能继续访问。
- 不同服务的 Key 不能互相冒用。
- 管理 Key 不能作为普通 Service Key 使用。
- 客户端伪造身份 Header 不改变可信身份。
- Key 只在创建时展示一次，存储和日志无明文。
- Key 轮换期间新旧 Key 的有效窗口符合配置，撤销后缓存及时失效。
- 未认证请求不能访问诊断管理和内部管理接口。
- 安全审计能追踪成功和拒绝操作。

### 16.2 配置和可观测性验收

- 缺少必需配置时启动失败并指出字段名，不输出 Secret。
- 非法超时、URL、并发和 TTL 能被拒绝。
- Request ID 在请求响应和日志中一致。
- Trace Context 能在内部调用传播。
- 错误码和错误分类稳定。
- Authorization、Cookie、Provider Key、Webhook Secret 不出现在日志和 Trace。
- Metrics 不包含高基数 symbol / task_id / request_id 标签。

### 16.3 诊断验收

- 未配置 Provider 显示 skipped / not_configured。
- 网络失败显示 failed 或 unavailable，按 Check 语义归类。
- HTTP 可连通但字段不完整，不能显示 healthy。
- 部分 Provider 可用时显示 degraded，并说明能力覆盖。
- Probe 有超时、并发限制和调用审计。
- 诊断结果可追溯 Check 版本、执行时间和失败原因。

### 16.4 HTTP / DB / Redis / Task 验收

- 非幂等写请求不会被无条件自动重试。
- 总超时不会被多层重试无限放大。
- DB 连接池有上限、超时和关闭。
- Redis 缓存故障不导致已持久化事实丢失。
- Key 有明确 TTL 和 owner。
- Migration 编号冲突能在集成前发现。
- 任务崩溃后能识别过期 running 状态并按策略恢复。
- 重复 idempotency_key 不重复产生业务效果。
- 取消、超时和重试的状态转换符合状态机。

## 17. 风险与决策门槛

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 过早抽象公共平台 | 大量接口尚未稳定，导致二次重构 | 先盘点，先抽最小稳定接口 |
| 把组件全部拆成服务 | 部署、网络和故障面扩大 | 组件优先，按独立生命周期决定部署 |
| 所有业务共用万能 Service Key | 任一泄露影响全部模块 | 每服务/环境独立 Key 和 Scope |
| 只依赖内网隔离 | 横向移动或误配置导致越权 | 网络隔离 + 应用认证 + 最小授权 |
| 诊断主动 Probe 过重 | 触发大量 Provider 请求或真实通知 | 分级、超时、并发限制、明确副作用 |
| 多层重试叠加 | 请求风暴、重复写入 | 统一重试预算和幂等语义 |
| 任务状态只放 Redis | Redis 故障导致任务事实丢失 | MariaDB 保存事实状态 |
| 多分支同时改公共入口 | 冲突、注册遗漏、启动失败 | 单一公共实现归属，入口集中集成 |
| Migration 并发或编号冲突 | Schema 不一致 | 统一注册和发布顺序 |
| 过早引入复杂 IAM / 消息队列 | 开发和运维成本失控 | 以当前个人研究系统规模为基准，达到阈值再演进 |

### 17.1 必须重新评估的触发条件

出现以下任一情况，再评估将公共管理能力拆成独立服务：

- 多个 Go 进程需要共享服务身份和权限管理，且本地配置/缓存无法满足一致性要求。
- 诊断需要跨进程聚合、长期历史查询和统一调度。
- 任务需要多个独立 Worker、跨进程租约和可靠恢复。
- 需要多实例部署并发生共享状态竞争。
- 现有组件已成为明确的运维瓶颈，且独立部署能降低而非增加总复杂度。

## 18. 开发执行规则

1. 每项 PLAT 任务开始前，核对目标分支最新 HEAD 和现有实现路径。
2. PLAT-001/002 完成前，不大规模创建公共包或改造业务模块；平台代码只在 `feat/platform-foundation` 开发。
3. 安全中间件必须先满足 News 的最小接入场景，再扩展其他业务权限。
4. 不以“新增了 middleware 包”作为安全完成；必须通过认证、授权、Key 轮换、伪造 Header 和日志脱敏测试。
5. 不允许各业务分支复制平台实现；临时 Adapter 必须可删除。
6. 不同时修改多个分支的 main.go、wiring、路由注册和 Migration 总入口。
7. 先新增接口和适配，后替换调用，最后删除旧实现。
8. 每批按一个完整能力目标集中提交，不因单个小文件变更频繁提交。
9. 文档状态只记录已验证事实；没有运行时证据时标记待验收。
10. 公共平台不借机重构无关业务代码。
