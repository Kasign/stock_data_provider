# 统一时间服务设计与实施

- 适用分支：`integration`
- 首次实施基线：`2642457c708fae478d122256ebeddeff63d2f683`
- 目标：统一当前时刻来源、UTC 语义和 IANA 时区转换；不把服务器部署地域当作业务时区。

## 1. 时间语义

- Instant 表示全球唯一时刻，系统内部、持久化和跨服务接口统一使用 UTC。
- Local Time 是 Instant 在明确 IANA 时区下的表示，不是另一种时间源。
- 业务日历（交易日、自然日、营业时间）必须显式指定业务时区。
- 用户展示时区由 Server/用户配置决定，不继承服务器本地时区。
- 固定偏移量不能代替 IANA 时区；例如使用 `Asia/Shanghai`，不使用 `UTC+8` 作为时区标识。
- 超时和耗时测量使用单调时钟/Context Deadline；不可用墙上时钟差值计算耗时。

## 2. Platform API

通用 API 归属：`internal/platform/time/`；数据库适配器按技术实现隔离在 `internal/platform/time/mariadb/`。

- `Source`：权威当前时刻来源接口。
- `SystemClock` / `SystemSource`：读取操作系统时钟，适用于普通本地时间需求；不保证跨主机一致。
- `time/mariadb.Source`：通过 `UTC_TIMESTAMP(6)` 读取数据库时钟，适用于 Run 创建、Deadline、Lease 等跨实例协调场景；SQL 查询、`database/sql` 接口和解析逻辑均封装在该适配器包中。
- `Service.NowUTC(ctx)`：读取当前 UTC Instant。
- `Service.NowIn(ctx, timezone)`：读取同一当前 Instant 在指定 IANA 时区的表示。
- `ToLocal`、`LoadLocation`、`StartOfDay`、`AddCalendarDays`：统一转换与当地日历操作。

Platform 只提供时间原语，不决定业务时区，也不决定数据的 available_at、published_at 或 PIT 可用性。

## 3. 时钟准确性与权威来源

统一 API 不能修复错误的底层时钟。生产主机必须配置 NTP/Chrony 等系统时间同步；部署侧负责同步服务和运行状态。Platform 的 SystemSource 读取操作系统时钟，不自行访问公网时间 API。

跨实例一致性要求高的写入和状态迁移使用同一 MariaDB UTC 时钟。MariaDBSource 的结果仅代表数据库服务器当前报告的时间；数据库主机自身也必须同步时间。应用主机与数据库主机存在偏差时，以数据库时钟作为该类操作的权威来源。

时间同步偏差监控作为后续部署诊断接入项，不在本次原语中伪造 NTP 同步状态。当前没有 NTP/Chrony 运行证据，不得宣称时钟同步健康。

## 4. 调用边界

- Server 负责装配时间依赖。普通进程时间通过 Platform `SystemClock` 注入 Notification/Research 等需要简单 `Now()` 的端口；需要 UTC/时区转换的调用方使用 `Service`；跨实例协调继续注入 MariaDB Source。
- Researchflow 的 Run 创建、Deadline、Lease 等跨实例协调仍使用 MariaDB UTC；Repository 中仅用于状态转移合法性校验的临时时刻读取 Platform `SystemClock`，持久化时间戳仍由数据库生成。
- Research Outbox 投递调度（Claim/Lease/Confirm/Retry/Reject）统一以 MariaDB `UTC_TIMESTAMP(6)` 为权威时钟；Application 只传递 Lease Duration/Retry Delay，不传绝对截止时间。事件自身的 `occurred_at`、`published_at` 等领域时间仍按原有事务语义生成。Notification EventReceiver 等普通进程时间消费者仍可使用 Platform `SystemClock`。
- LLM 等普通本地时钟调用可以复用 Platform SystemClock；不为迁移而改变无关业务 API。
- News/Data/Quant 的业务时间字段继续由领域定义语义；Platform 不擅自把来源时间转换成 available_at。
- WebUI 不自行推断服务器或用户时区；需要展示当地时间时，使用服务端明确提供的时间和时区标识。

## 5. 存储与接口规范

- 数据库时间统一按 UTC 读写；具体 SQL 类型和驱动解析配置必须与现有 Repository 契约一致。
- API 时间使用 ISO 8601，必须携带 `Z` 或明确偏移量；禁止无时区的模糊时间字符串。
- 需要表达“当地日期”时，同时明确业务时区，不能只传递服务器本地日期。
- Run 的 `system_as_of` 是研究时间基准；`deadline_at` 是执行截止时间，两者语义独立。
- 当前时点研究由 Server 生成时间；未来历史 PIT 请求应把用户指定研究时点作为稳定业务意图，并验证数据时间证据。

本次完成 Platform 通用时间包、独立 MariaDB 适配器、固定时钟和时区单测，以及 Researchflow 现有 MariaDBDatabaseClock 的委托复用。`platform/time` 不再依赖 `database/sql`；Researchflow 事务内读取仍使用传入的 `*sql.Tx`，没有改变事务边界。未修改 Run 状态机、Deadline 策略、幂等指纹、数据库 Schema 或其他模块业务语义。

## 7. MariaDB 适配器边界复核（2026-11-17）

原 `internal/platform/time/mariadb.go` 将 `database/sql`、MariaDB 专用 SQL 和时间解析放在通用时间包内，造成通用 API 对具体数据库实现产生依赖。本次将其拆分为 `internal/platform/time/mariadb`：

- 通用 `time` 包只定义 `Source`、`Clock`、`Service` 和时区/日历操作，不导入 `database/sql`。
- MariaDB 适配器公开 `Source`、`NewSource`、`ReadUTC` 和 `ClockQuery`；`ReadUTC` 接受 `*sql.DB` 或 `*sql.Tx` 所满足的查询接口。
- Researchflow 的应用端口保持不变；Run 创建事务内的时钟读取继续使用同一事务，不引入额外连接或改变锁/提交顺序。
- 不强制普通本地时间消费者依赖 MariaDB；是否使用数据库权威时钟仍由具体用例决定。


## 8. Server 本地时钟消费者接入（2026-11-17）

- Server 不再在 Notification 与 Research Outbox 装配处直接创建 `time.Now()` 闭包，统一注入 Platform `SystemClock`。
- Research Storage 未显式提供 Clock 时，也使用 Platform `SystemClock` 作为默认值，保留原有可注入测试接口。
- Researchflow Repository 的 CAS 状态迁移校验改用 Platform `SystemClock`；这只是纯状态转移校验所需的临时时刻，真正写入的 `started_at/finished_at` 仍由 MariaDB `UTC_TIMESTAMP(6)` 生成。
- 这一步只统一进程时钟抽象，不代表跨实例时钟一致性由 SystemClock 保证，也不代表 NTP/Chrony 已完成部署验收。


## 9. Research Outbox 调度时钟收敛（2026-11-17）

- Research Outbox 的创建可用时间、Claim、Lease 截止时间、Confirm、Retry、Reject 全部由 MariaDB `UTC_TIMESTAMP(6)` 生成和校验，避免多实例应用主机时钟偏差影响投递互斥与重试时机。
- Application/Repository Port 只传递相对 `leaseDuration` 与 `retryDelay`；不再接收应用层计算的绝对时间。相对时长要求为正且精确到微秒，Service 继续保留 Lease/Retry 的业务范围校验。
- Outbox Repository 不再依赖 Platform `SystemClock`。`created_at`、`available_at`、`delivered_at`、`updated_at` 和 `lease_until` 使用数据库当前 UTC 时间及其相对时长计算。
- 仅改变 Outbox 投递调度时间来源，不改变事件 `occurred_at`、`published_at`、`system_as_of` 等业务时间语义，也不改变 Notification Inbox 的接收时间策略。
- MariaDB 集成测试使用真实数据库时钟验证应用时钟偏差、活动 Lease 不可重复领取、Retry 延迟生效、过期 Lease 的旧 token 无法 Confirm/Retry/Reject。


## 10. MarketData 时钟注入（2026-11-17）

- MarketData 的既有构造函数保持兼容，默认使用 Platform `SystemClock`；新增显式时钟注入构造入口，供确定性测试和后续 Server 装配使用。
- MarketSession 的 `server_time` 与 `fetched_at` 使用注入时钟，交易日期与时段判断仍使用明确的 `Asia/Shanghai` 业务时区。
- TradingCalendar 的 Provider 时间校验和缓存年龄判断使用同一注入时钟。缓存时间来自序列化快照，不包含单调时钟读数，因此使用 UTC Instant 差值判断 TTL；不能将此规则推广为进程内耗时测量。
- 本次不改动行情 Provider 时间字段、PIT `as_of` 语义及其他尚未完成盘点的时间调用。后续按具体时间语义逐项迁移，不进行全局机械替换。


## 11. MarketData 交易时区与日 K 上下文

- A 股业务时区通过 Platform 时间包加载 `Asia/Shanghai`，并在服务进程内缓存，避免重复加载。
- MarketData 服务包内嵌 Go 时区数据库，不再在加载失败时静默退化为固定 UTC+8；若时区数据仍不可用，明确失败，不以错误日期继续计算。
- 日 K 缺失上下文的历史日历判断使用 DataService 注入时钟；纯函数保留系统时钟兼容入口，测试可直接使用指定时刻。


## 12. MarketData 公司行动与证券状态时间

- 公司行动和复权因子的当前时间、PIT 未来时间校验统一使用 DataService 注入时钟；历史查询的 `as_of` 仍作为独立查询边界，不被当前时钟替代。
- 证券交易状态的交易日边界、修订观察时间和 Provider 快照时间校验使用统一时钟。
- 市场情绪快照的采集时间及默认交易日使用统一时钟和 `Asia/Shanghai`。


## 13. MarketData 基本面与估值时间

- 基本面和估值快照的 Provider 时间、发布日期、缓存年龄与 PIT 未来时间边界使用 DataService 注入时钟。
- 纯校验函数保留系统时钟兼容入口，服务调用显式传入当前时刻，确保同一请求的时间判断可测试。


## 14. MarketData 公告、热榜与资金流时间

- 公告日期范围默认值使用 A 股业务时区和 DataService 注入时钟；公告 Provider 时间与发布时间校验使用同一时间基准。
- 热榜和市场资金流快照的 Provider 时间验证、缓存年龄判断统一使用注入时钟。


## 15. MarketData 指数目录与指数历史

- 指数目录、成分股和指数日 K 的 Provider 时间、报告日期、缓存年龄及历史区间观察时间校验使用 DataService 注入时钟。
- 指数历史查询日期仍按 `Asia/Shanghai` 业务日期解释，PIT 查询时间不由当前时间覆盖。


## 16. MarketData Provider Probe 时间

- Probe 报告开始、结束和检查时间统一使用 DataService 注入时钟。
- Probe 单项耗时仍使用单调时钟测量，且不把墙上时钟差当作执行耗时。
- 日 K Probe 日期范围使用 A 股业务时区和注入时钟校验。


## 17. MarketData 市场股票与涨跌停事件

- 市场股票快照的服务采集时间使用 DataService 注入时钟。
- 涨跌停特殊事件的交易日边界和 Provider 证据时间校验使用统一时钟。


## 18. MarketData 复权重建与交易规则时钟

- PIT 复权因子重建使用 DataService 注入时钟筛选系统观察时间和可用时间，避免重建逻辑自行读取系统时钟。
- 独立交易规则纯函数保留无参数兼容入口，并通过 Platform SystemClock 获取当前时刻。
- TradingCalendar 的纯校验兼容入口也使用 Platform SystemClock；DataService 正常路径继续显式传入注入时钟。

## 19. MarketData Provider 时钟与时区边界

- Provider 的 UTC 采集时间、规范化时间、默认日期和请求缓存参数统一通过 Platform `SystemClock` 获取。
- Provider 的 A 股本地时间解析统一使用内嵌 IANA `Asia/Shanghai`，不再使用固定 UTC+8 代替地区时区。
- Provider 保留的 `time.Now` / `time.Until` 仅用于限流时间点，`time.Since` 仅用于真实执行耗时；这些场景依赖单调时钟语义。跨调用保存的时间戳年龄使用 UTC Instant 差值。
- MarketData Quote 保留策略的数据库清理截止时间使用 Platform `SystemClock`；周期调度器和上下文超时继续使用单调时钟语义。


## 20. MarketData HTTP API 时钟注入

- HTTP API Server 默认使用 Platform SystemClock，并提供显式时钟注入构造入口。
- API 的默认市场会话时刻、批量行情采集时间、健康响应时间及 PIT 非未来校验使用 Server 时钟。
- API 对 A 股交易日期的边界判断统一使用 MarketData Asia/Shanghai 时区，不再使用固定 UTC+8 回退。
- 请求耗时统计继续使用单调时钟；Request ID 的随机生成仍以密码学随机数为主。


## 21. BaoStock 季度报告期时钟

- BaoStock 季度财务查询的当前年份边界、报告期未来日期校验和退出协议时间戳使用 Config 注入的 Platform Clock；协议时间戳明确按中国市场时区格式化。
- 中国市场日期统一通过 MarketData 内嵌 IANA `Asia/Shanghai` 时区计算，不再回退到固定 UTC+8。
- TCP 连接与请求截止时间继续使用单调时钟语义，不通过业务时钟注入。


## 22. MarketData PIT 修订观察时间

- DailyBar、Fundamentals、Valuation、AdjustmentFactor、CorporateAction 和 SecurityTradingStatus 的 `recorded_at` 由 MariaDB `UTC_TIMESTAMP(6)` 生成，避免多实例应用时钟偏差改变 PIT 修订顺序。
- Provider 的 `fetched_at`、`available_at` 仍保留来源语义，不使用数据库当前时间覆盖。
- PIT 查询的 `as_of` 是调用方给定的 UTC Instant；它与数据库记录的观察时刻比较，不改变历史时间边界。
