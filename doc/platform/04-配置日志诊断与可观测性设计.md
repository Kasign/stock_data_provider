# 配置、日志、诊断与可观测性设计

## 1. Config / Secret

### 1.1 配置分类

| 类别 | 示例 | 所属方 |
|---|---|---|
| 平台运行配置 | 服务名、环境、监听地址、超时、并发 | Platform |
| Secret | DB 密码、Service Key、Provider Token、Webhook Secret | Secret Provider / 部署环境 |
| 业务配置 | Provider 优先级、新闻源启停、通知订阅 | 对应业务模块 |
| 动态运营配置 | 限流阈值、任务并发上限 | 有明确热更新需求后再引入 |

### 1.2 加载原则

默认值 < 配置文件（如启用） < 环境变量 < 部署 Secret 注入。环境变量读取集中在配置装载层，业务代码接收已校验配置结构。启动时完成类型、范围、必填项和依赖校验。

- 配置快照不可被业务随意修改。
- 不在普通日志、诊断、错误和管理响应中回显 Secret。
- 缺少可选 Provider Key 应标记 not_configured/skipped，不冒充连接失败。
- dotenv 仅作为本地开发辅助，不是生产 Secret 系统。
- 首期不建设动态配置中心和远程热更新。

### 1.3 配置契约

每个服务定义独立 Config struct，通过统一 Loader/Validator 接口装载。平台只统一加载行为、错误格式、脱敏和来源优先级，不把所有业务配置塞进一个全局巨型结构体。

## 2. Logger / Error

### 2.1 结构化日志字段

建议统一字段：
- timestamp、level、service、environment、version
- request_id、trace_id、span_id
- method、route、status_code、duration_ms
- principal_type、service_id（仅稳定标识）
- error_code、error_category、retryable
- task_id、run_id、dependency、provider、attempt（适用时）

禁止记录 Authorization、Cookie、Service Key、Provider Token、数据库密码/DSN、原始请求体、完整新闻正文和模型上下文。访问日志只记录路由模板，不记录查询参数和敏感路径片段。

### 2.2 错误模型

统一错误至少包含：
- code：稳定机器可读标识。
- category：validation、authentication、authorization、configuration、dependency、timeout、rate_limit、data_quality、conflict、internal。
- safe_message：可对调用方暴露的安全摘要。
- retryable：是否允许重试。
- dependency：失败依赖名称。
- cause：仅内部保留，禁止直接序列化。

HTTP 映射由 Transport 层负责，领域错误不直接携带 HTTP 状态码。错误包装保留 errors.Is/As 能力。

## 3. Request ID / Trace

- 每个入口生成或校验 Request ID；不可信或格式非法的外部值重新生成。
- 跨服务调用传播 W3C Trace Context；Request ID 与 Trace ID 不混为同一个概念。
- Background Task 保存 traceparent、request_id 和 actor 快照，异步执行时建立新的 Span 并关联父上下文。
- 不接受客户端直接传入的 principal 身份字段作为可信身份。
- Trace attributes 使用低基数、非敏感字段；股票代码、用户标识等业务高基数字段不默认进入 Metrics 标签。

## 4. 统一诊断框架

### 4.1 四层诊断

| 层 | 回答的问题 | 示例 |
|---|---|---|
| Liveness | 进程是否仍活着 | goroutine/进程响应，不探测所有依赖 |
| Readiness | 当前实例能否接收工作 | 必需 DB、配置、关键组件可用 |
| Capability | 某项业务能力是否可执行 | 某 Provider、新闻源、通知渠道、LLM Adapter |
| Data Quality | 返回的数据是否可信 | 完整性、时间新鲜度、单位、覆盖率、异常值 |

Liveness、Readiness 不能替代 Capability 和 Data Quality。

### 4.2 Check 契约

Check 至少声明：
- id、name、category、criticality、timeout
- dependencies、enabled、visibility
- Run(ctx) -> CheckResult

CheckResult 至少包含：
- status、checked_at、duration
- summary、reason_code、safe_message
- dependency、source、metadata（经过白名单过滤）
- evidence_ref（如有持久化证据）

检查必须有独立 timeout、并发上限和 panic recovery。一个 Check 失败不能阻断其他独立 Check；聚合层按关键性和状态计算总状态。

### 4.3 状态语义

| 状态 | 含义 | 聚合含义 |
|---|---|---|
| healthy | 检查通过 | 不降低整体状态 |
| degraded | 可用但质量/能力受限 | 整体至少 degraded |
| unavailable | 目标依赖或能力当前不可用 | 关键项时整体 unavailable |
| skipped | 未执行，例如未配置或不适用 | 不算成功，也不算失败 |
| failed | 检查执行异常或系统性失败 | 关键项时整体 failed/unavailable |

skipped 必须附 reason_code，例如 not_configured、not_applicable、disabled、missing_credential。不能把 skipped 映射为 healthy。

### 4.4 公共框架与领域诊断边界

公共平台负责 Check 接口、注册、执行器、超时、并发、结果结构和聚合。Data 保留 Provider Probe、字段校验、Freshness、PIT、覆盖率等质量逻辑；News 保留来源可信度、抓取延迟、去重和内容质量；Research 保留证据完整性、Context 质量和任务阶段诊断。领域模块通过 Adapter 注册 Check。

### 4.5 查询和历史

首期提供进程内诊断快照和受保护查询接口；是否持久化历史由 PLAT-001 的实际需求确认。若持久化，保存 Check 结果摘要和 evidence reference，不默认保存完整原始数据或 Secret。

## 5. Metrics

首期只定义埋点和导出接口，不自建存储。指标建议：
- http_requests_total、http_request_duration_seconds
- dependency_requests_total、dependency_request_duration_seconds
- dependency_failures_total、retry_attempts_total
- diagnostics_checks_total、diagnostics_check_duration_seconds
- tasks_created_total、tasks_completed_total、tasks_failed_total、task_queue_depth
- service_key_auth_failures_total、authorization_denials_total

标签必须低基数：service、route template、method、status class、dependency、operation。禁止把 URL、错误原文、Key、用户 ID、股票代码作为默认标签。

## 6. 运行时告警建议

先定义告警信号，不绑定具体监控产品：
- 认证失败率突增、管理操作异常。
- 关键依赖持续 unavailable。
- 诊断 Check 超时或 failed。
- 任务队列积压、任务长时间无状态推进。
- DB 连接池耗尽、Redis 连接错误。
- 外部 Provider 错误率、超时和重试率持续升高。

告警策略、阈值和通知渠道由部署/Notification 方案确认，不在平台包内硬编码。
