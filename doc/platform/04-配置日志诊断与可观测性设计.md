# 配置、日志、诊断与可观测性设计

## 1. 配置与 Secret

每个服务维护自己的类型化 Config。平台统一装载方式、默认值、校验和脱敏，不建立全局巨型配置结构。

配置优先级：代码默认值 < 配置文件（如启用） < 环境变量 < 部署 Secret 注入。启动时完成类型、范围、必填项和依赖校验；配置快照启动后不可随意修改。

- dotenv 仅作为本地开发辅助，不覆盖进程已有环境变量。
- `internal/platform/config.Env` 只负责读取和类型解析；每个服务自行定义 Config struct、默认值和跨字段 Validate，不把业务配置集中到平台。
- 配置解析错误只包含键名和期望类型，不回显输入值。
- `Secret` 的格式化和 JSON 输出固定脱敏；只有显式调用 `Value()` 才能取出明文，调用方不得将其写入日志或错误。
- 环境变量只应在 bootstrap/config 装载边界读取；handler、domain 和 use case 不直接调用 os.Getenv。
- 生产 Secret 由部署环境注入；首期不建设动态配置中心。
- 错误可指出配置键和错误原因，但不能回显 Secret 值。
- Provider Key 未配置时按领域策略标记 skipped/not_configured，不伪装成网络失败。

## 2. 日志

首期使用标准库 slog，不再包装一层没有实际价值的 Logger Interface。Logger 通过构造参数注入，不使用可变全局 Logger。Secret 实现 slog.LogValuer，日志值固定脱敏；其他敏感字段仍须在调用处遵守白名单，不得把原始 Secret 转成普通字符串后记录。

必要字段：
- timestamp、level、service、environment；
- request_id、task_id（适用时）；
- method、route template、status_code、duration_ms；
- dependency/provider、operation、attempt（适用时）；
- error_code、error_category。

必须过滤 Authorization、Cookie、Service Key、Provider Token、密码、DSN 和 Secret。默认不记录请求/响应 Body、URL Query、完整 Provider 响应或模型上下文。

日志应能回答：哪个服务、哪个请求/任务、哪个依赖、哪个阶段、耗时多少、失败原因是什么。

## 3. 错误模型

统一错误至少包含 Class、稳定 Code、安全摘要、内部 Cause，以及可选 Dependency 和 Retryable 元数据。Class 的首期枚举严格以《08-公共平台契约规范》为准：validation、unauthenticated、forbidden、not_found、conflict、unavailable、timeout、internal。configuration、dependency、data_quality 等业务细分通过稳定 Code 和可选 Dependency 表达，不新增互相重叠的通用 Class。

- Cause 保留内部错误链，不序列化给客户端。
- HTTP 状态码由 transport 层映射。
- 对外错误不得包含 SQL、DSN、Token、原始上游响应或堆栈。
- 重试判断由明确错误类别和调用策略共同决定，不对所有错误盲目重试。

## 4. Request ID

首期只要求 Request ID，不引入完整 Trace/Span 系统。

- `internal/platform/observability.Middleware` 在入口校验 X-Request-ID；非法值重新生成，并将最终值写入 Context 和响应 Header。
- `internal/platform/observability.Middleware` 仅在入站 `X-Request-ID` 恰好出现一次且格式合法时保留；缺失、重复或非法值统一重新生成。重复 Header 不得通过选择首值/末值消除歧义。
- 响应返回最终 Request ID。
- 平台 HTTP Client 从 Context 自动传播该 ID；其他自定义 HTTP Client 使用 `PropagateRequestID`。
- 后台任务保存创建时 Request ID，并在执行日志中同时记录 task_id。
- 后台任务可通过 `WithRequestID` 恢复创建时的 ID。
- Request ID 只用于关联，不代表身份和权限。

若未来仅凭 Request ID 无法定位跨服务并行链路，再引入 W3C Trace Context 和 Span。

## 5. 诊断模型

### 5.1 所有权原则

统一诊断采用“公共契约 + 领域事实”的模式，而不是由平台接管所有诊断逻辑。

- Platform：公共 Fault/Observation、Check 定义、执行器、超时/并发限制、基础聚合、访问保护。
- Data：Provider Probe、熔断器被动诊断、Validation/Reporter、Freshness、Coverage、Cross-Provider、交易上下文和 Probe 历史。
- News：来源授权/可用性、搜索/抓取/解析/标准化/去重/证券关联/持久化诊断。
- Research：Analysis Run、Stage、Dependency、Context、Evidence 和结果可复现性诊断。
- Notification：渠道能力、投递 Run、重试、幂等、积压和最终投递状态。
- WebUI：消费服务端诊断摘要和领域明细，不自行推导质量结论。

Data 已有成熟诊断体系，PLAT-007 不重新实现 Data Probe/Reporter/Freshness，也不要求 Data 迁移其领域存储。完整跨模块现状、映射和路线见项目规划分支《统一诊断体系与跨模块接入规划.md》。

### 5.2 诊断层次

| 类型 | 作用 | 示例 |
|---|---|---|
| Liveness | 进程是否存活 | HTTP 服务可响应 |
| Readiness | 必需依赖是否可用 | MariaDB 连接正常 |
| Capability | 某项外部能力能否执行 | Provider、LLM Gateway |
| Data Quality | 数据是否可信 | 完整性、新鲜度、覆盖率 |

首期 Check 采用轻量接口和顺序/有限并发执行，不建设插件平台。每项有 ID、超时、是否必需；结果统一包含状态、reason_code、safe_message、checked_at、duration 和可选 evidence_ref。失败项互不阻断。

状态：
- healthy：检查通过；
- degraded：能力受限但仍可工作；
- unavailable：关键依赖不可访问；
- skipped：未配置或不适用，必须给原因；
- failed：检查自身异常或违反契约。

可选项 skipped 不降低整体状态；必需依赖缺失不能以 skipped 掩盖。公开健康接口只返回总体最小状态，详细诊断需 owner/service 权限。

诊断结果首期以实时快照为主。只有确有排查需求时才保存历史摘要，不存储完整原始响应和 Secret。

字段语义与序列化约束以《08-公共平台契约规范》Diagnostics 章节为准：reason_code 是稳定机器标识，safe_message 是脱敏摘要，evidence_ref 是可选的不透明证据引用。attributes 只允许有界、低敏感的结构化标量，不作为正文、snippet、原始响应或任意 JSON 的承载容器。

### 5.3 Check 执行模型

Check 是一次有边界的诊断动作，不是领域质量模型。当前首期 Go 实现字段为 ID、Name、Required、Timeout、Run；暂不增加没有真实调用方的 Category、SideEffect、Dependency 元数据。Runner 只承载只读、可取消的检查；写入、通知和高成本全量探测不得作为普通 Check 暴露，必须由领域侧显式授权并自行编排。

- 单项失败或超时不得阻断其他独立 Check。
- 全部 Check 受总 Deadline、最大并发和单项 Timeout 约束。
- optional 未配置/不适用返回 skipped，并提供 reason_code。
- required 依赖缺失返回 unavailable 或 failed，不能用 skipped 隐藏。
- 诊断默认只读；真实写入、真实通知和高成本 Provider 全量扫描必须显式授权。
- 执行器异常使用 failed；业务能力降级不能误报为执行器失败。

### 5.4 状态聚合与领域状态

平台聚合只产生整体摘要，不覆盖领域原始状态。Data 的 ProviderOutcome、Quality、Freshness 等状态继续保留；News/Research/Notification 也可维护自己的细分状态。Adapter 输出公共 Observation 时，必须保留原领域状态或可追溯 evidence_ref，禁止把多个不同维度压成单一健康值。

### 5.5 存储与历史

平台首期不建设通用诊断历史数据库。实时基础设施 Check 可即时执行并返回；领域历史由领域拥有：
- Data：MariaDB Probe Run/历史查询；
- News：Ingestion Run 与阶段结果；
- Research：Analysis Run/Stage 与 Evidence；
- Notification：Delivery Run/投递记录。

平台只透传 evidence_ref 和领域 Run/Task 标识，不直接查询领域表。后续只有在跨服务长期历史查询成为真实需求时，才评估统一摘要索引；事实数据仍归领域。


### 5.6 权限与敏感数据

公开 liveness 仅返回最小存活状态；readiness 及详细诊断按 owner/service 授权。诊断结果不得包含 Secret、URL Query、正文、snippet、原始 Provider 响应或敏感上下文。attributes 必须有字段白名单和大小限制。

## 6. Metrics 与告警

首期不部署 Metrics 存储系统。优先通过结构化日志记录耗时、重试、队列积压和错误分类；确有展示需求时再接轻量 exporter。

不把股票代码、用户标识、完整 URL、错误原文或 Key ID 作为高基数标签。主动告警由后续 Notification/部署方案决定，不在平台包中硬编码。

## 7. 验收

- 一个 Request ID 能串起入口、内部 HTTP 调用和任务日志。
- 失败日志能定位依赖、阶段、错误码和耗时。
- Secret 不出现在日志、诊断或错误响应。
- 关键依赖失败与可选 Provider 未配置能被区分。
- 不依赖外部日志/Trace/Metrics 平台也能完成基本排障。

## 9. PLAT-007 首期实现与接入边界复核（2026-11-05）

## 10. PLAT-006 Request ID / Fault 边界审查（2026-11-05）

本轮按 `d45e34a380a12f2e7879f8b3ee04d4531726dfcd` 检查平台实现与历史 Analysis HTTP transport，结论如下：

### 平台公共原语

- `observability.Middleware` 对入站 Request ID 做 ASCII 白名单和 128 字节上限校验；非法值重新生成随机 ID，并写入 Context/响应 Header。该校验可阻断 CR/LF、空白和超长值，但**不能证明调用方可信，也不能防止有效格式 ID 被恶意复用或伪造**。
- 因 Request ID 不代表身份，公网入口若不希望客户端控制日志关联键，必须由可信 Gateway 在边界覆盖/清理外部 X-Request-ID，再由服务接受 Gateway 生成的值。服务不得根据 Request ID 授权、归属数据或执行审计主体识别。
- `WithRequestID` 只接受符合格式的值；`PropagateRequestID` 将 Context 中的值复制到出站请求。后台 Worker 是否恢复 Request ID，仍由领域任务持久化创建时的 ID 并在执行入口显式调用。
- `fault.Fault` 的 `Cause` 使用 `json:"-"`，JSON 序列化不会输出 Cause；但 `SafeMessage`、`Code`、`Dependency` 是调用方提供的公开字段，Fault 结构本身不会自动识别或清洗秘密。生产者必须只写稳定错误码、固定脱敏摘要和逻辑依赖标识，禁止把 `err.Error()`、URL、DSN、Token、SQL 或用户输入直接填入这些字段。
- `Fault.Error()` 返回 SafeMessage（缺失时返回 Code/类别摘要），因此日志记录 Fault 本身不会自动泄露 Cause；但若调用方另行记录 `Cause.Error()` 或原始错误，仍可能泄露内部信息。日志脱敏必须由字段白名单和调用点共同保证，不能依赖 Fault 自动净化任意字符串。

### 历史 Analysis HTTP transport 的接入风险

`internal/platform/httpapi/server.go` 实际是历史 Analysis API（直接依赖 Analysis domain 和 Store），不是纯 Platform transport。本轮发现它仍自带一套 Request ID middleware，与 `internal/platform/observability` 重复；其 readiness、Runner 和 Store 错误响应部分直接使用 `err.Error()`，存在把内部依赖错误返回客户端的风险。该文件归属和迁移应由 Analysis/Server 集成分支处理，本 Platform 分支不直接修改。

后续 Analysis/Server 接入验收必须：
1. 统一使用平台 Request ID 原语，删除重复实现；由可信入口明确决定是否接受上游 Request ID。
2. 客户端响应只返回稳定 Code 和固定 SafeMessage；内部 Cause 仅进入受控日志，且日志字段不得包含凭据/连接串/原始上游响应。
3. HTTP access log 使用路由模板而不是任意原始 Path；不记录 Query、Body、Authorization 或 Cookie。
4. panic 日志只记录 request_id、route、method、panic 类型等必要元数据，不输出 panic 内容和堆栈到客户端。
5. 通过测试断言注入类似 `redis://user:password@host/db`、Token 和 SQL 的底层错误不会出现在响应 JSON。

PLAT-006 的平台原语与单测不等于上述 Analysis/Server 集成验收已完成，任务继续保持开发中。

## 11. PLAT-005 dotenv 原子装载边界（2026-11-05）

dotenv 文件必须先完整解析并校验，再写入进程环境。文件中后续行存在非法键、非法值或读取错误时，不得留下前面行已经写入的部分配置，避免调用方捕获错误后重试时处于混合配置状态。

- 进程已有环境变量优先于 dotenv。
- dotenv 同一键重复出现时，保持首个有效条目优先，避免改变既有装载行为。
- 文件缺失仍视为可选配置文件，不报错。
- dotenv 只用于本地辅助配置；生产 Secret 仍由部署环境注入。


## 12. PLAT-005 历史服务配置接入差距审查（2026-11-05）

审查基线：`2db7a7ac879f81cd67e930fdc0803cf73d952627`。

本轮仅审查并记录接入差距，不在 Platform 分支改动历史服务 bootstrap、领域 Adapter 或独立 Go Module：

- `cmd/analysis-api/main.go` 仍直接读取 `LOG_LEVEL`、`HTTP_ADDR`；`intEnv` 直接读取环境变量。
- `internal/service/wiring.go` 的 `EnvDuration` 仍直接读取环境变量。
- `internal/adapters/storage/mysqlredis/config.go`、`internal/adapters/marketdata/config.go`、`internal/adapters/pythonapi/config.go` 各自实现环境变量读取和解析，没有统一通过 `config.Env`。
- 存储 Adapter Config 仍以普通 string 保存 `DBPassword`、`RedisPassword`；行情/旧 Python Adapter Config 仍以普通 string 保存 API Key、Bearer Token、Cookie。平台 `config.Secret` 尚未贯穿到 Adapter 构造边界。
- `cmd/analysis-api/main.go:intEnv` 和 `internal/adapters/storage/mysqlredis/config.go:envInt` 将 `strconv.Atoi` 错误用 `%w` 包装。Go 的 `strconv.NumError` 会包含原始非法输入，因此启动错误可能回显配置值。应改为只返回键名和期望类型，不包装原始解析错误。
- 行情/Python Adapter 的部分解析错误已使用固定摘要，不应为了统一而回退成回显输入值的错误。

接入策略：

1. 根 Go Module 内的 Server/Analysis 集成方负责统一 bootstrap Config：先加载 dotenv（如启用），再一次性读取所有配置，完成类型/范围/跨字段校验，之后才创建 DB、Redis、HTTP Client、Provider、Worker 和 HTTP Server。
2. 每个领域仍维护自己的 Config struct；由组合根将 `config.Secret` 在构造客户端/驱动的最窄位置显式解包。不得在业务对象、日志字段或通用配置快照中长期保存明文 Secret。
3. Adapter 不再自行读取进程环境；改为接收已验证的 Config。禁止 handler、domain、use case 和 Worker 读取环境变量。
4. 错误只允许输出配置键和固定原因；禁止用 `%w` 包装会包含原始输入的解析错误。测试必须使用包含明显秘密标记的非法值验证错误不回显。
5. Data 等独立 Go Module 不得 import 根 Module 的 `internal/platform/config`；通过各自模块的配置边界实现同等安全契约，或未来另行评估公开共享 Module，不跨越 Go internal 边界。

PLAT-005 当前仍为开发中。平台 `Env/Secret` 原语已有包级验证，但历史服务尚未完成上述接入，不得标记为服务级配置统一完成。


## 13. PLAT-007 诊断路由权限矩阵（2026-11-05）

诊断 Runner 不提供 HTTP 路由，也不负责认证授权。服务组合根必须将每条健康/诊断路由注册到 `security.Router`，并按最小权限配置：

| 路由/能力 | 建议策略 | 说明 |
|---|---|---|
| liveness（仅进程存活） | `AnonymousAccess()` | 只返回最小存活状态，不包含依赖、配置或诊断明细 |
| readiness | 默认 `OwnerAccess()`；若部署探针需要匿名访问，必须单独评审并严格限制返回字段 | 不因便利而匿名暴露数据库/Redis/Provider 状态 |
| Platform 基础设施详细诊断 | `OwnerAccess()` | 仅 owner 可查看内部依赖检查和运行信息 |
| Data 领域诊断 | `OwnerOrServiceAccess(ScopeDataDiagnose)` | 领域 Adapter 保留 Data Probe/质量报告/历史；平台只承载授权和公共 Observation |
| Research 领域诊断读取 | `OwnerOrServiceAccess(ScopeResearchRead)` | 只读诊断沿用 Research read Scope，不赋予运行任务权限 |
| News / Notification 详细诊断 | 首期 `OwnerAccess()` | 当前平台 Scope 尚无独立 news/notification diagnose；不借用无关 Scope。出现真实跨服务调用方后再新增专属 Scope |

补充约束：

- `OwnerOrServiceAccess` 对 owner 放行；service 必须满足列出的全部 Scope。Owner 不自动继承任何业务 Scope。
- 详细诊断的 GET 路由只允许只读 Check；写入探测、真实通知和高成本全量 Provider 扫描不得仅因挂在 diagnostics 路径就获得执行权限。
