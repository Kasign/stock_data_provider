# 代码结构与模块详细设计

## 1. 设计目标

平台代码以根 Go module 的 `internal/platform` 为实现位置。只抽取多个真实调用方都需要的技术能力；领域模型、Repository、数据质量和业务流程继续由各领域拥有。

首期不创建完整目录树。某个能力只有在有真实调用方或独立契约测试时才创建 package。

## 2. 目标目录（按需形成）

    internal/platform/
      security/       # 认证身份和路由访问策略
      config/         # 类型化配置装载与 Secret 脱敏
      fault/          # 稳定错误类别和安全错误摘要
      observability/  # Request ID、slog 字段和脱敏
      diagnostics/    # Check 执行、结果与聚合
      httpclient/     # HTTP Transport、超时、响应限制、重试
      storage/        # 通用 DB/Redis 生命周期（确有复用时）
      migration/      # 版本记录和执行约定
      task/           # 仅长任务确有跨领域复用时建设

不预建 identity/audit/metrics/trace/task 等空包。简单类型优先放在最接近的稳定 package，避免过度拆分。

## 3. 依赖方向

    cmd / bootstrap / transport
       -> platform/*
       -> application
            -> domain
            -> ports
       adapters -> ports

- platform 不得 import Data、News、Research、Notification 或 WebUI。
- platform 不访问领域表、不持有领域 Repository。
- 底层类型不反向依赖 HTTP Middleware 或业务服务。
- 禁止循环 import、可变全局单例和跨 module internal import。
- 根服务与 services/market-data 是独立 Go module；行情服务通过 HTTP 契约和自身 Adapter 接入，不复制根模块 internal 包。

## 4. Package 职责和首期限制

| Package | 负责 | 不负责/暂缓 |
|---|---|---|
| security | 认证、可信身份上下文、路由访问模式和少量权限判断 | 用户中心、组织/租户、动态策略引擎 |
| security | 从配置的 Secret 验证 owner/service 身份，建立可信上下文 | 动态凭证管理、用户中心、策略引擎 |
| config | 类型化配置、默认值、校验、Secret 脱敏 | 远程配置中心、热更新、业务配置 CRUD |
| fault | 稳定错误类别、Code、安全摘要、错误链 | HTTP 状态码和领域错误规则 |
| observability | Request ID、slog 字段、敏感信息过滤 | Span SDK、Trace Collector、日志平台 |
| diagnostics | Check、超时、结果和简单聚合 | 领域质量算法、复杂历史分析 |
| httpclient | Transport 复用、超时、Body 上限、有限重试 | Provider 请求/响应解析、通用熔断平台 |
| storage | DB/Redis 生命周期和基础健康能力 | 万能 Repository、领域 SQL |
| migration | Migration 标识、版本记录、显式执行约定 | 多集群编排、自动在线 DDL |
| task | 仅长任务的生命周期原语 | 通用工作流、分布式调度 |

## 5. 现有实现复用策略

### 5.1 Config

保留各领域 Config struct 和业务配置归属。平台只统一装载行为、默认值、校验和 Secret 脱敏；不将 ProviderSettings、新闻源配置和研究策略塞进全局配置对象。

### 5.2 HTTP Middleware

根服务和行情服务已有局部 Request ID、访问日志、Recovery、认证等实现。先按契约统一行为，再逐项接入；不整体搬迁 Handler、路由和业务 API。

### 5.3 Diagnostics

行情 Provider Probe、Freshness 和 Data Quality 是领域能力。平台只提供轻量 Check 执行和结果结构，不重写现有探针，不要求所有检查都持久化历史。

### 5.4 Storage

DB/Redis 连接生命周期可评估复用；领域 Repository、SQL 和表结构不迁移。若只是单一调用方，保留现有 Store，不为形式统一而拆层。

### 5.5 Task

当前分析 Task Queue 是业务任务实现。先修复其明确可靠性缺口；只有 Research 等模块确实需要同一任务生命周期时，才提炼通用 package。首期不先建设独立任务服务。

## 6. Go Module 边界

- 根服务直接使用根 module 内的 platform package。
- 行情独立 module 不 import 根 module internal 包。
- 不为少量共享代码立即拆公共 Go module。
- 若未来多个独立 module 确实需要共享同一套实现，再单独评估提取公开 module，并核算版本发布和维护成本。

## 7. 禁止事项

- 不预建无调用方的空 package。
- 不为“统一”搬迁领域 Repository 或 SQL。
- 不把平台拆成多个网络服务。
- 不引入只有一个调用方且没有明确复用价值的抽象层。
- 不同时修改服务端集成分支的启动入口和平台 package。


## 8. 首期 Go Module 落点确认（2026-11-05）

首期公共实现位于根 Go Module 的 `internal/platform`，不新增独立 `platform/go.mod`。

- 根服务与根 Module 内的 News 运行时代码可直接复用平台 package。
- Data 行情服务属于独立 Go Module；其 Provider Probe、质量校验、Freshness、Coverage 和诊断历史继续由 Data 所有，通过 HTTP API/Adapter 对接，不跨 Module 引用根模块 `internal`。
- `go-core` 当前属于历史/迁移路径，不作为首期公共平台的强制依赖方。
- 根 Module 与独立 Module 不允许跨边界 import `internal` 包。
- 只有多个独立 Module 出现真实且稳定的同一份可执行代码复用需求时，才重新评估提取公开 Module；不能仅因它们共享 HTTP/JSON 契约就拆 Module。

本次 PLAT-007 的 Fault/Diagnostics 实现因此落在：
- `internal/platform/fault`
- `internal/platform/diagnostics`

PLAT-008 的安全 HTTP Client 也落在根模块 `internal/platform/httpclient`，首期由根模块内需要访问不可信来源的领域调用。独立服务仍通过各自 Adapter 和 HTTP 服务契约接入。
