# 代码结构与模块详细设计

## 1. 设计目标

公共代码需要具备明确的目录所有权和单向依赖。平台内部实现可以替换，但业务模块只依赖稳定公开契约。首期不搬迁全部现有实现，先盘点、定义接口，再通过 Adapter 渐进统一。

## 2. 当前代码结构盘点

当前根 Go module 为 example.com/stock-analysis-flow，Go 版本声明 1.22；行情服务 services/market-data 是独立 Go module。

| 路径 | 当前职责 | 当前边界问题/注意事项 |
|---|---|---|
| internal/platform/config | dotenv 加载 | 仅文件装载辅助，不是完整配置系统 |
| internal/platform/httpapi | 分析 HTTP Handler、Request ID、访问日志、Recovery、健康检查 | 当前与分析 API 紧耦合，不直接抽成全局平台 API |
| internal/platform/taskqueue | 分析任务 MariaDB 持久化、Worker、幂等和事件 | 已有业务任务实现，先抽象通用任务语义，不搬迁业务 SQL |
| internal/adapters/storage/mysqlredis | 分析服务 DB/Redis 连接、健康、自检和 Schema 检查 | 与分析表结构绑定，基础连接可抽象，业务 Repository 留在领域 |
| internal/service | 分析应用装配和依赖 Wiring | 属于高冲突集成区 |
| services/market-data/internal/config | 行情服务专属配置和 Provider 配置 | 与根模块配置分别演进 |
| services/market-data/internal/httpapi | 行情 API 路由、API Key 校验、Request ID、访问日志、超时和安全 Header | 局部实现可作为现状参考，不能默认与分析服务完全一致 |
| services/market-data/internal/service/provider_probe.go 等 | Provider 能力探测、诊断和质量处理 | 领域诊断逻辑应保留，公共层提供通用 Check/Result 契约 |

## 4. 包职责和依赖方向

| 包 | 负责 | 不负责 |
|---|---|---|
| security | 主体上下文、认证、授权、路由策略 | 用户注册、登录 UI、业务资源规则 |
| servicekey | 内部服务凭证生命周期 | Provider Token、外部用户密码 |
| config | 类型化装载、默认值、校验、Secret 访问 | 业务配置 CRUD、动态配置中心 |
| observability | Logger、Error、Request ID、Trace、Metrics、脱敏 | 日志/指标/Trace 存储 |
| diagnostics | Check 注册、执行、聚合和结果模型 | Data 的字段质量算法、News 的内容质量规则 |
| httpclient | HTTP Policy、超时、重试、并发和错误映射 | 业务 API Client、Provider 数据解析 |
| storage | DB/Redis 连接生命周期和通用健康能力 | 业务 SQL、领域 Repository |
| migration | Migration 元数据、排序、锁和执行约定 | 所有领域表的 SQL 内容所有权 |
| task | 任务状态机、Worker 生命周期、幂等、租约 | 研究业务流程和任务具体步骤 |
| audit | 审计事件模型、写入接口和访问约束 | 普通应用日志和业务分析历史 |

依赖方向：

    cmd / bootstrap
       -> platform
       -> application / domain
       -> adapters
    platform -X-> business domains
    platform -X-> web

平台包之间也应避免循环依赖。身份上下文、错误模型等基础类型应放在足够小的包中。

## 5. API 与可见性

- 对外公开的跨模块契约放在明确的 platform package 或 contracts package。
- 具体存储实现、Key 哈希实现和驱动配置不暴露给业务模块。
- 业务模块通过接口注入 Repository、Clock、Logger、HTTP Doer、Diagnostics Registrar 等依赖。
- 不暴露可被业务随意修改的全局单例。
- 配置在启动阶段装载为不可变快照；热更新需要独立设计。
- 需要跨 Go module 复用时，优先评估提取独立 module 的成本；首期不因未来可能拆 module 而提前拆仓库。

## 6. 当前代码的复用策略

### 6.1 dotenv

保留当前不覆盖进程已有环境变量的行为；补齐重复 Key、非法 Key、文件权限、转义语义和错误脱敏测试。dotenv 是开发辅助，不得成为生产 Secret 唯一来源。

### 6.2 HTTP API Middleware

当前分析服务和行情服务分别有 Request ID、访问日志、Recovery/超时等局部实现。先建立统一 Middleware 接口和测试，再逐个接入。业务 Handler 和路由不要在平台抽取批次中重写。

### 6.3 Task Queue

当前分析任务队列使用 MariaDB 保存任务，支持幂等键和 Worker；这是业务任务实现，不等于已具备通用任务框架。先提炼状态机、租约、执行器和事件语义；保持分析任务请求和结果模型在分析领域。

### 6.4 Storage

当前 mysqlredis Store 负责 DB/Redis 连接、Ping、自检和分析 Schema 检查。连接管理可以作为基础能力，分析 Schema 校验和分析 Repository 不应放入公共 storage package。

### 6.5 Market Data 独立模块

行情服务有自己的配置、API Key、Provider Probe 和存储实现。由于它有独立 go.mod，公共包不能直接跨 module import。首期通过契约和 Adapter 对齐，不为共享代码制造跨 module 相对路径或复制粘贴；后续再评估独立 platform module。

## 7. 禁止事项

- 不将当前 internal/platform/httpapi/server.go 整个改名为公共 HTTP 框架。
- 不将 analysis_tasks、analysis_runs 等业务表塞进平台 schema。
- 不让平台 storage 依赖分析 domain。
- 不从平台 package 调用 Provider 或新闻业务。
- 不通过全局变量共享配置和身份。
- 不为每个业务服务保留一套语义不同的“公共”实现。
