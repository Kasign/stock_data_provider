## 4. 关键实现事实

### 4.1 根分析服务

启动入口：`cmd/analysis-api/main.go`。

装配顺序包含 dotenv、日志、根 Store、行情 Adapter、Runner、Task Queue、HTTP API、HTTP Server。根 Store 同时持有 `*sql.DB` 与 go-redis Client，并向 Task Queue 暴露 DB。

根 HTTP API 当前路由：
- `/healthz`、`/readyz`
- `/api/v1/analysis/runs`
- `/api/v1/analysis/tasks`

Handler 外层为 request ID、request log、panic recoverer。未见统一认证授权中间件。Compose 将宿主机 8092 绑定到 127.0.0.1，但这只是当前部署暴露边界，不应替代应用层身份验证。

根 readiness 当前调用 Store.Health，依次检查 MariaDB、分析表结构、Redis；这属于分析服务的依赖就绪判断，不等于可扩展的诊断 Registry。

### 4.2 行情服务

启动入口：`services/market-data/cmd/market-data/main.go`。

它独立读取配置、建立 MariaDB Store、按配置执行 Migration、初始化 Redis Cache、创建 Provider、按能力开关注册 Provider、创建 DataService 和 HTTP API。

行情 HTTP API 明确将 live/ready 路由公开，业务路由通过 `Server.auth` 保护；校验 `X-API-Key` 或 Bearer Token，使用常量时间比较。当前没有 Key ID、Scope 或按主体授权。

Provider Probe 支持主动检查、超时/并发控制、错误分类、错误脱敏、结果持久化和历史查询。Probe 数据结构、Provider 能力名称、质量阈值、Freshness 规则属于行情域，不应抽成平台领域模型。

### 4.3 异步任务边界

根任务队列具备：
- MariaDB 持久化任务和阶段事件；
- `Idempotency-Key` 与请求一致性比较；
- Worker 数量、队列容量和执行超时配置；
- 数据库事务领取 queued 任务；
- 启动时处理遗留 running 任务。

当前恢复语义是把进程中断时的 running 任务标记 failed（`worker_interrupted`），并非租约过期后重新领取。没有 heartbeat、owner/lease token 或多实例协调的完整 fencing 机制。因此已有队列可以作为领域任务实现参考，但不能直接宣称满足通用 Task Runner 目标；PLAT-010 需要先定义至少一次执行、幂等副作用和恢复策略。

### 4.4 存储与 Migration

根 Store 的分析表为 analysis_runs、analysis_stage_events、analysis_snapshots、analysis_tasks；行情 Store 拥有 market_data_* 表。两者均通过代码内 DDL 创建表，且行情表新增字段另有显式兼容/检查逻辑，但未见全仓库统一 Migration 版本账本。

平台层应提供 Migration 注册、排序、版本记录和执行治理；具体 SQL、Repository、数据模型继续由领域模块拥有。不得把行情历史数据表并入根分析 Store，也不得让平台包依赖业务 model。

### 4.5 新闻与研究分支

新闻分支 `f740fedd...` 的文档已明确目标新闻运行时归属根 Go module 的 `internal/news/`，并明确不依赖 go-core internal、不过度复制旧 Searcher、不保留 Python fallback。当前该分支文件树可见 `doc/news/**`，但没有 `internal/news/**` 运行时代码。因此平台设计应提供未来新闻模块可消费的公共契约，不要以旧搜索 Adapter 反推新闻业务模型。

研究分支 `cf69ccc4...` 当前可见的研究工作流实现仍在独立 `go-core` module；其 HTTP 认证使用 `X-Go-Core-Token`，并有独立 request ID/recoverer。新闻搜索也位于 `go-core/internal/adapters/newssearch`。这些实现可用于行为和边界参考，但新平台不能 import 其 internal 包，也不应将其当作根服务的公共基础设施。

## 5. 重复实现与复用判断

| 重复点 | 当前实现 | 建议处理 |
|---|---|---|
| HTTP Middleware | 根、行情、go-core 三套 | 先冻结 platform/http 契约；逐项抽出 request ID、recover、access log、timeout、security headers；认证/授权按统一主体模型重做，不机械复制 |
| 静态内部凭证 | 行情 X-API-Key/Bearer；go-core X-Go-Core-Token | 新建 Service Key；内部服务身份与 Provider 凭证分离；旧 token 不作为兼容包袱 |
| 配置读取 | 根多个 Adapter/main 分散；行情单一大 Config | 建立平台 Config Loader/类型化装配约定；ProviderSettings 留在行情领域 |
| Logger / Error / Request ID | 各服务独立实现 | 建立稳定接口和字段约定，优先注入 Logger，不依赖全局 slog；错误码保持领域命名空间 |
| Redis 客户端 | 根 go-redis；行情手写 RESP | 评估让行情服务使用成熟客户端依赖；统一连接/超时/关闭约定，保留领域缓存接口 |
| DB/Migration | 两套 Store 与 DDL | 不统一领域 Repository；统一 Migration 注册/版本治理，明确每个 migration owner |
| 诊断 | 行情 Provider Probe/Freshness/Quality | 复用诊断执行框架的设计经验，不复用行情 DTO/Check 逻辑；新闻、研究保留自己的质量规则 |
| HTTP Client | Provider/Adapter 各自 Client 和重试 | 平台提供可配置 Client Policy；Provider 只声明幂等性、超时预算和领域限流策略 |
| Task Runner | 根分析任务队列 | 保留为分析业务当前实现；平台先定义通用执行语义，再决定抽取哪些底层原语 |

## 8. 建议的公共平台落地顺序

本轮盘点后，建议保持原路线，但按实际风险明确先后：

1. **PLAT-002 契约冻结**：先定义 package 边界、身份上下文、错误、Request ID/Trace、Config、Diagnostics、HTTP Client 和 Migration 契约。
2. **PLAT-003/004 安全**：根 API 的认证缺口和静态 Key 缺乏生命周期是首要风险；先建主体/Scope 与 Service Key，再逐服务接入。
3. **PLAT-005/006 运行上下文**：类型化配置、Logger、错误分类、Request ID/Trace，避免后续中间件再重构。
4. **PLAT-007 诊断框架**：复用行情 Probe 的执行治理经验，抽取 Check/Runner/Result/Aggregator；行情 Quality/Freshness 仍归行情域。
5. **PLAT-009 存储治理**：统一连接生命周期与 Migration 版本规则；优先处理行情手写 Redis 客户端，但需独立验证 module 依赖和部署。
6. **PLAT-008 HTTP Client**：按统一超时/响应上限/幂等重试/限流契约接入 Provider 和内部 Adapter。
7. **PLAT-010 Task Runner**：以现有分析任务表和队列为事实基线，补齐租约、心跳、恢复与幂等副作用语义后再抽象。
8. **PLAT-011/012**：按平台统一身份和日志上下文补 Metrics、Audit。
9. **PLAT-013**：Data、News、Research 分别接入；不提前要求新闻领域尚未实现的运行时代码。
