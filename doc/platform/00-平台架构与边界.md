# 公共平台架构与边界

## 1. 建设目标

本系统首先服务于个人研究和使用，不以多租户 SaaS、团队协作平台或大规模公开 API 为目标。公共平台的价值是减少重复实现，并保证系统长期可维护、性能稳定、出现问题能够定位和恢复。

首期目标：

1. 服务入口有明确认证边界，内部调用不能仅凭内网位置获得信任。
2. 配置集中装载、启动时校验，Secret 不进入日志和接口响应。
3. 每个请求和后台任务有可追踪 ID，错误能定位到模块、依赖和阶段。
4. DB、Redis、外部 HTTP 调用有超时、资源上限和清晰故障行为。
5. 诊断能区分进程、关键依赖、外部数据能力和数据质量。
6. 长任务有持久化状态、幂等保护和可解释的失败/恢复方式。
7. 平台实现简单、可测试，不制造额外部署和运维负担。

## 2. 规模假设与设计边界

首期按以下假设设计：

- 一个实际所有者，不建设注册、组织、角色管理和多租户体系。
- 少量 Go 服务，主要在可信私有网络或同一部署环境内通信。
- 低频个人研究请求，少量并发；但外部 Provider 可能慢、限流或不稳定。
- 以单实例运行作为默认部署模式；不把多实例协调作为首期前提。
- MariaDB 是持久化事实源；Redis 是可丢失的缓存/辅助设施。
- 运行问题主要由所有者排查，要求日志和诊断信息足够清楚，不要求企业级可观测性平台。

这些是假设，不是硬编码限制。若将来出现多个用户、公开 API、多个服务实例或持续高并发，应先更新容量和威胁模型，再扩展设计。

## 3. 核心原则

### 3.1 最小可靠闭环

安全认证、配置校验、结构化日志、Request ID、依赖超时、健康诊断、DB Migration 和任务持久化属于基础要求，不能因个人使用而省略。

### 3.2 不建设规模化基础设施

首期不建设：
- OAuth/OIDC、完整 IAM、组织/角色/租户体系。
- 服务注册中心、服务网格、API Gateway 集群。
- Kafka/RabbitMQ、事件总线和通用工作流引擎。
- 独立日志、Metrics、Trace 存储集群。
- 分布式追踪采样平台、复杂告警规则平台。
- 多节点任务调度、分布式锁框架和复杂租约协调。
- 动态配置中心、配置热更新平台。
- 为所有组件单独部署进程。

### 3.3 组件优先，单体部署优先

公共能力以 Go package、接口和 Middleware 形式嵌入现有服务。只有确实需要独立生命周期、跨进程集中管理或独立扩缩容时，才考虑拆服务。

### 3.4 领域所有权不转移

Data 拥有行情、Provider 和数据质量；News 拥有新闻来源、采集和内容质量；Research 拥有 Context、Evidence、研究编排和结果；Notification 拥有通知规则与投递。平台只提供通用技术能力。

### 3.5 先有调用方，再增加抽象

不预建空 package、不为未来可能的多个消费者设计复杂插件系统。每个公共组件必须有真实调用方或明确的契约测试。

## 4. 首期逻辑结构

    HTTP API / Worker
          |
    Request ID + Access Log + Recovery
          |
    认证与最小权限
          |
    Data / News / Research / Notification
          |
    Platform packages
    Config / Secret / Fault / Diagnostics
    HTTP Client / DB lifecycle / Migration
    Task primitives（仅长任务需要）
          |
    MariaDB / Redis / External Providers / Existing LLM Gateway

以上是逻辑分层，不代表独立进程。LLM Gateway 继续复用现有独立服务。

## 5. 首期能力分级

| 能力 | 首期要求 | 暂不建设 |
|---|---|---|
| 身份认证 | 单所有者管理入口 + 服务间独立凭证；默认拒绝 | 用户中心、组织、多租户、完整 IAM |
| 授权 | 少量明确权限组/Scope，按路由声明 | 动态策略引擎、复杂角色继承 |
| 配置 | 类型化配置、启动校验、环境注入、脱敏 | 动态配置中心、热更新 |
| 日志与错误 | slog、稳定错误类别、Request ID、错误链 | 独立日志平台、复杂日志查询服务 |
| Trace | 先用 Request ID 跨服务关联 | Span SDK、Trace Collector、Baggage |
| 诊断 | Liveness、Readiness、Capability、Data Quality | 通用诊断 SaaS、复杂历史分析 |
| HTTP | 连接复用、超时、响应体限制、有限幂等重试 | 通用熔断平台、复杂自适应限流 |
| 存储 | MariaDB/Redis 生命周期和清晰故障策略 | 分布式数据访问层 |
| Migration | 有版本记录、显式执行、失败可定位 | 多集群迁移编排平台 |
| Task | 仅长耗时任务持久化、幂等、有限 Worker | 通用工作流、多实例调度 |
| Metrics | 必要计数/耗时可由日志和轻量指标提供 | 自建监控存储和大规模指标体系 |
| Audit | 仅敏感管理操作留审计记录 | 全量业务行为审计平台 |

## 6. 安全与部署边界

- 所有业务路由必须明确访问策略；未声明策略默认拒绝。
- 公开健康路由只返回最小状态，不泄露依赖地址、SQL、配置或凭证。
- 服务间调用使用独立凭证；Provider Token 不作为内部服务身份。
- 管理入口只供所有者使用，优先通过私有网络/部署边界限制访问，应用层仍需认证。
- 不把内网 IP、反向代理路径或自定义身份 Header 当作认证。
- MariaDB 保存需要长期可信的任务、凭证元数据和审计事实；Redis 故障不能造成事实数据丢失。
- 不将平台表与领域业务表混在一起。

## 7. 扩展触发条件

只有出现以下真实需求，才启动相应扩展评审：

| 触发条件 | 再评估的能力 |
|---|---|
| 增加第二个实际用户 | 用户认证、用户级授权、数据隔离 |
| 多实例同时运行 | DB 租约、任务 fencing、共享限流和缓存一致性 |
| 请求量或 Provider 并发持续增长 | 限流、熔断、连接池和容量指标 |
| 跨服务故障难以仅凭 Request ID 定位 | W3C Trace/Span |
| 需要长期趋势和主动告警 | Metrics exporter、告警渠道 |
| 管理操作明显增多 | 完整审计查询和管理界面 |
