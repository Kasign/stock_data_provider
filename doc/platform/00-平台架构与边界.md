# 公共平台架构与边界

## 1. 目标

公共平台为 Data、News、Research、Notification 和后续 Go 模块提供稳定、统一、可测试的技术基础能力。目标是统一横切能力和运行约束，不是把业务代码集中到一个大包，也不是把所有组件都拆成独立服务。

核心目标：

1. 统一身份认证、授权、服务身份和安全审计。
2. 统一配置装载、Secret 访问、启动校验和脱敏。
3. 统一结构化日志、错误模型、Request ID 和 Trace 传播。
4. 统一依赖访问策略，包括 HTTP 超时、重试、并发限制和故障隔离。
5. 统一诊断协议，区分存活、就绪、能力可用性和数据质量。
6. 统一 MariaDB/Redis 生命周期、Migration 协作、任务状态和幂等语义。
7. 让公共能力能独立测试、独立演进，并通过稳定契约被多个业务模块消费。

## 2. 非目标

首期不建设：

- 独立服务注册中心、服务网格、复杂 API Gateway。
- 自研完整 OAuth/OIDC、用户中心或多租户 IAM。
- Kafka/RabbitMQ 等新消息基础设施。
- 通用工作流引擎、规则引擎或 Agent Runtime。
- 自建日志、指标、Trace 存储平台。
- 所有业务模块共享的万能 Domain、万能 Repository 或全局大锁。
- 每个公共组件一个部署进程。

## 3. 架构原则

### 3.1 组件优先，管理能力按需集中

优先使用 Go package / Interface / Middleware 形式提供能力，由各服务进程内嵌。只有存在独立生命周期、跨进程共享状态、集中管理或独立扩缩容需求时，才引入公共管理 API 或独立进程。

### 3.2 领域所有权不转移

公共平台只负责技术基础设施。Data 拥有行情和数据质量领域；News 拥有采集、文章、事件来源；Research 拥有研究上下文、证据和编排；Notification 拥有通知规则、渠道和投递领域。平台不持有这些领域的业务表和业务规则。

### 3.3 依赖方向单向

业务模块依赖平台公开接口；平台不得依赖业务模块。平台内部实现依赖标准库和经过评估的基础库，不反向导入 Data、News、Research 或 WebUI。

### 3.4 先契约后实现

跨分支需要共享的类型、错误语义、身份上下文、诊断状态、配置结构和管理 API 必须先形成文档和契约测试。业务模块不得依赖平台分支的临时内部实现路径。

### 3.5 最小可用而非一次性大而全

先实现安全、配置、日志错误追踪和诊断的最小闭环；HTTP、存储、任务、指标和审计按依赖推进。任何复杂机制必须由真实威胁、运行规模或故障案例驱动。

## 5. 组件层与管理层

| 层级 | 能力 | 首期形态 |
|---|---|---|
| 基础组件 | Security Middleware、Config、Secret Provider | Go package |
| 运行观测 | Logger、Error、Request ID、Trace、Metrics | Go package + exporter interface |
| 诊断 | Check、Registry、Runner、Report | Go package；管理 API 由宿主服务装配 |
| 外部依赖 | HTTP Client Policy、限流、重试、熔断接口 | Go package |
| 存储 | DB/Redis Bootstrap、Migration Runner 约定 | Go package / 领域 Repository |
| 任务 | Task Contract、Runner、Lease、Idempotency | 先复用 MariaDB 持久化，Redis 只做协调 |
| 管理能力 | Service Key 管理、诊断聚合、审计查询 | 由服务端集成分支装配的受保护 API |

## 6. 服务边界与部署

- 对公网暴露的入口由服务端统一控制；内部管理接口默认不暴露公网。
- 内部模块可以在同一进程内以 package 方式调用，不应为了“公共化”增加网络跳转。
- 跨进程调用必须使用明确的服务身份和授权 Scope。
- MariaDB 是任务、身份凭证元数据、审计和业务事实的持久化来源。
- Redis 只用于缓存、短期协调、速率限制计数或有明确恢复机制的队列，不作为唯一事实源。
- LLM Gateway 继续复用用户已有独立服务，平台只提供适配器和统一 HTTP 调用策略。

## 8. 关键架构决策

| 决策 | 结论 | 原因 |
|---|---|---|
| 平台是否独立分支 | 是，feat/platform-foundation | 公共代码集中开发，避免业务分支并发改同一实现 |
| 是否独立微服务 | 首期否 | 大部分能力无独立运行生命周期 |
| 安全模型 | 内外部身份分离 + Service Key + Scope | 满足内部调用，复杂度可控 |
| 配置中心 | 首期否 | 环境注入 + 类型化加载足够 |
| 诊断模型 | 公共框架 + 领域 Check | 不把数据质量误当成基础设施连通性 |
| 任务持久化 | MariaDB 为事实源 | Redis 故障不应丢失任务事实 |
| 迁移策略 | Adapter 优先，逐模块替换 | 避免一次性重写造成行为回归 |
| LLM Gateway | 复用现有服务 | 避免重复建设 |

## 9. 不允许的架构

- 平台 package import 业务 package。
- 业务模块直接使用平台内部未冻结结构。
- 用内网 IP、路径名称或自定义身份 Header 代替认证。
- 让所有服务共享一个万能 Service Key。
- 让 Redis 成为唯一任务状态存储。
- 把 Data/News/Research 领域表放进 platform schema。
- 为了统一诊断而删除领域自己的质量规则。
- 以“方便复用”为由将所有能力做成远程微服务。
