## 1. 当前判断

Platform 已经具备一批可复用的基础原语，但多个任务仍处于“平台包有实现、服务尚未接入”的状态。后续不应继续以增加 Platform package 数量为目标，而应推进契约冻结、组合根装配、真实消费者接入和部署边界闭环。

PLAT-CTR-005 流式能力的 A1 是 Platform 包级技术验收；它不等于 LLM A2 联调或生产 A3 验收。当前状态以第 8 节为准；历史提交的 CI 状态仅作当时记录，不能替代当前分支 HEAD 的精确 SHA 检查。

## 2. 任务分层与责任原则

| 责任层 | 负责内容 | 不负责内容 |
|---|---|---|
| Platform | 稳定公共原语、契约、错误语义、安全边界、资源生命周期和通用测试 | 领域 DTO、领域状态机、领域 Repository、业务规则、跨模块业务编排 |
| Server / Bootstrap | 组合根、Config Bootstrap、依赖注入、路由注册、认证策略装配、Migration 总注册、服务生命周期 | 重新实现 Platform 原语或接管领域业务 |
| 领域模块 | 自己的 Config、Adapter、DTO、诊断规则、Repository、Migration、业务状态和错误映射 | 直接依赖其他模块私有包；修改 Platform 公共契约来迁就单一领域 |
| Integration | 解决跨分支冲突、按冻结契约接线、端到端验证和部署配置 | 未经评审擅自改变契约或引入第二套公共实现 |

特别约束：
- 根 Go Module 的 `internal/platform` 只能被同一 Module 内允许的代码使用；Data、Research 等独立 Go Module 不得跨边界 import。
- Server 是组合根，不应把所有模块的领域逻辑集中到 Server。
- Platform 不建设通用工作流、万能 Repository、通用领域诊断历史库或动态配置中心。
- 消费者接入必须有真实调用场景；不得为“统一”而制造无调用方的 Adapter。

## 4. 建议执行顺序与可并行项

建议顺序：

1. REM-001 契约冻结与 REM-002 Server 组合根方案同步推进；契约变更必须由接口 Owner 评审。
2. REM-003/004/005 由 Server 与各服务并行接入，公共实现缺陷再回 Platform 修复。
3. REM-006/008/009/012/013/014/016/017 可按模块并行开发；依赖冻结契约，不要求所有模块串行等待。
4. REM-007/010/011 由 Server 统一装配，领域模块提供 Adapter、Repository 和 Migration。
5. REM-015 在公开 Facade 可用后推进；Researchflow 不应等待所有模块部署验收才开始自己的业务开发。
6. REM-018/019/020 分别由领域、部署和 Server Owner 完成。
7. REM-021/022 在 Integration 环境执行。

## 5. 当前 Platform 分支下一步只做什么

在 `feat/platform-foundation` 上，接下来优先做以下 Platform 所属工作：

1. 完成 PLAT-002 契约评审材料的差异整理；不擅自替其他模块宣布冻结。
2. 对 PLAT-003/005/006/007/008/009 的公共 API 做一次消费者视角检查，发现真实缺口才修改 Platform。
3. 为 Server 提供明确的 Bootstrap/路由/资源生命周期接入约定；不在 Platform 分支直接实现 Server 代码。
4. 将 PLAT-013 差距矩阵更新为当前模块分支快照，旧 SHA 不能继续作为最新基线。
5. 生产 DNS/egress、Secret 和部署证据由部署 Owner 提供；Platform 本地测试不能替代。

## 6. 明确不新增的 Platform 任务

以下事项当前不应启动：

- 动态 Service Key 管理（PLAT-004）：没有动态创建、撤销和无停机轮换的真实需求。
- 独立 Metrics/Exporter 平台（PLAT-011）：没有明确展示或告警消费者。
- 通用 Task Queue / Workflow Framework：Research/Researchflow 的任务和工作流语义属于领域。
- 通用 Diagnostics 历史数据库：领域负责历史和 evidence。
- 第二套 HTTP Client、第二套 Fault、第二套 Request ID 或公共万能 Repository。
- 为了让独立 Go Module 直接 import 根 `internal/platform` 而仓促拆分新 Module。

## 7. 状态维护规则

- 本文是剩余任务分工清单，不替代各模块自己的任务总览和接口契约。
- 每次状态更新必须附目标分支 HEAD、具体文件/接口、提交 SHA 和必要测试证据。
- “平台原语已实现”“消费者代码已接入”“跨模块联调通过”“生产部署验收通过”是四种不同状态，禁止合并成一个“已完成”。
- 领域分支状态只读更新；Platform 分支不得代替领域 Owner 修改其代码或任务状态。
- 发现任务已由模块总览明确完成时，更新状态并链接证据，不重复创建实现。
