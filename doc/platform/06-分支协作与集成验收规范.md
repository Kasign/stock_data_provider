# 分支协作与集成验收规范

## 1. 分支职责

| 分支 | 职责 | 与平台关系 |
|---|---|---|
| feat/platform-foundation | 公共平台组件、契约、测试、平台专属文档 | 公共平台唯一实现分支 |
| feat/full-go-data-providers-api-switch | Data/Provider、数据服务和最终服务端集成 | 集成平台组件、DI、路由、Migration 和启动装配 |
| feat/research-news-ingestion | 新闻采集、标准化、存储、搜索和新闻诊断 | 按冻结契约接入，不复制公共实现 |
| feat/research-analysis-flow-native-go | Quant、Context、Evidence、研究编排、持久化和 Notification | 按冻结契约接入；复用既有 LLM Gateway |
| feat/webui-market-data-console | WebUI 和浏览器验收 | 只消费 Server API |
| feat/design_doc | 项目总体规划 | 维护项目级边界和路线，不承载平台实现 |

## 2. 平台分支工作范围

允许：
- 新增 internal/platform 下的公共 package。
- 新增 platform 自身契约、测试、示例和 doc/platform 文档。
- 对现有局部实现做只读盘点和独立 Adapter 设计。
- 在不改变业务行为的前提下，为平台 package 增加独立测试。

默认不允许：
- 修改 Data/News/Research 的领域规则、业务 API、Repository 和业务表。
- 修改服务端主线的启动入口、全局 DI、路由总表、Migration 总注册入口。
- 修改 WebUI、部署拓扑和其他分支专属文档。
- 直接把平台分支合并到其他业务分支或创建 PR，除非另行授权。

若平台实现必须修改高冲突集成点，先在文档记录所需变更、目标文件、集成责任人和回滚方式，由服务端集成分支在统一批次处理。

## 3. 契约冻结流程

1. 在对应设计文档中定义目的、输入输出、错误、权限、超时和兼容规则。
2. 提供最小 Go Interface/DTO 示例和契约测试。
3. 标注契约版本、冻结日期、影响模块和迁移方式。
4. News/Data/Research 对契约进行接入评审；有异议先修订，不让多个分支各自猜测。
5. 契约冻结后才允许接入分支依赖；内部实现可以继续演进但不得破坏契约。

## 4. 集成顺序

平台 package 与单测
    -> 平台契约冻结
    -> 服务端集成分支集成组件
    -> 启动装配、DI、路由和 Migration 批次
    -> News / Data / Research 分别接入
    -> 跨模块契约测试与真实环境验收
    -> 更新总规划和各专项任务状态

平台分支不直接对多个业务分支做 cherry-pick；集成分支负责协调公共依赖的最终落点。

## 5. 高冲突文件保护

以下属于集成区，平台分支不主动修改：
- cmd/**/main.go
- internal/service/wiring.go
- 各服务 bootstrap / DI 装配入口
- 全局 HTTP 路由注册
- Migration 总注册和执行入口
- 根 docker-compose、部署文件和 CI 主工作流

允许新增独立 package；如确需改动集成区，先提出完整变更清单，避免两个分支同时改同一文件。

## 6. 验收门禁

### 代码门禁
- gofmt、go vet、go test 覆盖新增和受影响 package。
- 平台 package 无业务模块 import。
- 无循环依赖、无全局可变单例、无明文 Secret。
- 并发、超时、取消、错误和资源关闭路径有测试。

### 安全门禁
- 默认拒绝、最小 Scope、身份 Header 不可信。
- Key 明文只展示一次，DB 不存明文，日志不泄露。
- 轮换、撤销、缓存和审计故障策略有测试。

### 诊断门禁
- healthy/degraded/unavailable/skipped/failed 语义一致。
- 未配置和不适用项正确标记 skipped。
- 诊断超时和并发限制有效。
- 领域质量检查仍由领域模块实现。

### 集成门禁
- 接入分支使用冻结接口，不复制平台实现。
- 集成前检查共同祖先、双方 HEAD、目录冲突、Go module、Migration、路由和 DI。
- 真实服务依赖未验证时，明确标记待验收，不写通过。

## 7. 提交纪律

- 一个提交应对应一个可审查的完整文档或功能批次。
- 不为单行调整频繁提交。
- 提交信息中文、明确范围。
- 更新分支前读取最新 HEAD；使用 expected SHA，冲突后重新读取和重算。
- 不 force push，不重写已有提交。
