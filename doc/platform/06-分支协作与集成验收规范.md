# 分支协作与集成验收规范

## 1. 分支职责

| 分支 | 职责 |
|---|---|
| feat/platform-foundation | 公共平台契约、组件、测试和 doc/platform 文档 |
| feat/full-go-data-providers-api-switch | Data/Provider 领域实现与独立服务；当前远端差异集中在 Probe、验收文档和专项 Workflow，未承担根 Server 组合根 |
| feat/research-news-ingestion | 新闻采集、标准化、存储、搜索和新闻诊断 |
| feat/research-analysis-flow-native-go | Quant、Context、Evidence、研究编排、持久化和 Notification |
| feat/webui-market-data-console | WebUI，只消费服务端 API |
| Server/组合根集成 | 当前未发现独立 Server 分支；Owner 与分支基线待确认 |
| feat/design_doc | 项目整体规划 |

## 2. 平台工作范围

允许：
- 新增有真实调用方的 internal/platform package；
- 增加独立契约测试和平台文档；
- 只读检查其他分支并记录接入差异；
- 在不改变业务行为的前提下逐步统一局部实现。

不允许：
- 修改其他分支领域规则、业务 API、Repository 和业务表；
- 擅自修改服务端集成分支启动入口、全局 DI、路由总表和 Migration 总入口；
- 修改 WebUI 和其他分支专属文档；
- 未授权合并、创建 PR 或切换分支。

## 3. 契约流程

1. 先在 08 文档定义真实需要共享的输入、输出、错误、安全和超时语义。
2. 只为实际调用方定义必要接口，不冻结没有调用方的未来能力。
3. 平台侧完成最小契约测试。
4. 相关业务分支评审接入方式；存在冲突先修订契约。
5. 冻结后由业务分支或服务端集成分支接入，不复制平台实现。

## 4. 集成顺序

平台 package 与单测
 -> 契约评审
 -> 明确 Server/组合根 Owner 与分支
 -> Server 集成分支装配
 -> Data/News/Research 按实际依赖接入
 -> 跨模块契约测试
 -> 部署验证和故障演练

## 5. 高冲突文件

平台分支不主动修改：
- cmd/**/main.go
- internal/service/** 和 bootstrap/DI 入口
- 全局 HTTP 路由注册
- Migration 总注册/执行入口
- 根 Compose、部署文件和 CI 主工作流

需要这些变更时形成文件清单和集成说明，由明确指定的 Server/组合根集成分支统一处理。当前 feat/full-go-data-providers-api-switch 的远端提交差异没有修改这些入口，不能仅凭旧规划表格将其视为 Server 分支。

## 6. 验收门禁

- gofmt、go test、必要的 go vet 覆盖新增和受影响 package。
- 平台无业务模块依赖、无循环依赖、无明文 Secret。
- 请求/任务有可关联 ID；超时、取消、资源关闭路径有测试。
- 诊断区分关键依赖失败、可选能力跳过和数据质量异常。
- DB/Redis 故障行为符合设计；任务不会因 Redis 丢失事实状态。
- 不要求接入独立 Metrics/Trace 平台；本地日志和诊断必须足以定位基本故障。
- 未做真实部署验证时明确标记未知，不写通过。

## 7. 提交纪律

- 每个提交对应完整可审查的功能或文档批次。
- 中文提交信息，避免单行调整单独提交。
- 更新前读取最新 HEAD，使用 expected SHA；不 force push。
- 不修改其他分支，不擅自合并或关闭 PR。
