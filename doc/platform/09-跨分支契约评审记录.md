| 能力 | 当前代码证据 | 评审结论 |

## 4. 关键冲突与处理建议

### 4.1 根分析 API 缺少统一认证

当前根 HTTP Handler 路由包含分析执行和任务创建接口，外层 Middleware 主要为 Request ID、访问日志和 Recovery。平台安全契约必须在业务接入前落地。

处理：
- 根服务先增加 owner/service 身份验证和路由策略；
- liveness 明确匿名，readiness 和业务/管理路由按访问矩阵保护；
- 不接受客户端传入的身份 Header 作为可信身份；
- 服务端集成分支负责将 Middleware 装配到全局路由。

### 4.2 行情 API 现有单一 API Key

行情服务当前 Server 构造参数接收单个 apiKey。不能直接把它解释为未来全部服务通用的 Service Key。

处理：
- 适配为调用方独立环境 Secret；
- 暂时保留行情领域的认证接入点，等平台 security 契约冻结后由集成分支统一接入；
- 不改变 Provider Token 的用途；
- 不要求行情模块直接 import 根模块 internal 包。

### 4.3 Redis 连接方式存在真实性能问题

行情 Redis Adapter 的每次 Get/Set/Ping 都建立新 TCP 连接，并重新执行 AUTH/SELECT；这会增加延迟和连接开销。根服务已经使用 go-redis/v9，具备连接池客户端。

处理：
- 在行情服务自身 module 内评估引入 go-redis/v9；
- 使用连接池和 context deadline；
- 保留现有缓存接口及 TTL 语义，先做 Adapter 替换和单测；
- 通过基准或连接行为测试验证，不在本平台分支直接改行情业务代码。

### 4.4 Readiness 不应把可选 Redis 等同必需依赖

根 Store 当前 Health 同时检查 MariaDB、Schema 和 Redis。平台诊断契约应由服务声明 required/optional：
- MariaDB 对持久化任务和研究结果通常是 required；
- Redis 若仅作缓存则应为 optional，失效时缓存旁路或降级；
- 若某项业务明确依赖 Redis 的非缓存语义，再单独标记 required。

不能把“配置了 Redis”自动等同于“Redis 不可用就整个服务不可用”。

### 4.5 Task 恢复策略必须由任务语义决定

根 Task Queue 已有持久化和幂等能力。当前启动恢复会将 running 任务明确标记 failed，而不是自动重放。这是偏保守但可解释的策略，不能仅为符合通用任务框架而改成全部重排。

处理：
- 保留当前安全默认；
- 每个任务类型声明是否可安全重试；
- 对可重入任务才允许恢复重排；
- 对存在外部副作用的任务保留人工处理/失败状态；
- 先在现有 Queue 内完善，不提炼通用框架。

## 5. 契约冻结建议

PLAT-002 可以冻结以下最小公共语义：
1. 身份模式：anonymous、owner、service；owner Token 与 service Secret 分离。
2. 路由默认拒绝，身份由 Bearer 凭证验证建立。
3. X-Request-ID 入口生成/校验、响应回传、内部调用传播。
4. slog 字段约定和 Secret 脱敏。
5. Diagnostics Check/Result 及 required/optional 语义。
6. HTTP Timeout、MaxResponseBytes、context cancel 和有限幂等重试。
7. MariaDB/Redis required/optional 健康语义。
8. Migration namespace/version 约定。
9. 任务恢复由任务类型声明安全重试能力，不强制通用 Task Runner。

暂缓：
- 动态 Service Key 数据库管理；
- 统一 Logger Interface；
- 公共 Storage/Repository 抽象；
- 通用 Task Framework；
- 独立 Metrics/Trace 后端；
- 公共 Go Module 拆分。
