# stock_analysis_web 功能评估与实施计划

> 参考项目：[Kasign/daily_stock_analysis](https://github.com/Kasign/daily_stock_analysis)。本文不是照搬参考项目的完整功能清单，而是按本项目现阶段的后端能力、单股分析价值和实现成本筛选功能。
>
> **前端只使用原生 HTML、CSS、JavaScript（ES Modules）；不使用 React/JSX、Vue、Svelte、TypeScript、Vite 或其他前端框架。** 保留 `web/` 独立目录、Nginx 同源代理和 Docker 部署方式。

## 当前执行顺序（下一阶段）

为了防止任务列表太大而失去优先级，按下面的顺序交付。每个批次集中修改、Review、补测试和更新进度，不按单文件拆分提交。

1. **P0-A 代码闭环：单股分析入口、任务状态、RunResult 结构化呈现、浏览器恢复和报告导出已实现。** 当前继续改进报告可读性，并扩展真实响应的模拟测试；单股请求的真实业务语义仍待部署验收。
2. **P0-B 接口场景验证：** 固定 Go RunResult fixture、Markdown 导出、API 错误分类与 UI DOM 契约测试已通过 CI；真实 Worker 语义、重复提交竞态及 NAS/1Panel 真接口验收仍需独立验证。
3. **P1-A 本地自选与快捷访问：** 已完成并通过 CI：浏览器内最多 50 只自选、可编辑名称、查行情/发起分析和删除。存储只保留标的引用、自定义名称与更新时间，不保存完整报告或密钥。
4. **P1-B 行情图表：** 已实现并通过 CI：收盘线/K 线切换、OHLC 蜡烛、成交量柱、悬停详情、可选起止日期、复权口径与质量原因显示，以及日 K 查询失败时清除旧标的图表。图表使用后端返回的价格序列，不自行混算复权。
5. **P1-C 历史分析：** 先提交后端历史列表 API 需求与契约草案，待独立后端任务落地后再做服务端历史、筛选、回放和同股比较。当前最近分析列表仍只是在本浏览器保存 task/run 引用。
6. **P2 市场研究扩展：** 筹码分布与个股资金流已有行情 API，本批按需面板接入这两项；行业/题材、新闻公告、财务与市场广度仍等待后端真实接口，不提前虚构数据。
7. **真实部署验收：** 由 NAS/1Panel 环境完成代理、鉴权、刷新恢复及真实字段比对。这部分必须实际访问部署环境，不能靠 mock 或 Docker 构建宣布通过。

**上一批交付：** 在不改变后端的前提下，接入已有筹码分布与个股资金流接口，采用手动加载、并行独立呈现，明确展示数据日期、来源、质量与缺失值。GitHub Actions #39910050023 已通过（44 项 Node 测试、语法检查、Nginx 镜像构建）；真实上游仍需 NAS/1Panel 验收。

**本批交付：** 完善浏览器本地最近分析管理：支持按股票代码、任务/run ID、状态和任务类型关键词筛选；单条移除与一键清空前说明只删除本地引用，不影响服务端任务/报告。处理旧的最近任务指针，避免删除后自动恢复时重新写回；清理当前正在查看的任务时不取消当前页面中的运行，但停止其向本地历史重新写入。此能力仍只管理当前浏览器最近 10 条引用，不是服务端历史列表。

**验证结果：** [WebUI checks #39911788624](https://github.com/Kasign/stock_data_provider/actions/runs/39911788624) 成功：48 项 Node 测试全部通过，JS 语法检查与 Nginx 镜像构建通过。仍需在真实浏览器/NAS 环境确认交互与存储策略。

## 1. 结论：先把单只股票分析真正跑通

当前最重要的不是功能多，而是用户输入一只股票后，能可靠完成一次分析，并明确知道结果意味着什么、使用了哪些数据、哪些数据缺失、哪些规则通过或阻止了信号。

当前 WebUI 已能查询行情、读取日 K、创建 Go 异步分析任务、轮询状态和阶段事件、读取 Run 结果；但结果区目前以指标卡、候选信号摘要和原始 JSON 为主，离易于日常使用的单股分析界面还差一段。Go 分析结果模型已包含质量门禁、市场状态、因子、候选信号、可交易性判断、风险判断、计划/拒绝原因和警告，首要工作应是把这些已有结果解释清楚，而不是先开发一批新页面。

**第一阶段目标：完成“输入单只 A 股 → 提交分析 → 查看进度 → 阅读结构化结论 → 解释风险与数据质量 → 刷新后恢复结果”的闭环。**

当前 Go 分析 API 验证的股票代码规则是 6 位 A 股代码；第一阶段按这一真实契约实现，不提前宣称支持港股、美股或其他市场。现有 API 使用 `POST /api/v1/analysis/tasks`，配合单个 `symbols` 与现有 `task_type`。在没有确认语义之前，不在前端擅自发明新的分析类型或修改后端契约。

## 2. 参考功能评估：哪些实用，哪些应延后

| 功能 | 评估 | 处理计划 |
| --- | --- | --- |
| **单只股票分析主流程** | 核心中的核心，没有它其他页面价值有限 | **立即完成**：输入、任务、阶段、结果、错误、恢复 |
| **分析报告结构化展示** | 非常实用；原始 JSON 不适合日常阅读 | **立即完成**：市场状态、因子、信号、入场/退出/失效规则、风险门禁、拒绝原因、警告 |
| **数据来源与质量诊断** | 极实用，决定用户能否信任分析结果 | **立即完成**：有效时间、质量门禁、缺失数据、来源、回退与降级原因 |
| **阶段进度与失败原因** | 必需；行情或模型等步骤可能较慢，用户必须能定位卡点 | **立即完成**：显示服务端持久化的阶段和错误，不伪造进度百分比 |
| **最近分析/刷新恢复** | 成本低、使用频率高；防止关页面后找不到结果 | **立即完成**：浏览器记录当前 task/run 标识，并在刷新后尝试恢复；不把浏览器记录冒充服务器历史 |
| **历史报告列表** | 长期实用，能比较同股不同时点的分析变化 | **下一阶段**：先补/确认后端分页历史查询 API，再做历史列表、详情回放；现有单个 Run 查询接口不能代替列表接口 |
| **自选股/最近查询** | 实用，但不应阻挡单股分析 | **下一阶段**：先保存最近查询和少量固定标的；需要跨设备同步时再加后端自选 API |
| **大盘、行业/题材背景** | 对单股分析有价值，特别是理解个股强弱和市场环境 | **报告内优先**：先展示本次分析引擎真实输出的市场状态与相关证据；行业/题材排名和市场宽度只有后端提供时才展示，不先做一套独立行情大屏 |
| **技术指标与 K 线** | 实用，但指标多不等于分析可靠 | **第一阶段保留基础 K 线/报价；之后逐步增加有明确口径与测试的指标**，避免前后端计算相互矛盾 |
| **个股比较** | 有一定价值，但需要统一日期、复权和数据覆盖才能公平比较 | **后续**：先稳定单股，再支持 2–3 只股票横向比较 |
| **新闻、公告、财务、筹码/资金流** | 能补充单股判断证据，但可用性取决于数据源和当前 API | **按真实数据能力纳入报告**：明确标记可用、缺失、不支持、过期或抓取失败；不能用空值推断为 0 |
| **条件选股/扫描** | 将来可能高频使用，但依赖成熟策略、筛选条件和结果解释 | **后续独立模块**：先证明单股分析有效，再扩展成多股票扫描 |
| **大盘复盘页面** | 有价值，但不是完成单股分析闭环的前置条件 | **后续**：先在单股报告中展示必要的市场背景，再考虑专用市场复盘页 |
| **Agent 多轮问股** | 交互性强，但会引入会话、上下文、流式接口和模型调用成本 | **暂缓**：等核心结果结构与证据链稳定后再接入 |
| **回测/信号后验评估** | 是验证系统质量的长期关键能力，但没有可信历史样本和成本模型时容易误导 | **中长期**：后端提供可复现评估后再建设页面；展示样本量、交易成本、时间点和局限 |
| **持仓、账户和组合风险** | 用户开始依赖分析做组合管理后才有较大价值；开发面较广 | **暂缓**：不放入第一阶段，后端账本和估值规则稳定后再做 |
| **智能导入（图片/Excel）、报告分享图** | 方便但不是单股分析必需，额外增加解析、兼容和安全成本 | **暂缓**：以后按实际使用频率决定 |
| **自动告警/消息推送** | 需要服务器端常驻监控、规则持久化和通知状态，不是单纯前端功能 | **暂缓**：后端能力成熟后单独实施 |
| **主题切换/中英文界面** | 体验增强，暂时不会提高分析正确性或主流程完整度 | **低优先级**：先保证中文、可读性和响应式布局，不占用主流程资源 |
| **多市场支持** | 当前 Go 主流程的代码校验和数据规则以 A 股为准，过早扩展会扩大测试范围 | **明确不进入第一阶段**：先做好 A 股，再按各市场数据契约分别增加 |

### 第一阶段不做的事

- 不复制参考项目的 React 技术栈和复杂 UI 组件架构。
- 不为了看起来丰富而增加空壳页面或静态模拟数据。
- 不优先做主题、语言切换、图片分享、智能导入、Agent、回测、持仓和自动通知。
- 不在前端根据有限字段自行编造“买入/卖出结论”、收益预测或置信度。
- 不把没有返回的指标显示成 0，不把数据降级隐藏成正常状态。
- 不为 WebUI 的页面需求直接重构 Go 数据源、Python bridge 或分析核心；接口缺口先单独确定契约。

## 3. 第一阶段主流程：具体页面应该怎么用

主界面应以“分析一只股票”为中心，而不是让用户先在行情工作台和任务页之间来回切换。

### 第一步：输入股票

- 首页有醒目的股票代码输入框，默认示例为 `600519`，支持一只 A 股。
- 支持回车提交、输入校验、防止重复点击；错误提示说明具体原因。
- 本阶段不强制要求自选股管理，也不要求完整证券代码自动补全。后端搜索 API 就绪后再增加名称/代码补全。

### 第二步：提交分析与显示执行进度

- 提交现有 Go 异步分析任务，保存返回的 `task_id` 和 `run_id`。
- 显示排队、当前阶段、阶段开始/结束时间、耗时、警告和失败原因。
- 按服务端事件序号增量拉取，不重复展示事件；断线/刷新后可继续查询。
- 区分排队、运行、成功、部分成功、数据质量阻断、请求拒绝和失败。最终状态必须以 API 实际返回的状态枚举为准。
- 使用当前后端支持的轮询和持久化事件，不为“更实时”而先引入 SSE/WebSocket。

### 第三步：用人能读懂的方式呈现结果

优先使用已有 Go API 的结构化结果，至少分成以下区域：

1. **本次分析概况**：股票代码、分析时点、运行状态、总体质量门禁、数据质量是否允许继续。
2. **市场环境**：展示后端返回的市场状态、关键指标与证据；没有证据时明确标记缺失，不自行推导大盘趋势。
3. **分析因子**：因子名称、值、单位、输入质量、时间点、缺失原因和证据引用。
4. **候选信号**：方向、所属策略、信号时间、参考价格、有效期限、入场规则、退出规则、失效规则和证据。
5. **可交易性与风险检查**：分别展示是否通过，以及未通过的规则和原因；未通过不能用绿色“可执行”样式呈现。
6. **计划与拒绝原因**：若后端产生计划，展示方向、数量、参考价格、止损/目标价、风险预算和有效时间；未生成计划时展示后端拒绝/阻断原因，不自行补造价格。
7. **数据质量与警告**：显示质量问题、缺失数据、数据源、有效时间、部分成功和回退信息。
8. **原始结果**：保留可折叠 JSON，便于排查和开发验收；提供复制结果/复制诊断信息。

**注意：** 当前 Go `RunResult` 是结构化的量化分析结果，不等于参考项目那样的完整自然语言 AI 研报。第一阶段先把真实结构化结果呈现完整；如果后续要加入新闻/财务综合解读和自然语言研报，需要单独确认分析引擎/模型接口与证据来源，不能只靠前端把 JSON 包装成一份“AI 报告”。

### 第四步：查看上次结果

- 浏览器刷新后尝试用本地保存的 `task_id` 恢复任务状态；任务结束时通过 `run_id` 读取已持久化结果。
- 请求失败时保留标识并允许重试查询，不能因为一次网络错误清空有效结果。
- 这不是完整历史功能。跨设备、跨浏览器的历史列表需要后端提供分页任务/报告查询接口后再做。

## 4. 第一阶段要核实的后端契约

在 WebUI 开发前，已有 Go API 与部分接口定义，并非从零设计协议。当前调用路径、请求头和已知文档缺口见 [WebUI API 集成契约](./API_CONTRACT.md)。异步任务 OpenAPI 是任务接口的主要规范；前端不得据此假定行情端点和 Run 结果端点已经全部纳入统一 OpenAPI，也不得为适配 UI 单方面改写后端契约。


已有 Go 分析 API 当前具备的相关路径：

- `POST /api/v1/analysis/tasks`：创建异步任务，支持 `Idempotency-Key`。
- `GET /api/v1/analysis/tasks/{task_id}`：查询任务状态。
- `GET /api/v1/analysis/tasks/{task_id}/events`：增量读取持久化阶段事件。
- `GET /api/v1/analysis/runs/{run_id}`：读取已保存的分析结果。
- `GET /api/v1/analysis/runs/{run_id}/events`：读取某次运行的阶段事件。

实施前还必须核实：
- UI 的单股请求是否与 `post_market_scan` 的后端语义一致，以及单个 `symbols` 的行为是否被端到端测试覆盖。
- Worker 的实际状态值和 Run 结果状态值不同，前端需要分别处理，避免任务结束但报告一直转圈。
- 当前结果里的市场状态、因子、信号、风险与数据质量字段是否有稳定契约与真实运行样本。
- 当前是否有能列出历史任务/Run 的后端 API；如没有，历史列表必须先列入后端独立需求，不能假设 `GET /runs/{run_id}` 能返回列表。
- 现有质量检查是否把关键数据的缺失、过期、单位不明和复权口径不一致显式返回。

如果 `post_market_scan` 不能正确表达单股分析语义，应先新增/明确后端 API 契约并补测试，再接入 UI；不能只在前端改标签而不改实际语义。

## 6. 前端实现约定

继续使用独立的 `web/` 目录与原生 JS 模块：

- `index.html`：主页面结构与导航。
- `styles.css`：布局、状态样式、响应式显示。
- `src/api.js`：统一 API 请求、错误处理、请求取消与鉴权头。
- `src/app.js`：页面启动、事件绑定和主流程编排。
- `src/chart.js`：原生 SVG 行情图。
- `src/format.js`：金额、时间、百分比、状态格式化。
- 后续如 `app.js` 明显膨胀，再按页面拆分 `src/pages/`；当前不为了预想中的功能过早搭建大量空目录。
- `tests/*.test.mjs`：纯 JS 单元测试；CI 保留语法、测试及 Docker 镜像构建检查。
- `API_CONTRACT.md`：记录当前 WebUI 实际调用的接口路径、参数、鉴权与已知契约文档缺口；它是集成清单，不替代 Go 服务的 OpenAPI/领域类型。

每次功能批次集中修改并 review，不按单文件拆成连续提交。WebUI PR 原则上只改 `web/`、专项 CI 和相关文档；后端接口不足时另开后端任务/PR，通过明确契约集成。
