# 行情研究台：页面功能与 API 总规划

- 文档版本：v1.0
- 更新日期：2026-10-29
- 适用分支：`feat/webui-market-data-console`
- 范围：产品页面信息架构、模块功能、页面交互、现有 API 复用关系、新 API 需求及实施优先级
- 边界：本文提交在 WebUI 分支的 `web/` 目录内；不修改 Go 数据层、服务端、数据库或部署配置。

> **产品优先级原则：所有页面功能是第一优先级，数据层能力必须围绕页面需求建设。** 本文先冻结页面与功能，再为每个功能定义 API 依赖。当前接口缺失不构成删除页面功能的理由；应标记“待接入/待实现”，同时把 API 需求纳入数据层待办。不得以模拟行情、前端本地假数据或推算出的伪统计填充页面。

## 1. 产品目标与设计原则

产品用于观察国内 A 股市场、发现热点与候选股票、分析个股趋势和量价、形成带有依据和失效条件的走势情景，并持续跟踪与复盘；不提供券商交易下单能力。

1. **页面需求先行**：先定义页面任务、数据字段、刷新频率和交互，再决定复用或新增 API。
2. **事实、指标、结论分层**：行情原始事实与计算指标分开，研究判断必须展示证据、参考时点、适用周期及失效条件。
3. **接口真实状态可见**：区分已实现、已声明但待核实、Provider 不支持、需要新增 API、前端尚未接入；OpenAPI 有定义不等于运行环境已可用。
4. **不伪造数据**：缺失数据使用 null/unknown/空态及原因；不把未知转成 0，不用成交额代替资金净流入，不生成没有历史快照支撑的历史曲线。
5. **统一数据契约**：保留 Go 数据层既有单位归一化、来源信息、时间语义、质量状态与质量门禁；WebUI 不重复猜单位或静默换算。
6. **可追溯**：研究结论应能追溯到当时的行情快照、数据质量、算法版本和触发条件。
7. **页面可独立降级**：某个接口失败时，其他模块仍可显示；每个数据组件明确显示 loading、empty、error、stale、degraded、unknown 等状态。

## 2. 一级导航与页面树

一级导航按用户工作流排列，系统运维功能放在后部：

1. **市场总览**：市场状态首页。
2. **市场热点**：板块排行、板块详情、资金流向、涨跌停分析、人气榜、龙虎榜、热点持续性、交易日历。
3. **个股行情**：股票搜索、个股行情详情、技术图表与指标。
4. **自选与观察**：自选分组、观察池、趋势跟踪、观察笔记。
5. **选股与分析**：条件选股、批量概览、个股深度研究、走势情景、分析任务。
6. **告警与事件**：告警规则、触发记录、市场事件、公告事件、数据异常通知。
7. **研究记录**：研究报告、历史判断、结果验证、复盘统计。
8. **数据中心**：服务健康、Provider 与能力、接口目录、质量、覆盖率、巡检历史。
9. **设置中心**：连接、密钥、显示偏好、指标参数、观察与告警规则。

全局能力：股票搜索、通知入口、连接状态、手动刷新、主题切换、服务连接设置。问股是深度研究的辅助入口，也可由全局入口打开；必须继承当前股票、时间范围及可用数据上下文，不应成为没有数据上下文的独立数据孤岛。

### 2.1 现有导航 ID 迁移原则

当前页面已有 `market`、`stocks`、`watchlist`、`research`、`tasks`、`screening`、`alerts`、`chat`、`data`、`notifications`、`settings` 等视图标识。重排时优先保留既有 ID、事件绑定和路由行为：
- `market` → 市场总览
- `stocks` → 个股行情
- `watchlist` → 自选与观察
- `research` → 个股深度研究
- `tasks` → 分析任务（可作为选股与分析的子页面）
- `screening` → 条件选股
- `alerts` → 告警与事件
- `chat` → 问股辅助
- `notifications` → 通知中心，可整合进告警与事件，但迁移前必须保留原功能入口
- `data` → 数据中心
- `settings` → 设置中心

市场热点、研究记录等新增子页面可先以现有页面中的子导航/标签实现；确认后端能力和交互闭环后再决定是否拆分独立视图。不可为追求导航名称而删除现有功能。

## 3. 页面规格：功能、字段与 API 依赖

状态标签定义：
- **现有调用**：WebUI API 客户端已有对应调用封装；仍需以目标服务版本确认真实路由和 Provider 可用性。
- **待核实**：已有路由/契约线索，但必须检查 Handler、字段、Provider 和部署版本。
- **需新增 API**：当前 WebUI 契约中未确认有完整接口，需数据层评估与实现。
- **前端编排**：可基于已返回的真实数据做呈现或确定性计算，不代表新增服务端能力。

### 3.1 市场总览

| 页面区域 | 必须具备的功能/字段 | API 依赖与状态 |
|---|---|---|
| 市场时钟与状态 | 市场交易日、交易阶段、服务端时间、时区、数据更新时间 | `GET /api/v1/market/session`（待核实）；不得仅用浏览器本地时钟推断交易状态 |
| 核心指数卡 | 指数代码/名称、最新价、涨跌额/幅、成交额（若有）、行情时间、来源、质量 | `GET /api/v1/market/indices`（现有调用/待核实） |
| 市场广度 | 上涨/下跌/平盘家数、覆盖证券数、涨跌比例、成交额及统计范围 | `GET /api/v1/market/breadth`（现有调用/待核实） |
| 市场情绪摘要 | 涨停/跌停、炸板、连板高度、赚钱效应和统计口径 | `GET /api/v1/market/limit-pools` + `/market/breadth`；历史情绪需新增快照 API |
| 市场趋势 | 指数历史 K 线、均线、成交量与选定时间范围 | 指数日线 `GET /api/v1/market/indices/{symbol}/daily`（待核实）；现有股票日 K 不能冒充指数 K 线 |
| 热点速览 | 行业/概念排行、涨幅/成交额/资金方向维度、领涨股 | `GET /api/v1/market/sectors`、`/market/hot-stocks`；多维排行需核实或新增 |
| 我的观察 | 自选股票价格、涨跌幅、趋势摘要、质量状态 | 单股 `/quotes/{symbol}` 可复用；批量观察 API 需评估，禁止大规模逐股请求 |
| 交易日历 | 交易日、休市日、日期范围、来源/质量 | `GET /api/v1/market/trading-calendar`（现有调用/待核实） |

首页顺序：市场状态栏 → 核心指数与广度 → 市场趋势/情绪 → 热点与异动 → 我的观察池 → 交易日历摘要。首页显示摘要与导航入口，完整榜单回到市场热点子页。

### 3.2 市场热点

| 子页面 | 功能与主要字段 | API 依赖与状态 |
|---|---|---|
| 板块排行 | 行业/概念切换；今日涨幅、成交额、近 5 日涨幅、资金净流入排序；排名、总数、覆盖率、数据日期 | `GET /api/v1/market/sectors?type=industry|concept`（现有调用/待核实）；通用 sort/order/page/cursor 需核实，近 5 日与资金维度可能需新增 API |
| 板块详情 | 板块行情、成分股、领涨/领跌、板块历史表现、质量 | 板块详情/成分接口需核实；指数成分 `/market/indices/{symbol}/constituents` 只适用于其真实标识的指数，不能自动等同于任意概念板块 |
| 资金流向 | 市场/板块/个股资金净流入、分项口径、统计时间、单位、覆盖与来源 | 个股 `GET /api/v1/stocks/{symbol}/capital-flow`（现有调用）；市场级与板块级资金流需新增 API；成交额不可代替资金净流入 |
| 涨跌停分析 | 涨停、跌停、炸板、连板梯队、封板时间、统计口径、按交易日查看 | `GET /api/v1/market/limit-pools`（现有调用/待核实）；字段依 Provider 能力明确可选性与缺失原因 |
| 人气榜 | 人气/热度榜、异动榜、排名变化、统计时间 | `GET /api/v1/market/hot-stocks?type=popular|surge&limit=...`（现有调用）；历史排名变化需历史快照 API |
| 龙虎榜 | 交易日、证券、上榜原因、买卖席位/金额/净额、来源报告时间 | `GET /api/v1/market/dragon-tiger`（现有调用/待核实）；按实际 Provider 字段展示，不臆造缺失席位信息 |
| 热点持续性 | 热点持续交易日、排名变化、成分股扩散、领涨股轮动 | 需板块/人气/资金历史快照与统一稳定板块 ID，属于需新增 API/持久化 |
| 交易日历 | 交易日、休市日、市场日期说明 | `GET /api/v1/market/trading-calendar`（现有调用/待核实） |

板块排行必须清楚展示排序维度。若只有前 N 个候选样本，必须标注样本榜，不可称为完整全市场排名。

### 3.4 自选与观察

| 子页面/区域 | 功能 | API 依赖与状态 |
|---|---|---|
| 自选分组 | 创建/重命名/删除分组、添加/移除股票、排序 | 需要服务端自选 CRUD API（需新增）；若现阶段只有浏览器本地功能，必须明确为当前浏览器私有，不宣传为跨设备同步 |

### 3.5 选股与分析

| 子页面/区域 | 功能 | API 依赖与状态 |
|---|---|---|
| 条件选股 | 证券范围、行业/概念、价格/涨跌幅、成交额、换手、均线趋势、财务/估值条件；组合筛选、排序、分页 | 需要全市场证券清单与分页筛选 API（需新增/先盘点现有接口）；不能通过浏览器遍历全市场单股 API |
| 股票概览列表 | 价格、涨跌幅、MA5/20/60/120/250、成交额/换手、板块、质量状态 | 需要批量股票概览 API（需新增）；估值批量接口不能替代行情概览 |
| 个股深度研究 | 趋势与关键价位、量价、资金、板块环境、基本面/事件风险、数据质量 | 组合 quote/bars/bundle/profile/boards/fundamentals/announcements/capital-flow/chip-distribution；各分区单独显示质量与可用性 |
| 走势情景 | 偏强/震荡/偏弱路径、依据、触发条件、失效条件、观察周期与不确定性 | 需要分析服务生成/保存研究结论的正式契约；不能把单纯文字回答当作结构化、可追踪的预测 |
| 分析任务 | 新建任务、任务状态、阶段进度、事件续读、取消/重试（仅后端支持时） | `POST /api/v1/analysis/tasks`、`GET /api/v1/analysis/tasks/{task_id}`、`GET /api/v1/analysis/tasks/{task_id}/events?after_sequence=&limit=`（现有调用）；取消/重试需核实 |
| 研究结果 | 单次 Run 详情、质量、证据、失败原因 | `GET /api/v1/analysis/runs/{run_id}`（现有调用；运行中可能返回 409） |
| 历史任务/研究检索 | 按股票、状态、任务类型、时间筛选；分页与跨设备历史 | 服务端 Run/Task 列表 API 当前未确认；建议 `GET /api/v1/analysis/runs?...&limit=&cursor=`，需新增并定义持久化/权限/保留期 |

### 3.6 告警与事件

| 子页面 | 功能 | API 依赖与状态 |
|---|---|---|
| 告警规则 | 创建、编辑、启停、删除价格/涨跌幅/趋势/量价/板块/市场条件 | 需要服务端告警规则 CRUD API（需新增） |
| 告警触发记录 | 触发时间、规则版本、实际值、阈值、关联证券、确认/忽略状态 | 需要告警事件查询/更新 API（需新增） |
| 市场事件 | 市场级异动、市场情绪变化、热点变化 | 需要事件聚合/历史 API（需新增，或明确各现有源覆盖范围） |
| 公告事件 | 公告、财报日期、重要事件与关联股票 | 个股公告 API 可作为详情数据；跨股票事件流需新增 API |
| 数据异常 | Provider/服务异常、数据过期、质量降级、任务失败 | 复用服务健康和任务 API；Provider 级真实诊断及历史需要新增受保护诊断 API |
| 通知中心 | 未读/已读、类别筛选、跳转来源、批量已读 | 需要通知列表/状态 API（需新增）；当前无服务端接口时保持明确待接入 |

告警规则保存与触发必须由服务端完成；前端轮询行情不能冒充后台告警引擎。诊断 API 不允许客户端提交任意 URL，不得泄露 Provider 凭据。

### 3.7 研究记录

| 页面区域 | 功能 | API 依赖与状态 |
|---|---|---|
| 研究报告列表 | 按股票、时间、结论类型、状态筛选与分页 | 需新增服务端研究记录列表 API；现有按 run_id 读取接口不是列表接口 |
| 报告详情 | 原始判断、数据引用、快照 ID、参考时间、算法版本、质量与风险 | 复用 RunResult；需确认结果是否持久化全部引用数据/快照 |
| 判断验证 | 触发条件是否发生、观察窗口内表现、失效条件是否满足 | 需要保存判断结构和历史行情/指标快照的 API（需新增） |
| 复盘统计 | 不同情景的命中率/偏差、样本数、统计区间与缺失样本 | 需新增验证与统计 API；未积累真实样本前显示“样本不足” |
| 研究笔记 | 备注、标签、关联股票/任务/报告 | 需要 CRUD API（需新增） |

验证逻辑必须防止前视偏差：历史判断只能使用当时可获得的数据；需保存可审计的 available/publication time、参考时间、复权口径和算法版本。

### 3.8 数据中心

| 子页面 | 功能 | API 依赖与状态 |
|---|---|---|
| 服务健康 | 行情服务 live/ready、分析服务 healthz/readyz、响应耗时与安全错误 | `GET /health/live`、`GET /health/ready`、`GET /healthz`、`GET /readyz`（现有调用） |
| Provider 与能力 | Provider 注册/启用状态、声明能力、优先级（仅展示服务端实际暴露字段） | `GET /api/v1/data-sources`（现有调用）；清单不等于上游真实健康 |
| 接口能力目录 | 接口路径、能力域、支持的证券范围/历史深度/参数、最近状态 | 需新增或扩展受保护能力目录 API；可先由文档提供静态说明，但不可冒充动态状态 |
| 数据质量 | valid/degraded/stale/invalid/unknown、原因、来源、时间戳、覆盖/样本量 | 复用各业务 API 的真实质量元数据；不能只用一个全局状态替代字段级质量 |
| 覆盖率 | 股票池覆盖、交易日覆盖、板块/指数覆盖、缺失区间 | 需新增质量/覆盖率汇总 API |
| Provider 实测诊断 | 按 Provider 和 capability 探测、超时/限频、最近成功与安全错误 | 需新增受保护诊断触发/结果 API；需并发上限、超时、冷却与安全约束 |
| 巡检历史 | 检查记录、状态变化、持续故障时间 | 需新增持久化诊断历史 API |
| 单位/口径说明 | 价格、成交量、成交额、百分比、复权、资金统计定义 | 依据统一数据契约和 OpenAPI；不能让前端猜单位 |

“立即检查”现有范围仅包含页面可达性、两类服务的 live/ready、Provider 能力清单及分析服务暴露的依赖子状态。Provider 上游探测必须等服务端诊断 API 实现后才能显示为真实检测结果。

### 3.9 设置中心与问股辅助

| 功能 | 页面行为 | API 依赖与状态 |
|---|---|---|

## 6. 所有 API 的统一契约要求

### 6.1 单位和数值

- 价格：CNY/股；成交额：CNY；成交量：股；涨跌百分比用百分点表达，例如 `1.25` 表示 1.25%。
- 若 Provider 原始成交量为“手”，只在来源契约明确时由 Go 数据层换算；WebUI 不猜单位、不重复换算。
- 缺失金额保持 null，并标记单位未知；不能以 0 代替缺失。
- 同一技术序列必须使用一致复权口径；实时价与复权 K 线混用时必须显示服务端质量警告。

### 6.2 时间与历史可用性

- 分离交易日、Provider 行情时间、报告/公告时间、fetched_at、normalized_at 和 analysis_reference_time。
- 带时区时间戳使用 RFC3339/ISO 8601；交易日使用 `YYYY-MM-DD`。
- 服务端负责交易时段与有效交易日判断；前端本地时钟只能用于显示，不能替代市场状态 API。
- 历史分析不能将后来发布的财务、公告或修订后的数据回填为当时已知信息。

### 6.3 质量、来源与错误

- 统一保留 `quality_status`：`valid`、`degraded`、`stale`、`invalid`、`unknown`；同时保留质量原因/警告、source/provider、fetched_at 和适用的覆盖/样本数量。
- `unknown`、null、空数组、0 和“确认无记录”含义不同。
- 错误响应尽量包含稳定错误码、可安全展示的消息与 request_id；不得返回 API Key、密码或上游凭据。
- 只有真实的全量覆盖和完整候选范围才能声称“全市场榜”；部分样本必须披露范围与覆盖率。

### 6.4 分页、排序与规模

- 列表 API 必须定义默认/最大页大小、稳定排序、cursor 或 offset 语义、总数是否精确以及是否仅为下界。
- 排序维度必须是服务端允许的枚举，不接受任意字段名拼接 SQL。
- 对批量接口定义最大批量、单项失败表达、超时和部分成功规则；不要在前端发起无上限并发请求。

## 7. 页面状态与交互规范

每个数据组件至少有以下状态，且状态含义一致：

- `loading`：正在请求；保留合理的布局占位。
- `success/valid`：请求成功且质量满足该组件用途。
- `degraded`：有数据但覆盖或字段不完整；展示原因。
- `stale`：数据超过业务新鲜度阈值；显示实际更新时间。
- `unknown`：服务无法确认数据是否有效。
- `empty`：服务明确返回无记录；不得把未知误显示为空。
- `error`：请求失败，显示安全摘要、重试入口和 request_id（如有）。
- `unavailable/not implemented`：接口或能力尚未接入，明确标注缺少的 API/字段。

交互闭环：
- 全局搜索 → 个股行情 → 深度研究。
- 板块/人气/涨跌停/龙虎榜中的股票 → 个股详情。
- 个股详情 → 加入自选/观察、创建告警、启动分析任务。
- 条件选股结果 → 批量加入观察池或创建分析任务。
- 分析任务 → 结构化结果 → 保存研究记录 → 后续验证与复盘。
- 数据中心中的缺口项 → 对应页面和 API 需求编号。

### 11.4 下一轮实施顺序

1. **P0：页面接线盘点落地**。逐个组件确认 app.js 实际请求、响应字段及 loading/error/unknown/empty 状态，优先完成已有封装但未接线的市场数据与个股详情区块。
2. **P0：避免重复请求**。个股研究优先评估用 getMarketBundle 一次取得报价和日 K，避免同页重复调用 getQuote/getDailyBars；只有存在独立刷新或参数差异时才拆分请求。
3. **P1：列表与流程闭环**。筛选结果、任务列表/历史、研究历史、自选持久化、告警、通知、聊天按真实服务能力逐步接入；没有后端 API 的先定义契约，不造假数据。
4. **P1：市场总览与热点**。逐项接线指数、广度、板块、涨跌停、人气、龙虎榜、日历并核对覆盖与质量；情绪历史、多维榜和市场级资金流按新增 API 推进。
5. **P2：数据中心增强**。在健康/能力清单基础上增加服务端真实 Provider 诊断和历史，不把配置声明显示成实时健康。
6. 每完成一个模块，同步更新状态与数据分支缺口文档；本分支只改 web/**，Go/OpenAPI/Provider 另行提交到数据分支。
