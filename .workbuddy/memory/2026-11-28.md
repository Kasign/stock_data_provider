## risk 三类事实数据补录路径排查（同日）
- **执行顺序**：`RiskAdapter.Execute`（`internal/quant/stage/risk.go:85-102`）依次创建交易状态 → 盘口 → 涨跌停快照，任一失败即中断；三者都是 required。
- **交易状态（硬阻塞）**：唯一 provider 是 Tushare（`provider/tushare_security_trading_status.go:18`），部署 `providers.json` 中 tushare `enabled=false` 且 `security_trading_status=false`。实测 `GET /api/v1/stocks/600519.SH/trading-status?date=2026-11-27` → 503 `PROVIDER_UNAVAILABLE`。`CreateSecurityTradingStatusFactsSnapshot` 明确不做实时降级（`bootstrap/snapshot_application.go:53`）。补录入口本身存在：`SecurityTradingStatus`（`service/security_trading_status.go:54`）会 `SaveSecurityTradingStatus` 持久化 PIT。
- **发现的代码缺陷**：`overrideProvider`（`internal/marketdata/config/config.go:475-498`）覆盖了 20 项 provider 能力，**唯独漏了 `SecurityTradingStatus`**；容器镜像不含 `configs/`（Dockerfile 未 COPY、compose 无 volume），运行时用编译进二进制的 `defaultProviderFile()`，其 tushare `security_trading_status=false`。因此即便设 `MARKET_DATA_TUSHARE_ENABLED=true` 也无法启用交易状态能力 → 容器部署下该能力永远不可用。修复=在 `overrideProvider` 补一行 `p.SecurityTradingStatus = boolEnv("MARKET_DATA_"+prefix+"_SECURITY_TRADING_STATUS_ENABLED", p.SecurityTradingStatus)`。
- **盘口**：`OrderBookFactsSnapshotCollector.Persist`（`application/order_book_facts_snapshot.go:91-108`）优先复用「不晚于 system_as_of 的最新快照」，否则实时 `FetchOrderBook`。但对 `trade_date` 有强约束（`quant/application/create_risk.go:288-305`）：`observed_at` 必须与 trade_date 同一天；收盘后评估要求 `observed_at >= 15:00`。故周末无法补采 11-27 的盘口，只能在交易日盘后用 `make order-book-collect ARGS="-symbol 600519.SH"` 采集。
- **涨跌停**：provider 可用，实测 `GET /api/v1/market/limit-pools?type=up&date=2026-11-27` → 200 + 10 条。`LimitPoolFactsSnapshotCollector.Persist` 同样优先复用（`GetLatestLimitPoolFactsSnapshotAtOrBefore`），且要求 `system_as_of >= 交易日 15:00`（`limitPoolTradeDateClosed`）。可用 `make limit-pool-collect ARGS="-symbol 600519.SH -trade-date 2026-11-27"` 或 risk 执行时自动拉取。
- **结论**：risk 无法仅靠补录跑通——交易状态需 Tushare 付费 token + 修配置覆盖缺陷；盘口必须在交易日当天盘后采集；涨跌停可用。这是数据源能力缺口，不是本次日历修复能覆盖的范围。
