# 本地测试与使用说明（中文）

本仓库位于 `Kasign/stock_data_provider`。Go 代码与旧 Python 上游分开保存，不需要把此项目复制到 `daily_stock_analysis/go/`。根模块、`go-core` 和 `services/market-data` 是三个独立 Go module，测试命令必须分别在各 module 运行。

## 1. 当前可运行能力

根目录 `cmd/analysis-api` 是单股分析主 API。它通过原生 Go `services/market-data` HTTP API 获取实时行情和日 K，不再调用旧 Python 行情 API，也没有静默 Python fallback。

行情服务使用东方财富/腾讯获取行情和日 K，新浪作为仅报价的第三个兜底源。可选 MX_API 提供筹码和资金流，默认关闭。财务、指数/全市场广度、板块、龙虎榜、新闻公告等并未全部迁移到 Go；`go-core` 仍有 Python bridge 辅助能力，不能把当前版本理解为完全去 Python 化。

本项目是工程链路 MVP，不是成熟的交易策略或可实盘系统。核心质量门禁、可交易性/风险门禁和历史时点限制仍可能导致结果为 partial 或拒绝计划。

## 2. 配置本地环境

在仓库根目录执行：

~~~bash
cp .env.example .env
~~~

编辑根目录的 `.env`，至少确认以下配置。这里用占位说明，不要将真实密码提交到 Git：

~~~dotenv
# 两个 Go 服务必须使用同一个至少 32 字符的随机 key
MARKET_DATA_API_KEY=替换为随机生成的密钥
MARKET_DATA_BASE_URL=http://127.0.0.1:8091
MARKET_DATA_REQUEST_TIMEOUT=135s
MARKET_DATA_HISTORY_DAYS=200
MARKET_DATA_MAX_CONCURRENCY=4
MARKET_DATA_MARKET_TIMEZONE=Asia/Shanghai
MARKET_DATA_ADJUSTMENT=forward_adjusted

# 行情服务连接现有 MariaDB / Redis；按实际 Docker 网络服务名修改
MARKET_DATA_DB_HOST=127.0.0.1
MARKET_DATA_DB_PORT=3306
MARKET_DATA_DB_USER=stock_analysis_server
MARKET_DATA_DB_PASSWORD=替换为真实数据库密码
MARKET_DATA_DB_NAME=stock_analysis_server
MARKET_DATA_DB_CHARSET=utf8mb4
MARKET_DATA_DB_TIMEZONE=UTC
MARKET_DATA_REDIS_ADDR=Redis:6379
MARKET_DATA_REDIS_PASSWORD=替换为真实 Redis 密码
MARKET_DATA_DB_AUTO_MIGRATE=true

# 根分析 API 的持久化连接配置
DB_HOST=127.0.0.1
DB_PORT=3306
DB_USER=stock_analysis
DB_PASSWORD=替换为真实密码
DB_NAME=stock_analysis
DB_AUTO_MIGRATE=true
REDIS_ADDR=127.0.0.1:6379
REDIS_PASSWORD=
REDIS_DB=0

# 日志
LOG_LEVEL=info
~~~

宿主机直接运行服务时，数据库和 Redis 通常使用 `127.0.0.1`；如果在 Docker 容器中运行，则应使用 Docker 网络中可解析的服务名，例如 `Mariadb`、`Redis`。`MARKET_DATA_DB_*` 是行情服务自己的连接配置，分析 API 使用 `DB_*` 和 `REDIS_*`；新配置不需要手工拼接 DSN。

只有明确要启用妙想时才设置：

~~~dotenv
MARKET_DATA_MX_ENABLED=true
MARKET_DATA_MX_API_KEY=替换为真实 MX API Key
MARKET_DATA_MX_API_TIMEOUT=10s
~~~

MX 默认关闭。显式启用后缺少有效 Key 应启动失败；MX 不提供日 K，不参与行情 fallback。

## 3. 运行测试

在仓库根目录运行根 module：

~~~bash
go mod download
go test ./...
go test -race ./...
go vet ./...
go run ./cmd/storage-check
~~~

然后分别检查两个 Go module：

~~~bash
cd go-core
go test ./...
go test -race ./...
go vet ./...
cd ../services/market-data
go test ./...
go test -race ./...
go vet ./...
~~~

`storage-check` 会真实连接 MariaDB 与 Redis，并执行已配置的 schema/读写检查。单元测试绿色不代表真实供应商、生产密钥和 Docker 网络已通过联调。

## 4. 推荐：使用 Docker Compose 启动两个 Go 服务

前提是已有 `1panel-network`，并且现有 MariaDB/Redis 服务已经加入这个网络。使用 Compose 时，确认根目录 `.env` 中的 `MARKET_DATA_DB_*`、`MARKET_DATA_REDIS_*`、`DB_HOST`、`REDIS_ADDR` 指向实际服务；已有 `.env` 不要被 `.env.example` 覆盖。然后运行一键部署预检：

~~~bash
bash ./scripts/deploy-go.sh
~~~

脚本会检查 Compose 语法和 `1panel-network`，构建两个 Go 镜像、启动容器，并等待健康检查通过。若需要手动执行：

~~~bash
docker compose -f docker-compose.go.yml config --quiet
docker compose -f docker-compose.go.yml build market-data stock-analysis-go
docker compose -f docker-compose.go.yml up -d
docker compose -f docker-compose.go.yml ps
docker compose -f docker-compose.go.yml logs --since=10m market-data stock-analysis-go
~~~

Compose 会启动：

- `market-data`：容器网络内部端口 8091，不向宿主机公开。
- `stock-analysis-go`：宿主机回环地址 `127.0.0.1:8092`，依赖 market-data 健康后启动。

宿主机用 `http://127.0.0.1:8092` 测试。如果 1Panel OpenResty 容器也加入 `1panel-network`，反向代理上游使用 `http://stock-analysis-go:8092`；API 还没有内置认证，对外发布前必须加鉴权及来源限制。不要为此额外创建 MariaDB/Redis 容器；若服务名不是默认的 `Mariadb` 或 `Redis`，修改根 `.env` 对应地址。

## 5. 手动启动服务

如需直接在宿主机运行 market-data 调试，需先将需要的 `MARKET_DATA_*` 变量显式导出到当前 shell，再在 `services/market-data` 目录运行 `go run ./cmd/market-data`。**不要直接把整个 `.env` 文件当作 shell 脚本执行**：旧版配置中的 `MARKET_DATA_MYSQL_DSN` 含 `&` 等字符时，未引用的值会被 shell 当作控制符；密码中的 `$` 也可能被展开。生产部署建议统一使用上面的 Compose 脚本。

然后另开终端回到仓库根目录启动分析 API（根 API 会自动加载根目录 `.env`）：

~~~bash
cd /路径/到/stock_data_provider
go run ./cmd/analysis-api
~~~

两者应使用相同的 `MARKET_DATA_API_KEY`；根 API 的 `MARKET_DATA_BASE_URL` 应指向可达的 market-data 服务。启动日志会显示服务地址和健康/连接错误。

## 6. 健康检查与行情 API

~~~bash
curl -i http://127.0.0.1:8092/healthz
curl -i http://127.0.0.1:8092/readyz
curl -i http://127.0.0.1:8091/health/live
curl -H "X-API-Key: $MARKET_DATA_API_KEY" http://127.0.0.1:8091/api/v1/quotes/600519.SH
curl -H "X-API-Key: $MARKET_DATA_API_KEY" "http://127.0.0.1:8091/api/v1/bars/600519.SH/daily?limit=30&adjustment=forward_adjusted"
~~~

`/healthz` 只说明根 API 进程存活；`/readyz` 会检查持久化依赖；market-data 的 `/health/ready` 检查其配置依赖。行情响应应检查来源、时间、`volume_unit=shares`、`amount_unit=CNY`、复权口径与质量告警，不能只看 HTTP 200。

## 7. 发起分析与查询阶段事件

~~~bash
curl -sS -X POST 'http://127.0.0.1:8092/api/v1/analysis/runs' \
  -H 'Content-Type: application/json' \
  -H 'X-Request-ID: manual-test-001' \
  -d '{"symbols":["600519"]}'
~~~

请求会同步执行分析，并在响应中返回 `run_id`、质量状态、候选信号、风险/可交易性判定、计划和 stage events。查询已结束的运行：

~~~bash
curl -sS 'http://127.0.0.1:8092/api/v1/analysis/runs/<run_id>'
curl -sS 'http://127.0.0.1:8092/api/v1/analysis/runs/<run_id>/events'
~~~

### 异步任务接口

新调用方可使用异步 API，旧的同步 API 仍保留：

~~~bash
# 创建异步任务，正常返回 HTTP 202 与 task_id
curl -i -X POST 'http://127.0.0.1:8092/api/v1/analysis/tasks' \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: manual-test-001' \
  -d '{"symbols":["600519","000001"]}'

# 用返回的 task_id 轮询状态
curl -sS 'http://127.0.0.1:8092/api/v1/analysis/tasks/<task_id>'

# 增量读取阶段事件；下次请求使用响应中的 next_after_sequence
curl -sS 'http://127.0.0.1:8092/api/v1/analysis/tasks/<task_id>/events?after_sequence=0&limit=100'
~~~

状态为 `queued`、`running`、`succeeded`、`partial` 或 `failed`。排队时事件可能为空；Runner 执行后，阶段事件会写入 MariaDB，按 `sequence` 增量读取。可通过 `.env` 中的 `ANALYSIS_WORKERS`（默认 2，范围 1–32）与 `ANALYSIS_MAX_QUEUED`（默认 100）调整本实例的并发 Worker 数和最大排队量。重启时尚未执行的 queued 任务会保留；遗留的 running 任务会标记为 `worker_interrupted`，不会自动重跑。SSE、取消和前端进度 UI 尚未实现，详情见 `docs/architecture/LOGGING_AND_TASK_PROGRESS_PLAN.md`。

## 8. 检查日志与结果持久化

根 API 和 market-data 使用 JSON 结构化日志；可以按 `request_id`、`run_id`、`stage`、`provider` 和 `status_code` 检索。日志只记录安全摘要，不应打印 API key、完整请求/响应体或 LLM prompt。

MariaDB 里可以使用：

~~~sql
SELECT run_id, status, task_type, as_of, started_at, finished_at
FROM analysis_runs ORDER BY started_at DESC LIMIT 10;

SELECT run_id, stage, status, event_at, duration_ms
FROM analysis_stage_events ORDER BY id DESC LIMIT 30;

SELECT run_id, snapshot_type, snapshot_id, as_of, created_at
FROM analysis_snapshots ORDER BY created_at DESC LIMIT 20;
~~~

## 9. 旧 Python API smoke 工具

`cmd/pythonapi-smoke` 和 `internal/adapters/pythonapi` 仅为旧服务诊断/迁移对照工具；它们不是根分析 API 的运行时行情依赖。只有当你主动使用这些旧诊断命令时，才需要提供 `PYTHON_API_BASE_URL` 等旧变量：

~~~bash
go run ./cmd/pythonapi-smoke --stock 600519
go run ./cmd/pythonapi-smoke --stock 600519 --profile --overview
~~~

`cmd/demo` 使用内存模拟数据，只验证主流程编排，不连接 DB/Redis，也不能替代真实行情测试：

~~~bash
go run ./cmd/demo
~~~

## 10. 故障排查

- market-data 配置失败：检查 `MARKET_DATA_API_KEY` 是否有效、Provider 超时预算是否足够、`MARKET_DATA_DB_*` 字段和 Redis 主机名是否正确。
- 根 API 无法调用行情服务：确认 `MARKET_DATA_BASE_URL` 可达，且双方配置的 `MARKET_DATA_API_KEY` 相同。
- MariaDB/Redis 就绪失败：检查现有实例的网络、用户名、密码、库名、ACL 权限与 migration 权限。
- 行情质量降级：检查 Provider 返回时间、原始单位、复权字段和质量原因，不要手动补 0 或随意进行 100 倍换算。
- MX 接口不可用：确认默认关闭开关是否按预期；若显式开启，检查 MX API Key、上游权限和自然语言响应表格结构。
- CI 全绿但服务器联调失败：检查目标网络的实际端点、访问权限、供应商限流和容器 DNS；CI mock 不验证生产网络。

本项目不真实下单、不生成成交记录。策略有效性需要单独回测、成本建模、样本外验证和持续监控，不得从一次成功执行推断准确性或盈利能力。
