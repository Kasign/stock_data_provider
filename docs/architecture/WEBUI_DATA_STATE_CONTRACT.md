# WebUI 与数据层状态及响应契约

> **数据层开发前必读。** 新增或修改 market-data API、Provider 适配器、归一化模型、分析服务消费字段时，先阅读本文，再对照 `services/market-data/openapi.yaml`、`docs/architecture/market-data-contract.md` 与对应 Go 模型/处理器。本文规定跨层语义，不替代各接口的 OpenAPI schema。

## 1. 目标与边界

本文统一约定 WebUI 如何解释后端响应，以及数据层必须提供哪些信息，避免以下问题：

- 切换股票、报告期、日期范围或分页后，旧响应被误当成新条件的结果。
- 将“请求成功但源端未提供数据”“确认无记录”“接口失败”都显示成同一种空状态。
- 将 `null`、未知单位、未知时间或缺失字段补成 0、当前时间或猜测值。
- 把降级/过期数据误报为完全有效，或在请求失败时继续显示旧快照而不作说明。
- 前后端对状态大小写、百分比口径、时间和分页字段的解释不一致。

本文不要求所有数据域使用同一种响应 DTO，也不要求为纯 UI 状态增加后端 API。优先使用现有字段；确有语义缺口时再按第 8 节演进。

## 2. 两类状态必须分开

### 2.1 请求/展示状态（由 UI 管理）

UI 应按当前请求生命周期区分：

| UI 状态 | 含义 | 页面行为 |
|---|---|---|
| `idle` / `not_loaded` | 尚未请求当前条件 | 显示引导文案，不暗示数据为零 |
| `loading` | 当前条件正在请求 | 显示加载状态；不把上一快照伪装成本次响应 |
| `success` | 当前响应成功且有可展示记录 | 展示记录及其来源、时间、质量状态 |
| `empty_unconfirmed` | HTTP 请求成功，但契约不能证明源端确实无记录 | 使用“接口未返回记录/暂无法确认”等文案，不宣称确实不存在 |
| `degraded` / `stale` | 响应可展示，但有质量或新鲜度限制 | 保留数据，同时醒目标示质量状态、原因和可用的时间信息 |
| `error` | 本次请求未成功或响应无法使用 | 展示本次错误；不能把错误渲染成正常空列表 |
| `key_required` | 缺少或无效的 WebUI 到服务端 API Key | 提示检查本地连接设置；不显示需要当前凭据才能获取的旧快照 |

这些是 UI 内部语义，不应强行新增为每个后端 DTO 的 `status` 字段。

### 2.2 数据质量状态（由数据层提供）

标准化数据质量状态使用现有枚举：

- `valid`：在此接口定义的检查范围内有效；不代表适用于所有投资/回测用途。
- `degraded`：部分字段、Provider、时间或质量检查存在限制；需提供可用的 `quality_reasons` 或响应 `warnings`。
- `stale`：数据已超过对应数据域的新鲜度规则，或明确属于过期快照；若仍返回可展示缓存，必须保留来源时间。
- `invalid`：数据未通过该数据域的使用条件或质量校验，不得在 UI 中伪装成正常有效数据。
- `unknown`：无法确定质量；不能自动提升为 `valid`。

数据层质量状态来自响应字段；UI 的 `loading/error/key_required` 属于请求过程。两者不能混为一谈：例如 HTTP 200 可能返回 `quality_status=degraded`，HTTP 503 则是本次请求失败，不能合成一个状态。

## 3. 响应数据规则

### 3.1 数据是否存在

1. HTTP 2xx 表示请求层成功，不自动意味着数据完整、质量有效或源端存在记录。
2. `items: []`、`bars: []`、缺失的可选对象或 `has_data=false` 不能脱离当前 schema 的说明，自动解释为“确认没有数据”。
3. 只有当该资源的契约明确保证空集合代表确认的空结果时，UI 才可显示“没有匹配记录”。如果源端无记录含义不确定，应使用“接口未返回记录/无法确认是否存在”。
4. 已有领域语义优先遵从 OpenAPI。例如股票板块、公告接口的 `has_data` 已说明空列表不一定证明没有成员/公告，不得更改为肯定语义而不更新 schema、适配器和契约测试。
5. 缺失字段、`null`、空字符串和数值 0 语义不同；不得将缺失值或 `null` 默认替换为 0。

### 3.2 来源和时间

- `source` 应指向实际的数据供应商/来源，不得只用 HTTP API 名或内部服务名冒充底层 Provider。
- `source_version`、`normalization_version`、`request_id` 在对应领域可用时应保留，以利审计和问题定位。
- `fetched_at` 表示服务端获取/完成采集的时间，不得冒充供应商更新时间、行情时间或公告发布时间。
- `quote_time`、`provider_timestamp`、公告 `published_at` 等源端时间，源端未提供时保持 null；不得用当前时间填补。
- 日期型筛选与交易日字段保持日期语义（`YYYY-MM-DD`）；瞬时时间使用 RFC3339 时间戳并明确时区/UTC 口径。
- 对历史 `as_of` 请求，当前快照不能倒灌到过去。无法提供严格时点值时返回明确的质量原因/警告，不得声称具备 PIT 可复现性。

### 3.3 数值、单位与缺失

1. 先遵从 `docs/architecture/market-data-contract.md` 和 OpenAPI 的单位定义；适配器必须在规范化边界完成一次转换，不可由 UI 或分析层二次猜测。
2. 价格、成交量、成交额、涨跌幅、比例、成本和资金流字段必须按各自字段的单位展示。不能仅按数值大小推测单位。
3. 缺失数值维持 null/缺失语义，UI 显示“未提供”；不能补 0。
4. 比例字段必须通过 schema 说明是 ratio（如 0.125）还是 percentage points（如 12.5 表示 12.5%）。不得改变已有口径却不更新契约和样例。
5. 使用 `quality_reasons` 解释数据为什么降级/未知/不可用；面向请求级问题可使用稳定的错误码和 `request_id`，不要只返回不可分类的自由文本。

## 4. 查询条件必须可追溯

响应必须保留或明确标识解释当前结果所需的查询条件。按数据域适用，包括：

- 股票标的 `symbol`（使用标准化股票代码）；
- 财务报告期 `year`、`quarter`，以及源端报告日/披露日；
- 日期区间 `start_date`、`end_date` 或 `start`、`end`；
- 分页参数 `page`、`page_size`，以及 `returned`、`total`、`pages`、`has_more` 等现有字段；
- K 线 `period`、`adjustment_basis` 和适用的参考日期；
- 其他会改变结果含义的过滤类型、市场或排序条件。

如果当前响应已经有这些字段，应保持其与请求一致，不必重复添加无用字段。缺少必要的条件回显时，应先在 OpenAPI/模型中记录缺口；不要仅依靠 UI 记忆当前筛选值去证明响应属于本次请求。

## 5. HTTP 错误契约

错误响应沿用现有公共结构：

```json
{
  "error": {
    "code": "stable_machine_readable_code",
    "message": "可安全展示的摘要",
    "request_id": "可选的请求关联 ID"
  }
}
```

要求：

- `code` 是稳定机器码，客户端根据错误类型处理时不能依赖中文 `message` 的精确内容。
- `message` 不得包含 API Key、Authorization 头、上游密钥或敏感连接字符串。
- 同一类错误跨 endpoint 保持相同的 HTTP 语义及机器码；不得出现同类鉴权失败有时返回空列表、有时返回 HTTP 200 的情况。
- HTTP 4xx 表示请求、认证或授权问题；5xx 表示服务端/Provider 暂不可用或内部错误。更具体的代码和状态必须在 OpenAPI 中逐 endpoint 定义。
- 对缺少/无效 Key、参数不合法、路由未部署、Provider 未启用/不可用、请求限流和内部错误，数据层须遵从服务当前约定的状态码并提供明确 `error.code`。若现有行为与该规则不一致，先核对中间件/错误映射，再集中修正并更新 OpenAPI 与契约测试；不要只改文案。
- 数据源没有数据不应以 5xx 表示；上游超时/异常不得包装成 HTTP 200 的确认空结果。

## 6. 重复请求、取消和旧响应

- 请求取消和“忽略旧响应”通常是 UI 责任：每个相互独立的面板/筛选流程使用自己的取消控制和请求序号（generation/request token），只有当前序号的响应才可更新界面。
- 后端应保留请求 ID，并在日志中关联 Provider 尝试和最终响应；取消连接不保证上游执行一定已停止，因此不得依赖取消作为服务器端幂等性的替代。
- 如果响应中存在查询条件回显，UI 应在应用响应前核对标的/报告期/区间；若不匹配，视作旧响应或契约异常，不更新当前视图。
- 后端不能替 UI 决定何时清理 DOM，但它必须准确返回实际响应的标的、时间和筛选元数据，不得在响应中填入另一个请求的字段。

## 7. 分页和快照策略

- **整页刷新**：UI 开始新的筛选/整页请求时先清除旧列表、旧来源时间和旧质量原因；若本次失败，只显示本次错误，不能把旧列表包装成当前筛选结果。
- **追加下一页**：仅在分页条件与上一成功页相同、且已成功记录仍属于当前查询时，可保留已有行。追加失败需单独标记本页失败，不修改已有行的质量语义。
- 后端须明确当前页记录数、总量/总页数（若源端可提供）、`has_more` 和实际采用的页码；不能把源端总量与本页返回数混用。
- 如果服务端只支持当前快照，没有持久化历史值或历史分页保证，需在文档说明；不能暗示重新加载的历史响应和旧页组成了同一时点的完整数据集。

## 8. 契约修改流程（数据层开发约定）

凡新增/修改 endpoint、DTO、Provider 字段、单位、质量计算或错误语义，合并前必须：

1. 先阅读本文与领域契约：`docs/architecture/market-data-contract.md`、`services/market-data/openapi.yaml`，以及分析 API 的 `docs/architecture/analysis-tasks.openapi.yaml`（若影响任务/运行流）。
2. 确认真实 Provider 的源字段、单位、时间语义与空结果含义；未确认的内容要标记 unknown/degraded，不能猜测。
3. 同步更新 Go DTO/适配器/处理器、OpenAPI schema 与成功/失败响应样例；不要只改 Go 结构体或前端字段读取。
4. 为关键语义增加/更新契约测试：正常响应、缺失字段/空数据、质量降级、鉴权失败、上游错误，以及适用时的分页/筛选条件回显。
5. 让 WebUI 直接按契约映射，不重复实现后端的单位换算、质量判断或 Provider 选择策略。
6. Review 时检查旧客户端兼容、真实 OpenAPI 与实现是否一致，以及是否将失败错误误包成成功空响应。

## 9. 已知缺口与优先级

本文件先固定双方必须遵守的语义边界，并不表示所有现有接口已完全满足这些要求。实现层 Review 时优先检查：

- 认证失败、参数错误、路由未实现和 Provider 不可用的状态码/错误码是否统一；
- 每个资源的 `has_data`、空集合和 `quality_status` 是否具有可理解且有文档支撑的语义；
- 筛选条件回显、时间字段 null 语义以及来源/版本信息是否齐全；
- 数据域是否缺少 `quality_reasons`、响应 `warnings` 或必要的分页元数据；
- 任何单位换算、默认值或“空列表即无记录”的推断是否缺少 Provider 契约证据。

如果短期内某接口无法提供字段，应显式记录为缺口并由 UI 降级显示；不要为追求外观统一而造数据、补零或假装服务端已实现某能力。
