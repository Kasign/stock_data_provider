# A 股分析系统 Go 主流程：代码设计说明（中文）

- 文档版本：v1.0
- 对应代码：`internal/analysis/`
- 当前状态：已提供正式 HTTP API 入口、Python 行情适配器、MariaDB 运行/事件/快照持久化、Redis 缓存与保守趋势基线 MVP；尚未达到可实盘交易或可靠历史回测的生产标准。
- 设计基线：`个人 A 股分析系统：主流程设计与复审记录`（2026-10-20）。

## 1. 本设计要解决什么问题

这部分代码的职责是稳定地编排一次“指定分析时点”的 A 股研究任务，而不是在主流程中实现所有业务算法。它负责确定阶段顺序、验证各模块输出、阻止不合格数据或未通过风险门禁的信号继续流转，并记录运行状态和审计事件。

以下能力仍需继续完善或建设：复权及公司行动处理、完整数据质量规则、完整市场环境分析、技术/基本面因子、成熟选股策略、完整可交易性判定、生产风控规则、仓位计算、模拟成交、回测与报告。MariaDB/Redis 适配器和基础 HTTP API 已经接入；真实存储与 Python 服务的端到端运行仍需在部署环境验证。

**不能把当前 MVP 理解为已经具备成熟的交易决策能力。** `cmd/demo` 使用内存模拟数据；`cmd/analysis-api` 才是连接 Python API、MariaDB 和 Redis 的真实服务入口。

## 2. 架构总览

采用分层架构，并在层之间使用显式接口（Ports）。依赖方向指向领域契约，不让领域对象依赖 HTTP、数据库、数据供应商或具体策略实现。

```text
HTTP API / CLI / 定时任务（入口层；HTTP API 与 CLI 演示已提供）
                 |
                 v
应用编排层：internal/analysis/app/Runner
                 |
       +---------+----------+
       |         |          |
       v         v          v
数据/质量端口  因子/策略端口  组合/风控/执行端口
       |         |          |
       +---------+----------+
                 |
                 v
领域契约：internal/analysis/domain
                 ^
                 |
生产适配器（未来实现）：行情源、MariaDB、Redis、交易规则、日志/监控
```

模块依赖的基本规则：

1. `domain` 不依赖 `app`、数据库驱动、Web 框架或第三方行情 SDK。
2. `app.Runner` 只依赖领域类型和接口，不通过股票代码、策略名称或数据源名称分支。
3. 具体实现通过 `app.Dependencies` 注入；生产程序应在 composition root（应用组装入口）中创建并注入依赖。
4. 模块注册只在启动阶段完成；检查配置后冻结注册表，不允许在一次运行中动态替换算法。
5. HTTP、CLI 和定时任务应调用同一个应用服务，避免各入口分别实现一套业务流程。

## 4. 一次分析任务的主流程

`Runner.Run()` 是单一分析时点的应用服务。整体阶段如下：

1. 校验任务输入、生成或检查 `RunID`，冻结参数副本并创建运行记录。
2. 按 `AsOf` 解析股票池版本，拒绝空股票池、重复证券及未来股票池快照。
3. 根据策略注册信息解析核心数据、策略数据及因子依赖。
4. 采集数据，并将原始快照持久化，返回可追溯的 `RawSnapshotID`。
5. 标准化行情与公司行动处理结果，并保存标准化快照。
6. 执行核心数据质量门禁和策略级数据门禁。
   - 核心门禁失败：状态为 `blocked_data_quality`，不生成有效信号。
   - 某个策略未通过/未被显式判定：只跳过该策略，不默认为通过。
   - 辅助数据缺失：允许部分分析，但应保留警告和质量问题。
7. 计算市场环境；仅针对通过数据门禁的策略解析必要因子并执行策略。
8. 校验信号 ID、股票池归属、策略版本、信号时点、有效期、入场/退出/失效规则。
9. 对每个候选信号执行可交易性检查，并加载、保存 `AsOf` 时点的模拟组合快照。
10. 执行独立风险规则。风控规则采用“任意规则拒绝，则整体拒绝”的合并语义。
11. 只有同时得到显式可交易性放行和风控放行的信号，才能进入仓位规划。
12. 校验计划数量、方向、价格、风险预算、费用估算、交易规则版本、最早执行时间和过期时间。
13. 对每个计划给出明确执行评估。计划在 `AsOf` 之后成交时，当前任务不能声称它已经成交，默认状态应为 `pending`。
14. 持久化结果和各阶段事件，返回带有状态、警告、快照 ID、因子、信号、风控决定、计划的结构化结果。

### 4.1 状态与错误语义

- `completed`：主流程完成，未标记为部分可用；不等于策略已证明盈利。
- `partial`：流程可继续，但数据/分析存在已记录的限制。
- `blocked_data_quality`：核心数据门禁未通过；无有效策略信号。
- `rejected_request`：任务参数本身无效。
- `failed`：数据源、模块、审计或持久化等运行故障导致流程未能正常完成。

业务门禁阻断应尽可能通过状态和原因表达；基础设施故障应返回错误。调用方必须同时检查 `error` 与 `RunResult.Status`。

## 5. 稳定主流程的关键约束

### 5.1 时点数据

`RunRequest.AsOf` 是本次分析的截止时点。股票池、行情、财务、公告、组合快照都不能晚于此时点。行情事件日期、信息公开/可用时间和系统采集时间是不同概念；生产数据模型必须保存这些时间及来源。

### 5.2 失败关闭（Fail-closed）

如果质量报告没有明确标注某策略可用，应跳过该策略。每个信号必须恰好有一个可交易性结果和一个风险结果；缺结果、重复结果或未知信号 ID 均视为模块契约错误，而不是默认放行。

### 5.3 风险不可被评分覆盖

候选信号、研究排名与最终可规划信号是不同概念。综合分数不允许覆盖可交易性否决、风险否决、数据门禁或组合约束。

### 5.4 计划不等于成交

交易计划需要明确 `EarliestExecuteAt` 与 `ExpireAt`。本 Runner 不推进未来时间，不使用未来价格或 K 线生成实际成交。未来行情驱动的模拟成交应由独立 Paper Execution Worker 负责，回测应由独立 BacktestService 和事件账本负责。

### 5.5 持久化和幂等

生产版的 `RunStore`、`SnapshotStore` 必须做到：运行 ID 有唯一约束或幂等键；快照不可变且可查询；阶段事件可追踪；单次调用失败时记录失败状态；不在数据采集期间持有长事务。Redis 只承担适合缓存/协调的任务，不能作为唯一事实库。

### 5.6 版本冻结

每次任务必须固定策略配置、风险配置、交易规则版本和数据质量政策版本。生产端还应持久化实际运行的策略/因子/风险规则版本及配置摘要，确保历史结果可以复现。

## 6. 如何扩展而不修改 Runner

| 需求 | 实现位置 | 是否修改 `Runner` |
|---|---|---|
| 新增行情或公告源 | 新增 `DataSource` adapter，由 collector/router 管理能力、优先级和降级 | 否 |
| 新增因子 | 实现 `FactorCalculator` 并注册 | 否 |
| 新增策略 | 实现 `Strategy`，声明因子和数据需求并注册 | 否 |
| 新增风险检查 | 实现 `RiskRule`，声明稳定的 ID、版本、优先级并注册 | 否 |
| 调整指标/策略参数 | 版本化配置；不能在运行中途变化 | 否 |
| 更换 MariaDB/Redis 访问实现 | 替换对应 adapter | 否 |
| 增加报告格式 | 消费 `RunResult` 的报告/导出 adapter | 否 |
| 增加回测 | 新增独立 `BacktestService`，不在 Runner 内增加回测分支 | 否 |
| 增加新的强制业务阶段 | 优先映射到既有扩展点；确实改变业务契约时，只增加一个阶段端口并在 Runner 编排一次 | 少量 |

不要为了追求“完全零改动”引入没有可观测性、无法明确失败语义的通用 DAG 引擎。固定主干加清晰扩展点，更容易测试和维护。

## 7. Web 状态与建议接法

当前没有随 Go 子项目提供的 Web 前端，但已经有可启动的 Go HTTP API 服务器。执行 `go run ./cmd/demo` 只运行内存模拟演示，不会连接真实行情源或 MariaDB/Redis；执行 `go run ./cmd/analysis-api` 才会加载 `.env`、连接 MariaDB/Redis 并启动 HTTP 服务。

未来 Web 建议分为：

- `cmd/analysis-api`：HTTP 入口，负责参数校验、鉴权、创建分析任务、查询任务状态/结果；不在 Handler 中直接执行因子或策略算法。
- `cmd/analysis-worker`：组装真实模块、执行 `Runner.Run()`、持久化阶段状态与结果。
- Web 前端：提交任务、查看阶段进度、数据质量问题、候选信号、风控理由和计划；前端显示的是研究辅助结果，不是券商下单入口。

当前 MVP 通过 `POST /api/v1/analysis/runs` 同步执行分析并返回 `run_id`；可使用 `GET /api/v1/analysis/runs/{run_id}` 和 `/events` 查询结果与审计事件。更长任务的异步队列和 Worker 尚未实现。

## 8. 当前已实现与未实现

已实现：流程编排、领域契约、可插拔模块契约与注册表、质量与信号/计划门禁、阶段事件、单元测试、内存 Mock 冒烟演示。

尚未实现：生产级多数据源优先级/熔断/限流、标准化及复权算法、完整财务/行业/资金流指标、生产风控公式、交易规则版本库、真实模拟组合账本、Paper Execution Worker、回测与样本外验证、Web 前端和 API 鉴权。MariaDB/Redis 适配器与基础 HTTP API 已经接入，但仍需要服务器端真实集成测试。

**在以上生产能力实现并验证之前，不能把结果当成真实交易建议，不能声称系统已可实盘或策略具有盈利能力。**

## Go 接入现有 Python 数据服务

新增 `internal/adapters/pythonapi` 作为边界适配器，实现现有 `app.DataCollector` 端口。HTTP 路由、JSON 类型、超时、认证头和响应大小限制全部留在该目录，`app.Runner` 不直接依赖 Python 的 URL 或 schema。

基础地址通过根目录 `.env` 的 `PYTHON_API_BASE_URL` 配置；Go 启动时调用 `internal/platform/config.LoadDotEnvIfExists`，再调用 `pythonapi.ConfigFromEnv`。部署环境直接注入的环境变量优先于 `.env`。接入明细及现有 Python API 的元数据限制见 [`Go 接入 Python API（中文）`](Go-Python-API-adapter-中文.md)。

该适配器仅解决“拿到数据并保留可审计缺口”，不把 Python 聚合报告当作 Go 的策略结果。Python 现有接口没有逐行 Provider、精确 available_at 和复权口径的完整契约，因而这些字段会被显式标记为缺失/未知；缺失量价字段使用指针保留 nil，不应被解读成 0。真实标准化、完整门禁和策略实现仍是后续必需工作。
